АНАЛИЗ ВЫЛЕТА  hota.dll+0x205E34  (выделение и очистка буферов)
================================================================================

    Модель: GPT-5.6 Sol
    Дата:   14.08.2026
    Заключение: HotA передаёт NULL в _memset без проверки в ресурсном
    пути и в пути расчёта движения ИИ. Локальная запись по нулевому
    адресу доказана; причина предшествующего состояния установлена частично.


КРАТКОЕ РЕЗЮМЕ
--------------

    Во всех 213 уникальных случаях HotA вызывает _memset с нулевым
    адресом назначения и ненулевой длиной. Инструкция rep stosb записывает
    первый байт по адресу 0x00000000 и вызывает исключение.

    Установлены две подсистемы-поставщика нулевого адреса: загрузка ресурсов
    в 139/213 случаях и очистка строки данных движения ИИ в 73/213 случаях.
    Ещё 1/213 случай с длиной 4 оставлен отдельным из-за неполного стека.

    Для ресурсных путей NULL возвращает operator new. Для пути ИИ NULL
    возвращает A0_AIMgr_Get_AIMapMoveInfo_sub_42ECC0 при нулевом поле
    [+24h] менеджера ИИ. Почему выделение или поле стали нулевыми, сокращённые
    дампы не показывают.

2. Проверка листинга и адреса
-----------------------------

    HotA.dll имеет базу листинга 0x10000000. RVA 0x205E34 даёт адрес
    0x10205E34. Два выбранных DMP дают независимую проверку:

    0x03155E34 - 0x02F50000 + 0x10000000 = 0x10205E34
    0x6CED5E34 - 0x6CCD0000 + 0x10000000 = 0x10205E34

    В листинге HotA 1.8.0 функция _memset начинается по 0x10205E10,
    а целевой адрес находится внутри неё на смещении 0x24:

    .text:10205E34                 rep stosb

    Версия листинга соответствует HotA 1.8.0, указанной во всех 213/213
    уникальных журналах. В 43 целевых DMP RVA подтверждён контекстом;
    31 из них дополнительно проходят строгую проверку метаданных пары.

    Родственный адрес hota.dll+0x21228C соответствует 0x1021228C и лежит
    в векторной ветви той же _memset:

    .text:1021228C                 movdqa  xmmword ptr [ecx], xmm0

    Поиск 0x21228C прошёл 5794 текстовых файла проекта. Инцидентов с таким
    адресом не найдено; найдены только листинг и описания методики. Поэтому
    адреса +0x205E34 и +0x21228C не объединяются в одну семью дефекта:
    общий библиотечный помощник не доказывает общего поставщика NULL.


3. Точка сбоя
-------------

    _memset получает адрес назначения в EDI, байт заполнения в AL и длину
    в ECX. По адресу 0x10205E34 инструкция rep stosb начинает запись.

    Во всех 213/213 уникальных контекстах выполняется один инвариант:

    EAX = 0x00000000
    EDI = 0x00000000
    ECX = EDX > 0

    Следовательно, наблюдаемая операция имеет вид:

    _memset(0x00000000, 0, N), где N > 0

    Ресурсный DMP подтверждает CONTEXT.EIP = HotA.dll+0x205E34 и
    ECX = EDX = EBP = 0x002A701D. DMP пути ИИ подтверждает тот же адрес
    при ECX = EDX = 0x000010E0 и ESI = 0x00000000.

    Содержимое кучи имеет статус not_captured: оба выбранных DMP являются
    сокращёнными, не содержат Memory64List и не захватывают требуемые
    объекты. Поэтому факт записи по NULL доказан, а состояние аллокатора
    перед вызовом непосредственно не наблюдается.

5. Первопричина
---------------

    Локальный дефект одинаков для трёх установленных потребителей:
    поставщик возвращает нулевой адрес, а потребитель вызывает _memset
    с ненулевой длиной без проверки этого адреса.

    В основной ресурсной ветви sub_101615B0 вызывает operator new по
    0x10161664. Возвращённый EAX записывается в поле [EDI+108h] по
    0x1016166A и без test/cmp передаётся в _memset по 0x10161670.

    В альтернативной ветви той же функции operator new вызывается по
    0x1016174E. EAX записывается в [EDI+108h] по 0x10161750 и без
    проверки используется в _memset по 0x1016175C.

    Родственная функция sub_10161510 перед освобождением проверяет поле
    [ESI+108h], затем обнуляет указатель и длину. Это показывает, что
    нулевое значение допустимо для очищенного объекта, но две ветви
    создания обращаются с результатом выделения как с ненулевым.

    Сравнение с оригиналом SoD: operator new по 0x00617492 находится в
    h3hota.exe и вызывает __nh_malloc(a1, 1). Этот путь может вернуть
    EAX = 0. Ресурсный код HotA не учитывает такой результат.

    В пути ИИ sub_10027370 вызывает функцию
    A0_AIMgr_Get_AIMapMoveInfo_sub_42ECC0. Она проверяет поле менеджера
    ИИ [+24h] и штатно возвращает EAX = 0, когда поле равно нулю.
    Между возвратом и вызовом _memset по 0x10027457 проверки EAX нет.

    Поле [+24h] хранит основной массив _AIMapMoveInfo_. Функция
    A0_AIMgr_ClearCellsOrHexes_sub_4B11C0 проверяет старый указатель,
    освобождает его, обнуляет поле и выделяет новый массив по 0x004B1231.
    Объём полного массива вычисляется как:

    60 x ширина карты x высота карты x число уровней

    После выделения результат проверяется. При EAX = 0 поле [+24h]
    остаётся нулевым. Позднее sub_10027370 получает этот NULL через
    функцию поиска и пытается очистить строку длиной 30 x ширина карты.

    Доказан ближайший поставщик NULL в каждой основной ветви. Не доказано,
    почему operator new вернул NULL либо почему поле менеджера ИИ было
    нулевым именно в момент обращения. Совместимы как минимум три объяснения:

    1) отказ выделения из-за состояния 32-битного адресного пространства;
    2) переход жизненного цикла после очистки массива;
    3) повреждение объекта или служебных данных кучи.

    Сокращённые DMP не содержат кучу и поле менеджера ИИ. Поэтому ни одно
    из трёх объяснений нельзя повысить до установленной первопричины.

    Для отдельного случая N = 4 ближайший поставщик не установлен. Перенос
    адресов из листинга HD_HOTA 5.7 R18 на сборку 5.6 R18 недопустим;
    этот случай не включён ни в ресурсную, ни в ИИ-подгруппу.

6. Условия сбоя
---------------

    Для достижения адреса нужны одновременно три условия:

    1) поставщик адреса назначения возвращает 0;
    2) рассчитанная длина очистки остаётся больше 0;
    3) выполняется одна из ветвей без проверки адреса перед _memset.

    В ресурсной подгруппе длина переменна и не сводится к одной формуле
    карты. В подгруппе ИИ длина строго равна 30 x ширина карты; наблюдаются
    ширины 72, 108, 144, 180, 216 и 252.

    Серия содержит разные режимы, поэтому ни сеть, ни совпадение активного
    игрока с локальным не являются обязательными условиями:

    Network Game = 0: 150/213; Network Game = 1: 63/213.
    Me = Active Player: 126/213; не совпадают: 76/213;
    значение Me отсутствует: 11/213.

    Graphics.Mode принимает значения 2, 3, 4, 5, 6 и 7. Число
    Graphics.Threads меняется от 0 до 16. Quick Combat = 0 встречается
    в 139/213 случаях, Quick Combat = 1 в 73/213, ещё в 1/213 поле
    отсутствует. Эти настройки коррелируют с отдельными запусками, но код
    поставщиков NULL не ветвится по ним в прочитанных участках.

    Во всех 213/213 журналах указаны Memory.Mod = 0 и
    Graphics.AdvMap.Threads = -1. Без контрольной серии успешных запусков
    эти постоянные значения нельзя считать причиной.

    Из 213 уникальных журналов 6 содержат текст игрока. Дословно:

    "i cannot play and turn on all game"
    "ропуск хода"
    "wtf bro"
    "this errror repeats. it usually happens when i end my turn and
    sometimes when i enter a town with a hero"
    "left game for 1h ilde and it crashed"
    "again"

    Показания про завершение хода согласуются с путём ИИ, а упоминание входа
    в город совместимо с загрузкой ресурсов. Это контекст воспроизведения,
    но не доказательство происхождения NULL. Сообщение о простое показывает,
    что явное действие пользователя не обязательно непосредственно перед
    исключением.

    Инвентаризация вложений содержит 172 физических сейва и 169 уникальных
    SHA-256. Роли: 168 производных и 4 неизвестных. Ни одному сейву не
    назначена роль исходного источника, поскольку не доказано, что именно
    он был загружен перед вылетом.

    Представитель ресурсной подгруппы BATTLE__hotseat_.GM2 имеет SHA-256
    b407efafa070bc4494ef833d9fd678ec5683fc8b857d930a01cf19a4bf5da891.
    Он успешно распакован как raw-deflate со смещения 10; сигнатура H3SVG,
    версия формата 10, карта ZZZazzUntitled.h3m.

    Представитель подгруппы ИИ AUTOSAVE.GM2 имеет SHA-256
    5ded0b8fa2bbd26b1c3d30c0b26bd4fbe70bc2efddd46ab94f2d8a5f3188dc5f.
    Он успешно распакован как raw-deflate со смещения 10; H3SVG найден по
    смещению 0x49, версия формата 10.

    Оба представителя являются производными сейвами. Их успешная распаковка
    подтверждает пригодность файлов, но не превращает их в источник
    состояния и не доказывает причинность содержимого карты.

7. Воспроизведение вылета
-------------------------

    Сам механизм детерминирован: при нулевом адресе и N > 0 первая запись
    rep stosb всегда приводит к тому же адресу. Получение предшествующего
    нулевого состояния по имеющимся материалам недетерминировано.

    Вероятностный путь для ресурсной подгруппы:

    1) запустить HotA 1.8.0 в одной из наблюдаемых сборок HD-мода;
    2) многократно загружать ресурсы карты, города и боя в длинной сессии;
    3) принять повтор только при CONTEXT.EIP = HotA.dll+0x205E34,
       EAX = EDI = 0 и ECX = EDX > 0;
    4) отдельно проверить адрес возврата HotA.dll+0x161675 либо ветвь
       вызова _memset по HotA.dll+0x16175C.

    Вероятностный путь для подгруппы ИИ:

    1) использовать карты с шириной 72, 108, 144, 180, 216 или 252;
    2) довести выполнение до расчёта движения ИИ после завершения хода;
    3) принять повтор при адресе возврата HotA.dll+0x2745C;
    4) проверить, что ECX равен соответственно 0x0870, 0x0CA8, 0x10E0,
       0x1518, 0x1950 или 0x1D88.

    Для различения трёх источников предшествующего состояния нужен парный
    журнал и полный DMP с Memory64List. В момент повторения требуется
    зафиксировать:

    1) результат operator new в ресурсных точках HotA.dll+0x161664 и
       HotA.dll+0x16174E;
    2) значение [AIMgr+24h] до и после выделения по 0x004B1231;
    3) карту виртуального адресного пространства и состояние кучи;
    4) последовательность освобождения и нового заполнения поля [+24h].

    Дифференциальная проверка считается успешной, если наблюдение покажет
    один из взаимоисключающих переходов: выделение вернуло 0; поле было
    обнулено после успешного выделения; либо поле изменилось без штатного
    писателя. Одна только защита от записи по NULL подтверждает локальный
    потребитель, но не устанавливает первый источник нулевого состояния.

8. Достоверность и ограничения
------------------------------

Подтверждено:

- Адрес 0x10205E34 совпадает с rep stosb внутри _memset.
- В 213/213 уникальных контекстов EAX = EDI = 0 и ECX = EDX > 0.
- Два DMP подтверждают точку и адреса возврата ресурсного пути и пути ИИ.
- Основная ресурсная ветвь выделена в 134/213 случаях, вторая ресурсная
  ветвь в 5/213, путь ИИ в 73/213.
- В обеих ресурсных ветвях NULL поступает из operator new и не проверяется.
- В пути ИИ NULL возвращает функция поиска при нулевом [AIMgr+24h].
- Шесть размеров пути ИИ точно равны 30 x ширина карты.
- Два производных сейва успешно распакованы как H3SVG; причинность их
  содержимого не заявляется.

Ограничения:

- Происхождение отказа operator new не видно в сокращённых DMP.
- Содержимое [AIMgr+24h] и состояние кучи имеют статус not_captured.
- Memory64List отсутствует в двух основных выбранных DMP.
- Точный источник отдельного случая N = 4 не установлен.
- Листинг HD_HOTA 5.6 R18 отсутствует; кадр HD_HOTA.dll+0x219F8F не
  разобран переносом из другой сборки.
- Сведения о свободных диапазонах и целостности кучи отсутствуют.
- Исходный сейв воспроизведения не установлен.

Подтверждено:

Подтверждено:

    Виновный код находится в HotA.dll: три установленные ветви передают
