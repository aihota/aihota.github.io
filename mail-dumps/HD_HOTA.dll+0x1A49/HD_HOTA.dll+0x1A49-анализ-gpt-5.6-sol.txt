АНАЛИЗ ВЫЛЕТА HD_HOTA.dll+0x1A49 — отказ выделения памяти HD-мода
====================================================================

    Модель: GPT-5.6 Sol
    Дата: 03.09.2026
    Заключение: в шести уникальных DMP HD_HOTA.dll выполняет int 3 после
    возврата NULL из _malloc. Размеры запросов: 0x00100004,
    0x00180004, 0x0D680004 и 0x0D880004 байта.

КРАТКОЕ РЕЗЮМЕ
--------------

Что произошло:

    Проверены шесть уникальных инцидентов HotA 1.8.0 и 1.8.1 на сборках
    HD-мода 5.7 R35, R39, R40 и 5.8 R8. Во всех шести EIP нормализуется
    в HD_HOTA.dll+0x1A49, байт CC подтверждает int 3, а EAX=0 — NULL
    после _malloc. Точные листинги всех четырёх сборок совпадают по логике.

Локальный механизм:

    Локальный механизм подтверждён: сборки R35, R39 падают при создании буфера
    1 МиБ с аргументом 0x00100004, а R40 и R8 — в общем пути роста
    динамического буфера. Для двух R40-инцидентов зафиксированы запросы
    214,5 и 216,5 МиБ; в R8 — 1,5 МиБ.

    Истинный аргумент лежит по ESP-4. Для R8 это 0x00180004; возврат
    0x041F659E ведёт в sub_1046540+0x5E. ECX после _malloc волатилен и
    не является источником размера; прежний вывод malloc(8) отозван.

Охват семейства:

    Материализованная перепись содержит 67 физических TXT, сведённых
    в 65 уникальных инцидентов. Подтверждены шесть случаев +0x1A49:
    два R35, один R39, два R40 и один R8. Остальные 59 инцидентов имеют
    другие точные точки сбоя и явно исключены из целевого семейства.

Граница доказанности:

    Причина возврата NULL окончательно не установлена. Для R40 основной
    рабочей гипотезой остаются давление и фрагментация 32-битного адресного
    пространства. R8 падает при гораздо меньшем запросе 1,5 МиБ, поэтому
    эту гипотезу нельзя переносить на всю семью: сильная фрагментация,
    исчерпание и повреждение кучи остаются неразличимы без полной памяти.

3. Точка сбоя
-------------

Локальный механизм:

- sub_1001A30 принимает полезный размер в ECX и добавляет 4 с насыщением:
  при переносе разряда запрос становится 0xFFFFFFFF.
- Переноса нет ни в одном из шести инцидентов: ECX равен 0x00100000,
  0x00180000, 0x0D680000 либо 0x0D880000, поэтому переполнение исключено.
- Затем функция вызывает _malloc и проверяет EAX.
- При EAX=0 выполняется int 3; во всех шести сохранённых контекстах EAX=0.

Извлечённые аргументы выделения:

    Инцидент  Аргумент _malloc  Полезный размер  Возврат в вызывающий код
    --------  ----------------  ---------------  ------------------------
    R35-1     0x00100004        1 МиБ            HD_HOTA+0x9ABC8
    R35-2     0x00100004        1 МиБ            HD_HOTA+0x9ABC8
    R39       0x00100004        1 МиБ            HD_HOTA+0x9B1F8
    R40-1     0x0D680004        214,5 МиБ         HD_HOTA+0x465DE
    R40-2     0x0D880004        216,5 МиБ         HD_HOTA+0x465DE
    R8        0x00180004        1,5 МиБ           HD_HOTA+0x4659E

Интерпретация стека и регистров:

- После возврата _malloc аргумент остаётся по ESP-4.
- По ESP-8 лежит адрес возврата 0x...1A42.
- ECX после _malloc равен 8 в пяти DMP и 0xB155DBB9 в шестом.
- Прежний вывод malloc(8) отозван: размер берётся со стека, а не из ECX.

5. Первопричина
---------------

Доказанный локальный дефект:

- Общий обработчик NULL в HD_HOTA.dll намеренно выполняет int 3.
- Отказ памяти превращается в безусловный вылет.
- Для R40 ловушка срабатывает раньше штатной ветки loc_1046681;
  для R8 — раньше соответствующей ветки loc_1046641.

Рабочая гипотеза для R40:

- Для роста нужен непрерывный блок 214,5 либо 216,5 МиБ.
- Старый блок 214 либо 216 МиБ в этот момент ещё остаётся жив.
- Два независимых компьютера остановились на соседних границах буфера.
- Это поддерживает давление и фрагментацию 32-битного адресного пространства.

Граница для R35, R39 и R8:

- Запросы 1 и 1,5 МиБ совместимы с сильной фрагментацией или исчерпанием.
- Тот же результат совместим с повреждением кучи.
- Все шесть DMP сокращённые, поэтому окончательный выбор пока невозможен.

Исправление на стороне HD-мода:

1. Проверять указатель нового буфера на NULL до первого доступа и до
   временной записи состояния.
2. При NULL немедленно завершать ветку: не вызывать int 3, вернуть явную
   ошибку и сохранить старый объект без частичных изменений.
3. Сначала выделить и проверить новый блок, затем скопировать данные.
4. Только после успеха заменить указатель, размер и ёмкость, затем освободить
   старый блок.
5. Перед патчем сверить точную сигнатуру, байтовую последовательность и хеш
   листинга; при несовпадении сигнатуры патч не применять.

Дифференциальный тест:

- До исправления внедрённый отказ вызывает вылет.
- После исправления тот же отказ возвращает явную ошибку без ловушки,
  завершает функцию без вылета и сохраняет старое состояние.

Дополнительное уменьшение риска:

- Для sub_1046580/sub_1046540 использовать сегментированный или потоковый буфер.
- Ввести верхнюю границу размера и отказ до большого выделения.
- В sub_109AB60 и sub_109B190 передавать ошибку выше.
- Записывать полезный размер, поля +0x108/+0x110/+0x114, частную память и
  крупнейший свободный диапазон виртуальных адресов.

Межверсионная граница:

- В точном листинге 5.7 R33 ветка после NULL выполняла mov [esi],esi.
- В R35–R40 и 5.8 R8 в этой точке стоит int 3.
- Изменение формы аварии не доказывает общую причину 59 архивных логов.

3. Внедрить отказ ровно для _malloc(0x00100004) в sub_1001A30.

1. Довести dword_21B7CA0 до курсора 0x0D5FFFFFF либо 0x0D7FFFFFF.
2. Добавить пять байт.
3. Внедрить отказ для нового блока.
4. На исходной сборке проверить останов по +0x1A49.

Тест C — рост буфера R8:

1. В sub_1046540 воспроизвести заполнение 0x000FF576.
2. Добавить 0xF00 байт, чтобы получить 0x00100476.
3. Внедрить отказ для _malloc(0x00180004).
4. Проверить останов по +0x1A49 и возврат ошибки после исправления.

Ожидаемый результат исправленной сборки:

- Все три теста завершаются без int 3.
- Вызывающий код получает явную ошибку.
- Старый буфер остаётся доступным.
- Поля указателя, размера и ёмкости не меняются частично.
- Верхняя граница буфера и повторный запуск партии проверяются отдельно.

Необходимая телеметрия:

- Пять приложенных сейвов использовать как входы для повторов.
- Записать частную память и крупнейший свободный диапазон виртуальных адресов.
- Записать размер первого неуспешного выделения.
- Получить полный DMP с <Sys.FullDump> = 1.
- По этим данным отделить фрагментацию от повреждения кучи.

8. Достоверность и ограничения
------------------------------

Подтверждено:

- Все 6 уникальных DMP: EXCEPTION_BREAKPOINT, EIP по +0x1A49, EAX=0.
- Во всех 6 DMP аргумент _malloc прочитан по ESP-4, возврат — по ESP.
- R35/R39: три запроса 0x00100004 и точные вызывающие функции конструктора.
- R40: два запроса 0x0D680004/0x0D880004 из sub_1046580.
- R8: запрос 0x00180004 из sub_1046540; добавление 0xF00 и новая ёмкость
  0x00180000 восстановлены из кадра вызывающей функции.
- Точные листинги R35, R39, R40 и R8 подтверждают обе локальные ветви.
- Во всех 6 DMP CONTEXT_THREAD_MISMATCH; контексты потоков не смешивались,
  а поток стека определён только по диапазону ESP.

Матрица уверенности:

- Точка сбоя: подтверждена
- Локальный механизм: подтверждён
- Происхождение состояния: частично установлено
- Охват семейства: подтверждён
- Уровень причинности: L1

Ограничения:

- Все 6 DMP — MemoryList без Memory64List; полной кучи процесса нет.
- Причина возврата NULL не доказана окончательно. Для R40 давление VA
  существенно вероятнее, но повреждение кучи всё ещё не исключено.
- Поля объектов R40/R8 не попали в минидамп. Доступные размеры
  выведены из сохранённых кадров и детерминированного кода округления.
- Сейвы не проигрывались под инструментированной сборкой.
- 59 legacy-логов с другими смещениями не включены в подтверждённый счёт.

Отрицательные результаты:

- Покрытие: просмотрены все 6 уникальных DMP; полной памяти нет ни в одном.
  Контроль: каждый содержит код sub_1001A30 и стек с аргументом malloc.
- Восемь верхнеуровневых DMP свёрнуты в шесть SHA-256-групп; две пары
  совпали побайтово, а различия TXT оказались только форматированием.
- Все 6 TXT не содержат пользовательского блока Comment.
- Графический режим, полноэкранность, число потоков и карта не постоянны.
- По +0x1A49 нет чтения или записи памяти: это инструкция int 3 без операнда.

ВЫВОД
-----

Контрольный расчёт:

    нормализованный EIP = 0x01001A49
    инструкция = int 3
    EAX после _malloc = 0
    запросы R35 и R39 = 0x00100004
    запрос R8 = 0x00180004
    запросы R40 = 0x0D680004 и 0x0D880004
    прежний вывод malloc(8) = опровергнут

Происхождение состояния:

    Конечный механизм доказан: sub_1001A30 превращает NULL в int 3.
    Причина самого NULL частично установлена. Для R40 давление и
    фрагментация 32-битного адресного пространства являются основной
    рабочей гипотезой. Запрос R8 всего 1,5 МиБ, поэтому для всей семьи
    первопричина не обобщается; повреждение кучи не исключено.

Действия:

    Адресат: разработчик HD-мода.

    1. Убрать int 3 из рабочего пути NULL и передавать явную ошибку выше.
    2. Ограничить либо сегментировать динамический буфер R40/R8.
    3. Сохранять старое состояние до успешного выделения и копирования.
    4. Записывать размер запроса, частную память и крупнейший свободный
       диапазон виртуальных адресов.

Критерий завершения:

    Исправление завершено, когда все три теста внедрения отказа проходят без
    int 3, вызывающий код получает ошибку, поля буфера остаются согласованы,
    а полный DMP или телеметрия первого отказа уточняют источник NULL.
