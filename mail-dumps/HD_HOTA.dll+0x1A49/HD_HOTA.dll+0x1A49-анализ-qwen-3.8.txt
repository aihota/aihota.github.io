================================================================
АНАЛИЗ ВЫЛЕТА HD_HOTA.dll+0x1A49 (отладочный аллокатор HD-мода)
================================================================

Модель: Qwen 3.8
Дата: 01.08.2026
Заключение: Виновник — HD-мод (HD_HOTA.dll). В сборке 5.7 R35
автор заменил аварийную запись mov [esi],esi на ловушку int 3,
но без отладчика ловушка тоже убивает процесс. Корень прежний —
отказ malloc в сетевой партии (повреждение кучи или исчерпание
адресного пространства — по сокращённому минидампу не различить).

КРАТКОЕ РЕЗЮМЕ
--------------
Игра падает, когда HD-мод не может выделить память. В HD-моде
есть собственный отладочный распределитель памяти: он вызывает
malloc, а перед возвращаемым блоком ставит служебную метку
0xF00DBEEF. В сборках до R33 включительно при отказе malloc
(возврат NULL) распределитель выполнял запись mov [esi],esi
по адресу, равному запрошенному размеру, — и происходило
нарушение доступа (семейство адресов 0x1A0E / 0x1A4E / 0x19AE /
0x1ABE, 59 логов; подробный разбор — в отчёте HD_HOTA.dll+0x1A4E
и семейном отчёте).

В сборке 5.7 R35 код перекомпилирован. Теперь при отказе malloc
функция выполняет int 3 (намеренная точка останова) и возвращает
NULL. Запись по мусорному адресу устранена — но ловушка int 3
без подключённого отладчика вызывает EXCEPTION_BREAKPOINT,
который тоже завершает процесс. Тем самым вторичный баг (запись
в никуда) исправлен, однако штатная нехватка памяти по-прежнему
превращается в аварийное завершение игры: вместо тихого возврата
NULL процесс гибнет на ловушке.

Оба дампа сняты одним игроком с разницей 5 минут в одной сетевой
партии. Запрошенный размер — всего 8 байт (4 байта данных + 4
байта служебного заголовка). malloc(8) вернул NULL. Причина отказа
по сокращённому минидампу не видна: это может быть как исчерпание
адресного пространства 32-битного процесса, так и повреждение кучи
CRT (метаданные SBH, free-листы) — в том числе самим отладочным
аллокатором, который в версиях до R33 при отказе malloc пишет
mov [esi],esi по мусорному адресу и способен повредить кучу.
Отказ столь малого выделения в начале партии (Day 1 1 1) скорее
указывает на повреждение кучи, чем на честное исчерпание.

3. Точка сбоя
-------------
Формула: IDA_addr = runtime_addr − load_base + imagebase.

Дамп 1:
    runtime EIP = 0x04A91A49 (из сырого стека: 04A91A49)
    load_base   = 0x04A90000
    imagebase   = 0x01000000
    IDA_addr = 0x04A91A49 − 0x04A90000 + 0x01000000 = 0x01001A49

Дамп 2:
    runtime EIP = 0x04421A49 (из сырого стека: 04421A49)
    load_base   = 0x04420000
    IDA_addr = 0x04421A49 − 0x04420000 + 0x01000000 = 0x01001A49

Оба дают 0x01001A49 — инструкция int 3 в листинге:

    .text:01001A49                 int     3               ; Trap to Debugger

Адрес сбоя попадает НА ГРАНИЦУ инструкции (int 3 — однобайтовая
инструкция CC), что подтверждает совпадение версии листинга.

Верификация листинга: entry point модуля из лога (offset
0x1C4C67) совпадает с процедурой start в листинге по адресу
0x011C4C67. Timestamp листинга 6A6D5839 (01.08.2026) — сборка
R35, совпадает с версией из лога (HOMM3 HD version: 5.7 R35).

5. Первопричина
---------------
Корень — тот же, что у семейства 0x1A0E / 0x1A4E / 0x19AE /
0x1ABE: отказ malloc в сетевой партии. Подробный разбор групп
размеров (1 МиБ, 47–296 МиБ, ~1.27 ГБ) и повреждённого поля
длины — в отчёте HD_HOTA.dll+0x1A4E и семейном отчёте.

В обоих дампах 0x1A49 запрошенный размер — 8 байт (ECX = 8,
то есть 4 байта данных + 4 байта заголовка). malloc(8) вернул
NULL. Причина отказа по сокращённому минидампу не различима:
исчерпание адресного пространства или повреждение кучи CRT
(метаданные SBH, free-листы). Отказ 8-байтового выделения
в начале партии (Day 1 1 1) скорее указывает на повреждение
кучи: для честного исчерпания нужно забить всё адресное
пространство, а партия только началась. Сам отладочный аллокатор
в версиях до R33 — источник потенциальной порчи: при отказе
malloc он пишет mov [esi],esi по мусорному адресу, и если этот
адрес попадает в метаданные кучи, все последующие malloc ломаются.

Что изменилось в R35. В сборках до R33 функция sub_1001A30
при отказе malloc выполняла:

    .text:01001A45                 test    eax, eax
    .text:01001A47                 jnz     short loc_...
    .text:01001A49                 mov     [esi], esi      ; ← запись по размеру

где ESI = запрошенный размер (например, 0x00100000). Запись
по адресу, равному размеру, вызывала EXCEPTION_ACCESS_VIOLATION.

В R35 код перекомпилирован:

    .text:01001A45                 test    eax, eax
    .text:01001A47                 jnz     short loc_1001A4B
    .text:01001A49                 int     3               ; Trap to Debugger
    .text:01001A4A                 retn
    .text:01001A4B loc_1001A4B:
    .text:01001A4B                 mov     dword ptr [eax], 0F00DBEEFh
    .text:01001A51                 add     eax, 4
    .text:01001A54                 retn

Запись по мусорному адресу устранена: теперь при NULL функция
попадает на int 3 и возвращает NULL (retn с EAX = 0). Служебная
метка 0xF00DBEEF пишется только при успешном выделении (в [eax],
а не в [esi]). Однако int 3 без подключённого отладчика вызывает
EXCEPTION_BREAKPOINT, который завершает процесс. Штатная нехватка
памяти по-прежнему превращается в аварийное завершение — но уже
без записи по недопустимому адресу.

Дефект унаследован от предыдущих сборок HD-мода: функция
sub_1001A30 присутствует во всех версиях семейства (5.6 R19 —
5.7 R35), меняется лишь код обработки отказа malloc.

7. Воспроизведение вылета
-------------------------
Условие активации: отказ malloc в сетевой партии (повреждение
кучи или исчерпание адресного пространства).

Базовый сценарий:
- Запустить сетевую партию на многопользовательской карте
  (напр. LEGIONS ARENA LUCKTEST.h3m).
- Играть до отказа памяти (накопление буферов автобоя,
  рост строковых объектов, либо повреждение кучи —
  см. семейный отчёт).
- Вылет произойдёт при очередном выделении памяти, когда
  malloc вернёт NULL.

Воспроизведение нестабильно: зависит от состояния кучи
(повреждение или исчерпание), числа игроков, длительности
партии. В обоих дампах вылет произошёл на старте партии
(Day 1 1 1), что скорее указывает на повреждение кучи,
чем на честное исчерпание.

Дифф-тест: в R33 и ранее тот же сценарий даёт
EXCEPTION_ACCESS_VIOLATION (запись mov [esi],esi); в R35 —
EXCEPTION_BREAKPOINT (int 3). Корень один, форма различается.

8. Достоверность и ограничения
------------------------------
Подтверждено:
- Адрес сбоя 0x01001A49 совпадает с int 3 в листинге R35
  (граница инструкции, совпадение версии листинга подтверждено).
- Листинг верифицирован по entry point (offset 0x1C4C67 =
  процедура start в листинге) и timestamp (01.08.2026, R35).
- EAX = 0 в обоих дампах — malloc действительно вернул NULL.
- ECX = 8 в обоих дампах — запрошено 8 байт (4 + заголовок).
- Механизм (int 3 при NULL из malloc) доказан кодом функции
  sub_1001A30 в листинге R35.
- Принадлежность к семейству аллокатора подтверждена: та же
  функция, тот же вызывающий код (sub_1001C70), те же
  регистровые инварианты (EAX = 0), тот же модуль.

Ограничения:
- Минидампы сокращённые (без кучи): причина отказа malloc
  (повреждение кучи или исчерпание) по дампам не различима
  (установлена семейным отчётом по 61 логу).
- Стек содержит трамплины patcher_x86 (адреса 0x02D0xxxx),
  которые искажают автоматическую реконструкцию стека;
  непосредственный вызывающий код
  определён по XREF листинга, а не по стеку.
- Точный триггер отказа malloc (повреждение кучи или
  исчерпание; какой именно объект повреждён) по двум дампам
  не установить — нужен полный дамп (Sys.FullDump = 1)
  или рантайм-трассировка.
