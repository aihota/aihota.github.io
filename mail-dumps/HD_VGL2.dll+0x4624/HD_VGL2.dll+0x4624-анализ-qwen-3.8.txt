================================================================
АНАЛИЗ ВЫЛЕТА HD_VGL2.dll+0x4624 (отрисовка, OpenGL-рендер HD-мода)
================================================================

Модель: Qwen 3.8
Дата: 02.08.2026
Заключение: рабочий поток OpenGL-рендера HD-мода не проверяет
результат malloc при выделении буфера кадра; отказ выделения
роняет игру записью по нулевому указателю.


КРАТКОЕ РЕЗЮМЕ
--------------
Рабочий поток OpenGL-рендера HD-мода выделяет буфер кадра вызовом
malloc и тут же пишет в него, не проверив результат. Когда malloc
возвращает NULL, первая же запись mov [eax],ecx при EAX=0 бьёт по
адресу 0x00000000, и процесс падает с EXCEPTION_ACCESS_VIOLATION.
Непроверенное выделение здесь не случайность: соседний malloc на
0x4C байта в той же функции проверяется (test esi,esi; jz), а
очистка пула буферов обходит список с проверками на NULL. Крупный
буфер кадра (3-9 МБ) такой проверки не получил. Размер буфера во
всех четырёх дампах кратен произведению разрешения на 4 байта
(внутренняя глубина 32 бита), вылет повторяется на версиях HD-мода
5.7 R23/R29/R30/R33 в графическом режиме 7 при многопоточной
отрисовке. Почему malloc отказал (исчерпание адресного пространства
32-битного процесса или порча метаданных кучи), по сокращённому
минидампу не установить.

2. Проверка листинга и адреса
-----------------------------
Сопоставление адресов (формула runtime - адрес_загрузки +
базовый_адрес_образа). Базовый адрес образа HD_VGL2.dll во всех
трёх листингах modules/ (HD_VGL2.dll-R23.txt, HD_VGL2.dll-R33.txt,
HD_VGL2.dll.txt) одинаков: Imagebase = 0x10000000.

    дамп R33: база загрузки 0x6DB60000, EIP 0x6DB64624
        IDA = 0x6DB64624 - 0x6DB60000 + 0x10000000 = 0x10004624
    дамп R23: база загрузки 0x5C8B0000, EIP 0x5C8B4624
        IDA = 0x5C8B4624 - 0x5C8B0000 + 0x10000000 = 0x10004624

Смещение точки сбоя +0x4624 одинаково в R23 и R33 (функция не
смещалась между сборками); дампы R29 и R30 падают по тому же
смещению +0x4624.

Верификация версии листинга. В логах вылетов HotA нет timestamp/хэшей
модуля, секция Modules пуста, поэтому сверка выполнена двумя
способами:

1) Побайтно по минидампу R33. Из дампа прочитаны байты кода вокруг
   точки сбоя (сегмент 0x6DB645A4-0x6DB646A4 присутствует):

       runtime 0x6DB6460B:
       8B 77 34  0F AF 77 2C  8D 46 18  50  E8 1E D2 00 00
       8B 0D 70 25 B9 6D  83 C4 04  89 08  8D 48 18 ...

   что в точности совпадает с листингом HD_VGL2.dll-R33.txt:

       .text:1000460B  mov  esi, [edi+34h]
       .text:1000460E  imul esi, [edi+2Ch]
       .text:10004612  lea  eax, [esi+18h]
       .text:10004615  push eax
       .text:10004616  call _malloc
       .text:1000461B  mov  ecx, Block
       .text:10004621  add  esp, 4
       .text:10004624  mov  [eax], ecx

   Адрес сбоя EIP=0x10004624 попадает НА ГРАНИЦУ инструкции
   (mov [eax],ecx = байты 89 08), а не в середину — листинг
   соответствует сборке. CONTEXT минидампа (EAX=0, ECX=0x19283020,
   ESI=0x0032E700, EIP=0x6DB64624) совпадает с полем Context лога

2) Листинг HD_VGL2.dll-R23.txt воспроизводит те же инструкции по
   тем же адресам (0x10004616 call _malloc, 0x1000461B mov ecx,Block,

Листинги: modules/HD_VGL2.dll-R33.txt (SHA256 A57A8740...,
Timestamp 6A5E4BA4 = 20.07.2026) и modules/HD_VGL2.dll-R23.txt
(SHA256 C3CB0DB0..., Timestamp 6A420D08 = 29.06.2026).

Семья адресов. Это один адрес +0x4624, стабильный между версиями
HD-мода (не плавающий). Родственный вылет того же модуля —
HD_VGL2.dll+0x9807 (функция sub_10009770, создание поверхности: два
равных malloc подряд, первый успешен, второй возвращает NULL) —
тот же класс «отказ кучи» в тракте выделения буферов OpenGL-рендера,
но ДРУГАЯ функция и другой адрес; разбирается отдельным отчётом.
Наша падающая функция sub_10003970 вызывает sub_10009770 для
создания поверхности, а затем выделяет СОБСТВЕННЫЙ буфер кадра,
который и отказывает.


3. Точка сбоя
-------------
Падающая инструкция (листинг HD_VGL2.dll-R33.txt):

    .text:1000460B  mov  esi, [edi+34h]     ; высота кадра
    .text:1000460E  imul esi, [edi+2Ch]     ; esi *= шаг строки
    .text:10004612  lea  eax, [esi+18h]     ; размер = кадр + 0x18
    .text:10004615  push eax                ; Size
    .text:10004616  call _malloc            ; eax = malloc(...)
    .text:1000461B  mov  ecx, Block         ; ecx = глобал Block
    .text:10004621  add  esp, 4
    .text:10004624  mov  [eax], ecx         ; ВЫЛЕТ: запись [NULL]

Механика. Код выделяет узел пула буферов: размер равен
[edi+34h] * [edi+2Ch] + 0x18, где произведение даёт размер кадра в
байтах, а 0x18 — заголовок узла (поле следующей ссылки и
выровненный указатель на данные). malloc возвращает результат в
EAX. Следующая же инструкция mov [eax],ecx записывает прежнее
начало пула (глобал Block) в поле [+0] нового узла. Когда malloc
вернул NULL (EAX=0), запись идёт по адресу 0x00000000.

Адресная проверка. Адрес сбоя 0x00000000 равен базовому регистру
записи: операнд [eax] при EAX=0 даёт ровно 0x00000000. Запись
подтверждена минидампом: Information[0]=1 (запись),
Information[1]=0x00000000 (адрес сбоя). Проверка сошлась.

Сразу после точки сбоя код продолжил бы наполнять узел:

    .text:10004626  lea  ecx, [eax+18h]
    .text:10004629  and  ecx, 0FFFFFFF0h    ; выровнять данные
    .text:1000462C  mov  [eax+4], ecx       ; указатель данных
    .text:10004630  mov  Block, eax         ; новый узел в пул
    .text:1000463E  call _memset            ; обнулить кадр

а затем загружал кадр в OpenGL-текстуру (вызовы с константами
0xDE1 = GL_TEXTURE_2D, 0x1908 = GL_RGBA, 0x1401 = GL_UNSIGNED_BYTE,
0x80E1 = GL_BGRA, 0xCF2 = GL_UNPACK_ROW_LENGTH и glTexImage2D).
Назначение буфера — процессорная копия кадра для загрузки в текстуру
рабочим потоком рендера.

Вылет происходит НЕ в основном потоке игры, а в рабочем потоке

5. Первопричина
---------------
Непосредственная причина — пропущенная проверка результата malloc.
Код безоговорочно разыменовывает возвращённый указатель (mov
[eax],ecx), не сверив его с NULL.

Это не случайный пробел, а непоследовательность внутри одной
функции. Сравнение с родственным кодом показывает, что проверка
результата выделения здесь ШТАТНО предусмотрена:

1) Первый malloc в той же sub_10003970 (структура на 0x4C байта,
   IDA 0x100045BE) ПРОВЕРЯЕТСЯ:

       .text:100045BE  call _malloc
       .text:100045C3  mov  esi, eax
       .text:100045C8  test esi, esi
       .text:100045CA  jz   short loc_10004604   ; ветка отказа

   При отказе код уходит на loc_10004604 и обнуляет локальный
   указатель, то есть автор признаёт возможность отказа malloc.

2) Очистка пула буферов (sub_10002EA0) обходит глобальный список
   Block с проверками на NULL:

       .text:10002EA0  mov  eax, Block
       .text:10002EB4  test edx, edx
       .text:10002EB6  jz   short loc_10002ED9   ; пустой список
       .text:10002EC3  test edx, edx
       .text:10002EC5  jnz  short loc_10002EB8   ; обход узлов

   и освобождает узлы через j___free_base, корректно снимая узлы
   с головы списка (mov [esi],ecx перед free).

3) Второй malloc — крупный буфер кадра (IDA 0x10004616) — проверки
   НЕ имеет: за call _malloc сразу следует mov [eax],ecx. Именно
   этот пробел и реализует вылет.

Таким образом, контракт «malloc может вернуть NULL» в модуле
соблюдается и в соседнем выделении той же функции, и в очистке
пула, но не применён к самому крупному выделению — буферу кадра.

Поставщик данных (размер выделения). Размер берётся из полей
поверхности: [edi+34h] (высота) и [edi+2Ch] (шаг строки в байтах).
Произведение даёт размер процессорной копии кадра. Поверхность edi
готовит sub_10009770 — конструктор дескриптора поверхности (та же
функция, что фигурирует в родственном вылете HD_VGL2.dll+0x9807):
она заполняет поля структуры (+0..+24h) размерами и параметрами
формата из переданных аргументов и вычисляет тип пикселя OpenGL
(0x1401 = GL_UNSIGNED_BYTE либо 0x8363). То есть размеры кадра —
штатные значения, которые выставляет рендер при настройке
поверхности, а не произвольное содержимое памяти. Сами значения
полей edi лежат в куче и в сокращённом минидампе недоступны, однако
размер восстанавливается по регистру ESI (на момент сбоя
ESI = размер кадра, он ещё не сброшен):

    R23: ESI = 0x3E0400 = 4 064 256 = 1344 * 4 * 756  (точно)
    R30: ESI = 0x8CA000 = 9 216 000 = 1920 * 4 * 1200 (точно)
    R33: ESI = 0x32E700 = 3 336 960 ~ 1255 * 4 * 664  (с выравниванием шага)
    R29: ESI = 0x529A00 = 5 413 376

Размер правдоподобен (единицы мегабайт, старший бит не взведён, на
пиксельный мусор не похож) — это реальный буфер кадра внутренней
глубины 32 бита, а не испорченное поле размера. Следовательно,
malloc отказывает не из-за заведомо мусорного размера, а из-за
состояния кучи.

Почему malloc вернул NULL — вопрос открытый. Возможны две причины:
исчерпание/фрагментация виртуального адресного пространства
32-битного процесса (лимит 2 ГБ; несколько рабочих потоков держат
пулы многомегабайтных буферов кадра) либо повреждение метаданных
кучи. По сокращённому минидампу (без кучи) эти варианты не
различаются; для различения нужен полный дамп.

Отношение к SoD. HD_VGL2.dll — собственный OpenGL-рендер HD-мода.
В SoD движок рисовал через GDI/DirectDraw, OpenGL-рендера там не
было, поэтому у падающей функции нет SoD-оригинала и дефект не
унаследован от SoD. Это подтверждается и графом вызовов sub_10003970:
функция зовёт только CRT (_malloc/_memset/free), таблицу диспетчеризации
OpenGL (dword_1003244C..dword_100324D0) и внутренние подпрограммы
HD_VGL2; вызовов по абсолютным адресам h3hota.exe (признак репликации
логики движка) в ней нет. Это собственная инфраструктура HD-мода
(рабочий поток загрузки текстуры), а не перехват функции движка:
регистрации вида «push <адрес SoD>; call [reg+3Ch]» у sub_10003970 нет.

Виновный модуль — HD-мод (HD_VGL2.dll): дефект в его рабочем потоке
отрисовки.


6. Условия сбоя
---------------
Общее для всех четырёх дампов:

- Graphics.Mode = 7 (внутренняя глубина 32 бита, растяжимый вывод).
  Режим 7 входит в набор 32-битных внутренних режимов; наблюдаемые
  дампы покрывают только режим 7, других режимов в серии нет.
- OpenGL.Renderer = 0.
- Многопоточная отрисовка: Graphics.Threads = 4 (R23, R30) или 8
  (R29, R33); Graphics.AdvMap.Threads = -1 (по числу ядер). В
  процессе R33 минидамп фиксирует 12 потоков.
- OpenGL.Upscaling = 1/2/4 (апскейл увеличивает буферы кадра).
- 32-битный процесс h3hota HD.exe.

Различия между дампами (не влияют на механизм, функция не ветвится
по этим осям):

- Разрешение: 1344x756 / 1550x872 / 1920x1200 / 1255x664 (меняет
  размер буфера, не логику).
- Network Game: 0 (R23, R30) и 1 (R29, R33).
- День партии: 1 2 7 / 1 4 4 / 1 1 1 / 2 1 7 — партия начата во
  всех дампах (не предыгровое состояние).
- Версия HD-мода: R23 / R29 / R30 / R33 (один и тот же адрес сбоя).

Вылет наблюдался при разных разрешениях, сетевой и одиночной игре,
на четырёх версиях HD-мода — при общем условии режима 7 и
многопоточной отрисовки.


7. Воспроизведение вылета
-------------------------
Вылет недетерминирован: он наступает при отказе malloc, а момент
отказа зависит от динамики потребления памяти рабочими потоками
рендера и состояния кучи. Гарантированной последовательности шагов
нет; ниже — вероятностный путь для тестера.

Условие активации пути: графический режим 7 (внутренняя глубина
32 бита) при многопоточной отрисовке (Graphics.Threads >= 4) и
включённом апскейле. Путь — рабочий поток OpenGL-рендера,
выделяющий буфер кадра.

Вероятностный сценарий:

- Запустить игру в режиме Graphics.Mode = 7, Graphics.Threads = 8,
  с высоким OpenGL.Upscaling и крупным разрешением (например
  1920x1200) — это максимизирует размер и число буферов кадра.
- Дать партии поработать: длительное пребывание на карте
  приключений с активной прокруткой/перерисовкой, чтобы рабочие
  потоки активно выделяли и переиспользовали буферы кадра.
- Варьировать разрешения и число потоков между прогонами.

Что ловить в минидампе (признаки того, что пойман именно этот
вылет):

- Exception: HD_VGL2.dll+0x4624, write of address: 0x00000000;
- EAX = 0x00000000, EDX = 0x00000000;
- ESI = размер буфера кадра (кратен разрешению * 4);
- вершина стека V2: HD_VGL2.dll+0x4624, ниже HD_VGL2.dll+0x24F7
  (StartAddress), BaseThreadInitThunk.

Дифференциальная диагностика причины отказа malloc (для разработчика
модуля, не обходной путь): снять ПОЛНЫЙ дамп (включить
<Sys.FullDump> = 1 в _HD3_Data/Settings/hota.ini, тогда репортёр
приложит полный .dmp с кучей). По полному дампу в отладчике видно
состояние кучи в момент отказа: исчерпание/фрагментация
(свободные блоки исчерпаны, крупнейший непрерывный блок меньше
запрошенного) либо повреждение метаданных (разрушенные заголовки
блоков/свободные списки). Сокращённый дамп репортёра эту развилку
не закрывает.


8. Достоверность и ограничения
------------------------------
Подтверждено:

- Точка сбоя и механика доказаны побайтно: байты кода вокруг
  0x10004624, прочитанные из минидампа R33, совпадают с листингом
  HD_VGL2.dll-R33.txt; адрес сбоя попадает на границу инструкции
  mov [eax],ecx.
- CONTEXT минидампа R33 совпадает с полем Context лога дословно
  (EAX=0, EIP=HD_VGL2.dll+0x4624, запись по 0x00000000).
- Версии листингов подтверждены для R23 и R33 (побайтно); R29 и
  R30 падают по тому же смещению +0x4624.
- Вызывающий код (StartAddress, возврат HD_VGL2.dll+0x24F7)
  подтверждён фактическим стеком V2 во всех четырёх дампах.
- Пропуск проверки malloc доказан сравнением: первый malloc той же
  функции и очистка пула проверяют результат, буфер кадра — нет.
- Размер буфера восстановлен по ESI и сходится с произведением
  разрешения на 4 байта (R23 и R30 — точно).
- Размер кадра — штатный, а не мусорный: sub_10009770 (конструктор
  дескриптора поверхности) выставляет размеры и формат из аргументов
  при настройке поверхности.
- Собственный код HD-мода, не SoD: граф вызовов sub_10003970 содержит
  только CRT, таблицу диспетчеризации OpenGL и внутренние подпрограммы
  HD_VGL2; вызовов по абсолютным адресам h3hota.exe нет.
- Инвариант серии: EAX=0 и EDX=0 во всех четырёх дампах;
  Graphics.Mode = 7 во всех четырёх дампах.

Ограничения:

- Минидамп сокращённый (MemoryList без кучи, ~52 КБ, 37 сегментов):
  объект поверхности edi и содержимое кучи недоступны. Поля
  [edi+2Ch]/[edi+34h] (шаг строки/высота) прочесть нельзя; размер
  буфера восстановлен косвенно по ESI.
- Корневая причина отказа malloc НЕ установлена: сокращённый дамп
  не различает исчерпание/фрагментацию адресного пространства и
  повреждение метаданных кучи. Нужен полный дамп (Sys.FullDump = 1).
- Полезность лога для исправления — СРЕДНЯЯ. Пробел (отсутствие
  проверки результата malloc у буфера кадра) реален и локализован,
  что доказано соседним проверенным выделением и очисткой пула;
  однако триггер — давление на кучу в многопоточном 32-битном
  рендере, то есть первопричина выше по потоку, а её глубокая часть
  (почему именно отказала память) без полного дампа не определяется.
- Показаний игроков нет (блок Comment содержит только автотекст
  репортёра), поэтому сценарий воспроизведения построен по коду и
  настройкам, а не по описанию действий игрока.
- Серия покрывает только графический режим 7; поведение в других
  режимах по этим данным не оценивается (в падающей функции нет
  ветвления по режиму, но другими режимами серия не представлена).


ВЫВОД
-----
Виновник — HD-мод (render-подмодуль HD_VGL2.dll). Рабочий поток
OpenGL-рендера выделяет буфер кадра вызовом malloc и разыменовывает
результат без проверки на NULL; при отказе выделения первая же
запись mov [eax],ecx при EAX=0 бьёт по адресу 0x00000000 и роняет
процесс. Пробел непоследователен: соседнее выделение в той же
функции и очистка пула буферов результат malloc проверяют, а самое
крупное выделение (буфер кадра внутренней глубины 32 бита, 3-9 МБ)
проверки не получило. Вылет повторяется на версиях HD-мода
5.7 R23/R29/R30/R33 в графическом режиме 7 при многопоточной
отрисовке. Почему malloc отказал — исчерпание адресного
пространства 32-битного процесса или порча метаданных кучи — по
сокращённому минидампу не установить; для этого нужен полный дамп.
