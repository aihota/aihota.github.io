====================================================================
АНАЛИЗ ВЫЛЕТА HD_HOTA.dll+0x174B8B (и HD_HOTA.dll+0x17480B) — выбор случайного игрока в сетевом коде HD-мода
====================================================================

Модель: Qwen 3.8
Дата: 01.08.2026
Заключение: HD-мод выбирает случайного активного игрока делением
rand() на число активных игроков; когда активных игроков ноль,
происходит деление на ноль. Проверка «число игроков > 0» отсутствует.

КРАТКОЕ РЕЗЮМЕ
--------------
HD-мод в сетевой партии выбирает случайного активного игрока: считает,
сколько игроков сейчас в игре, берёт случайное число и делит его на это
количество (rand % число_игроков). Если в момент вызова активных игроков
ноль, делитель равен нулю и происходит вылет EXCEPTION_INT_DIVIDE_BY_ZERO.

Это семейство из 9 вылетов на 7 адресах (HD 5.6 R21 — 5.7 R35), одна и та
же функция HD-мода (sub_1174710 в R35, sub_1174390 в R34), адрес которой
смещается между сборками (плавающий адрес). Все 9 логов дают один регистровый
инвариант (EDX = 0, ESI = 0xD7, EDI = 0x4CE6E0, EAX == ECX), что доказывает
тождество функции; в сборке 5.7 RC9 (HD_HOTA.dll+0x126BEB, sub_1126770) код
подтверждён ещё и побайтно — идентичная последовательность call _rand; cdq;
mov edi, 4CE6E0h; idiv [ebp+var_30].

Механизм доказан полностью: инструкция вылета, адресная арифметика и
поставщик данных (функция, строящая список активных игроков) прочитаны.
Корень — пропущенная проверка «число активных игроков > 0» перед делением.
Почему количество игроков оказывается нулевым — условие во время работы:
оба вылета случились в самом начале сетевой партии (день 1 1 1), когда
сетевые идентификаторы игроков (net_id) ещё не заполнены либо уже сброшены.

2. Проверка листинга и адреса
-----------------------------
Оба адреса — одна и та же инструкция idiv [ebp+var_30] внутри одной функции,
смещённой между сборками. Формула сопоставления стандартная:
IDA_addr = runtime_addr - load_base + imagebase. Базовый адрес образа
HD_HOTA.dll = 0x1000000 (в обоих листингах), поэтому IDA_addr = 0x1000000 + RVA.

    R35: 0x1000000 + 0x174B8B = 0x1174B8B (функция sub_1174710)
    R34: 0x1000000 + 0x17480B = 0x117480B (функция sub_1174390)

Смещение инструкции от начала функции одинаково в обеих сборках:
0x1174B8B - 0x1174710 = 0x47B (R35) и 0x117480B - 0x1174390 = 0x47B (R34).
Это доказывает тождество функции между R34 и R35 (код сместился целиком,
не изменившись). Вызывающий код тоже сместился единообразно: обработчик
сообщения на 0x117AED8 (R34) и 0x117B278 (R35).

Листинги сверены с логами по точке входа. Точка входа HD_HOTA.dll из лога:
R35 = 0x04344C67 при адресе загрузки 0x04180000 (RVA 0x1C4C67, то есть
IDA 0x11C4C67), R34 = 0x039748B7 при адресе загрузки 0x037B0000 (RVA
0x1C48B7, то есть IDA 0x11C48B7). В обоих листингах процедура start лежит
ровно по этим адресам. Шапки листингов: R35 — Timestamp 6A6D5839
(01.08.2026), SHA256 1E905E36...; R34 — Timestamp 6A6AF52B (30.07.2026),
SHA256 C892698E.... Отрицательный тест версии пройден: адрес сбоя попадает
НА границу инструкции idiv [ebp+var_30] в обоих листингах.

Для родственного адреса +0x126BEB (5.7 RC9) использован листинг 5.7 RC9;
последовательность инструкций совпала побайтно (см. раздел 3). Для вылетов
5.6 (0x1069FB, 0x1254CB, 0x1254DB, 0x126C1B) точных листингов 5.6 нет,
поэтому для них инструкция сопоставлена НЕ побайтно, а по регистровому
инварианту: EDX = 0, ESI = 0xD7, EDI = 0x4CE6E0, EAX == ECX совпадает во
всех этих логах с R34/R35 и RC9, что доказывает тождество функции (см.
раздел 1). Два вылета 5.6 (0x1F6920 R10, 0x1F6FF0 R15) дают другую
регистровую картину (EDI = 0, ESI = крупный адрес) — это иное место деления
на ноль, не данное семейство.

3. Точка сбоя
-------------
Инструкция вылета одинакова в R34 и R35 (и побайтно совпадает в RC9):

    .text:01174B80  call    _rand
    .text:01174B85  cdq
    .text:01174B86  mov     edi, 4CE6E0h
    .text:01174B8B  idiv    [ebp+var_30]
    .text:01174B8E  mov     ecx, ds:699538h
    .text:01174B94  mov     esi, edx
    .text:01174B96  call    edi

Инструкция idiv [ebp+var_30] выполняет знаковое деление 64-битного делимого
EDX:EAX на 32-битный делитель из памяти [ebp+var_30]. Перед ней call _rand
кладёт случайное число в EAX, cdq расширяет знак в EDX (EDX = 0, число
положительное). Делитель var_30 — локальная переменная, в которую функция
только что посчитала число активных игроков.

Адресная проверка: сбой происходит не по адресу памяти, а по исключению
деления на ноль — делитель [ebp+var_30] равен 0. Это видно по тому, как
var_30 заполняется: функция подсчитывает ненулевые флаги (см. ниже), и если
ни один не установлен, var_30 остаётся 0. Делимое EDX:EAX при этом живое
(EAX = 0x5752 / 0x3EE7), что исключает порчу регистров — падает именно
деление на нулевой делитель.

Подсчёт делителя (фрагмент R35, 0x1174B14–0x1174B7D):

    .text:01174B14  xor     eax, eax
    .text:01174B19  cmp     byte ptr dword_120E04C+1, al
    .text:01174B1F  setnz   al
    .text:01174B22  cmp     byte_120E053, 0
    .text:01174B29  mov     [ebp+var_30], eax
    ...             ; далее те же проверки для byte_120E059, 120E05F,
                    ; 120E065, 120E06B, 120E071, 120E077 с inc eax
    .text:01174B80  call    _rand
    .text:01174B8B  idiv    [ebp+var_30]

var_30 = число ненулевых байтов-флагов среди восьми записей (120E04D,
120E053, 120E059, 120E05F, 120E065, 120E06B, 120E071, 120E077 — восемь
записей по 6 байт, флаг по смещению +1). Ниже показано, что этот флаг
означает «игрок активен», то есть var_30 = число активных игроков.

Поставщик данных — функция sub_11744F0 (R35), строит список активных
игроков из массива игроков движка:

    .text:011744F8  mov     edi, 699538h        ; глобальный _GameMgr_
    .text:011744FF  mov     eax, offset dword_120E04C  ; записи (8 шт.)
    .text:01174510  mov     ecx, [edi]          ; экземпляр _GameMgr_
    .text:01174512  mov     ecx, [ecx+esi+20B98h]  ; player[i].net_id
    .text:01174519  mov     byte ptr [eax+3], 0FFh
    .text:0117451D  test    ecx, ecx
    .text:0117451F  jz      short loc_117454B   ; net_id == 0 -> нет игрока
    .text:01174521  mov     byte ptr [eax+1], 1 ; флаг «игрок активен»
    ...
    .text:0117454B  mov     word ptr [eax], 0   ; net_id == 0 -> флаг = 0
    ...
    .text:01174554  add     eax, 6              ; следующая запись
    .text:01174557  inc     edx
    .text:01174558  add     esi, 168h           ; следующий игрок (360 байт)
    .text:0117455E  cmp     eax, (offset dword_120E07A+2)
    .text:01174563  jl      short loc_1174510

Функция обходит восемь слотов игроков и для каждого читает поле net_id
(сетевой идентификатор) из массива игроков движка. Если net_id != 0 —
ставит флаг «активен» (байт record+1 = 1), если net_id == 0 — флаг = 0.
Сумма этих флагов и есть var_30 в месте вылета.

Назначение функции (что происходит сразу после деления). Остаток от деления
(rand % var_30, попадает в ESI) задаёт число шагов обхода связного списка
активных игроков: начиная со своего идентификатора (GetMyID_AsPlayer),
функция следует по указателям «следующий» (байт record+3 тех же записей
120E04C; список строит sub_11744F0, связывая активных игроков: record+3
первого хранит индекс второго, второго — третьего и так далее, у последнего
равен 0xFF). Пройдя столько шагов, функция выбирает случайного активного
игрока и заполняет его индексом побайтный буфер dword_120E07A, обходя игроков
(шаг структуры 0x168). Иначе говоря, это построение рандомизированного
распределения по игрокам, а не единичный выбор. Сбой происходит на самом
первом шаге — вычислении rand % var_30 при var_30 = 0, до обхода списка дело
не доходит.

Что такое поле net_id и массив игроков, подтверждено по листингу главного
EXE (h3hota.exe). Комментарий декомпилятора в A0_Recieve_NewTurnMsg
(0x4CBB5F): «v14 = 360 * a4; v69 = A0_GameMgr_dword_699538->player_astr20AD0[a4].net_id_dwordC8».
Массив игроков player_astr20AD0 начинается у _GameMgr_ по смещению 0x20AD0,
размер структуры игрока 360 (0x168) байт, поле net_id_dwordC8 лежит по
смещению 0xC8 внутри структуры: 0x20AD0 + 0xC8 = 0x20B98 — ровно тот адрес,
который читает HD-мод. Глобаль 699538h — это A0_GameMgr_dword_699538
(указатель на менеджер игры), а 4CE6E0h — функция
A0_GameMgr_GetMyID_AsPlayer_sub_4CE6E0 (возвращает идентификатор локального
игрока).

Признаки поиска в других версиях: контекст-инварианты EDX = 0, EDI = 0x4CE6E0,
EAX == ECX, EXCEPTION_INT_DIVIDE_BY_ZERO; текстовая сигнатура —
последовательность call _rand; cdq; mov edi, 4CE6E0h; idiv [ebp+var_30];
mov ecx, ds:699538h; mov esi, edx; call edi. Адрес вылета = (начало функции
выбора случайного игрока в данной сборке) + 0x47B.

4. Цепочка вызовов и контекст
-----------------------------
Непосредственный вызывающий код взят из фактического стека, а не из
XREF-комментария листинга (у падающей функции две точки вызова). Путь
от игрового цикла до точки сбоя:

h3hota.exe  A0_MainMgr_PlayMgr_sub_4B0BA0 (менеджер воспроизведения, игровой цикл)
-> patcher_x86.dll  трамплины 0x02C6xxxx (перехват HD-мода)
-> HD_HOTA.dll  обработчик сообщения 0x117B230 (код 0x3F8; условие — хост)
-> HD_HOTA.dll  sub_1174710 (выбор случайного игрока) — СБОЙ: idiv [ebp+var_30], делитель var_30 = 0

Верх стека V1 (R35), сырые кадры:

    [ HD_HOTA.dll+0x174710 ] called from [ HD_HOTA.dll+0x17B278 ]
    [ HD_HOTA.dll+0x17B230 ] called from [ 0x02C6A411 ]
    [ HD_HOTA.dll+0x18D3F0 ] called from [ 0x02C6C3C1 ]
    ? called from before [ HD_HOTA.dll+0x3FDC1 ]
    [ HD_HOTA.dll+0x3FDB0 ] called from [ 0x02C5EFC4 ]
    ...
    [ 0x004B0BA0 ] called from [ 0x004F0516 ]

Стек подтверждает: первый кадр 042F4B8B (HD_HOTA, база 0x04180000) = RVA
0x174B8B (вылет), второй кадр 042FB27D = RVA 0x17B27D — это адрес возврата
сразу после call sub_1174710 на 0x117B278. Значит, падающую функцию вызвал
обработчик сообщения на 0x117B230 (а не sub_1179480, указанная в
XREF-комментарии листинга, — у функции две точки вызова).

Обработчик сообщения (R35, 0x117B230, stdcall retn 14h):

    .text:0117B233  mov     ecx, ds:699538h
    .text:0117B239  mov     eax, 4CE6E0h        ; GetMyID_AsPlayer
    .text:0117B23F  call    eax                 ; eax = мой идентификатор
    .text:0117B241  mov     esi, [ebp+0Ch]      ; сообщение
    .text:0117B244  cmp     eax, dword_120E08A  ; я — первый активный игрок?
    .text:0117B24A  jnz     short loc_117B28E   ; нет -> выход
    .text:0117B24C  cmp     dword ptr [esi+8], 3F8h  ; код сообщения == 1016?
    .text:0117B253  jnz     short loc_117B28E   ; нет -> выход
    .text:0117B25F  call    eax ; sub_1174D20
    ...
    .text:0117B278  call    sub_1174710         ; выбор случайного игрока
    .text:0117B27D  push    dword_120E07A
    .text:0117B289  call    sub_109D960         ; рассылка результата

Логика обработчика: когда приходит сетевое сообщение с кодом 1016 (0x3F8)
и локальный игрок является первым активным игроком (глобаль dword_120E08A
хранит индекс первого активного игрока, выставленный функцией sub_11744F0),
HD-мод выбирает случайного активного игрока (sub_1174710) и рассылает
результат остальным (sub_109D960). Глобаль dword_120E08A выставляется
писателем sub_11744F0 (строка «mov dword_120E08A, edx» для первого
найденного активного игрока).

Важно: в этом пути (через обработчик сообщения) писатель sub_11744F0
НЕ вызывается перед sub_1174710 — флаги активных игроков берутся из
глобального состояния, построенного ранее. sub_1174D20, вызываемая прямо
перед делением, мала (зовёт sub_109E040) и список игроков не перестраивает.
Существует и второй путь к sub_1174710 (через sub_1179480 в R35 / sub_11790E0
в R34), где писатель sub_1174ED0 вызывается непосредственно перед выбором;
но фактический стек обоих дампов указывает на путь через обработчик сообщения.

Кадр движка 0x004B0BA0 = A0_MainMgr_PlayMgr_sub_4B0BA0 (менеджер
воспроизведения игры, вызывается из 0x004F0516 с this = A0_MainMgr_dword_699550).
Промежуточные кадры 0x02C6xxxx — трамплины patcher_x86 (динамически выделенная
память, вне модулей), через которые HD-мод перехватывает игровой цикл.

5. Первопричина
---------------
Ближайшая причина общая для обоих вылетов: функция выбора случайного игрока
делит случайное число на число активных игроков, не проверяя, что это число
больше нуля. Когда активных игроков нет, делитель var_30 = 0, и idiv вызывает
EXCEPTION_INT_DIVIDE_BY_ZERO. Дефект — пропущенная проверка «число активных
игроков > 0» перед делением. Это баг кода HD-мода (закрытый модуль
HD_HOTA.dll): ни оригинальной функции SoD, ни её контракта здесь нет —
обработчик сетевого сообщения 1016 и выбор случайного игрока добавлены
HD-модом, поэтому дефект не унаследован от SoD.

Почему число активных игроков оказывается нулевым (глубинная причина).
Функция-писатель sub_11744F0 считает игрока активным, когда его поле net_id
(сетевой идентификатор) не равно нулю. Поле net_id управляется сетевой
подсистемой движка: оно обнуляется при инициализации/сбросе
(«this->net_id_dwordC8 = 0» в h3hota.exe:0x4B9BDD; «mov [ebx+20B98h], esi»
с esi = 0 в A0_MakeAndSend_Diff_Dat, h3hota.exe:0x4CB692) и выставляется при
сетевой настройке партии. Оба вылета случились в самом начале сетевой партии
(день 1 1 1). Вероятное окно сбоя — момент старта или перезапуска сетевой
партии, когда net_id игроков ещё не присвоены либо уже сброшены, но
обработчик сообщения HD-мода уже исполняется и пытается выбрать случайного
игрока из пустого списка.

Это окно — условие во время работы (соотношение по времени между
инициализацией сети движка и диспетчером сообщений HD-мода); по статике его
момент точно не фиксируется. Проверка «детерминированность против частоты»:
пропущенная проверка присутствует в коде всегда, но срабатывает редко
(единичные репорты) — значит, триггер (ноль активных игроков) не
детерминирован для каждой сетевой партии, а возникает в узком окне
инициализации. Это согласуется с редкостью вылета.

Отдельно: поле ingame values «Active Player» (глобаль движка
A0_Current_Player_ID_dword_69CCF4) не равно массиву net_id. Игра может считать
текущего игрока существующим (Active Player = 1 в R35), тогда как массив
net_id, который читает HD-мод, в этот момент нулевой. Поэтому «Active Player: 1»
в логе не противоречит нулевому числу активных игроков в коде HD-мода — это
разные поля.

6. Условия сбоя
---------------
Обстановка обоих вылетов:

- сетевая партия (Network Game = 1, Game Type = 2);
- самый старт партии — день 1 1 1 (в логе «Day = 1 11»);
- графический режим Graphics.Mode = 5 (внутренняя глубина 32 бита); режим
  влияет лишь на путь отрисовки и не участвует в механизме деления —
  ветвления по Graphics.Mode в падающей функции нет;
- локальный игрок — первый активный игрок (хост), иначе обработчик сообщения
  не дошёл бы до выбора случайного игрока;
- приход сетевого сообщения с кодом 1016 (0x3F8).

Разные карты (Air Supremacy у R35 и случайная сетевая карта у R34) и разные
машины при одном механизме показывают, что вылет не привязан к конкретной
карте или настройкам — условие в состоянии сетевой инициализации.

7. Воспроизведение вылета
-------------------------
Вылет недетерминирован: зависит от момента, когда обработчик сообщения HD-мода
исполняется при ещё пустом (или уже сброшенном) массиве net_id игроков.
Вероятностный путь: запуск сетевой партии (Network Game = 1) под HD-модом
5.7 RC9+ в роли первого активного игрока (хоста); цель — поймать окно в самом
начале партии (день 1 1 1), когда приходит сетевое сообщение с кодом 1016,
а список активных игроков HD-мода ещё пуст. Целевые инварианты ловимого дампа:
EXCEPTION_INT_DIVIDE_BY_ZERO, EDX = 0, EDI = 0x4CE6E0, адрес вылета = начало
функции выбора игрока + 0x47B для данной сборки. Для подтверждения нулевого
числа активных игроков полезен полный дамп (<Sys.FullDump> = 1): в нём видно
содержимое записей 120E04C.. (все восемь флагов нулевые) и массив net_id
игроков движка.

8. Достоверность и ограничения
------------------------------
Подтверждено:

- Семейство из 9 вылетов на 7 адресах (5.6 R21 — 5.7 R35) — одна функция:
  идентичная инструкция idiv [ebp+var_30], одинаковое смещение +0x47B от
  начала функции (R34/R35), единый регистровый инвариант (EDX = 0, ESI = 0xD7,
  EDI = 0x4CE6E0, EAX == ECX) во всех 9 логах; механизм детально разобран для
  R35.
- Адрес +0x126BEB (5.7 RC9) подтверждён побайтно: та же последовательность
  call _rand; cdq; mov edi, 4CE6E0h; idiv [ebp+var_30]. Вылеты 5.6 (0x1069FB,
  0x1254CB, 0x1254DB, 0x126C1B) отнесены к семейству по регистровому инварианту
  (точных листингов 5.6 нет).
- Поставщик данных прочитан: sub_11744F0 строит список активных игроков по
  полю net_id; var_30 = число активных игроков.
- Поля движка подтверждены по листингу h3hota.exe: массив игроков
  player_astr20AD0 (структура 360 байт, net_id по смещению 0xC8, итого
  0x20B98), глобаль 699538h = _GameMgr_, 4CE6E0h = GetMyID_AsPlayer.
- Версии листингов сверены по точке входа; адрес сбоя попадает на границу
  инструкции (отрицательный тест версии пройден).

Ограничения:

- Виновный код в закрытом модуле HD-мода; точка исправления — у разработчиков
  HD-мода.
- Глубинный триггер (почему массив net_id пуст в момент обработки сообщения
  1016) — условие во время работы (окно сетевой инициализации); по статике
  зафиксирован механизм, а не точный момент окна.
- Минидампы сокращённые (без кучи): по ним не прочитать содержимое записей
  120E04C.. и массива net_id напрямую; нулевой делитель доказан кодом
  (подсчёт флагов), а не чтением памяти дампа.
- Для вылетов 5.6 (0x1069FB, 0x1254CB, 0x1254DB, 0x126C1B) точных листингов
  5.6 нет: принадлежность к семейству доказана регистровым инвариантом
  (EDX = 0, ESI = 0xD7, EDI = 0x4CE6E0), но не побайтным чтением инструкции
  в этих сборках. Два вылета 5.6 (0x1F6920 R10, 0x1F6FF0 R15) по регистровой
  картине (EDI = 0) отличаются и к семейству НЕ отнесены — это другое место
  деления на ноль.
- Полезность высокая: дефект логики (пропущенная проверка числа игроков перед
  делением) локализован и доказан, точечная проверка устраняет вылет; природа
  триггера во время работы влияет на воспроизведение, но не на исправимость.

ВЫВОД
-----
Семейство из 9 вылетов на 7 адресах (HD_HOTA.dll+0x1069FB, +0x1254CB, +0x1254DB,
+0x126BEB, +0x126C1B, +0x17480B, +0x174B8B; HD 5.6 R21 — 5.7 R35) — один дефект
кода HD-мода: функция выбора случайного активного игрока делит случайное число
на число активных игроков (rand % число_игроков) без проверки, что игроков больше
нуля. Функция смещается между сборками (плавающий адрес, инструкция idiv [ebp+var_30]
в смещении +0x47B от начала); тождество функции доказано регистровым инвариантом
(EDX = 0, ESI = 0xD7, EDI = 0x4CE6E0) во всех 9 логах и побайтно в 5.7 RC9
(+0x126BEB). Список активных игроков строит функция sub_11744F0 по полю net_id
массива игроков движка; когда все net_id нулевые, делитель равен нулю и происходит
EXCEPTION_INT_DIVIDE_BY_ZERO. Все вылеты — в самом начале сетевой партии (день
1 1 1), что указывает на окно сетевой инициализации, когда net_id ещё не присвоены
или уже сброшены, а обработчик сообщения HD-мода (код 1016) уже выбирает случайного
игрока. Виновник — HD-мод (закрытый модуль HD_HOTA.dll); дефект не унаследован от
SoD (обработчик сообщения и выбор случайного игрока — добавление HD-мода). Два
вылета 5.6 (0x1F6920, 0x1F6FF0) с EDI = 0 — другое место деления на ноль, не это
семейство.
