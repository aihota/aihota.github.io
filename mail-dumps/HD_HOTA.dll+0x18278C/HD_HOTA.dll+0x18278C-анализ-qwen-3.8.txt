АНАЛИЗ ВЫЛЕТА HD_HOTA.dll+0x18278C
====================================================================

Модель: Qwen 3.8
Дата: 29.07.2026
Заключение: HD-мод не проверяет результат поиска объекта в
восьмислотовой таблице сетевых имён: когда таблица полна и ключ
не найден, NULL передаётся в функцию-инициализатор строки, и
первая же запись mov [esi+6], eax падает по адресу 0x6.

КРАТКОЕ РЕЗЮМЕ
--------------
Сетевое сообщение ссылается на объект с ключом 0xB043. Обработчик
сообщений ищет этот ключ в глобальной таблице на 8 слотов. Поиск
не находит ключ, а вставка не находит свободного слота — таблица
полна. Функция поиска возвращает NULL, но вызывающий код не
проверяет результат и сразу передаёт NULL как указатель на объект
в функцию-инициализатор строки. Та обнуляет поля объекта — первая
же запись mov [esi+6], eax при ESI=0 бьёт по адресу 0x6.
Родственная функция sub_1182950 делает тот же поиск, но проверяет
результат и пропускает вызов при NULL — значит, возврат NULL
штатно предусмотрен, а проверка пропущена именно в обработчике
сообщений. Из пяти вызывающих sub_1182780 два не проверяют NULL
(sub_118CEB0 и sub_1185660), два проверяют (sub_1182950 и
sub_118B380), один вставляет напрямую без поиска (sub_1188CC0).
Вылет воспроизводится только в сетевой игре;
на 21 лог приходится 15 разных адресов сбоя — функция смещается
между сборками HD-мода (5.6 R19 — 5.7 R33), механизм идентичен.

6. Механика отказа
------------------
Функция sub_1182780 — инициализатор строкового поля объекта.
Принимает this (ECX), указатель на строку-источник (arg_0)
и байт-флаг (arg_4). Обнуляет поля объекта по смещениям
+6, +0Ah, +0Eh, +12h, +16h, затем копирует до 16 байт
из источника в [this+6] группами по 4.

Инструкция краша:
.text:0118278C                 mov     [esi+6], eax

ESI = ECX = 0 (NULL this), EAX = 0. Запись нуля по адресу
0x00000006 — нарушение доступа на запись.

Вызывающий код (sub_118CEB0, case 1):
.text:0118D2EC                 mov     edi, [esi+4]
.text:0118D2EF                 mov     ecx, dword_21B5B14
.text:0118D2F5                 push    edi
.text:0118D2F6                 call    sub_1182820
.text:0118D2FB                 mov     ecx, eax
.text:0118D2FD                 test    ecx, ecx
.text:0118D2FF                 jnz     short loc_118D309
.text:0118D301                 push    edi
.text:0118D302                 call    sub_1182880
.text:0118D307                 mov     ecx, eax
; --- проверки НЕТ ---
.text:0118D309 loc_118D309:
.text:0118D309                 push    dword ptr [esi+2Ch]
.text:0118D30C                 lea     eax, [esi+1Ch]
.text:0118D30F                 push    eax
.text:0118D310                 call    sub_1182780

После sub_1182880 результат (EAX) копируется в ECX без
проверки. Если оба поиска вернули NULL, ECX=0 передаётся
в sub_1182780 как this.

7. Таблица поиска (dword_21B5B14)
---------------------------------
sub_1182820 — линейный поиск в фиксированной таблице:
.text:01182823                 lea     eax, [ecx+3]
.text:01182830                 cmp     [eax], ecx      ; ключ слота
.text:01182832                 jz      short loc_118283F
.text:01182835                 add     eax, 17h        ; шаг 23 байта
.text:01182838                 cmp     edx, 8          ; максимум 8
.text:0118283B                 jl      short loc_1182830
.text:0118283D                 xor     eax, eax        ; не найден, вернул 0

Таблица: 8 слотов по 0x17 (23) байт, начиная с this+3.
Ключ слота — dword по смещению +0 от начала слота.
Размер объекта таблицы: operator new(0xBB) = 187 байт
(3 байта заголовок + 8 * 23 = 187). Единственная точка
создания: sub_1001680 (0x01001684).

sub_1182880 — «найди или вставь»:
1) sub_1182820(ключ) — найти существующий;
2) если не найден: sub_1182820(0) — найти свободный (ключ==0);
3) если свободный найден: записать ключ, вернуть слот;
4) если свободных нет: вернуть NULL.

Краш наступает в случае 4: все 8 слотов заняты, новый ключ
не вставляется.

8. Условия сбоя
---------------
Обязательные условия:
- сетевая игра (все 21 лог — Network Game = 1);
- таблица на 8 слотов полностью заполнена;
- приходит сообщение с ключом, которого нет в таблице.

Ключи в 21 логе различаются (от 0x8141 до 0x13D84B), что
исключает конкретный битый объект. Вероятный сценарий:
в длительной сетевой партии накапливается более 8 именованных
объектов, и очередной объект не помещается в таблицу.

9. Первопричина
---------------
Пропущенная проверка результата sub_1182880 в обработчике
сетевых сообщений sub_118CEB0 (case 1) и в sub_1185660.
Функция sub_1182880 штатно возвращает NULL при переполнении
таблицы — это не сбой, а предусмотренный исход.

Полная картина по пяти вызывающим sub_1182780:
- sub_1182950: проверяет NULL (test eax,eax; jz) — безопасен;
- sub_118B380: проверяет NULL (test esi,esi; jz) — безопасен;
- sub_1188CC0: вставляет по вычисленному адресу без поиска —
  безопасен по построению;
- sub_118CEB0: НЕ проверяет после sub_1182880 — КРАШ;
- sub_1185660: НЕ проверяет после sub_1182880 — дефектен.

Внутри самого sub_118CEB0 case 7 делает тот же поиск
sub_1182820 и ПРОВЕРЯЕТ результат (test eax,eax; jz
def_118D2E5). Остальные case (2, 3, 4, 5, 6, 11, default)
к таблице не обращаются. Case 1 — единственный путь
в функции, где проверка пропущена.

Родственная функция sub_1182950 обрабатывает тот же исход
корректно:

.text:0118295C                 call    sub_1182820
.text:01182961                 test    eax, eax
.text:01182963                 jz      short loc_1182973   ; NULL -- пропуск
.text:0118296E                 call    sub_1182780          ; безопасно

Дефект в sub_118CEB0 и sub_1185660: после sub_1182880
результат передаётся в sub_1182780 без проверки.

Виновник — HD-мод (закрытый модуль HD_HOTA.dll).

11. Воспроизведение вылета
--------------------------
Роль 1 (базовый сценарий):
- сетевая игра (2+ игроков);
- длительная партия, в которой создаётся более 8 именованных
  объектов, попадающих в таблицу dword_21B5B14;
- когда таблица заполнена, любое сообщение, ссылающееся
  на объект вне таблицы, вызывает краш.

Роль 2 (рантайм-проверка):
- точное содержимое таблицы dword_21B5B14 в момент сбоя
  (какие 8 ключей заняты, какой ключ не вставляется) —
  только из полного минидампа или отладчика;
- какой именно тип объекта попадает в таблицу (герой, город,
  игрок) — определяется по коду заполнения (sub_1188CC0
  вставляет напрямую, sub_1182880 — через поиск свободного);
- точный сценарий переполнения (какие действия создают
  9+ объектов) — только рантайм.

Достоверность и ограничения
---------------------------
Подтверждено:
- механизм краша: mov [esi+6], eax при ESI=0, адресная
  арифметика 0+6=0x6 совпадает с адресом сбоя;
- пропущенная проверка: sub_118CEB0 не проверяет результат
  sub_1182880 перед вызовом sub_1182780;
- все 5 вызывающих sub_1182780 проверены: 2 с проверкой
  (sub_1182950, sub_118B380), 1 без поиска (sub_1188CC0),
  2 без проверки (sub_118CEB0, sub_1185660);
- таблица: operator new(0xBB) = 187 байт = 3 + 8*23,
  единственная точка создания sub_1001680;
- 21 лог, 15 адресов, все сетевые — функция смещается между
  сборками, код идентичен (подтверждено по R33 и R20);
- версия листинга R33 подтверждена по entry point.

Ограничения:
- содержимое таблицы dword_21B5B14 в момент сбоя недоступно
  (сокращённый минидамп без кучи);
- тип объектов в таблице (герои/города/игроки) не определён
  статикой — нужна трассировка заполнения;
- точный сценарий переполнения (какие действия создают 9+
  объектов) — только рантайм;
- начальное состояние слотов (operator new не обнуляет;
  обнуление зависит от кучи) — рантайм.

ВЫВОД
-----
HD-мод (HD_HOTA.dll) не проверяет результат поиска объекта
в восьмислотовой таблице сетевых имён. Когда таблица полна
и очередной ключ не найден, функция «найди или вставь»
sub_1182880 штатно возвращает NULL, но обработчик сообщений
sub_118CEB0 (case 1) и sub_1185660 передают этот NULL
в инициализатор строки sub_1182780 без проверки. Первая
же запись mov [esi+6], eax при ESI=0 падает. Родственная
функция sub_1182950 обрабатывает тот же исход корректно
(проверяет и пропускает), что доказывает штатность возврата
NULL. Дефект проявляется только в сетевой игре при
переполнении таблицы; 21 лог на 15 адресах (5.6 R19 — 5.7 R33).
