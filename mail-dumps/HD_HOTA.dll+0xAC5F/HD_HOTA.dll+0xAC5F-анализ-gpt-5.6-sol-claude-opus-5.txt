КРАТКОЕ РЕЗЮМЕ
----------------

Что произошло:

Два уникальных сетевых события HotA 1.8.0 / HD 5.7 R39 и HotA 1.8.1 / HD 5.8 R15 завершились чтением по недоступному адресу в HD_HOTA.dll. В обоих DMP точка исключения нормализуется в один адрес HD_HOTA.dll+0xAC5F.

Локальный механизм:

В sub_100AB50 код берёт hero_id из Player::heroes_ids, проверяет только значение -1, вычисляет hero_ptr = hero_id * 0x492 + [0x0041C6B5] + [0x00699538] и читает portrait_id по смещению +0x34. Перед чтением нет проверки верхней границы hero_id и нет проверки полученного hero_ptr.

Охват семейства:

Подтверждены 2 из 2 уникальных событий текущего дела: одинаковы конечная точка, функция, смещение внутри функции, машинная инструкция, поле +0x34, формула указателя и окно байтов DMP. Поиск точного адреса по 5502 распознанным журналам вылетов корпуса дал только эти 2 события.

Граница доказанности:

Точная команда чтения и локальная цепочка вычисления указателя подтверждены. Какое именно слагаемое стало неверным первым — выбранный Player, hero_id из heroes_ids либо одна из двух баз — по двум минимальным DMP не установлено.

3. Точка сбоя
--------------

<!-- claim:crash-site -->
Дамп + Регистры: в обоих событиях исполняется movzx ecx, byte ptr [ecx+34h], а вычисление ECX + 0x34 даёт ровно адрес исключения. Следовательно, падает чтение однобайтного поля по смещению +0x34.

Непосредственно перед этим sub_100AB50 сохраняет вычисленный hero_ptr в [ebp+arg_8], затем возвращает его в ECX. Команда по 0x0100AC5F читает поле portrait_id из структуры героя.

Формула: hero_ptr = hero_id * 0x492 + [0x0041C6B5] + [0x00699538]

Формула: fault_address = hero_ptr + 0x34

Проверки до точки сбоя:
- индекс панели EDI ограничен сравнением с 7;
- hero_id сравнивается со сторожевым значением -1;
- верхняя граница hero_id не проверяется;
- попадание hero_ptr в допустимый массив героев не проверяется;
- доступность hero_ptr + 0x34 не проверяется.

Локальная последовательность в обеих версиях одинакова:

.text:0100AB8C  cmp     edi, 7
.text:0100AB95  mov     eax, [esi+edi*4+8]
.text:0100AB9A  cmp     eax, 0FFFFFFFFh
.text:0100ABB6  imul    eax, 492h
.text:0100ABC2  add     eax, ds:41C6B5h
.text:0100ABC8  add     eax, ds:699538h
.text:0100ABCE  mov     [ebp+arg_8], eax
.text:0100AC5A  mov     ecx, [ebp+arg_8]
.text:0100AC5F  movzx   ecx, byte ptr [ecx+34h]    <-- СБОЙ

Диагностический вывод:
1. Нулевой указатель здесь не наблюдается: значения ECX различны и ненулевые.
2. Оба адреса чтения недоступны, но это само по себе не показывает, какое слагаемое формулы испортилось первым.
3. Одинаковый локальный код и одинаковое поле в двух сборках подтверждают один локальный механизм, но не общую первопричину.

4. Цепочка вызовов и контекст
-----------------------------

Исходная функция SoD A0_AdvMgr_UpdateHeroPort_sub_403560 обновляет элементы интерфейса портретов героев. HD_HOTA.dll регистрирует sub_100AB50 как замену этой функции: по одной регистрации обнаружено в полном листинге каждой исследованной версии.

A0_AdvMgr_UpdateHeroPort_sub_403560  исходная точка обновления портретов
-> patcher_x86.dll  переход через установленную замену
-> HD_HOTA.dll!sub_100AB50  функция замены
-> A0_GameMgr_GetMe_AsPlayer_sub_4CE670  выбор Player
-> Player::heroes_ids[EDI]  чтение hero_id
-> hero_id * 0x492 + две базы  вычисление hero_ptr
-> sub_100AB50+0x10F  чтение byte ptr [hero_ptr+0x34], СБОЙ

Статический поиск по полным листингам не нашёл обычных команд call на sub_100AB50, но нашёл её адрес в регистрации замены исходной функции 0x00403560. Поэтому адреса 0x02C629B4 и 0x02A830CC из текстовых стеков трактуются только как динамические переходные участки, а не как отдельные причины.

Разделение потоков:
- 5.7 R39: поток исключения 16868; текстовый стек относится к потоку 14328;
- 5.8 R15: поток исключения 19888; текстовый стек относится к потоку 22852;
- регистры точки сбоя взяты только из потоков исключения;
- кадры текстовых стеков не использовались для восстановления регистров точки сбоя.

5. Первопричина
----------------

<!-- claim:local-mechanism -->
Листинг: локальный дефект состоит в чтении portrait_id через вычисленный hero_ptr без полной проверки hero_id и итогового адреса. Этот механизм подтверждён одинаковым кодом двух версий и совпадающими окнами байтов DMP.

<!-- claim:state-origin -->
Граница доказанности: происхождение неверного hero_ptr не установлено. Доступные данные совместимы как минимум с четырьмя вариантами:
- A0_GameMgr_GetMe_AsPlayer_sub_4CE670 вернул не того Player для текущей сетевой фазы;
- в Player::heroes_ids оказался недопустимый hero_id, отличный от -1;
- неверным стало значение по 0x0041C6B5 либо база A0_GameMgr по 0x00699538;
- состояние было изменено другой подсистемой до входа в sub_100AB50.

Минимальные DMP содержат точку отказа и небольшой набор страниц, но не полную историю изменений состояния. Поэтому отсутствие нужных областей памяти не используется как доказательство какой-либо конкретной причины.

<!-- claim:fix-validation -->
Предлагаемое исправление в HD_HOTA.dll:
1. После чтения Player::heroes_ids[slot] проверять не только -1, но и допустимый диапазон hero_id по авторитетной границе таблицы героев.
2. После вычисления hero_ptr проверять, что весь диапазон [hero_ptr, hero_ptr + 0x34] принадлежит ожидаемому массиву героев.
3. При нарушении проверки подставлять безопасное изображение hpsxxx.pcx и прекращать обработку текущего элемента.
4. В диагностике записывать slot, hero_id, указатель Player, оба базовых слагаемых и итоговый hero_ptr.

Такой барьер закрывает наблюдавшееся чтение независимо от того, какой из перечисленных источников оказался первым неверным значением. Для устранения первопричины всё равно нужен управляемый повтор с фиксацией первой порчи состояния.

7. Воспроизведение вылета
--------------------------

Роль 1 — тестер за игрой:

1. Использовать отладочную сборку HD_HOTA.dll для одной из подтверждённых пар версий.
2. Начать сетевую игру и довести карту приключений до регулярного обновления панели портретов героев.
3. Переключать активного игрока, менять выбранного героя, передавать ход и выполнять повторное подключение только как отдельные контролируемые варианты.
4. Для каждого прогона сохранять журнал с номером варианта, slot, выбранным игроком и текущим днём.
5. Не считать AUTOSAVE исходным причинным входом без отдельного подтверждения времени его формирования.

Критерий воспроизведения: выполнение доходит до эквивалента 0x0100AC5F с hero_ptr вне допустимого массива либо с hero_id вне авторитетного диапазона.

Роль 2 — подтверждение причины:

1. Перед вычислением hero_ptr фиксировать указатель Player, slot и hero_id.
2. Фиксировать оба базовых слагаемых и границы массива героев.
3. Поставить точки наблюдения на конкретный слот Player::heroes_ids и на выбранные базовые значения после того, как первый неверный компонент станет известен.
4. Остановиться на первой записи, переводящей контролируемое значение из допустимого в недопустимое.
5. Сопоставить источник записи с фазой сетевого хода и обновлением панели.
6. Повторить тот же сценарий с защитной проверкой и убедиться, что код выбирает безопасное изображение без чтения по недоступному адресу.

Критерий завершения: один управляемый прогон показывает первое неверное слагаемое и его источник записи; второй прогон с исправлением проходит тот же сценарий без исключения и с ожидаемым запасным изображением.
