АНАЛИЗ ВЫЛЕТА HD_HOTA.dll+0x1A4E,HD_HOTA.dll+0x1A0E,HD_HOTA.dll+0x19AE,HD_HOTA.dll+0x1ABE (отладочный аллокатор HD-мода)
====================================================================

Модель: Qwen 3.8
Дата: 29.07.2026
Заключение: Один дефект отладочного аллокатора HD-мода (запись
mov [esi],esi при отказе malloc вместо возврата NULL) в сборках
HD 5.6 R19 — 5.7 R33; адрес сбоя смещается между сборками
(0x1A0E / 0x19AE / 0x1A4E / 0x1ABE), механизм идентичен.

КРАТКОЕ РЕЗЮМЕ
--------------
Четыре адреса сбоя оказываются одним дефектом. Отладочный
распределитель памяти HD-мода при отказе malloc (EAX = 0) выполняет
запись mov [esi],esi по адресу, равному запрошенному размеру, вместо
возврата NULL — и происходит сбой. Адрес сбоя — инструкция mov [esi],
esi в начале функции-аллокатора (смещение +0x1E от её начала); между
сборками функция смещается по образу, поэтому адрес плавает: 0x1A0E
(5.6 R19–R35, 5.7 RC1–RC2), 0x19AE (5.6 R37), 0x1ABE (5.7 R14),
0x1A4E (5.7 RC6–R33). Сигнатура во всех 59 логах одна: нарушение
доступа на запись, EAX = 0, ESI равен адресу сбоя (запрошенный
размер). Подробный разбор механизма, дефекта и первопричины — в
отчёте по адресу HD_HOTA.dll+0x1A4E; этот семейный отчёт добавляет
кросс-версионную картину.
Запрошенные размеры распадаются на группы: 1 МиБ (16 логов,
исчерпание адресного пространства), 47–296 МиБ (5 логов, крупные
накопленные буферы), ~1.27 ГБ (35 логов, адрес 0x1A0E в 5.7 RC1–RC2,
повреждение поля «использовано» объекта — use-after-free) и 1.65 ГБ
(1 лог R26, повреждённое поле длины объекта). Виновник — HD-мод
(закрытый модуль HD_HOTA.dll).

3. Сопоставление адресов
------------------------
Все четыре адреса — одна и та же инструкция mov [esi],esi (ветка
отказа аллокатора), лежащая в начале функции-аллокатора. В листинге
R33 аллокатор sub_1001A30 начинается с 0x01001A30, инструкция краха
mov [esi],esi — по 0x01001A4E, то есть смещение +0x1E от начала
функции. Между сборками HD-мода функция смещается по образу, поэтому
адрес краха = (начало аллокатора в данной сборке) + 0x1E:
    0x1A0E = начало 0x19F0 + 0x1E  (5.6 R19–R35, 5.7 RC1–RC2)
    0x19AE = начало 0x1990 + 0x1E  (5.6 R37)
    0x1A4E = начало 0x1A30 + 0x1E  (5.7 RC6–R33)
    0x1ABE = начало 0x1AA0 + 0x1E  (5.7 R14)
Формула сопоставления стандартная: IDA_addr = runtime_addr -
load_base + imagebase (imagebase HD_HOTA.dll = 0x01000000).

4. Верификация версии листинга
------------------------------
Детальный разбор механизма выполнен по листингу R33 (сверка по точке
входа: дамп R33 против DllEntryPoint листинга, timestamp 6A6186F1;
инструкция краха побайтно идентична в RC11 и R33). Для адресов 0x1A0E
и 0x19AE (HD 5.6) точных листингов нет; их принадлежность к тому же
аллокатору подтверждена идентичной сигнатурой краха (запись, EAX = 0,
ESI = адрес сбоя) и соотношением адрес = начало функции + 0x1E. Идиома
округления ёмкости (маска 7FFFFh) стабильна во всей линейке 5.7
(1493–1494 вхождения в R20/R23/R27/R29/RC11). Точные листинги
HD_HOTA.dll версий 5.6 R19–R37 и 5.7 R14 отсутствовали; при
необходимости их можно запросить для повышения точности.

5. Инструкция краша и адресная проверка
---------------------------------------
Инструкция краха одинакова во всех четырёх адресах (это одна
инструкция в разных сборках):
    mov     [esi], esi    ; запись ESI по адресу [ESI]
К ней приводит отказ malloc: аллокатор вызывает malloc(размер+4), при
успехе ставит в заголовок блока служебную метку 0xF00DBEEF и возвращает
указатель; при отказе (eax = 0) переходит на ветку mov [esi],esi.
Подробный разбор функции (sub_1001A30 в R33), парной функции
освобождения (проверка [ptr-4] == 0xF00DBEEF) и доказательство дефекта
сравнением с родственным кодом модуля (std::_Yarn, __wcsdup при NULL
возвращают NULL без сбоя) — в отчёте HD_HOTA.dll+0x1A4E.
Адресная проверка: эффективный адрес mov [esi],esi равен ESI + 0; во
всех 59 логах ESI в точности равен адресу сбоя из поля Information
(write of address). Проверка сошлась для всех четырёх адресов.

6. Цепочка вызовов
------------------
Аллокатор — общий распределитель памяти HD-мода (в R33 — 1039 точек
вызова), поэтому каждый адрес семейства — единый сток отказа malloc для
своей сборки. Непосредственные вызывающие различаются по версиям: в
5.7 RC6–R33 (адрес 0x1A4E) крупные размеры дают методы объекта растущего
строкового буфера автобоя (слияние sub_109F260, допись sub_1045D70 —
см. отчёт +0x1A4E); в 5.6 / 5.7 RC1–RC2 (адрес 0x1A0E) стек ведёт через
другие функции (в части дампов виден HW_HOTA.dll), а размер ~1.27 ГБ
запрашивается напрямую (не через округление роста буфера). Стек в дампах
зашумлён (трамплины patcher_x86, оборванные кадры), поэтому точный
вызывающий восстановим не для каждого дампа; принадлежность к семейству
определена по сигнатуре краха и адресу (начало аллокатора + 0x1E).

7. Анализ регистров и группировка
---------------------------------
Инварианты по всем 59 логам:
    EAX = 0 — malloc вернул NULL (главный инвариант).
    ESI = адрес сбоя = запрошенный размер (сохраняется через вызов
        malloc; в аллокаторе mov esi, ecx в прологе).
    Нарушение доступа — всегда ЗАПИСЬ (write of address).
Группы по запрошенному размеру (ESI):
    - 1 МиБ (0x100000), 16 логов — начальный буфер объекта; отказ
      столь малого выделения — признак исчерпания адресного
      пространства 32-битного процесса.
    - 47–296 МиБ, 5 логов — крупные накопленные буферы (кратны
      512 КиБ, рост буфера автобоя); поле «использовано» когерентно.
    - ~1.27 ГБ (0x4F897100 и его округление 0x4FA00000/0x4FA80000),
      35 логов — адрес 0x1A0E, 5.7 RC1–RC2, все от 13.04.2026. Это
      повреждение поля «использовано» объекта-буфера (use-after-free):
      поле содержит значение указателя 0x4F897005 (плотный кластер
      0x4F897004–0x4F897009), код роста читает его как размер и
      запрашивает round_up(0x4F897005) = 0x4FA00000 (~1.27 ГБ) либо
      0x4F897100 напрямую; malloc отказывает. Доказательство порчи (а
      не честного накопления): один и тот же размер 0x4F897100 в 18
      разных сетевых сессиях на 19 разных картах — разные партии не
      могут накопить ровно один размер. Не привязан к Quick Combat
      (встречается при 0 и 1) и к Graphics.Mode (5, 6, 7).
    - 1.65 ГБ (0x67680000), 1 лог (R26) — повреждённое поле длины
      объекта ([+108h] = 0x67616D42, «Bmag»), round_up(использовано+1)
      = ESI; см. отчёт +0x1A4E.

8. Первопричина
---------------
Ближайшая причина общая для всего семейства: дефектная ветка отказа
отладочного аллокатора HD-мода. Корректный распределитель при нехватке
памяти возвращает NULL (вызывающий код готов его обработать); здесь же
ветка отказа выполняет mov [esi],esi — запись по адресу, равному
размеру, что гарантирует сбой. Доказательство дефекта (сравнение с
родственным кодом модуля, возвращающим NULL) и анализ восстановимости
отказа — в отчёте HD_HOTA.dll+0x1A4E.
Глубинная причина (почему malloc вернул NULL) неоднородна по семейству:
    - 1 МиБ (16 логов) — исчерпание адресного пространства 32-битного
      процесса в сетевой партии (раздел 9); отказ столь малого
      выделения — признак реальной нехватки/фрагментации памяти.
    - 47–296 МиБ (5 логов) — крупные буферы; поле «использовано»
      когерентно, правдоподобно как накопление (исчерпание), но без
      полного дампа окончательно не отделено от порчи.
    - ~1.27 ГБ (35 логов, 0x1A0E, 5.7 RC1–RC2) — use-after-free
      объекта-буфера: поле «использовано» перезаписано значением
      указателя 0x4F897005, код роста запрашивает ~1.27 ГБ и получает
      отказ. Доказано порчей, а не накоплением: один размер 0x4F897100
      в 18 разных сессиях / 19 картах (разные партии не накопят ровно
      один размер); кластер привязан к сборкам 5.7 RC1–RC2 (вероятно,
      дефект жизненного цикла буфера в этих сборках).
    - 1.65 ГБ (R26) — повреждение поля длины объекта (доказано в отчёте
      +0x1A4E: поле «использовано» содержит строковые байты «Bmag»).
    Таким образом, доминирующий режим отказа в семействе — повреждение
    поля «использовано» объекта-буфера (35 логов кластера + 1 лог R26),
    а не исчерпание памяти (16 логов 1 МиБ); источник порчи (кто и когда
    перезаписывает поле) по сокращённым минидампам не виден — нужен
    полный дамп кучи.

9. Условия сбоя

    Версии HD-мода: 5.6 R19–R37 и 5.7 RC1–R33 (охват сборок порядка
        полугода); HotA 1.8.0.
    Адрес сбоя зависит только от сборки HD-мода (смещение функции

    Кластер ~1.27 ГБ сосредоточен в 5.7 RC1–RC2 (адрес 0x1A0E);

11. Воспроизведение вылета
--------------------------
Вылет недетерминирован (зависит от состояния адресного пространства).
Вероятностный путь: длительная сетевая партия (Network Game = 1) под
HD-модом 5.6 R19+ / 5.7, накопление данных в буферах автобоя до
исчерпания адресного пространства 32-битного процесса; целевые
инварианты ловимого дампа — EAX = 0, ESI = адрес сбоя, адрес краха =
начало аллокатора + 0x1E для данной сборки. Для различения исчерпания
и повреждённого либо ошибочного размера — полный дамп кучи
(<Sys.FullDump> = 1): разумен размер (1 МиБ) при NULL — исчерпание;
аномален (сотни МиБ / ГБ) — повреждение или ошибочное вычисление
размера выше по стеку.

Достоверность и ограничения
---------------------------
Подтверждено:
    - Все 4 адреса — один дефект: идентичная сигнатура (запись,
      EAX = 0, ESI = адрес сбоя) и соотношение адрес = начало
      аллокатора + 0x1E; механизм детально разобран для 0x1A4E.
    - 59 логов, версии 5.6 R19 — 5.7 R33, все сетевые.
    - Распределение размеров: 1 МиБ x16 (исчерпание), 47–296 МиБ x5,
      ~1.27 ГБ x35 (0x1A0E, 5.7 RC1–RC2, use-after-free объекта-буфера:
      поле «использовано» = 0x4F897005, один размер в 18 сессиях /
      19 картах), 1.65 ГБ x1 (R26, порча поля длины).
    - Дефектность ветки отказа доказана родственным кодом модуля
      (std::_Yarn, __wcsdup возвращают NULL без сбоя) — в отчёте +0x1A4E.
Ограничения:
    - Виновный код в закрытом модуле HD-мода; точка исправления — у
      разработчиков HD-мода.
    - Для адресов 0x1A0E / 0x19AE / 0x1ABE (HD 5.6 и 5.7 R14) точных
      листингов нет; принадлежность к аллокатору подтверждена сигнатурой
      и соотношением адрес = начало + 0x1E, но не прямым чтением
      инструкции в этих сборках.
    - Минидампы сокращённые (без кучи): природа запроса ~1.27 ГБ
      (исчерпание либо ошибочный размер) и источник порчи поля у R26
      по ним не различимы — нужен полный дамп.
    - Стек зашумлён; точный вызывающий восстановим не для каждого дампа
      (особенно в 5.6).
    - Полезность средняя: дефект ветки отказа локализован и доказан, но
      глубинный триггер (состояние кучи / источник размера) — рантайм;
      одна инструкция краха диагноз не исчерпывает.

ВЫВОД
-----

один дефект отладочного аллокатора HD-мода: при отказе malloc (EAX = 0)

МиБ (исчерпание адресного пространства), ~1.27 ГБ (детерминированный
крупный запрос в 5.7 RC1–RC2) и 1.65 ГБ (повреждение поля длины объекта
у R26). Виновник — HD-мод (закрытый модуль HD_HOTA.dll); детальный
разбор механизма и дефекта — в отчёте HD_HOTA.dll+0x1A4E.
