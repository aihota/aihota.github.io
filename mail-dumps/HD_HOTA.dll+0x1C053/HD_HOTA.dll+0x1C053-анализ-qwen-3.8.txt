================================================================
АНАЛИЗ ВЫЛЕТА HD_HOTA.dll+0x1C053 (отрисовка миникарты)
================================================================

Модель: Qwen 3.8
Дата: 02.08.2026
Заключение: вылет — чтение массива городов по невалидному
значению miu_setup. miu_setup наследника _MovableObject_ штатно
хранит setup клетки под объектом (индекс города, если объект
на городе), и миникарта использует его правомерно; вылетает при
повреждённом miu_setup. Механизм порчи прочитан: RemoveFromMap
восстанавливает клетку из miu_* без проверки границ cell_coords,
поэтому при битых координатах восстанавливается не та клетка —
тот же механизм даёт раздвоение героев. По оценке автора HD-мода,
корень — неудачное проектирование _MovableObject_ (замещение
типа/подтипа/сетапа клетки под собой); конкретный триггер порчи
координат — рантайм.

КРАТКОЕ РЕЗЮМЕ
--------------
Игра падает при отрисовке миникарты. HD-мод замещает функцию
миникарты SoD (A0_AdvMgr_Draw_Minimap_sub_412BA0) собственной
версией (sub_101AE10 в R33; sub_101B0E0 в R35). Для case 98
таблицы переходов код берёт foreground-клетку и читает её
«setup»-значение функцией A0_MapCell_GetSetup. Это значение
используется как индекс в массиве городов (поле
game_state+0x21614, шаг элемента 0x168 = 360 байт), а
прочитанный байт — как индекс цвета в 16-битной палитре
(A0_GamePal_16, 0x6AAD18).

Код миникарты (и SoD-оригинал A0_AdvMgr_Draw_Minimap, 0x412F7D)
использует результат GetSetup как индекс города ПРАВОМЕРНО:
у наследников _MovableObject_ (герой, корабль) поле miu_setup,
которое возвращает GetSetup, штатно хранит setup клетки под
объектом. Если герой или корабль стоит на клетке города,
miu_setup — это валидный индекс города, и отрисовка идёт штатно.

Вылет происходит, когда miu_setup содержит НЕВАЛИДНОЕ значение
(наблюдаемые индексы 91, 107, 141, 167, 173 многократно превышают
число городов на карте — максимум в движке 48, реально меньше).
Такая порча miu_setup —
не самостоятельный баг миникарты, а проявление общего дефекта
_MovableObject_: объект своим типом/подтипом/сетапом замещает
тип/подтип/сетап клетки под собой, записывая замещённые значения
в себя; при нарушении этого механизма возникают раздвоение героев,
невалидные координаты и — здесь — невалидный miu_setup. Если бы
дело было в «герой/корабль на клетке города», игра падала бы
постоянно и у всех; вылет редкий, что указывает на порчу данных,
а не на детерминированный дефект логики.

Пять дампов на пяти версиях HD-мода (R23, R29, R33, R34, R35)
падают на одной и той же инструкции, побайтно идентичной во
всех сборках. Все пять — сетевые партии на карте приключений.
Дефект стабилен между версиями: функция смещается по образу
(sub_1019F80 -> sub_101AC10 -> sub_101AE10 -> sub_101B0E0),
но код case 98 не меняется. Текущий адрес серии — +0x1C053
(R35); прежние адреса +0x1AEF3 / +0x1BB83 / +0x1BD83 — те же
инструкции в сборках R23 / R29 / R33-R34.

5. Первопричина
---------------
Виновный модуль: вылет проявляется в HD_HOTA.dll (миникарта,
case 98) — потребителе повреждённого miu_setup; миникарта
воспроизводит незащищённое индексирование SoD
(A0_AdvMgr_Draw_Minimap_sub_412BA0). Корень порчи miu_setup —
механизм _MovableObject_ в h3hota.exe (движок SoD:
PlaceToMap/RemoveFromMap). Точка сбоя: sub_101B0E0 (R35) /
sub_101AE10 (R33, R34) / sub_101AC10 (R29) / sub_1019F80 (R23),
case 98 таблицы переходов (jpt_101BFA7 в R35; jpt_101BCD7 в R33).

Код миникарты исправен по контракту. Case 98 (EBX = 0x62 =
OBJ_TOWN) рисует маркер города и правомерно использует
результат GetSetup как индекс массива городов: для клетки
с городом — или с героем/кораблём, стоящим на городе, —
GetSetup возвращает валидный индекс города.

Поставщик данных — A0_MapCell_GetSetup (h3hota.exe, 0x4FD280):

    .text:004FD280  mov  eax, [ecx+1Eh]   ; object_type клетки
    .text:004FD283  cmp  eax, 22h          ; тип 34 = герой
    .text:004FD286  jnz  short loc_4FD2B0
    ; для героя: возвращает hero_astr21620[setup].miu_setup
    .text:004FD2A5  lea  eax, [ecx+eax*2+21620h]
    .text:004FD2AC  mov  eax, [eax+14h]   ; miu_setup героя
    .text:004FD2AF  retn
    ; для корабля (тип 8): miu_setup лодки (boats[индекс*40+0x14])
    .text:004FD2B5  mov  ecx, [ecx]        ; индекс лодки (setup клетки)
    .text:004FD2BC  lea  edx, [ecx+ecx*4]  ; индекс*5
    .text:004FD2BF  mov  ecx, [eax+4E3BCh] ; база массива лодок
    .text:004FD2C5  mov  eax, [ecx+edx*8+14h] ; boats[индекс*40+0x14]
    .text:004FD2C9  retn
    ; для остальных: setup_dword0 клетки
    .text:004FD2CA  mov  eax, [ecx]
    .text:004FD2CC  retn

Запись лодки — 40 байт (подтверждено: A0_Savegame_Load_Boats
делит (end-data) массива лодок на 40), поле +0x14 — тот же
miu_setup, что у героя. Асимметрия: ветка героя проверяет
setup_dword0 == -1 (0x4FD28A), ветка лодки — НЕТ; при битом
индексе лодки GetSetup читает boats[-20] — выход за границу
массива лодок внутри самого GetSetup (отдельный латентный вылет,
не миникартный). Лодки стоят на воде, поэтому их штатный
miu_setup — setup клетки воды (малый); наблюдаемые большие
индексы (91-173) — порча, а не штатное значение.

Что такое miu_setup. У наследников _MovableObject_ (_Hero_,
_Boat_) поля miu_object_type (+0x0C), miu_object_c_flag (+0x10),
miu_setup (+0x14) хранят объект, стоявший на клетке ДО того,
как её занял движимый объект. При постановке на карту
A0_MoveableObject_PlaceToMap_sub_4D7840 сохраняет объект клетки
в эти поля и замещает клетку собой:

    .text:004D78E3  mov  edx, [eax+1Eh]   ; объект клетки (тип)
    .text:004D78E6  mov  [ecx+0Ch], edx   ; -> miu_object_type
    .text:004D78F6  mov  edx, [eax]       ; setup клетки
    .text:004D78F8  mov  [ecx+14h], edx   ; -> miu_setup
    .text:004D78FB  mov  edx, [ebp+ob_id] ; тип движимого объекта
    .text:004D7902  mov  [eax+1Eh], edx   ; клетка <- тип объекта
    .text:004D7905  mov  edx, [ebp+ob_setup]
    .text:004D7908  mov  [eax], edx       ; клетка <- setup объекта
    ; если замещённая клетка была городом (miu_object_type == 98):
    .text:004D790A  mov  eax, [ecx+0Ch]
    .text:004D790D  cmp  eax, 62h         ; OBJ_TOWN

Снятие с карты (A0_MoveableObject_RemoveFromMap_sub_4D7950)
восстанавливает клетку из miu_* (cell+1Eh <- miu_object_type,
cell+0 <- miu_setup). Поэтому, когда герой/корабль стоит на
клетке города, miu_setup = индекс этого города — валидное
значение, и миникарта рисует город штатно. То же значение
использует штатная функция доступа
A0_Hero_GetTown_InWhich_ItIsGuest (0x4D7700): он возвращает
towns_list[360*miu_setup], но ТОЛЬКО после проверок
miu_object_type == 98 и miu_setup != -1.

Корень вылета — НЕ логика миникарты, а НЕВАЛИДНОЕ значение
miu_setup. towns_list — динамический вектор (data =
[game_state+0x21614], end = [game_state+0x21618], шаг 0x168);
валидный индекс города — в диапазоне 0..(число_городов-1), где
число_городов = (end-data)/360 (на реальных картах заведомо
меньше 91; максимум в движке — 48). Наблюдаемые индексы
91, 107, 141, 167, 173 — не индексы городов, а повреждённые
значения miu_setup. Родственная функция A0_Cast_TownPortal
(0x41D5B9-0x41D5E0) перед тем же чтением towns_list[index*360+1]
проверяет index >= число_городов и выходит; миникарта (и HD-мода,
и SoD) ни miu_setup != -1, ни границу по числу городов не
проверяет, поэтому повреждённое значение уходит за границы
выделения.

Природа порчи miu_setup — та же, что у раздвоения героев и
невалидных координат. По оценке автора HD-мода, корень —
неудачное проектирование _MovableObject_, замещающего объект
клетки своим типом/подтипом/сетапом и записывающего замещённый
объект в свои miu_*. Конкретная последовательность, портящая
miu_setup, статически не установлена (рантайм). Проверенный
механизм (прочитано):
A0_MoveableObject_RemoveFromMap (0x4D7950) восстанавливает
клетку, вычисляя её индекс из cell_coords объекта ([this+7])
по той же формуле, что и PlaceToMap, — БЕЗ проверки границ.
При невалидных координатах (тот же класс багов) индекс выходит
неверный: фактическая клетка объекта НЕ восстанавливается
(остаётся с его типом/setup — «фантомный» объект, он же
механизм раздвоения), а чужая клетка перезаписывается значениями
miu_* объекта; сами miu_* после снятия не очищаются. Порча
miu_setup у следующего героя возникает, когда он встаёт на
испорченную клетку: PlaceToMap сохраняет её испорченный
setup_dword0 в miu_setup героя.

Раздвоение героев — второй симптом того же механизма
(прочитано). Жизненный цикл героя на карте идёт через
_MovableObject_: PlaceToMap (0x4D7840) замещает клетку героем
(клетка+1Eh = 34, клетка+0 = индекс героя) и сохраняет бывший
объект клетки в miu_* героя; RemoveFromMap (0x4D7950) должен
восстановить клетку из miu_*. Когда cell_coords героя битые,
RemoveFromMap восстанавливает не ту клетку, и возникает
раздвоение:

- герой H реально на клетке A (A: тип 34, setup = H);
- H уходит на клетку B: RemoveFromMap считает индекс клетки
  из битых cell_coords и восстанавливает чужую клетку C;
- клетка A НЕ восстанавливается — остаётся тип 34, setup = H
  («фантомный» герой на карте);
- PlaceToMap ставит H на B (B: тип 34, setup = H);
- итог: две клетки (A и B) помечены «здесь герой H» при одном
  реальном герое — раздвоение.

Раздвоение и вылет миникарты — два проявления одного wrong-
cell-restore: фантомная клетка A даёт раздвоение, а
перезаписанная чужая клетка C (значениями miu_*) даёт порчу
miu_setup у следующего героя, который на неё встанет. Триггер
(порча cell_coords / x/y/z героя) — рантайм-коррупция памяти;
все штатные пути присвоения координат корректны (см. ниже).

Потенциальный триггер порчи координат — сетевой путь (прочитано
в h3hota.exe). Координаты героя приходят из сетевых сообщений;
диспетчер A0_AdvMgr_Action_FromNetMsg_Gameplay (0x481930)
обрабатывает два кейса:

- Телепорт (case 1051, 0x481962): координаты берутся прямо из
  сообщения (msg[+18h]) и передаются в A0_AdvMgr_Hero_Teleport
  (0x41DAB0) БЕЗ сверки; телепорт ставит hero->x/y/z из сырых
  координат и зовёт PlaceToMap. Валидация A0_DoesCoordsCorrect
  (0x4B1090) проверяет только x и y (в пределах карты), но НЕ z
  (уровень) — при левом z индекс клетки (z*map_size+y)*map_size+x
  уходит за границу массива клеток. Индекс героя из сообщения
  (msg[+14h]) проверяется только на -1, верхней границы нет.
- Шаг (case 1050, A0_MoveHeroWithOnlineMsg 0x4817F0): координаты
  сообщения сверяются с текущими координатами героя (защита от
  произвольной порчи), ход валидируется (A0_Hero_GetStepCost,
  A0_AdvMgr_Hero_CanMoveToDirection); уязвим только индекс героя
  без верхней границы (байт 0-255).

Формирует сообщение телепорта (type 1051) единственный
отправитель — сам A0_AdvMgr_Hero_Teleport в локальном пути
(0x41DAEC), при касте Dimension Door (A0_Cast_DD_sub_41D210)
или Town Portal (A0_Cast_TownPortal_sub_41D4E0). В сообщение
кладутся hero->id (msg[+14h]) и координаты назначения
(msg[+18h]). Отправитель ВАЛИДИРУЕТ назначение: Dimension Door
проверяет координаты через DoesCoordsCorrect (x/y) до телепорта,
Town Portal дополнительно проверяет индекс города по числу
городов; z приходит из таргетинга заклинания (корректный).
Поэтому штатное сообщение сформировано корректно, а пробел
валидации z на приёмнике — латентный (не первичный триггер).

Источник битого сообщения — не баг формирования координат,
а порча hero->id: отправитель кладёт битый hero->id в msg[+14h]
-> приёмник делает hero_array[битый_индекс] -> выход за границу
(тот же класс дефектов _MovableObject_), либо сетевое
повреждение байтов сообщения в транзите. При некорректном
сообщении телепорт ставит битые координаты/работает с чужой
записью -> cell_coords портится -> RemoveFromMap восстанавливает
не ту клетку (механизм выше). Факт некорректного сообщения
в наблюдаемых вылетах по минидампам не восстановить — точный
триггер остаётся рантайм.

Присвоение hero->id (прочитано). hero->id задаётся корректно
при инициализации: A0_GameMgr_Clear_Map_Prop_sub_4BEE60 обходит
массив героев циклом и ставит hero_array[i].id = i
(A0_Hero_ClearProp_sub_4D8990, запись [hero+1Ah] = аргумент).
Массив героев — 156 записей (cmp edi, 9Ch), шаг записи 1170;
валидный диапазон индекса 0..155. Приёмник телепорта (case 1051)
проверяет индекс героя только на -1, верхнюю границу (< 156)
не проверяет. Поэтому битый индекс героя в сообщении возможен
только при порче самого hero->id (запись мимо массива в поле
+1Ah) — через ту же рантайм-коррупцию _MovableObject_ — либо
при сетевом повреждении сообщения. Все статические звенья
присвоения координат и hero->id (инициализация, таргетинг
заклинаний, валидация отправителем) корректны; источник битых
значений — рантайм-коррупция памяти или сеть.

Дефект унаследован из движка SoD: и код миникарты без проверки
границ (A0_AdvMgr_Draw_Minimap, 0x412F7D-0x412FC1), и сам
механизм _MovableObject_ (PlaceToMap/RemoveFromMap) — код
h3hota.exe:

    .text:00412F7D  mov  ax, [ebx+0Ch]    ; case 98
    .text:00412F81  test al, 40h
    .text:00412F8E  call A0_MapCell_Get_Fore_Cell_sub_4FD0F0
    .text:00412F95  test eax, eax
    .text:00412F9F  call A0_MapCell_GetSetup_sub_4FD280
    .text:00412FAA  lea  eax, [eax+eax*4]     ; * 5
    .text:00412FAD  mov  edx, [ecx+21614h]    ; towns_list
    .text:00412FB9  lea  eax, [eax+eax*8]     ; * 45
    .text:00412FBC  movsx eax, byte ptr [edx+eax*8+1] ; *360+1
    .text:00412FC1  mov  si, [ecx+eax*2+9Ch]  ; палитра

Доказательная база (родственные функции). Штатная функция
доступа A0_Hero_GetTown_InWhich_ItIsGuest (0x4D7700)
индексирует towns_list[360*miu_setup] С проверками
miu_object_type == 98 и miu_setup != -1 — в отличие от
миникарты.

Полный аудит кейсов миникарты, использующих GetSetup как индекс
(прочитано в SoD 0x412F8E-0x4130D7 и в HD-mod R35 sub_101B0E0).
Четыре кейса делают Get_Fore_Cell -> GetSetup -> индекс малого
массива БЕЗ проверки границ (уязвимы к порче miu_setup):

    - case 98:    towns_list [+0x21614], шаг 360, +1 (вылет)
    - case 42/53: mines      [+0x4E38C], шаг 64
    - case 17/20: dwellings  [+0x4E39C], шаг 92, +0x57
    - case 33:    garnisons  [+0x4E3AC], шаг 64

Case 87 использует GetSetup как индекс палитры (movsx ecx, al —
знаковое расширение байта), а не как индекс списка — иной класс.
В HD-mod R35 эти 4 кейса продублированы в двух таблицах переходов
(jpt_101B686 и jpt_101BFA7 — два прохода отрисовки), итого
8 уязвимых точек; в SoD они в одной таблице (jpt_412F50).
Наблюдаемые вылеты семьи — только case 98 (towns_list).

Плавающие адреса +0x1BD83 (R33/R34), +0x1BB83 (R29),
+0x1AEF3 (R23) — тот же дефект (данный отчёт, дампы 1-4);
серия переименована на +0x1C053 (R35) по актуальной версии.
Отличать от других вылетов подсистемы отрисовки:
HD_HOTA.dll+0x1B107B — другой дефект (NULL-разыменование при
отказе конструктора поверхности Pcx16; механизм, регистры,
стек полностью различны). HD_HOTA.dll+0x1AFF9 — другой дефект
(EBX = 0x220, не case 98; ESI != 0x699538). Семейство
аллокатора HD_HOTA.dll+0x1A0E — другой дефект (отказ
operator new -> NULL -> memset/memcpy по NULL; общий корень
«давление на кучу», но другой механизм и место сбоя).

6. Условия сбоя
---------------
Обязательные условия:
    - Игра на карте приключений (миникарта активна)
    - Отрисовка case 98 (EBX = 0x62 = OBJ_TOWN): клетка
      города либо герой/корабль на клетке города
    - miu_setup foreground-клетки ПОВРЕЖДЁН (содержит значение,
      не являющееся валидным индексом города)
    - Повреждённое значение превышает размер массива городов
      (поэтому штатный город с валидным miu_setup не падает)

Наблюдаемые условия:
    - Все 5 дампов: сетевая игра (Network Game = 1)
    - День 1-4 — активная фаза игры с героями на карте
    - Graphics.Mode: 5 и 7 — не влияет на механизм
    - Карты: разные (5 карт в 5 дампах) — не зависит
      от конкретной карты

7. Воспроизведение вылета
-------------------------
Путь недетерминированный: вылет вызывает не конкретный
сценарий, а порча miu_setup (рантайм-последовательность
в механизме _MovableObject_ не установлена). Воспроизведение
вероятностное: набирать статистику попыток в условиях, где
движимые объекты активно занимают и освобождают клетки городов.

Условия, повышающие вероятность:
    - Сетевая партия, 2+ игроков (все 5 дампов — сетевые)
    - Карта с городами и героями/кораблями, активно
      перемещающимися по карте (частые PlaceToMap/RemoveFromMap
      на клетках городов)
    - Активная фаза игры (день 1-4), герои рядом с городами

Варьирование:
    - Graphics.Mode: не влияет (наблюдались 5 и 7,
      в падающем коде нет ветвления по режиму)
    - Версия HD-мода: дефект стабилен (R23, R29, R33, R34, R35)
    - Карта: не зависит (5 разных карт в 5 дампах)

Дифф-тест (направление поиска триггера):
    - Ловить момент, когда miu_setup героя/корабля на клетке
      города перестаёт равняться индексу этого города (штатно
      они равны). Кандидаты-триггеры: невалидные координаты
      героя (RemoveFromMap восстановит не ту клетку), повторное
      снятие/постановка, раздвоение героя.
    - Штатный город и штатный герой на городе НЕ падают
      (miu_setup валиден); падает только повреждённое значение.

8. Достоверность и ограничения
------------------------------
Подтверждено:
- Инструкция краха и адресная арифметика —
  совпадение по всем 5 дампам
- Побайтная идентичность кода case 98 в пяти сборках
  (R23, R29, R33, R34, R35) — функция смещается, код не меняется
- Регистровые инварианты: EBX=0x62, ESI=0x699538 —
  стабильны по всем дампам
- towns_list ([game_state+0x21614]/[+0x21618]) — динамический
  вектор городов, шаг 0x168; валидный индекс 0..(число_городов-1),
  число_городов = (end-data)/360 — прочитано; A0_Cast_TownPortal
  (0x41D5B9-0x41D5E0) проверяет index >= число_городов перед тем
  же чтением towns_list[index*360+1], миникарта проверку не делает
- Полный аудит кейсов миникарты (прочитано): GetSetup как индекс
  массива используют 4 кейса — 98 (towns), 42/53 (mines +0x4E38C),
  17/20 (dwellings +0x4E39C), 33 (garnisons +0x4E3AC), все БЕЗ
  проверки границ; в HD-mod R35 продублированы в двух проходах
  (jpt_101B686 + jpt_101BFA7, 8 точек), в SoD — одна таблица
  (jpt_412F50); case 87 — индекс палитры (movsx ecx,al), иной класс
- A0_MapCell_GetSetup (0x4FD280) для героя (тип 34) возвращает
  miu_setup героя, для корабля (тип 8) — значение из массива
  лодок, иначе setup_dword0 клетки — прочитано
- miu_setup наследника _MovableObject_ хранит setup объекта,
  стоявшего на клетке ДО героя/корабля; для клетки города это
  индекс города — прочитано в A0_MoveableObject_PlaceToMap
  (0x4D7840: клетка+1Eh/+0 -> miu_object_type/miu_setup,
  затем клетка замещается типом/setup объекта)
- Штатная функция доступа A0_Hero_GetTown_InWhich_ItIsGuest
  (0x4D7700) индексирует towns_list[360*miu_setup] С проверками
  miu_object_type==98 и miu_setup!=-1; миникарта тех проверок
  не делает — прочитано
- A0_MoveableObject_RemoveFromMap (0x4D7950) восстанавливает
  клетку из miu_*, НЕ очищая miu_* после снятия, и ищет клетку
  по cell_coords героя — прочитано (вектор порчи при
  невалидных координатах)
- Сетевой путь (прочитано): телепорт героя (case 1051,
  A0_AdvMgr_Hero_Teleport 0x41DAB0) берёт координаты прямо из
  сообщения без сверки; A0_DoesCoordsCorrect (0x4B1090) проверяет
  x/y, но НЕ z; индекс героя из сообщения без верхней границы.
  Пошаговое перемещение (case 1050, 0x4817F0) сверяет координаты
  с текущими (защита), но делит пробел индекса героя без границы.
  Отправитель телепорта (Dimension Door/Town Portal) ВАЛИДИРУЕТ
  назначение (DoesCoordsCorrect, для Town Portal — индекс города),
  штатное сообщение корректно; источник битого сообщения — порча
  hero->id или сеть, не баг формирования координат
- hero->id присваивается корректно при инициализации
  (A0_GameMgr_Clear_Map_Prop 0x4BEE60: цикл hero_array[i].id = i,
  A0_Hero_ClearProp 0x4D8990); массив героев — 156 записей
  (диапазон 0..155), приёмник телепорта верхнюю границу не
  проверяет — прочитано
- sub_101AE10 (R33) / sub_101B0E0 (R35) — замена
  A0_AdvMgr_Draw_Minimap (хук на 0x412BA0; регистрация
  в sub_1034EC0+2991 в R33, в sub_1035190+2ADD в R35)
- Оригинальный код SoD (0x412F7D-0x412FC1) содержит
  функционально идентичный паттерн без проверки границ;
  механизм _MovableObject_ (PlaceToMap/RemoveFromMap) — тоже
  код h3hota.exe (SoD)
- 0x6AAD18 = A0_GamePal_16 (16-битная палитра),
  byte_1 структуры города = индекс цвета для миникарты

Ограничения:
- Минидампы сокращённые (без кучи): фактическое значение
  miu_setup и тип foreground-клетки в момент сбоя не
  проверялись; повреждённость miu_setup выведена из того, что
  наблюдаемые индексы (91, 107, 141, 167, 173) не являются
  валидными индексами городов (диапазон 0..число_городов-1,
  максимум в движке 48)
- Конкретная рантайм-последовательность, портящая miu_setup,
  не установлена: статически видны механизм PlaceToMap/
  RemoveFromMap, вектор через невалидные координаты героя
  и сетевой триггер (телепорт case 1051 с непроверенным z
  и индексом героя без границы), но факт некорректного
  сообщения в наблюдаемых вылетах по минидампам не
  восстановить — точный триггер остаётся рантайм
- Логи SoD (без HD-мода) не проверялись: оригинальный
  код A0_AdvMgr_Draw_Minimap содержит тот же дефект,
  но подтверждений вылета в чистом SoD нет
- Нет данных по версиям HotA до 1.8.0: все 5 дампов сняты
  на HotA 1.8.0, наличие дефекта в более старых версиях
  HotA не проверялось

ВЫВОД
-----
Вылет HD_HOTA.dll+0x1C053 (и плавающие адреса +0x1BD83,
+0x1BB83, +0x1AEF3 в сборках R33/R34, R29, R23) — чтение за
границами массива городов при отрисовке миникарты по
ПОВРЕЖДЁННОМУ значению miu_setup.

Механизм. Case 98 (EBX = 0x62 = OBJ_TOWN) миникарты рисует
маркер города: берёт foreground-клетку, вызывает
A0_MapCell_GetSetup и использует результат как индекс массива
городов (towns_list[360*setup+1] -> цвет в палитре). Для
клетки города — или героя/корабля на городе — GetSetup
возвращает валидный индекс города: у наследников _MovableObject_
поле miu_setup хранит объект, стоявший на клетке до них
(PlaceToMap сохраняет объект клетки в miu_*, для города это
индекс города). Код миникарты исправен по контракту и
воспроизводит SoD (A0_AdvMgr_Draw_Minimap, 0x412F7D-0x412FC1).

Корень. Вылетает не логика миникарты, а НЕВАЛИДНОЕ значение
miu_setup: наблюдаемые индексы 91, 107, 141, 167, 173 — не
индексы городов (диапазон 0..число_городов-1, максимум 48),
а повреждённые значения.
Миникарта (в отличие от штатной функции доступа
A0_Hero_GetTown_InWhich_ItIsGuest, проверяющего
miu_object_type==98 и miu_setup!=-1) индекс не проверяет,
поэтому повреждённое значение уходит за границы towns_list.

Природа порчи miu_setup — та же, что у раздвоения героев и
невалидных координат. По оценке автора HD-мода, корень —
неудачное проектирование _MovableObject_ (PlaceToMap/RemoveFromMap
замещают объект клетки типом/сетапом объекта, записывая
замещённый в miu_*). Конкретная последовательность, портящая
miu_setup, статически не установлена (рантайм); проверяемый
вектор — невалидные координаты героя, при которых RemoveFromMap
восстанавливает не ту клетку.

Дефект унаследован из движка SoD: и незащищённое индексирование
миникарты, и механизм _MovableObject_ — код h3hota.exe.
Присутствует минимум в пяти версиях HD-мода (R23, R29, R33,
R34, R35), не зависит от графического режима, карты или числа
игроков; все наблюдаемые вылеты — в сетевой игре на карте
приключений. Серия переименована на +0x1C053 по актуальной
версии (R35); дамп 5 (R35, индекс 173) добавлен к четырём
ранее разобранным.

Фикс (HD-мод, защитный). Кейсы миникарты 98, 42/53, 17/20, 33
в sub_101B0E0 (HD_HOTA.dll) индексируют towns_list / mines
[+0x4E38C] / dwellings [+0x4E39C] / garnisons [+0x4E3AC]
результатом GetSetup (miu_setup) без проверки границ — в отличие
от штатных A0_Hero_GetTown_InWhich_ItIsGuest (miu_setup != -1)
и A0_Cast_TownPortal (индекс < числа городов). Направление
правки: добавить проверку перед чтением массива — miu_setup != -1
и miu_setup < размер массива (число городов для towns_list и т. п.);
при невалидном индексе пропустить маркер или взять цвет по
умолчанию. Это снимает вылет даже при порче miu_setup. Корень
порчи (механизм _MovableObject_) — в движке h3hota.exe, репорт
разработчикам HotA.
