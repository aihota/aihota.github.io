АНАЛИЗ ВЫЛЕТА KERNELBASE.dll+0x169F54
====================================

Модель: Qwen 3.8
Дата: 02.08.2026
Заключение: движок HotA (h3hota.exe) не сбрасывает позицию горизонтальной
прокрутки поля ввода чата при очистке текста после отправки; цикл подгонки
ширины берёт подстроку с устаревшим смещением, которое превышает длину
очищенного текста, что бросает необработанное std::out_of_range.

Визуализация вылета
-------------------

См. врезку (extra.html).

КРАТКОЕ РЕЗЮМЕ
--------------

Игра вылетает при отправке сообщения в чате сетевого лобби. Причина --
необработанное C++-исключение std::out_of_range("invalid string position"),
которое бросает движковая функция обновления поля ввода текста.

Механизм. Поле ввода чата умеет горизонтально прокручиваться: когда набранный
текст шире окна ввода, движок наращивает внутреннее смещение прокрутки
(поле +6Ah контрола), чтобы курсор оставался видимым. При нажатии Enter
движок отправляет сообщение и очищает поле ввода (задаёт пустой текст),
НО НЕ СБРАСЫВАЕТ смещение прокрутки. Функция обновления затем запускает цикл
подгонки ширины, который берёт подстроку текста, начиная с этого смещения
(`std::string::substr(offset)`). Текст уже пуст (длина 0), а смещение
осталось большим -- проверка границ `if (длина < offset) throw` срабатывает,
летит std::out_of_range. Обработчика catch нигде в цепочке нет, поэтому
исключение доходит до RaiseException и аварийный репортёр HD-мода фиксирует
вылет.

Дефект -- в движке HotA (h3hota.exe): функция очистки/обновления текста чата
не сбрасывает смещение прокрутки, а цикл подгонки ширины не ограничивает
смещение длиной текста. HD-мод (HD_HOTA.dll) выступает только триггером: его
хук диспетчера диалогов передаёт нажатие Enter в движковый обработчик чата.
Соседняя функция (обработчик клавиш) корректно ограничивает смещение
прокруткой позицией курсора -- то есть движок умеет делать это правильно,
но путь очистки текста проверку теряет.

Вылет наблюдается на 2 версиях HD-мода (5.7 R34 и 5.7 R35), оба раза у одного
и того же игрока (одинаковая метка репорта, имя Kerajel), с разницей в день:
игрок обновил HD-мод с R34 до R35 и столкнулся с вылетом повторно -- сценарий
для него воспроизводимый.

Проверка типа исключения. Параметр Information[2] = 0x00647FD0 -- это
указатель на структуру ThrowInfo (_ThrowInfo) бросаемого исключения.
В листинге по этому адресу:

исключения 0xE06D7363 = ('msc' | 0xE0000000) -- стандартный код C++-throw

исключения лежит на стеке (Information[1] = 0x001A70EC, рядом с ESP/EBP).

KERNELBASE.dll (RaiseException, +0x169F54) -- системная DLL, листинг не
требуется: это штатная точка, через которую CRT пробрасывает любое
C++-исключение в SEH. Адрес сбоя как таковой здесь не вычисляется
(это не нарушение доступа, а намеренный бросок).

HD_HOTA.dll: imagebase 0x01000000. R35 load_base 0x04870000, R34 load_base
0x04850000. Кадры HD-мода в стеке: R35 +0x1AE43F (IDA 0x011AE43F),

в V2 -- артефакт стек-вокера (разрешение по ближайшему символу), а не имя
функции.

3. Точка сбоя
-------------

Фактический бросок происходит в движковой функции-помощнике
A0_StringPosition_Error_sub_60B1E3 (аналог std::string::_Xran -- штатный
бросатель «недопустимая позиция строки»):

    .text:0060B201  mov  esi, offset aInvalidStringP ; "invalid string position"
    .text:0060B212  call A0_String_Create_From_Cstr_sub_404180
    .text:0060B22A  push offset __TI3?AVout_of_range@std@@
    .text:0060B230  mov  dword ptr [ebp+var_3C], offset ??_7out_of_range@std@@6B@
    .text:0060B237  call A0_Call_Exception_sub_617B07   ; _CxxThrowException

Помощник конструирует строку "invalid string position", строит из неё объект
std::out_of_range (устанавливая его vtable ??_7out_of_range@std@@6B@) и зовёт
_CxxThrowException (A0_Call_Exception_sub_617B07), который через RaiseException
передаёт исключение в SEH.

Непосредственный вызывающий код помощника в данном вылете -- функция
sub_472E90 (адрес возврата 0x00472EBE, точка вызова 0x00472EB9). sub_472E90 --
это конструктор подстроки (аналог std::string::substr/конструктора из
диапазона): он принимает исходную строку (this, регистр ecx), назначение
([ebp+8]), смещение ([ebp+0Ch]) и длину ([ebp+10h]) и ПРОВЕРЯЕТ ГРАНИЦУ:

    .text:00472EB1  mov  eax, [esi+8]      ; eax = длина исходной строки
    .text:00472EB5  cmp  eax, edx          ; edx = запрошенное смещение
    .text:00472EB7  jnb  short loc_472EBE  ; если длина >= смещение -- ОК
    .text:00472EB9  call A0_StringPosition_Error_sub_60B1E3  ; иначе бросок

То есть sub_472E90 ИСПРАВНА: она штатно проверяет границу и бросает
исключение при смещении больше длины. Проблема не в ней, а в том, КТО
передал ей заведомо большее смещение (раздел 5).

5. Первопричина
---------------

Виновный код -- в движке h3hota.exe (закрытый модуль HotA). Дефект состоит
из двух связанных упущений в тракте поля ввода чата.

Поля контрола поля ввода текста (this):

- +30h -- текст (std::string-подобный объект; длина в [this+38h]/[+8]);
- +58h -- позиция курсора (word);
- +5Ch -- ширина окна ввода в пикселах (signed word);
- +68h -- режим контрола (значение 3 включает горизонтальную подгонку);
- +6Ah -- смещение горизонтальной прокрутки (word), сколько символов
  пропущено с начала строки, чтобы курсор вписался в окно.

Цикл подгонки ширины в F2 (достигается только при [this+68h] == 3):

    .text:005BBB97  cmp  word ptr [ecx+68h], 3   ; режим горизонтальной подгонки
    .text:005BBB9C  jnz  loc_5BBCE4              ; иначе цикл не запускается
    .text:005BBBA2 loc_5BBBA2:                   ; начало цикла
    .text:005BBBAF  movsx ecx, word ptr [eax+6Ah] ; смещение = +6Ah
    .text:005BBBB3  push  ecx                    ;   ... передать как offset
    .text:005BBBB5  mov   ecx, ebx               ; источник = текст (+30h)
    .text:005BBBB7  call  sub_472E90             ; substr(text, offset, npos)
    ...                                          ; измерить ширину подстроки
    .text:005BBC39  inc   word ptr [esi+6Ah]     ; offset++
    .text:005BBC3D  jmp   loc_5BBBA2             ; повторять, пока не впишется

Цикл наращивает смещение +6Ah, пока оставшийся хвост текста не впишется
в ширину окна +5Ch. Каждая итерация берёт substr(text, offset). Проверка
границы живёт ВНУТРИ sub_472E90: если offset > длина текста -- бросок.

Упущение 1 (не сбрасывается прокрутка). Когда игрок набирает длинное
сообщение (шире окна ввода), обработчик клавиш и сам цикл наращивают +6Ah.
При отправке (Enter) F3 очищает текст через F2 (передаёт пустую строку),
но НИ F3, НИ F2 НЕ СБРАСЫВАЮТ +6Ah -- смещение остаётся от длинного текста.

Упущение 2 (цикл не ограничивает смещение). После очистки текст пуст
(длина 0), а +6Ah хранит прежнее большое значение. Первая же итерация цикла
делает substr(пустой_текст, offset=+6Ah): проверка `длина(0) < offset`
истинна -- бросается std::out_of_range. Цикл не сравнивает offset с длиной
текста ДО вызова substr.

Доказательная база через родственные функции.
Соседний обработчик клавиш A0_DlgTextEdit_ProcMsg_Keydown_sub_5BB000
КОРРЕКТНО ограничивает смещение прокрутки позицией курсора:

    .text:005BB17B  movsx edx, word ptr [ebx+6Ah]  ; текущее смещение
    .text:005BB18C  cmp   ecx, edx                 ; новая позиция курсора
    .text:005BB18E  jge   loc_5BB46C               ; если курсор >= смещения -- не менять
    .text:005BB194  mov   [ebx+6Ah], ax            ; иначе смещение = курсор

То есть движок знает инвариант «смещение прокрутки не превышает позицию
курсора / длину текста» и соблюдает его при вводе с клавиатуры. Путь
очистки текста (F3 -> F2) этот инвариант нарушает: курсор сбрасывается
в 0, текст очищается, а смещение +6Ah остаётся. Функция A0_DlgTextEdit_SetText
также не трогает +6Ah (пишет курсор +58h и копирует строку, но поле +6Ah
не сбрасывает) -- то есть сброс прокрутки не заложен ни в один путь смены
текста.

Поставщик плохого значения. Писатели поля +6Ah (весь модуль, объект
поля ввода): 0x5BAD53 (A0_DlgTextEdit_Create -- инициализация), 0x5BB194
и 0x5BB265 (A0_DlgTextEdit_ProcMsg_Keydown -- следует за курсором), плюс
сам цикл F2 (inc). Ни один писатель не привязывает +6Ah к длине текущего
текста при его очистке. Плохое значение -- не результат разовой порчи,
а штатное значение, пережившее смену текста, для которой не предусмотрен
сброс.

Ретроспектива. Функции онлайн-чата (A0_DlgTextEditChat_Enter,
A0_Send_Online_Chat_Message, семейство A0_Chat_) -- добавление HotA
(в оригинальной SoD сетевого лобби-чата не было); режим [this+68h]==3
и сам путь горизонтальной подгонки поля ввода чата -- HotA-специфичны.
Базовый механизм текстового ввода (A0_DlgTextEdit) может восходить к SoD,
но конкретный дефектный путь (очистка чат-поля без сброса прокрутки) --
код HotA. Отдельный листинг чистой SoD для окончательного вывода о
наследовании не запрашивался: дефект локализован в HotA-специфичном тракте
чата, вопрос наследования здесь не влияет на диагноз.

6. Условия сбоя
---------------

- Сетевая партия (Network Game = 1), лобби / предыгровой чат. Оба показания
  игрока указывают на отправку сообщения в чате лобби («during chat in game
  lobby», «pre-game chat message send»).
- День 1 1 1 (старт партии, `Day = 1 11` в логе) -- чат лобби в начале партии.
- Режим контрола [this+68h] == 3 (горизонтальная подгонка ширины) -- штатный
  режим для поля ввода чата.
- Набранное сообщение ДОЛЖНО быть шире окна ввода, чтобы поле прокрутилось
  (смещение +6Ah стало > 0). Короткие сообщения, которые влезают в окно
  целиком, прокрутку не запускают и к вылету не приводят -- этим объясняется
  редкость вылета.
- Графический режим не влияет: в тракте поля ввода чата нет ветвления по
  Graphics.Mode (в обоих дампах режим 7, но логика чисто текстовая).

Триггер: ввести в чат лобби длинное сообщение (шире поля ввода, чтобы
появилась горизонтальная прокрутка) и нажать Enter для отправки.

7. Воспроизведение вылета
-------------------------

Условие активации пути: сетевое лобби, поле ввода чата в режиме
горизонтальной подгонки ([this+68h]==3), сообщение длиннее ширины окна ввода.

Базовый сценарий:

- Создать сетевую партию (HotA online), зайти в лобби.
- В поле ввода чата набрать сообщение, заведомо более длинное, чем ширина
  окна ввода (чтобы текст прокрутился по горизонтали и курсор ушёл вправо --
  это взведёт смещение прокрутки +6Ah).
- Нажать Enter для отправки сообщения.
- Ожидается вылет в момент очистки поля ввода после отправки
  (std::out_of_range в KERNELBASE.RaiseException).

Варьирование:

- Длина сообщения: варьировать длину так, чтобы часть сообщений влезала
  в окно без прокрутки (не вылетает), а часть -- шире окна (кандидат на
  вылет). Порог зависит от ширины окна ввода и шрифта.
- Повторная отправка: после первого вылета/успешной отправки набрать новое
  длинное сообщение -- эффект накапливается только если прокрутка взведена.

Дифференциация: короткие сообщения (без прокрутки) не вылетают; если вылет
воспроизводится только на длинных прокрученных сообщениях -- это подтверждает
диагноз «устаревшее смещение прокрутки».

8. Достоверность и ограничения
------------------------------

Подтверждено:

- Тип исключения: ThrowInfo из лога (0x00647FD0) побайтно совпадает
  с __TI3?AVout_of_range@std@@ в листинге; код 0xE06D7363 = C++ throw.
- Точка броска и проверочная логика sub_472E90 прочитаны в листинге
  (граница `длина < offset` -> бросок).
- Цепочка вызовов подтверждена фактическим стеком V2 (F3 -> F2 -> F1 ->
  бросатель); вызывающий код F3 -- HD-мод (кадр V1 + V2).
- Дефектное поле +6Ah и цикл подгонки прочитаны; писатели +6Ah перечислены
  перебором (Create / Keydown x2 / цикл F2) -- ни один не сбрасывает его
  при очистке текста.
- Родственный образец: Keydown корректно ограничивает +6Ah курсором,
  путь очистки -- нет (инвариант нарушается именно при очистке).
- Один механизм на двух версиях HD-мода (R34/R35), один игрок (одинаковая
  метка репорта) -- сценарий воспроизводимый для этого игрока.

Ограничения:

- Точные числовые значения +6Ah и длины текста в момент сбоя не извлечь:
  минидампы репортёра сокращённые (без кучи), а контрол поля ввода лежит
  в куче; механизм доказан статикой, числовое подтверждение потребовало бы
  полного дампа (<Sys.FullDump> = 1) или отладчика.
- Точный писатель, выставляющий [this+68h]==3 для чат-контрола, не искался
  прицельно (смещение +68h встречается у многих структур); сам факт режима 3
  подтверждён проверкой в F2, на диагноз это не влияет.
- HD_HOTA.dll прочитан для R34/R35 (точные версии дампов); роль HD-мода
  установлена как триггер (диспетчер сообщений), собственная чат-функция
  HD-мода sub_1020E40 в данном стеке не участвует.
- Ретроспектива «было ли в SoD» окончательно не закрыта отдельным листингом
  SoD; дефектный путь -- HotA-специфичный онлайн-чат, что делает вопрос
  наследования несущественным для диагноза.

ВЫВОД
-----

Вылет KERNELBASE.dll+0x169F54 -- это необработанное C++-исключение
std::out_of_range("invalid string position"), бросаемое движком HotA
(h3hota.exe) в тракте поля ввода сетевого чата.

Диагноз: при отправке длинного (прокрученного по горизонтали) сообщения
чат-функция A0_DlgTextEditChat_Enter_sub_554780 очищает поле ввода, но не
сбрасывает смещение горизонтальной прокрутки (поле +6Ah). Функция обновления
A0_DlgTextEdit_UpdateTextAndCaretPosition_sub_5BBA10 запускает цикл подгонки
ширины, который берёт substr(текст, offset=+6Ah); текст уже пуст, смещение
превышает длину -- срабатывает проверка границы sub_472E90 и бросается
std::out_of_range. Обработчика catch в цепочке нет, исключение доходит до
RaiseException -> вылет.

Классификация: дефект -- в закрытом движке h3hota.exe (функции
A0_DlgTextEditChat_Enter и A0_DlgTextEdit_UpdateTextAndCaretPosition).
Это репорт разработчикам HotA, а не правка бинаря. HD-мод (HD_HOTA.dll) --
триггер: его хук диспетчера диалогов передаёт Enter в движковый обработчик
чата; дефектную логику HD-мод не содержит. Со стороны HD-мода возможна лишь
оборонительная мера (перехват std::exception вокруг собственных вызовов
движкового чата, например в sub_1020E40), но это обход, а не исправление
корня -- корень в движке.

Полезность лога: СРЕДНЯЯ. Механизм и дефектное место локализованы точно
(конкретная функция, конкретное поле, конкретный пропущенный сброс), однако
падающая функция (sub_472E90) исправна -- первопричина у поставщика данных
выше по стеку (устаревшее смещение прокрутки), и исправление лежит в закрытом
движке, недоступном читателю отчёта.
