АНАЛИЗ ВЫЛЕТА hota.dll+0xA898E (приключенческая карта)
=====================================================

Модель: Qwen 3.8
Дата: 28.07.2026
Заключение: Виновник - HotA (hota.dll). Геттер свойства объекта карты
использует индекс типа без проверки на контрольное значение -1, тогда
как родственные геттеры его проверяют; при загрузке карты с объектом без
назначенного типа это даёт чтение за границами таблицы GameMgr.


КРАТКОЕ РЕЗЮМЕ
--------------
При загрузке карты игра перечисляет объекты и для каждого запрашивает
свойства через зарегистрированные функции-геттеры. Геттер sub_100A8970
читает из объекта индекс его типа и использует его как номер записи в
таблице GameMgr, не проверяя значение. У объекта на карте игрока индекс
оказался равен -1 (контрольное значение «тип не назначен»). Умножение
-1 на 9 даёт -9, и геттер читает 9-ю запись ДО начала таблицы, за
пределами выделенной памяти, что и вызывает сбой. Родственные геттеры
той же подсистемы проверяют отрицательный индекс и безопасно выходят,
а этот - нет.

Тип исключения: EXCEPTION_ACCESS_VIOLATION (чтение). Что произошло:
чтение записи table[-9] за нижней границей таблицы записей GameMgr. Где:
hota.dll+0xA898E, функция sub_100A8970. Корневой регистр: ESI = 0xFFFFFFFF
(-1, индекс типа); ECX = ESI*9 = -9 - масштабированный индекс записи.

5. Инструкция краша и адресная проверка
---------------------------------------
Функция sub_100A8970 (IDA 0x100A8970), точка сбоя 0x100A898E:

    .text:100A897C  mov  eax, [edi+18h]     ; eax = поле field_18 объекта edi

    .text:100A8981  call sub_100B5C60       ; eax = GameMgr (dword_10634AC8+0x699538)

    .text:100A8989  mov  eax, [eax]
    .text:100A898B  mov  eax, [eax+1Ch]     ; eax = база таблицы записей (field_1C)
    .text:100A898E  mov  eax, [eax+ecx*4]   ; eax = table[esi*9]  <- СБОЙ
    .text:100A8991  neg  eax
    .text:100A8993  sbb  eax, eax
    .text:100A8995  and  eax, 840h
    .text:100A899A  add  eax, 4C15EFh
    .text:100A899F  mov  [edi+20h], eax

Адресная проверка: база (EAX) + ECX*4 = 0x145AA020 + 0xFFFFFFF7*4 =
0x145AA020 + 0xFFFFFFDC = 0x145A9FFC, что равно адресу сбоя 0x145A9FFC.
Совпало.
Проверка масштаба: ECX = ESI*9, где ESI = 0xFFFFFFFF (-1); -1*9 = -9 =
0xFFFFFFF7 = ECX. Совпало.

Механика отказа: инструкция читает элемент table[esi*9] при esi = -1, то
есть обращается к table[-9] - на 9 dword (36 байт) ДО начала буфера
таблицы (база 0x145AA020). Адрес 0x145A9FFC лежит в странице памяти
перед выделенным буфером (граница 0x145AA000); чтение из неотображённой
страницы вызывает EXCEPTION_ACCESS_VIOLATION.

7. Анализ регистров и группировка
---------------------------------
ESI = 0xFFFFFFFF = -1 - индекс типа объекта; контрольное значение «тип
    не назначен».
ECX = 0xFFFFFFF7 = -9 = ESI*9 - масштабированный индекс (записи таблицы
    шириной 9 dword = 36 байт).
EAX = 0x145AA020 - база таблицы записей (поле field_1C объекта GameMgr
    по смещению 0x699538).
Адрес сбоя 0x145A9FFC = EAX - 36 = EAX + ECX*4.
EDI = 0x0019699C - указатель на объект-аргумент геттера: поле field_18
    объекта edi хранит указатель на индекс, поле field_20 - приёмник
    результата.

Регистровый инвариант: index = -1 (контрольное значение), stride = 9
dword, обращение table[-9] = база - 36.


8. Первопричина
---------------
sub_100A8970 - геттер свойства объекта карты. Он читает индекс типа
объекта (dword, на который указывает поле field_18 объекта edi), умножает
его на 9 и выбирает запись из таблицы GameMgr (поле field_1C объекта по
смещению 0x699538). Затем по признаку «запись нулевая / не нулевая»
(команды neg / sbb / and 840h) возвращает один из двух константных
указателей (0x4C15EF или 0x4C15EF + 0x840) в поле field_20 объекта edi.

Проверка индекса ОТСУТСТВУЕТ: значение -1 (контрольное «тип не назначен»)
используется как номер записи напрямую, без отсеивания.

Доказательство через родственные функции:
1) sub_100A8860 (тот же реестр свойств, ссылка sub_100AA500+166) получает
   индекс тем же путём и ПЕРЕД обращением к таблице проверяет его:
   «test ebx, ebx / js loc_100A8965» (безопасный выход при отрицательном
   индексе), плюс проверки границ «cmp esi, 20h / jl» и
   «cmp dword_10634D20, 4 / jl». Отрицательный индекс здесь - ШТАТНАЯ
   ситуация, которую положено отсеивать.
2) sub_100A89B0 (соседний геттер, ссылка sub_100AA500+9D3) использует тот
   же индекс esi*9, но вычисляет АДРЕС записи (lea) и сохраняет его в
   глобал dword_10634AFC без разыменования - поэтому сама не падает, но
   при индексе -1 сохраняет битый указатель.

Контрольное значение -1 подтверждено как штатное: sub_100A8860 проверяет
«cmp eax, 0FFFFFFFFh» и инициализирует локаль значением 0FFFFFFFFh; код
загрузки карты в h3hota.exe проверяет элементы массива GameMgr на -1
(A0_GameMgr_dword_699538, поле field_0 + v10*4 == -1).

Поставщик индекса: индекс хранится в объекте (поле field_18 объекта edi
указывает на dword). Конкретный объект с индексом -1 появляется при
загрузке данной карты: последовательность GameMgr сначала заменяет
случайных монстров (ReplaceRand_Mons_Arts_Res, строка 135), затем
устанавливает начальные параметры объектов (SetObjectsInitialParams,
строка 136), где и запускается геттер. Служебная строка лога
MovableObject_PlaceToMap (-1;-1;-1) фиксирует объект с невалидным
состоянием на этой карте. Какой именно объект получает индекс -1
(конкретный случайный монстр, не разрешённый при замене) - определяется
содержимым карты и требует минидампа/отладчика (см. раздел 11).

Дефект: пропуск проверки контрольного значения -1 в sub_100A8970 при
том, что родственные геттеры подсистемы такую проверку имеют.

11. Воспроизведение вылета
--------------------------
Условие активации пути: загрузить карту, содержащую объект, у которого
индекс типа остаётся равным -1 после фазы замены случайных монстров
(ReplaceRand_Mons_Arts_Res) - тогда в фазе SetObjectsInitialParams геттер
sub_100A8970 обратится к table[-9].

Базовый сценарий (по показаниям игрока, детерминирован для его карты):
1) В редакторе создать очень большую двухуровневую карту.
2) Расставить максимальное количество случайных монстров.
3) Сохранить и загрузить карту - сбой происходит при загрузке.

Варьирование: число и распределение случайных монстров, размер карты и
число уровней - чтобы определить, какое сочетание оставляет объект с
индексом -1.

Дифференциальный тест (подтверждение причины): загрузить ту же карту в
отладчике и в точке sub_100A8970 (hota.dll+0xA898E) проверить индекс ESI
и объект edi. Если ESI == -1 и edi указывает на объект из служебной
строки MovableObject_PlaceToMap (-1;-1;-1) - причина подтверждена.
Дополнительно: принудительно подставить валидный индекс и убедиться, что
сбой исчезает; и наоборот, подставить -1 на «здоровой» карте - сбой
появляется.

Что ловить в минидампе: регистры ESI = -1 / ECX = -9, базу таблицы EAX
и объект edi (поле field_18) для идентификации конкретного объекта без
назначенного типа.

---------------------------
Подтверждено:

Ограничения:
- Единственный дамп; корреляция по серии не проводилась.
- Кадры стека выше точки сбоя частично трамплинные (косвенный вызов

ВЫВОД
-----
Виновник - HotA (закрытый модуль hota.dll). Дефект: функция-геттер
свойства объекта карты sub_100A8970 использует индекс типа объекта как
номер записи в таблице GameMgr без проверки на контрольное значение -1
(«тип не назначен»). При загрузке карты, содержащей объект без
назначенного типа (в данном случае - карта с максимальным количеством
случайных монстров, где фаза замены случайных монстров оставляет объект
с индексом -1), геттер вычисляет -1*9 = -9 и читает 9-ю запись до начала
таблицы, за пределами выделенной памяти, что вызывает
EXCEPTION_ACCESS_VIOLATION. Родственные геттеры той же подсистемы
(sub_100A8860) проверяют отрицательный индекс и безопасно выходят;
sub_100A8970 и sub_100A89B0 такой проверки не имеют. Дефект присутствует
как минимум с версии 1.7.3. Это репорт разработчикам HotA.
