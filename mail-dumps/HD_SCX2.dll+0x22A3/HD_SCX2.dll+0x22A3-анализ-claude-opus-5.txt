==============================================================================
АНАЛИЗ ВЫЛЕТА HD_SCX2.dll+0x22A3 (системные курсоры, фильтр увеличения)
==============================================================================

Модель: Claude Opus 5
Дата: 08.08.2026
Заключение: HD_SCX2.dll при увеличении изображения системного курсора
делит ноль на ноль без проверки знаменателя. В этом процессе исключение
сопроцессора "недопустимая операция" не замаскировано, поэтому вместо
тихого NaN игра получает аппаратное исключение и падает.


КРАТКОЕ РЕЗЮМЕ
--------------

Модуль системных курсоров HD-мода (HD_SCX2.dll, PDB HD_SysCurX2.pdb)
масштабирует картинку курсора фильтром с интерполяцией. В функции
sub_2001E90 подряд вычисляются четыре коэффициента, каждый отдельным
делением. У четвёртого коэффициента делимое и делитель порождены одной и
той же величиной: делитель получается умножением этой величины на -4.0.
Если величина равна нулю, то есть соседние отсчёты совпали (однородный
участок картинки либо её граница, где индексы соседей ограничиваются и
указывают на один элемент), деление превращается в 0/0.

Минидамп доказывает это напрямую. Код исключения 0xC0000090
(EXCEPTION_FLT_INVALID_OPERATION). В стеке сопроцессора st(0) = 0.0,
st(6) = -0.0, st(5) = -4.0. Указатель последней команды сопроцессора
равен 0x02B722A1 - это fdivrp st(6), st. Адрес из заголовка лога (+0x22A3)
не является виновной инструкцией: там стоит fxch st(5), на которой
сопроцессор лишь доставляет отложенное исключение предыдущего деления.

Второе необходимое условие вылета - управляющее слово сопроцессора 0x1372:
маски "недопустимая операция", "деление на ноль" и "переполнение" сняты.
При стандартном для MSVC значении 0x027F то же самое 0/0 дало бы тихий
NaN и максимум артефакт в одной точке курсора, без падения. Кто снял
маску, статикой не определяется: сам HD_SCX2.dll управляющее слово в этом
коде не меняет.

2. Проверка листинга и адреса
-----------------------------

Листинг: modules/HD_SCX2.dll-5.7 R37.txt
    Imagebase 0x2000000, Virtual size 0x1158B, Timestamp 6A7696B7,
    PDB HD_SysCurX2.pdb.
В логе модуль загружен по 0x02B70000, размер 0x1F000, точка входа
0x02B77CCF.

Проверка точки входа:
    0x02B77CCF - 0x02B70000 + 0x2000000 = 0x2007CCF
В листинге по 0x02007CCF начинается библиотечная функция инициализации
(сразу после dllmain_raw), то есть база пересчёта верна.

Пересчёт адреса сбоя:
    0x02B722A3 - 0x02B70000 + 0x2000000 = 0x20022A3
Это граница инструкции: 0x020022A3 fxch st(5), внутри функции sub_2001E90
(0x2001E90 - 0x20023A9), смещение +0x413.

Побайтная сверка кода с дампом (адрес 0x02B7229F, 9 байт):

    DE F6        fdivrp  st(6), st      ; 0x020022A1
    D9 CD        fxch    st(5)          ; 0x020022A3 - адрес из лога
    D9 55 E4     fst     [ebp-1Ch]      ; 0x020022A5
Байты из дампа полностью совпадают с листингом 5.7 R37, соответствие
версии листинга упавшему модулю подтверждено машинно, а не по имени файла.

Соседние адреса того же модуля: серия HD_SCX2.dll+0x221F (35 уникальных
вылетов, версии от 5.6 R37 до 5.7 R35) относится к ДРУГОМУ дефекту -
чтение за границей таблицы курсоров в sub_2002030 с кодом
EXCEPTION_ACCESS_VIOLATION. Общими являются только модуль и подсистема,
в одну семью с настоящим вылетом эти адреса не объединяются.


3. Точка сбоя
-------------

Код вокруг точки сбоя (листинг 5.7 R37):

    .text:02002285                 fld1
    .text:02002287                 fsub    st, st(3)
    .text:02002289                 fld     dword ptr [eax]
    .text:0200228B                 fmul    st, st(2)
    .text:0200228D                 mov     eax, [ebp+var_48]
    .text:02002290                 fsubrp  st(2), st
    .text:02002292                 fdivrp  st(1), st      ; деление 3
    .text:02002294                 fst     [ebp+var_20]
    .text:02002297                 fld     ds:flt_2017ED8 ; константа -4.0
    .text:0200229D                 fmul    st(6), st      ; st(6) = st(6)*-4.0
    .text:0200229F                 fxch    st(5)
    .text:020022A1                 fdivrp  st(6), st      ; деление 4: ВИНОВНИК
    .text:020022A3                 fxch    st(5)          ; адрес из лога
    .text:020022A5                 fst     [ebp+var_1C]

Обращения к памяти в падающей инструкции нет, поэтому вместо разбора
адресной арифметики проверяются значения операндов сопроцессора из
минидампа.

Стек сопроцессора, восстановленный из TagWord 0x4507 и области регистров
(TOP = 1, занято 7 регистров):
    st(0) = 0.0     (делимое)
    st(1) = -0.25
    st(2) = -0.25
    st(3) = 0.0
    st(4) = 0.0
    st(5) = -4.0    (константа flt_2017ED8, попавшая сюда после fxch)
    st(6) = -0.0    (делитель)
    st(7) = пусто

StatusWord 0xC8A1 разбирается так: IE = 1 (недопустимая операция),
PE = 1, ES = 1, SF = 0. Нулевой SF означает, что переполнения или
опустошения стека сопроцессора НЕ было: st(5) не пуст, и версия про
"обращение к пустому регистру в fxch" исключается.

Механика виновной команды:
    fdivrp st(6), st  =  st(6) := st(0) / st(6), затем выталкивание
    st(0) / st(6)     =  0.0 / -0.0  =  0/0  -> недопустимая операция

Знак -0.0 у делителя сам по себе доказывает происхождение: делителем
стало значение, умноженное на -4.0 командой по 0x0200229D, то есть до
умножения там был ноль. А st(5) = -4.0 подтверждает, что обмен по
0x0200229F действительно уже выполнен, и на 0x020022A1 в st(0) лежит
числитель, а не константа.

Почему адрес в логе отличается от виновника: x87 сообщает о
незамаскированном исключении не сразу, а на следующей ожидающей команде
сопроцессора. Виновная команда - fdivrp по 0x020022A1 (её и записал
сопроцессор в FPU IP), а исключение доставлено на fxch по 0x020022A3.

5. Первопричина
---------------

Что делает sub_2001E90. Функция получает координаты точки (два целых),
вещественный параметр интерполяции, указатель на описание картинки в EDX
(данные, шаг строки, ширина, высота) и указатель на приёмник из трёх
float в ECX. Она выбирает центральный отсчёт и четырёх соседей из сетки
16-байтовых элементов (по три float на элемент), ограничивая индексы
шириной и высотой, затем длинной серией сравнений fcom/fnstsw выбирает
указатели на минимальные и максимальные значения (var_44, var_48, var_4C,
var_50) и по ним считает весовые коэффициенты.

Коэффициентов четыре, и каждый вычисляется делением:
    0x02002263  fdivp  st(1), st   -> var_28
    0x0200227D  fdivrp st(1), st   -> var_24
    0x02002292  fdivrp st(1), st   -> var_20
    0x020022A1  fdivrp st(6), st   -> var_1C   (падает здесь)
Ни перед одним из четырёх делений нет ни сравнения делителя с нулём, ни
ветвления по результату такого сравнения. Знаменатели строятся прямо из
разностей выбранных отсчётов, домноженных на константы 4.0 (flt_2017EB0)
и -4.0 (flt_2017ED8).

Первопричина: если соседние отсчёты равны между собой, разность равна
нулю, и тогда для четвёртого коэффициента и делимое, и делитель
обращаются в ноль. Получается 0/0 - математически неопределённое
выражение, для сопроцессора это "недопустимая операция", а не деление на
ноль в обычном смысле.

Нулевая разность возникает как минимум двумя путями, и оба закрываются
одной и той же проверкой:
    - однородный участок картинки: соседние отсчёты равны по
      содержанию;
    - точка на границе картинки: индексы соседей ограничиваются
      шириной [ebx+8] и высотой [ebx+0Ch], и после ограничения два
      соседа могут указывать на один и тот же элемент.

Ограничение индексов видно прямо в коде (одно из шести мест):

    .text:02001F9C                 cmp     edi, [ebx+0Ch]
    .text:02001F9F                 jl      short loc_2001FAB
    .text:02001FA1                 mov     eax, [ebx+0Ch]
    .text:02001FA4                 dec     eax
    .text:02001FA5                 mov     [ebp+var_48], eax

Граничный случай опаснее однородного: он не требует никаких свойств от
самого изображения - достаточно попасть в крайний ряд или столбец
либо получить картинку толщиной в один элемент. Какой именно из двух
путей сработал в этом вылете, по минидампу не различается: поля ширины
и высоты лежат в несохранённой памяти.

Косвенное подтверждение вырожденности входа: три предыдущих деления
отработали и дали ровно -0.25 каждое, что соответствует 1.0 / -4.0, то
есть нулевым разностям в числителе тех формул. В стеке сопроцессора на
момент сбоя три значения из семи равны нулю. Иными словами, фильтру
достались совпавшие соседние отсчёты картинки курсора.

Второе необходимое условие - снятая маска исключения. ControlWord = 0x1372
означает: IM = 0 (недопустимая операция НЕ замаскирована), ZM = 0, OM = 0,
замаскированы только денормализация, антипереполнение и потеря точности;
точность вычислений 64 бита, округление к ближайшему. Стандартное значение
для программы, собранной MSVC, - 0x027F, где замаскированы все шесть
исключений. При 0x027F то же 0/0 вернуло бы тихий NaN, дальше NaN попал бы
в запись цвета точки и в худшем случае дал бы артефакт на курсоре -
без вылета.

Кто снял маску, статическим анализом не устанавливается. Проверено:
в HD_SCX2.dll команда fldcw встречается только в библиотечном коде
(преобразование вещественных в целые, логарифм и подобные помощники),
где управляющее слово сохраняется и тут же восстанавливается; ни в
sub_2001E90, ни в её вызывающих fldcw нет. Проверены все доступные
листинги модулей процесса: h3hota.exe, HotA.dll, HD_HOTA.dll,
HD_SCX2.dll, HD_TC2.dll, HD_VGL2.dll, HW_HOTA.dll, _HD3_.dll,
patcher_x86.dll, mss32.dll, mp3dec.asi, binkw32.dll, IFC20.dll. Ни в одном
из них
нет загрузки управляющего слова 0x1372 или 0x1332. Единственные
значения, которые эти модули реально загружают, - 0x027F (стандарт
компилятора Microsoft) и 0x133F; у обоих маска недопустимой операции
выставлена, то есть создать условие вылета они не могли. Глобальные
слова, из которых идёт загрузка, инициализированы теми же значениями.

IFC20.dll проверен отдельно как главный подозреваемый и тоже
исключён. Управляющее слово он трогает только в двух местах: в
помощнике преобразования вещественного в целое, где слово сохраняется
и тут же восстанавливается, и в библиотечной паре _controlfp и
_control87, которую вызывает _setdefaultprecision при инициализации:

    .text:1000F2B7                 push    30000h          ; Mask
    .text:1000F2BC                 push    10000h          ; NewValue
    .text:1000F2C1                 call    __controlfp

Маска 0x30000 разрешает менять только управление точностью; биты масок
исключений в неё не входят, поэтому снять маску недопустимой
операции этот вызов не может. Заодно опровергнуто предположение о
происхождении этого модуля: имена _setdefaultprecision, _abstract_cw,
_hw_cw и _ms_p5_mp_test_fdiv принадлежат рантайму компилятора
Microsoft, а не Borland.

cursors.dll тоже выбывает: в списке модулей у неё точка входа
0x00000000, то есть это ресурсный файл без исполняемого кода, кода
для установки управляющего слова в ней просто нет.

HD_UPD.dll добавлен и проверен: тоже исключён. Все его места
загрузки управляющего слова - библиотечные помощники возведения в
степень, округления и обработки ошибок сопроцессора; загружаются
только 0x027F и 0x133F. Служебная вставка перед загрузкой устроена
так, что младший байт принудительно доводится до 0x7F:

    .text:1001AE65                 mov     edx, [esp+4]
    .text:1001AE69                 and     edx, 300h
    .text:1001AE6F                 or      edx, 7Fh
    .text:1001AE77                 fldcw   word ptr [esp+6]

Из слова сохраняется только управление точностью, а все маски
исключений выставляются в единицу. Такой код может маску только
поставить, снять - никогда. Происхождение модуля тоже не Borland:
имена вида __crt_strtox и __acrt_fp_class принадлежат рантайму
Microsoft, отладочный файл - hUpdate.pdb.

Разбор потока модулей самого минидампа снял главное ограничение
этого раздела: в текстовом логе перечислены только модули из папки
игры, а по разбору дампа записей 115. В процессе есть то, чего в
логе не видно: инородные перехватчики zHook.dll по адресу
0x04DD0000 и aswhook.dll по адресу 0x718D0000 (модуль антивируса),
драйвер видеокарты nvoglv32.dll по адресу 0x65E50000, а также
opengl32.dll, ddraw.dll, dplayx.dll, dsound.dll и msvcrt.dll. Именно
такие модули - внедрённые перехватчики и драйверы - типовые
виновники испорченного управляющего слова, и ни один из них ранее
не рассматривался, потому что их нет в логе.

Круг подозреваемых больше не сводится к библиотекам сборки.
Первыми на проверку идут zHook.dll и aswhook.dll как внедрённый
код, затем драйвер nvoglv32.dll и системные библиотеки.

Последние три модуля из папки игры тоже получили листинги и тоже
исключены. SMACKW32.DLL к сопроцессору не обращается вовсе: в ней
нет ни одной команды загрузки управляющего слова и ни одного
вызова управления сопроцессором. binkw32new.dll содержит ту же
библиотечную пару, что и IFC20.dll, и вызывает её из
инициализации ровно с той же маской 0x30000, то есть меняет
только точность. В discord.dll все места загрузки - помощники
преобразования вещественного в целое: слово сохраняется,
добавляется округление к нулю, затем восстанавливается;
единственная константа рядом - 0x133F, где маска выставлена.

Итог: ни один модуль из папки игры снять маску не мог - теперь
это проверено по листингам для всех них без исключения. Источник
испорченного слова находится вне папки игры. Значение 0x1372
совпадает с типовым управляющим словом рантайма Borland (0x1332 плюс
зарезервированный бит), которое такие модули устанавливают при
инициализации и часто не восстанавливают. Косвенный довод за эту
версию: старшая часть 0x13 у слова из минидампа та же, что и у 0x133F
из доступных листингов, то есть речь об одном семействе рантайма,
только с другими младшими битами масок. Это версия, а не доказанный
факт: конкретный установщик определяется только наблюдением в
рантайме.

Распределение ответственности:
    - отсутствие проверки нулевого знаменателя в четырёх делениях -
      дефект кода HD-мода (HD_SCX2.dll), собственный код мода, не
      воспроизведение оригинальной логики игры;
    - снятая маска исключения - внешнее по отношению к HD_SCX2.dll
      условие, приходящее из другого модуля процесса.
Вылет требует обоих условий одновременно.


6. Условия сбоя
---------------

Настройки, относящиеся к делу:
    Graphics.SystemCursors = 1  - включены системные курсоры, за них и
      отвечает HD_SCX2.dll; без этого режима код вообще не работает
    Graphics.Mode = 7, Graphics.Resolution = 1180, 664
    Graphics.ComplexFilter = 2, Graphics.SimpleFilter = 2
    OpenGL.Upscaling = 2, OpenGL.Interpolation = 2, OpenGL.Renderer = 0
    UI.HiRezCore = 1, UI.ClipCursor = 1, UI.AdvMgr.DragMap = 1,
      UI.AdvMgr.HigherFPS = 2
    Graphics.Threads = 2, Graphics.AdvMap.Threads = -1
    Memory.Mod = 0
Нестандартное разрешение 1180x664 задаёт дробный коэффициент увеличения
курсора, при котором фильтр интерполяции работает на каждой точке.

Окружение: Windows 7 6.1.7601, каталог совместимости #hota15, hota.ini,
русская локализация. В процессе присутствуют IFC20.dll, discord.dll,
mss32.dll, binkw32new.dll, patcher_x86.dll.

Игровая ситуация: карта приключений, первый день, одиночная игра,
полноэкранный режим, перемещение курсора по карте. Ничего специфического
для карты crapcore.h3m в механизме сбоя нет.

Случайность вылета: сам по себе дефект детерминирован (одна и та же
картинка курсора при одном и том же масштабе даёт одно и то же 0/0), но
срабатывает он только в те моменты, когда действует чужое управляющее
слово сопроцессора. Отсюда редкость: единственный отчёт по этому адресу
против 35 отчётов по соседнему адресу того же модуля.


7. Воспроизведение вылета
-------------------------

Основной сценарий:
1. Windows 7 или новее, HotA 1.8.0 с HD-модом 5.7 R37.
2. В hota.ini выставить Graphics.SystemCursors = 1, Graphics.Mode = 7,
   разрешение 1180x664, UI.HiRezCore = 1, OpenGL.Upscaling = 2,
   OpenGL.Interpolation = 2 - как в отчёте.
3. Запустить одиночную игру и водить курсором по карте приключений,
   меняя вид курсора (перемещение, атака, взятие объекта).
4. Ключевое условие: маска недопустимой операции у сопроцессора должна
   быть снята в игровом потоке. Проверяется отладчиком по значению
   управляющего слова: нужное состояние - 0x1372, обычное - 0x027F.

Ускоренный дифференциальный тест (надёжнее полного сценария):
1. Подключиться отладчиком к процессу и в момент до отрисовки курсора
   принудительно записать в управляющее слово 0x1372.
2. Подвигать курсор - ожидается исключение 0xC0000090 по адресу
   HD_SCX2.dll+0x22A3.
3. Вернуть управляющее слово в 0x027F и повторить - вылета быть не
   должно, вместо него в кадре курсора появятся значения NaN.
Разница между двумя прогонами и есть подтверждение механизма.

Что фиксировать в отладчике:
    - точка останова на 0x020022A1 (в рантайме база плюс 0x22A1);
      проверить, что st(0) и st(6) оба нулевые;
    - содержимое описания картинки по EDX в вызывающей функции: ширина,
      высота, шаг строки, и сами соседние отсчёты - они должны совпадать
      между собой;
    - управляющее слово перед входом в sub_2001E90 и историю его
      изменения (точка останова на записи слова), чтобы найти модуль,
      который снял маску.

Признаки этого же дефекта в других отчётах: код исключения 0xC0000090,
указатель последней команды сопроцессора на +0x22A1, слово состояния с
IE = 1 и SF = 0, управляющее слово, отличное от 0x027F.


8. Достоверность и ограничения
------------------------------

Подтверждено:
    - Соответствие листинга упавшему модулю: побайтное совпадение девяти
      байт кода вокруг точки сбоя и совпадение пересчитанной точки входа
      с началом функции.
    - Виновная инструкция: указатель последней команды сопроцессора в
      минидампе равен 0x02B722A1, что соответствует fdivrp st(6), st.
    - Значения операндов: 0.0 и -0.0 восстановлены из области регистров
      сопроцессора и согласованы с TagWord (оба помечены как ноль).
    - Тип ошибки: IE = 1 при SF = 0, деление ноль на ноль, а не
      переполнение стека сопроцессора и не деление конечного числа на
      ноль.
    - Снятая маска: ControlWord = 0x1372 прочитан из дампа.
    - Отсутствие проверок делителя: просмотрены все четыре деления в
      функции и код между ними.
    - Единственность вызывающей функции: перебор ссылок по листингу плюс
      адрес возврата 0x02B72616 из кадра стека.
    - Собственный код HD-мода: абсолютных вызовов в h3hota.exe из этой
      функции нет.

Отрицательные результаты (искали и не нашли):
    - Команда загрузки управляющего слова fldcw в sub_2001E90 и в её
      вызывающих: не найдено ни одного. Все вхождения fldcw в модуле
      лежат в библиотечном коде и сопровождаются обратным восстановлением
      слова.
    - Другие вызывающие sub_2001E90, кроме sub_20023B0: не найдено ни
      одного по всему листингу.
    - Абсолютные вызовы в h3hota.exe из этой функции: не найдено ни
      одного, то есть код не повторяет оригинальную логику игры.
    - Ссылки на функцию из таблиц виртуальных методов: не найдено ни
      одного, вызов только прямой.
    - Выделения памяти внутри функции: не найдено ни одного, версия
      про нехватку памяти отпадает.
    - Страницы с буферами курсора в минидампе: не найдено ни одного
      диапазона, покрывающего адреса 0x0E03DE80 и 0x0E03E290.

    - Загрузка управляющего слова 0x1372 или 0x1332 в доступных
      листингах модулей процесса: не найдено ни одного места.
      Единственное вхождение цифр 1372 - часть константы 91372h в
      командах xor в HotA.dll, к сопроцессору отношения не имеет.
    - Все модули из папки игры проверены по листингам: ни один не
      загружает 0x1372 или 0x1332. SMACKW32.DLL вообще не содержит
      команд работы с управляющим словом; binkw32new.dll и IFC20.dll
      меняют только управление точностью; discord.dll и HD_UPD.dll
      грузят лишь 0x027F и 0x133F; cursors.dll - ресурсный файл без
      кода. Листингов нет только для модулей вне папки игры.

    - Полнота списка модулей: в логе перечислены только модули из
      папки игры, а по разбору потока модулей минидампа записей 115.
      Ранее вообще не рассматривались внедрённые перехватчики
      zHook.dll и aswhook.dll, драйвер nvoglv32.dll и системные
      opengl32.dll, ddraw.dll, dplayx.dll, dsound.dll и msvcrt.dll;
      листингов для них в проекте нет.
    - Совпадение версий листингов с моментом вылета: для HD_VGL2.dll
      и HW_HOTA.dll редакции R37 в проекте нет, есть только более
      ранние; для HD_TC2.dll и patcher_x86.dll листинги без пометки
      редакции.

Ограничения:
    - Один отчёт, сравнить несколько дампов между собой невозможно.
    - Кучи в минидампе нет: сами пиксели курсора и поля описания картинки
      (ширина, высота, шаг) не прочитаны; вывод о конкретном виде вырождения
      сделан по нулевым разностям в стеке сопроцессора и нулям в кадре, а
      не по исходным данным.
    - Модуль, снявший маску исключения, статикой не найден. Совпадение
      0x1372 с типовым словом рантайма Borland - версия, требующая
      проверки в рантайме.
    - Точный смысл каждого из четырёх коэффициентов (какой именно фильтр
      реализован) не восстанавливался: для диагноза достаточно того, что
      делитель порождается той же величиной, что и делимое.
    - Верхние кадры цепочки вызовов взяты из стека, приведённого в самом
      отчёте игры, и проверены только по границам функций.


ВЫВОД
-----

Виновник - HD-мод, модуль системных курсоров HD_SCX2.dll версии 5.7 R37.
В функции sub_2001E90 (адрес 0x2001E90 в листинге), в блоке вычисления
весовых коэффициентов фильтра увеличения, четвёртый коэффициент считается
делением величины на эту же величину, умноженную на -4.0. На однородном
участке картинки курсора обе части равны нулю, и деление 0.0 / -0.0
становится недопустимой операцией. Проверки нулевого знаменателя нет ни
перед одним из четырёх делений функции.

Вылет происходит только потому, что в этом процессе снята маска
недопустимой операции у сопроцессора (управляющее слово 0x1372 вместо
стандартного 0x027F). При стандартной маске тот же код вернул бы NaN и
испортил бы в худшем случае одну точку курсора. Модуль, снимающий маску,
не определён; сам HD_SCX2.dll управляющее слово в этом коде не меняет.

Как исправить в коде HD_SCX2.dll: перед каждым из четырёх делений
(0x2263, 0x227D, 0x2292, 0x22A1) проверять знаменатель на ноль и
возвращать в этом случае значение центрального отсчёта - для однородного
участка это математически корректный результат интерполяции. Дополнительно
стоит фиксировать управляющее слово сопроцессора на входе в отрисовку
курсора и восстанавливать его на выходе: это закроет весь класс подобных
сбоев, вызванных чужими настройками сопроцессора.

Польза лога высокая: виновная инструкция, значения операндов и
отсутствующая проверка установлены точно, для исправления рантайм-проверка
не требуется. Рантайм нужен только для второго, внешнего условия - поиска
модуля, снявшего маску.
