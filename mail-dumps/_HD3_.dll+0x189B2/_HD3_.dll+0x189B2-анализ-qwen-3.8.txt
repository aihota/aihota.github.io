полноэкранности 698808 ещё не загружен из реестра (BSS=0),

который загружает глобальный указатель dword_1004C9EC и делает

(loc_100184B7 функции sub_100182C0) объект dword_1004C9EC не
создаёт вовсе, указатель равен 0 -- происходит чтение по адресу

Корень -- несогласованность оконного пути HD-мода: таблица
перехватчиков (с sub_100189A0, использующим dword_1004C9EC)

не создаётся. Перехватчик проверяет на NULL свой аргумент arg_0,
но НЕ проверяет глобальный указатель. Сбой детерминирован в
оконном режиме, а не случаен.

8. Первопричина
---------------
Глобальный указатель dword_1004C9EC хранит объект
внутренней поверхности DirectDraw, создаваемый HD-модом.

Жизненный цикл глобала:

1) Инициализация (sub_100182C0, строка 10018459):
    .text:10018459  push    offset dword_1004C9EC
    .text:10018460  call    dword ptr [ecx+18h]
   Адрес глобала передаётся как выходной параметр
   vtable-вызова; после успешного вызова глобал
   содержит указатель на объект.

2) Освобождение (sub_10018920, строка 1001898A):
    .text:10018979  mov     eax, dword_1004C9EC
    .text:10018984  push    eax
    .text:10018985  mov     ecx, [eax]
    .text:10018987  call    dword ptr [ecx+8]
    .text:1001898A  mov     dword_1004C9EC, edi
   При освобождении edi = 0 (результат предшествующего
   вызова), глобал обнуляется.

3) Использование (sub_100189A0, строка 100189A9):
    .text:100189A9  mov     eax, dword_1004C9EC
    .text:100189B2  mov     ecx, [eax]
   Глобал загружается и разыменовывается БЕЗ проверки.

Порядок инициализации (корень дефекта). Объект-обёртка
поверхности, чья таблица перехватчиков содержит
sub_100189A0, создаётся функцией sub_100182C0. Внутри
неё порядок операций следующий:

    +0x2E   call sub_100181A0     -- построить таблицу
              перехватчиков (слот +0x74 = sub_100189A0)
    +0x3C   mov [esi], edi        -- ОПУБЛИКОВАТЬ обёртку
              (с этого момента sub_100189A0 достижим
              через перехваченную vtable)
    +0x12F  call [ecx+18h]        -- создать первичную
              поверхность (dword_1004C9D8)
    +0x199  call [ecx+18h]        -- создать объект
              dword_1004C9EC (ТОЛЬКО полноэкранный путь)

Таким образом, обёртка публикуется (+0x3C) РАНЬШЕ, чем
создаётся объект dword_1004C9EC (+0x199). В интервале
между ними перехватчик sub_100189A0 уже достижим, но
глобал ещё равен нулю.

Два пути sub_100182C0. Ветвление по флагу
[arg_0+68h] & 0x200 (строка 1001836A):

    .text:1001836A  test    dword ptr [ebx+68h], 200h
    .text:10018371  jz      loc_100184B7

Полноэкранный путь (флаг установлен) создаёт
dword_1004C9D8, dword_1004C9F0 и dword_1004C9EC.
Оконный путь (loc_100184B7, флаг сброшен) создаёт
ТОЛЬКО объект по смещению +0x94 обёртки; глобал
dword_1004C9EC в этом пути НЕ создаётся вовсе и
остаётся равным нулю (неинициализированный BSS).
Таблица перехватчиков с sub_100189A0 строится и
публикуется в ОБЕИХ путях (до ветвления).

Следствие: если обёртка первичной поверхности создана
через оконный путь (или создание полноэкранного пути
завершилось неудачей), любой вызов перехватчика
sub_100189A0 детерминированно падает на разыменовании
нулевого глобала.

Как обёртка попадает в игру. Первичную поверхность
создаёт игровой код: A0_DirectDrawInit_sub_601AB0
вызывает sub_600BB0(1) (строка 00601B6A), результат
сохраняется в A0_DirectDraw_Surface_Primary_dword_6AAD24
(строка 00601B75). Вызов CreateSurface перехвачен
HD-модом и проходит через sub_10018B30 -> sub_100182C0,
которая и возвращает обёртку. Далее игра вызывает
vtable-метод обёртки (строка 00601C5D, call [ecx+70h]),
перехват направляет управление в sub_100189A0. К этому
моменту обёртка уже существует (строка 00601C5B
mov ecx, [eax] успешно читает её vtable), а глобал
dword_1004C9EC равен нулю.

Почему активируется оконный путь. Краш доказанно
происходит в оконной ветке (698808=0 в момент проверки
00601BF8). Происхождение 698808=0 установлено под
winedbg: A0_DirectDrawInit (0x601AB0) выполняется ДО
чтения настройки полноэкранности из реестра (запись
в 698808 по 0x4EDD22); ни одна из инструкций обнуления
HD-мода (sub_1000BF50, sub_100157A0, sub_10016430) НЕ
срабатывает до инициализации. Следовательно, 698808=0
в момент A0_DirectDrawInit -- это НЕинициализированное
BSS-значение (настройка ещё не загружена), а не активное
обнуление HD-модом. Оконная ветка при ранней инициализации
-- нормальное состояние флага.

Рассмотренные механизмы обнуления 698808 (все ОТВЕРГНУТЫ
как триггер данного краша):
1) sub_100157A0 -- обнуляет 698808, если разрешение не
   найдено среди родных режимов (sub_100154F0 вернул 0).
   Не подходит: 1920x1080 -- родной режим, sub_100154F0
   возвращает 1.
2) sub_1000BF50 -- обнуляет по номеру инстанции HD-мода
   (HD.instance_ix). Не сработал до инициализации (winedbg).
3) sub_10016430 -- инверсия 698808 (переключение экран/окно).
   Не сработал до инициализации (winedbg).

Таким образом, оконная ветка активируется не обнулением
флага, а тем, что флаг ещё не установлен (BSS=0) на момент
ранней инициализации DirectDraw. Краш возникает, когда к
этому добавляется второе условие -- объект dword_1004C9EC
не создан (оконный путь sub_100182C0 при Graphics.Mode=3).

Замыкание цепи: при ранней инициализации DirectDraw флаг
698808 ещё равен 0 (BSS, настройка не загружена), игра
выполняет оконную инициализацию (CreateClipper, SetHWnd,
SetClipper), SetClipper перехвачен (sub_100189A0); если
объект dword_1004C9EC не создан (оконный путь sub_100182C0
при Graphics.Mode=3) -- происходит разыменование нуля.
Модуль формирования отчёта читает 698808 ПОСЛЕ загрузки
настройки из реестра (значение уже 1), поэтому в логе
FullScreen Mode=1 при краше в оконной ветке. Все 11 логов
имеют Graphics.Mode=3 (растягиваемый режим).

Верификация под winedbg (Wine 11.0, h3hota_HD.exe,
Graphics.Mode=3, 1920x1080, UI.HiRezCore=1; h3hota_hd
грузится по базе 0x400000, _HD3_.dll -- по 0x10000000).
Точки останова на A0_DirectDrawInit (0x601AB0) и на
перехватчике sub_100189A0 (0x100189A0) подтвердили:
  - *(int*)0x698808 = 0 на входе в A0_DirectDrawInit:
    игра с Graphics.Mode=3 действительно идёт по оконной
    ветке DirectDraw (условие (а) краша подтверждено);
  - перехватчик sub_100189A0 (SetClipper) достигается
    при инициализации графики;
  - *(int*)0x1004C9EC = 0x411b778 (НЕ ноль) в момент
    sub_100189A0: под Wine объект создан, поэтому краш
    под Wine НЕ воспроизводится.
Порядок инициализации (точки на 0x601AB0 и на записи
настройки 0x4EDD22): A0_DirectDrawInit срабатывает РАНЬШЕ
чтения настройки полноэкранности из реестра; точки на
инструкциях обнуления HD-мода (sub_1000BF50/sub_100157A0/
sub_10016430) до инициализации НЕ срабатывают. Вывод:
698808=0 при ранней инициализации -- неинициализированное
BSS-значение, оконная ветка -- нормальное состояние флага
до загрузки настройки.
Глобалы поверхности в момент sub_100189A0 под Wine
(полноэкранный путь): dword_1004C9D8 = 0x3f1d188,
dword_1004C9EC = 0x3f1d2b8, dword_1004C9F0 = 0x47cf348
-- все три ненулевые. Это подтверждает, что полноэкранный
путь sub_100182C0 создаёт все три объекта; оконный путь
(loc_100184B7) не создаёт ни одного (по статике). Метод
различения путей по dword_1004C9D8 (0 = оконный путь,
не ноль = полноэкранный с неудачей создания) подтверждён.
Принудительный перевод всех вызовов sub_100182C0 в оконный
путь (патч ветки) роняет процесс под Wine, но не чисто в
sub_100189A0 (искусственный патч ломает инициализацию
раньше); на Windows оконный путь выбирается естественно
по биту [arg_0+68h] & 0x200 только для нужной поверхности.
Вывод: краш требует СОЧЕТАНИЯ двух условий -- (а) оконная
ветка DirectDraw игры (698808=0, SetClipper активен --
норма для ранней инициализации) и (б) оконный путь
sub_100182C0 (бит [arg_0+68h] & 0x200 сброшен, объект не
создаётся -- специфика Graphics.Mode=3). Под Wine
выполняется только (а), а (б) -- нет (бит установлен,
полноэкранный путь, объект создан). На Windows при
Graphics.Mode=3 выполняются оба условия. Этим объясняется
специфика вылета для Windows+Graphics.Mode=3 и его
отсутствие под Wine.

Сравнение с соседними функциями:

    sub_100189C0 (слот +0x78): проверяет arg_0,
        затем использует [arg_0+0x94] -- НЕ обращается
        к глобалу dword_1004C9EC.
    sub_100189E0 (слот +0x70): проверяет arg_0,
        затем использует [arg_0+0x94] -- НЕ обращается
        к глобалу.
    sub_10018580, sub_10018700 (обработчики Blt):
        используют dword_1004C9EC БЕЗ проверки на NULL
        (тот же паттерн, что и sub_100189A0).

Ни одна функция, использующая dword_1004C9EC, не
проверяет его на NULL. Инвариант «глобал всегда
валиден при активном перехватчике» нарушается: обёртка
публикуется до создания глобала, а в оконном пути
глобал не создаётся вовсе.

9. Условия сбоя
---------------
Состояние игры одинаково во ВСЕХ 11 логах семьи
(инвариант, не зависит от версии HD-мода):
    День 0, Game Type = 0, Network Game = 0 -- запуск
        игры, главное меню или начало сценария.
    Map file = test.h3m (тестовая карта).
    FullScreen = 1 (полноэкранный режим).
    Graphics.Mode = 3 (внутренняя глубина 16 бит,
        растягиваемый режим, вывод в 32 бит).

Комментарии игроков отсутствуют во всех логах (только
служебный автотекст).

Условие активации -- Graphics.Mode=3 (растягиваемый
режим). Краш возникает при ранней инициализации DirectDraw,
когда флаг полноэкранности 698808 ещё не загружен из
реестра (BSS=0, см. раздел 8) и игра идёт по оконной
ветке (SetClipper активен). Для Graphics.Mode=3 оконный
путь sub_100182C0 не создаёт объект dword_1004C9EC --
перехватчик SetClipper падает. Пользовательская настройка
FullScreen=1 не влияет: на момент ранней инициализации
флаг ещё не установлен. Постоянство конфигурации
(Graphics.Mode=3) по 8 версиям указывает на детерминированный
стартовый краш, а не на случайную гонку.

Сбой происходит при инициализации DirectDraw
(A0_DirectDrawInit_sub_601AB0), которая вызывается
при запуске графической подсистемы. Конкретный
триггер -- вызов SetClipper первичной поверхности
DirectDraw (vtable-смещение +0x70) в оконной ветке
инициализации, перехваченный HD-модом.

11. Воспроизведение вылета
--------------------------
Условие активации пути: растягиваемый графический режим
(Graphics.Mode=3). При ранней инициализации DirectDraw флаг
698808 ещё не загружен из реестра (BSS=0), игра идёт по
оконной ветке; для Graphics.Mode=3 оконный путь инициализации
не создаёт объект dword_1004C9EC, и первый же перехваченный
вызов SetClipper падает детерминированно.

Базовый сценарий:
    1) Установить HD-мод (любую из подверженных версий
       5.6 R37 -- 5.7 R33), HotA 1.8.0.
    2) Настроить Graphics.Mode = 3 (растягиваемый режим).
       FullScreen может быть 1 -- на момент ранней
       инициализации флаг 698808 ещё не загружен, игра
       идёт по оконной ветке.
    3) Запустить игру (загрузка главного меню или
       начало сценария).
    4) Вылет происходит в момент инициализации DirectDraw
       (оконная настройка клиппера), до отображения
       главного меню.

Воспроизводимость: вылет зафиксирован 11 раз в 8 версиях
HD-мода при идентичной конфигурации (Graphics.Mode=3,
день 0, карта test.h3m). Механизм детерминирован: в
оконном пути объект не создаётся вовсе, поэтому сбой
происходит при каждом запуске в растягиваемом режиме,
а не в случайной гонке. Для подтверждения тестеру:
запуск с Graphics.Mode=3 должен давать краш с EAX=0,
ESI=0x90000000, EDI=0x8 на каждой подверженной версии.

Дифференциальный тест:
    Запуск с отключённым HD-модом (чистый SoD/HotA)
    не даёт этого вылета -- код sub_100189A0
    существует только в _HD3_.dll. Смена Graphics.Mode
    на нерастягиваемый режим (например, 0) переводит
    инициализацию поверхности по полноэкранному пути
    sub_100182C0 (объект dword_1004C9EC создаётся)
    и исключает сбой -- это подтвердит привязку к
    оконному пути растягиваемых режимов.

Достоверность и ограничения
----------------------------
Подтверждено:
- Точка краша доказана: mov ecx, [eax] при EAX=0,
  адресная арифметика сошлась (0+0 = 0x00000000).
- Листинг _HD3_.dll верифицирован по entry point
  (0x1001B36C = DllEntryPoint) и timestamp.
- Механизм подтверждён чтением кода: глобал
  dword_1004C9EC инициализируется в sub_100182C0,
  обнуляется в sub_10018920, используется без
  проверки в sub_100189A0.
- Порядок инициализации прочитан: обёртка публикуется
  (mov [esi], edi на +0x3C) раньше создания глобала
  (+0x199); ветвление на полноэкранный/оконный путь
  по [arg_0+68h] & 0x200 (строка 1001836A).
- Оконный путь (loc_100184B7) прочитан полностью:
  dword_1004C9EC в нём не создаётся (глобал остаётся
  нулевым), таблица перехватчиков строится до ветвления.
- Оконный режим ДОКАЗАН по точке краша: инструкция
  00601C5D (call [ecx+70h] = SetClipper) лежит внутри
  блока if (!A0_Reg_Key_MainGameFullScreen_dword_698808);
  при ненулевом флаге jnz loc_601C75 (00601BFA) пропускает
  блок. Значит, в момент краша флаг 698808 = 0 (оконный
  режим DirectDraw).
- Механизмы обнуления флага 698808 в HD-моде найдены
  (sub_1000BF50: записи mov ds:698808h, 0 по номеру
  инстанции HD.instance_ix, строки 1000C05D-1000C0D0;
  sub_100157A0; sub_10016430), но ни один из них НЕ
  является триггером данного краша: под winedbg они не
  срабатывают до инициализации, 698808=0 здесь --
  неинициализированное BSS-значение (см. раздел 8).
- Перехватываемый метод идентифицирован: vtable-смещение
  +0x70 = 28-й метод IDirectDrawSurface = SetClipper.
- Цепочка вызовов восстановлена по V2 и V1:
  hota.dll, трамплины patcher_x86, диспетчер
  sub_10010CE0, A0_DirectDrawInit_sub_601AB0,
  перехваченный SetClipper. Обёртка первичной
  поверхности создаётся через sub_600BB0(1).
- Ни одна из функций, использующих dword_1004C9EC,
  не проверяет его на NULL (проверено по всем
  12 xref глобала).
- Кросс-версионная семья: 11 логов в 8 версиях HD-мода
  (5.6 R37 -- 5.7 R33) имеют идентичные регистры
  (EAX=0, ESI=0x90000000, EDI=0x8, EBX=0), адрес сбоя
  0x00000000, цепочку через h3hota.exe:0x00601C60 и
  состояние игры (Graphics.Mode=3, FullScreen=1, день 0,
  test.h3m). Это подтверждает единый дефект, не зависящий
  от версии HD-мода.

Ограничения:
- Точный листинг доступен только для версии 5.7 R33
  (адрес 0x189B2); для остальных 7 версий адреса
  (0x184C2, 0x18982, 0x18B72, 0x18C72) связаны по
  инвариантам и стабильному якорю h3hota.exe, но НЕ
  смаппены на инструкцию (листингов этих версий нет).
  Диагноз по ним -- по идентичности сигнатуры, не по
  прямому чтению кода каждой версии.
- Происхождение 698808=0 установлено под winedbg: флаг
  не обнуляется активно -- A0_DirectDrawInit выполняется
  ДО чтения настройки из реестра (запись по 0x4EDD22),
  и ни одна инструкция обнуления HD-мода не срабатывает
  до инициализации; 698808=0 -- неинициализированное
  BSS-значение. Оконная ветка при ранней инициализации --
  норма. Вопрос «что обнуляет флаг» снят.
- Верификация под winedbg (Wine 11.0, h3hota_HD.exe,
  Graphics.Mode=3) ПОДТВЕРДИЛА: 698808=0 на входе в
  A0_DirectDrawInit (оконная ветка игры), перехватчик
  sub_100189A0 достигается. Краш под Wine НЕ
  воспроизводится: dword_1004C9EC = 0x411b778 (объект
  создан, т.к. sub_100182C0 идёт по полноэкранному пути --
  бит [arg_0+68h] & 0x200 под Wine установлен). Таким
  образом, условие (а) оконной ветки игры подтверждено
  рантаймом; условие (б) оконного пути sub_100182C0
  (бит сброшен) на Windows при Graphics.Mode=3 установлено
  по тому факту, что в краш-логах dword_1004C9EC = 0
  (EAX=0), т.е. объект не создан. Два остатка, не
  закрываемые без Windows-отладчика: (1) прямое значение
  бита [arg_0+68h] & 0x200 на Windows не измерялось (под
  Wine оно установлено); (2) не различено, dword_1004C9EC=0
  на Windows -- это оконный путь (бит сброшен, объект не
  создавался) или полноэкранный путь с неудачей создания
  (различимо по dword_1004C9D8: в оконном пути тоже 0).
- Трамплины patcher_x86 (0x02C2xxxx, 0x02C5xxxx,
  0x02DCxxxx) не мапятся на листинг -- это
  рантайм-стабы, их содержимое недоступно.
- Полезность лога ВЫСОКАЯ: дефект полностью локализован
  (оконный путь sub_100182C0 не создаёт dword_1004C9EC,
  используемый перехватчиком SetClipper), условие
  активации установлено (Graphics.Mode=3), точечный фикс
  возможен; корень находится в модуле HD-мода (_HD3_.dll).

ВЫВОД
-----
Виновник: HD-мод (_HD3_.dll).

Перехватчик sub_100189A0 (слот +0x74 таблицы
перехватчиков, замещает SetClipper -- vtable-метод
поверхности +0x70) использует глобальный указатель

не создаёт вовсе, поэтому перехватчик читает память по
адресу 0x00000000. Дефект детерминирован в растягиваемых
режимах и подтверждён 11 логами в 8 версиях HD-мода.
