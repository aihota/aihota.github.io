====================================================================
АНАЛИЗ ВЫЛЕТА HD_HOTA.dll+0x1C5D37 (перечитывание memmove при записи сейва карты)
====================================================================

Модель: Qwen 3.8
Дата: 29.07.2026
Заключение: данные клетки карты в h3hota.exe битые; при записи сейва
memmove в потоке HD-мода перечитывает конец буфера-источника. Один
дефект в сборках HD 5.6 R30 — 5.7 R33 (адрес memmove плавает).

КРАТКОЕ РЕЗЮМЕ
--------------
Игра сохраняет карту в сейв. Функция h3hota.exe
A0_GameMap_Savegame_WriteCellsLevel обходит клетки карты и для каждой
пишет её массив данных (от указателя [edi+12h] до границы [edi+16h])
по 4 байта через виртуальный метод записи потока. HD-мод подменил этот
метод своей обёрткой sub_109DFC0: она передаёт указатель данных и размер
внутреннему объекту потока, а тот копирует данные в буфер потока через
memmove. Сбой происходит в memmove, в цикле CopyUpDwordLoop, на
инструкции mov edx, [esi] — чтение очередного dword из источника.
Источник (ESI) уходит за пределы доступной памяти двумя способами: либо
буфер данных клетки обрывается ровно на границе страницы и 4-байтное
чтение цепляет соседнюю недоступную страницу (дамп 2: ESI = 0x14E54FFE,
сбой по 0x14E55000), либо сам указатель данных мусорный или около-нулевой
(дамп 1: ESI = 0x0000FFFF). Регистры EAX = 4, ECX = 1, EDX = 4, EBX = 4
одинаковы в обоих дампах — это один и тот же путь, копирование хвоста
в 4 байта (один dword). Корень — в данных клетки карты (h3hota.exe, код
HotA): функция записи сейва берёт указатель и длину данных клетки без
проверки, и когда они битые, memmove перечитывает источник. Виновник
данных — HotA; memmove и поток HD-мода лишь исполняют чужие данные.
Это один дефект: тот же механизм и те же регистры повторяются в шести
сборках HD (адрес memmove плавает: 0x17A767 / 0x174C47 / 0x176317 /
0x1763B7 / 0x178E17 / 0x1C5D37), всего 8 логов.

1. Исходные данные
------------------
Уникальных вылетов: 2 в этой серии; семейство из 6 адресов / 8 логов
Класс сбоя: чтение/запись за концом буфера (перечитывание источника memmove)
Версия HotA: 1.8.0 (оба дампа)
Версии HD-мода: 5.7 R33 (оба дампа серии); семейство: 5.6 R30,
    5.7 RC2, RC10, RC11, R12, R33
Полезность лога для исправления: средняя
Подсистема: запись сейва карты

Исключение: EXCEPTION_ACCESS_VIOLATION, чтение по адресу (read of
    address) — в обоих дампах.
Контекст-инвариант: EAX = 4, ECX = 1, EDX = 4, EBX = 4; ESI = адрес
    сбоя (источник memmove), EDI = приёмник (буфер потока).

3. Сопоставление адресов (семейство)
------------------------------------
Тот же механизм и те же регистры (EAX = 4, ECX = 1, EDX = 4, EBX = 4,
чтение по адресу, ESI = адрес сбоя) встречаются в шести сборках HD.
Адрес сбоя — это положение memmove (CopyUpDwordLoop) в данной сборке;
между сборками функция смещается по образу, поэтому адрес плавает.
У всех логов семейства в стеке одна и та же функция записи сейва
h3hota.exe (004FEAE0 / 004FE590).

Адрес       HD-версия   ESI (адрес сбоя)          Сеть    День     Карта
----
0x17A767    5.6 R30     0x01CE0894                да      1 11     Vial of Life.h3m
0x174C47    5.7 RC2     0x00F67000 (граница)      да      1 11     (нет в логе)
0x176317    5.7 RC10    0x7A8800F3                да      1 11     (нет в логе)
0x1763B7    5.7 RC11    0x0FF20000 / 0x0C450000   нет     1 11-12  {Default}
0x178E17    5.7 R12     0x00200000 (граница)      нет     3 44     {Default}
0x1C5D37    5.7 R33     0x0000FFFF / 0x14E55000   да/нет  1 35     Jebus Outcast / {Default}

Значения ESI распадаются на две группы. Часть логов даёт точные границы
страниц (0x0FF20000, 0x0C450000, 0x00200000, 0x00F67000, 0x14E55000) —
буфер данных клетки обрывается на границе страницы, и чтение 4 байт
цепляет соседнюю недоступную страницу (перечитывание за конец буфера).
Другая часть — мусорные или около-нулевые указатели (0x7A8800F3,
0x01CE0894, 0x0000FFFF) — сам указатель данных клетки битый. Обе группы
— одно явление: поле данных клетки ([edi+12h]/[edi+16h]) не описывает
доступный буфер.

Формула сопоставления стандартная: IDA_addr = runtime_addr - load_base
+ imagebase (базовый адрес образа HD_HOTA.dll = 0x01000000). Для R33:
адрес сбоя 0x1C5D37 -> IDA 0x011C5D37 (CopyUpDwordLoop внутри _memmove).

4. Верификация версии листинга
------------------------------
Листинг HD_HOTA.dll-5.7 R33 сверен по точке входа: RVA точки входа из
лога 0x1C4547 (entry point 0x04374547 минус адрес загрузки 0x041B0000)
соответствует процедуре DllEntryPoint листинга по адресу 0x011C4547.
Timestamp листинга 6A6186F1 (23.07.2026), Input SHA256
AB45D6B6F85373F32AAE925E5F06118205F96096189F121629A794D0C8C3DA61.
Инструкция краха mov edx, [esi] по 0x011C5D37 (CopyUpDwordLoop) в точности
воспроизводит наблюдаемое поведение (чтение dword из источника memmove).
Семейство сверено побайтно для двух сборок: в R12 адрес 0x178E17 = IDA
0x01178E17 — тот же CopyUpDwordLoop (mov edx, [esi], XREF _memmove+514),
функция _memmove начинается с 0x01178910, цикл лежит на смещении +0x507
от начала — в точности как в R33. Для RC11 (адрес 0x1763B7) имеющийся
листинг (timestamp 6A0FFF76, 22.05.2026) относится к ДРУГОЙ сборке, чем
лог (24.05.2026): сопоставленный адрес 0x011763B7 попадает в промежуток
перед свёрнутой функцией _memmove_0 (0x01176430), то есть побайтно краш
не сверяется — нужен листинг точной сборки RC11 (ограничение; регистры
и стек записи сейва совпадают). Для 5.6 R30 (0x17A767) и 5.7 RC2
(0x174C47) точных листингов нет; принадлежность к тому же циклу memmove
подтверждена идентичными регистрами, равенством ESI адресу сбоя и стеком
записи сейва.

5. Инструкция краша и адресная проверка
---------------------------------------
Краш — во встроенной CRT-функции _memmove HD_HOTA.dll, цикл копирования
dword вверх (CopyUpDwordLoop):

    .text:011C5D30 CopyUpDwordTest:
    .text:011C5D30                 mov     eax, ecx
    .text:011C5D32                 shr     ecx, 2
    .text:011C5D35                 jz      short CopyUpByteTest
    .text:011C5D37 CopyUpDwordLoop:                    ; CODE XREF: _memmove+514
    .text:011C5D37                 mov     edx, [esi]  ; <- КРАШ: чтение из источника
    .text:011C5D39                 mov     [edi], edx  ; запись в приёмник (буфер потока)
    .text:011C5D3B                 add     edi, 4
    .text:011C5D3E                 add     esi, 4
    .text:011C5D41                 sub     ecx, 1
    .text:011C5D44                 jnz     short CopyUpDwordLoop

ESI — источник (данные клетки), EDI — приёмник (буфер потока), ECX —
счётчик dword. На момент краха ECX = 1, EAX = 4: копируется хвост в
4 байта (один dword), и первое же чтение из источника сбоит.

Назначение регистров подтверждено прологом memmove (R33):
    .text:011C5832  mov  esi, [esp+8+Src]    ; ESI = аргумент-источник (Src)
    .text:011C583A  mov  edi, [esp+8+arg_0]  ; EDI = аргумент-приёмник (dest)
То есть ESI несёт указатель, переданный вызывающим кодом как источник
копирования. Обёртка потока sub_109DFC0 передаёт внутреннему методу
записи указатель данных клетки (push [ebp+arg_0]) и размер 4 (push
[ebp+arg_4]) без изменения; метод записи копирует данные в буфер потока,
поэтому источник memmove — данные клетки, приёмник — буфер потока. Это
видно и по дампам: EDI (приёмник/буфер) во обоих логах — живой адрес кучи
(0x25391B28, 0x11A71E3E), тогда как ESI (источник/данные клетки) битый.
Следовательно, бит именно источник — данные клетки, а буфер потока HD-мода
исправен и виновником не является.

Адресная проверка (для string/CRT-помощников: регистр источника равен
адресу сбоя):
    Дамп 1: ESI = 0x0000FFFF, адрес сбоя 0x0000FFFF = ESI + 0. Чтение
        dword начинается в ESI; первый же байт лежит в NULL-зоне
        (0x00000000-0x0000FFFF) — сбой по самому ESI. Сошлось.
    Дамп 2: ESI = 0x14E54FFE, адрес сбоя 0x14E55000 = ESI + 2. Чтение
        dword по ESI охватывает 0x14E54FFE-0x14E55001 и пересекает
        границу страницы 0x14E55000; первые 2 байта доступны, сбой по
        границе страницы. Сошлось.
По всем логам семейства адрес сбоя равен ESI (для чтений, начинающих
в недоступной странице) либо ESI + 2 (для чтений, пересекающих границу
страницы). Проверка сошлась для всех 8 логов.

6. Цепочка вызовов
------------------
Фактический стек (V2 + V1), общий для обоих дампов:

    h3hota.exe  A0_GameMap_Savegame_WriteCellsLevel_sub_4FEAE0
        004FECC1  call dword ptr [edx+8]   ; поток->write(&данные[idx], 4)
        004FECC4  cmp eax, 4               ; кадр V2: 004FECC4
    HD_HOTA.dll  sub_109DFC0 (обёртка потока HD-мода)
        0109DFD1  call dword ptr [eax+8]   ; внутренний буфер->дописать(arg_0, arg_4)
        0109DFD4  add dword_12143DC, eax   ; кадр V2: +0x9DFD4 (только дамп 1)
    HD_HOTA.dll  sub_1045D70 (допись растущего буфера, vtable off_12001A4[+8])
        01045E3F  push [ebp+Src]           ; Src = arg_0 = указатель данных клетки
        01045E45  call _memmove            ; memmove(буфер+использовано, данные, 4)
    HD_HOTA.dll  _memmove
        011C5D37  mov edx, [esi]           ; КРАШ (CopyUpDwordLoop)

Функция записи сейва h3hota.exe обходит массив описателей клеток (edi
шагает по клеткам с шагом 0x26 байт) и для каждой клетки пишет её массив
данных: указатель данных [edi+12h], граница [edi+16h], число dword =
([edi+16h] - [edi+12h]) / 4. Каждый dword пишется отдельным вызовом
виртуального метода записи потока (push 4; push &данные[idx]; call
[edx+8]). HD-мод подменил объект потока: обёртка sub_109DFC0 достаёт
внутренний объект по [this+4]+68h и передаёт ему указатель данных и
размер без изменения (push arg_4; push arg_0; call [vtable+8]), накапливая
число записанных байт в глобальной переменной dword_12143DC. Внутренний
объект — растущий байтовый буфер (vtable off_12001A4; указатель буфера
[+10Ch], использовано [+108h], ёмкость [+114h]; создаётся в sub_109A7E0
с начальным буфером 1 МиБ через отладочный аллокатор sub_1001A30). Его
метод дописи sub_1045D70 копирует пришедшие данные в конец буфера вызовом
memmove(буфер + использовано, Src = arg_0, Size) — источник memmove здесь
в точности равен указателю данных клетки, переданному из h3hota. Сбой
происходит в этом memmove, когда указатель данных клетки битый. Тот же
класс буфера участвует в аллокатор-семействе HD_HOTA.dll+0x1A4E: там он
падает при росте (отказ sub_1001A30), здесь — при дописи (перечитывание
источника); дефекты разные, объект один.

Кадр обёртки +0x9DFD4 виден в V1/V2 только дампа 1; в дампе 2 обходчик
стека его пропустил (кадр мал, без bp-рамки у внутреннего метода), но
идентичные регистры EAX/ECX/EDX/EBX и тот же стек записи сейва подтверждают
один и тот же путь. Промежуточные кадры в области 0x02D0xxxx (дамп 1) /
0x0291xxxx (дамп 2) — трамплины patcher_x86 (исполняемая память без
модуля), адреса загрузки плавают между запусками.

7. Анализ регистров и группировка
---------------------------------
Инварианты по обоим дампам серии (и по всем 8 логам семейства):
    EAX = 4  — число байт хвоста (mov eax, ecx перед shr ecx, 2).
    ECX = 1  — счётчик dword в CopyUpDwordLoop (4 байта = 1 dword).
    EDX = 4  — Size: в прологе memmove mov edx, ecx (ecx = Size = 4);
               на коротком пути (Size < 32 -> сразу CopyUpDwordMov)
               не перезаписывается до инструкции краха.
    EBX = 4  — Size в методе дописи sub_1045D70 (mov ebx, [ebp+Size]);
               memmove сохраняет его через push ebx.
    ESI      — источник memmove = данные клетки; равен адресу сбоя
               (или на 2 меньше при пересечении границы страницы).
    EDI      — приёмник memmove = буфер потока (разный, служебный).
Все четыре регистра однозначно выводятся из Size = 4 на пути дописи
sub_1045D70 -> memmove (h3hota пишет по 4 байта на клетку), то есть
инвариант — отпечаток именно этого пути, а не случайное совпадение.
Путь РОСТА буфера в sub_1045D70 (memmove(new, old, использовано) при
used + Size > ёмкость ~1 МиБ) исключён: его memmove имел бы Size =
использовано (велик, ECX >> 1), тогда как ECX = 1 отвечает дописи Size = 4.
Нарушение доступа — всегда ЧТЕНИЕ (read of address), в отличие от
аллокатор-семейства HD_HOTA.dll+0x1A4E (запись, EAX = 0): это другой
дефект, хотя и в том же конвейере записи сейва (общий кадр 004FEAE0).
Группировка — по непосредственному вызывающему коду выше memmove
(обёртка потока sub_109DFC0, кадр +0x9DFD4) и по регистровому инварианту;
адрес самого memmove как идентификатор не используется (он плавает по
сборкам).

8. Первопричина
---------------
Ближайшая причина: memmove в потоке записи HD-мода перечитывает источник
— массив данных очередной клетки карты. Копирующая функция исправна; она
копирует ровно столько, сколько ей передал вызывающий код, и падает,
когда источник короче запрошенного либо указывает в недоступную память.
Глубинная причина — в данных клетки карты (h3hota.exe, код HotA). Битое
«поле данных» — это вектор списка объектов клетки: описатель клетки
(_ObjCell_, 0x26 байт) несёт по смещению +0xE динамический массив
(_Vector1_: указатель data = +12h, конец end = +16h, ёмкость +1Ch).
Функция A0_GameMap_Savegame_WriteCellsLevel берёт из описателя клетки
указатель data [edi+12h] и границу end [edi+16h] и пишет
([edi+16h]-[edi+12h])/4 dword, не сверяя указатель и длину с реально
выделенным буфером. Когда вектор списка объектов битый, происходит одно
из двух:
    - указатель [edi+12h] указывает в недоступную память (мусорные
      0x7A8800F3, 0x01CE0894; около-нулевой 0x0000FFFF) — чтение сбоит
      сразу;
    - длина ([edi+16h]-[edi+12h]) превышает фактический буфер, и обход
      уходит за его конец в соседнюю недоступную страницу (границы
      0x0FF20000, 0x0C450000, 0x00200000, 0x00F67000, 0x14E55000).
Почему вектор списка объектов становится битым — по сокращённым
минидампам не видно; нужна конкретная клетка и значения её полей (полный
дамп кучи либо отладчик). Писатель вектора проверен статически: список
объектов клетки растит A0_GameMap_Cell_AddObjectInfo_sub_505880 (вызывается
из A0_Place_Object_SetCells_sub_506170 при размещении объекта на клетке),
ручной реаллокацией operator new(4*ёмкость) / копия / operator delete.
Формула роста ёмкости v34 = v32 + v33, где v32 = max(число_элементов, 1)
и v33 = число_элементов, то есть новая ёмкость ≈ 2·число_элементов
(геометрическое удвоение); элементов после дописи число_элементов+1, и
2·число_элементов ≥ число_элементов+1 при числе_элементов ≥ 1 — выделение
всегда достаточно. Систематического бага ёмкости/длины в писателе нет
(отрицательный результат). Значит, вектор строится правильно, а битым
становится во время работы — порча уже построенного вектора (обращение к
освобождённой клетке, перехлёст извне либо гонка при записи сейва), а не
ошибка заполнения. Виновник данных — HotA (структура клеток карты в
h3hota.exe); HD-мод — место проявления (memmove в его потоке записи).
Обёртка потока HD-мода данные не искажает (передаёт указатель и размер
как есть), поэтому сбой не является багом HD-мода.

9. Условия сбоя
---------------
    Сбой привязан к записи сейва карты (автосохранение / турнирный
        сейв / ручное сохранение), не к отрисовке и не к сети.
    Network Game: встречается и в сетевых (дамп 1, 0x176317, 0x174C47,
        0x17A767), и в одиночных партиях (дамп 2, 0x1763B7, 0x178E17).
    День/карта: разбросаны (дни 1 11, 1 12, 1 35, 3 44; карты Jebus
        Outcast, {Default}, Vial of Life) — к конкретной карте не привязан.
    Версии HD-мода: 5.6 R30 — 5.7 R33 (охват порядка полугода); HotA 1.8.0.
    Graphics.Mode (5 и 7), разрешение и число потоков различаются и на
        сбой не влияют (краш не в отрисовке).
    Адрес сбоя зависит только от сборки HD-мода (положение memmove).

10. Сводные данные
------------------
Адреса сбоя: HD_HOTA.dll+0x1C5D37 (2 лога); семейство: +0x17A767 (1),
    +0x174C47 (1), +0x176317 (1), +0x1763B7 (2), +0x178E17 (1) — всего
    8 логов.
Модуль места сбоя: HD_HOTA.dll (HD-мод) — memmove в потоке записи.
Функция: _memmove (CopyUpDwordLoop, mov edx,[esi]); вызывается внутренним
    методом записи потока через обёртку sub_109DFC0, которую зовёт
    A0_GameMap_Savegame_WriteCellsLevel_sub_4FEAE0 (h3hota.exe).
Подсистема: запись сейва карты
Класс сбоя: чтение/запись за концом буфера
Виновный модуль: HotA (h3hota.exe) — источник битых данных клетки;
    HD-мод — место проявления (memmove).
Были до 1.8.0: семейство наблюдается в HD 5.6 R30+ при HotA 1.8.0;
    дампов HotA до 1.8.0 нет, ретро-флаг не подтверждён.
Были в SoD: не подтверждено — функция записи уровня клеток
    (A0_GameMap_Savegame_WriteCellsLevel) выглядит HotA-специфичной
    (расширение формата сейва); в чистом SoD не проверялась.

Признаки поиска в других версиях:
    Контекст-инварианты: EAX = 4, ECX = 1, EDX = 4, EBX = 4; нарушение
        доступа на чтение; ESI равен адресу сбоя (или на 2 меньше при
        пересечении границы страницы).
    Стек: h3hota 004FEAE0 / 004FE590 (запись сейва) над обёрткой потока
        HD-мода (кадр +0x9DFD4 в R33) над memmove.
    Адрес краха = положение CopyUpDwordLoop (mov edx,[esi]) в memmove
        данной сборки; искать в листинге соответствующей версии.

11. Воспроизведение вылета
--------------------------
Вылет недетерминирован: зависит от того, окажется ли поле данных
очередной клетки битым на момент записи сейва. Вероятностный путь:
партия под HD-модом 5.6 R30+ / 5.7 (сетевая или одиночная), в которой
происходит запись сейва карты (автосохранение включено: <Autosave> = 1,
<Misc.TournamentSaver> = 1 в логах); сбой срабатывает, когда описатель
одной из клеток несёт битый указатель или длину данных. Целевые инварианты
ловимого дампа: EAX = 4, ECX = 1, EDX = 4, EBX = 4, чтение по адресу,
ESI = адрес сбоя; адрес краха = CopyUpDwordLoop memmove для данной сборки.
Для различения мусорного указателя и завышенной длины — полный дамп кучи
(<Sys.FullDump> = 1): осмотреть описатель сбойной клетки ([edi+12h] /
[edi+16h]) и фактический размер выделенного буфера данных.

Достоверность и ограничения
---------------------------
Подтверждено:
    - Механизм: memmove (CopyUpDwordLoop, mov edx,[esi]) перечитывает
      источник при записи сейва карты; доказано дизассемблером, регистрами
      (EAX = 4, ECX = 1, EDX = 4, EBX = 4) и адресной проверкой (ESI =
      адрес сбоя или ESI + 2 на границе страницы) — сошлось для всех 8 логов.
    - Версия листинга R33 сверена по точке входа (DllEntryPoint 0x011C4547
      = RVA 0x1C4547 из лога).
    - ESI = источник копирования подтверждено прологом memmove (R33:
      mov esi,[esp+8+Src]; mov edi,[esp+8+arg_0]); в дампах EDI (буфер
      потока) — живой адрес кучи, ESI (данные клетки) — битый, то есть
      бит источник, а буфер HD-мода исправен.
    - Функция записи: h3hota 004FECC4 = A0_GameMap_Savegame_WriteCellsLevel_sub_4FEAE0;
      обёртка потока HD-мода sub_109DFC0 передаёт указатель и размер
      внутреннему объекту без изменения (данные не искажает).
    - Непосредственный вызывающий код memmove разрешён статически (резолв
      vtable): обёртка sub_109DFC0 вызывает vtable[+8] внутреннего буфера =
      sub_1045D70 (vtable off_12001A4); его путь дописи делает memmove(
      буфер+использовано, Src = arg_0, Size), то есть источник memmove в
      точности равен указателю данных клетки, переданному из h3hota.
    - Семейство: 6 адресов / 8 логов, один механизм и регистры, адрес
      memmove плавает по сборкам 5.6 R30 — 5.7 R33; у всех логов в стеке
      функция записи сейва 004FEAE0 / 004FE590. Для R12 (0x178E17) и R33
      (0x1C5D37) крах совпадает с CopyUpDwordLoop побайтно (цикл на
      смещении +0x507 от начала _memmove в обеих сборках).
    - Локализация и писатель: битое поле — вектор списка объектов клетки
      (_ObjCell_+0xE, data +12h / end +16h); писатель вектора
      A0_GameMap_Cell_AddObjectInfo_sub_505880 проверен статически — рост
      ёмкости корректен (удвоение, ≥ число_элементов+1), систематического
      бага длины/ёмкости нет; следовательно, корень — рантайм-порча уже
      построенного вектора, а не ошибка его заполнения.
Ограничения:
    - Виновные данные — в h3hota.exe (HotA, структура клеток карты);
      точка исправления — у разработчиков HotA. HD-мод — место проявления.
    - Конкретный источник рантайм-порчи вектора (которая клетка, что её
      портит — обращение к освобождённой клетке, перехлёст извне или гонка
      при записи сейва) по сокращённым минидампам не виден — нужен полный
      дамп кучи либо отладчик.
    - RC11 (0x1763B7): имеющийся листинг другой сборки, чем лог, побайтно
      краш не сверялся (нужен листинг точной сборки RC11); для 5.6 R30
      и 5.7 RC2 точных листингов нет — принадлежность по регистрам и стеку.
    - Кадр обёртки +0x9DFD4 виден только в дампе 1; в дампе 2 его пропустил
      обходчик стека, путь подтверждён идентичными регистрами.
    - Полезность средняя: падающая функция (memmove/поток) исправна, корень
      выше по стеку (данные клетки HotA); точечный фикс по статике невозможен.

ВЫВОД
-----
Вылет HD_HOTA.dll+0x1C5D37 — перечитывание источника в memmove при записи
сейва карты. Игра сохраняет карту (h3hota.exe, функция
A0_GameMap_Savegame_WriteCellsLevel), обходит клетки и пишет их массивы
данных через поток; HD-мод подменил метод записи обёрткой sub_109DFC0,
внутренний объект потока копирует данные в буфер через memmove. Когда
указатель или длина данных очередной клетки битые, memmove уходит за конец
доступной памяти (ESI = адрес сбоя; регистры EAX = 4, ECX = 1, EDX = 4,
EBX = 4 одинаковы во всех логах). Это один дефект: адрес memmove плавает
по сборкам HD (0x17A767 / 0x174C47 / 0x176317 / 0x1763B7 / 0x178E17 /
0x1C5D37, всего 8 логов, 5.6 R30 — 5.7 R33). Источник битых данных —
структура клеток карты в h3hota.exe (HotA); HD-мод лишь исполняет чужие
данные и виновником не является. Корневая причина порчи данных (которая
клетка и почему) по сокращённым минидампам не определяется — нужен полный
дамп кучи.
