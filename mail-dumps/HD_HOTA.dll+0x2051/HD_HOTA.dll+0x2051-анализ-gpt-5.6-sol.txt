АНАЛИЗ ВЫЛЕТА  HD_HOTA.dll+0x2051  (локализация и таблицы текстов HD-мода)
================================================================================

    Модель: GPT-5.6 Sol
    Дата:   30.08.2026
    Заключение: HD_HOTA.dll передаёт нулевой контейнер таблицы текстов в
                общий поиск и читает его поле +4 без проверки.


КРАТКОЕ РЕЗЮМЕ
--------------

Что произошло:

    В 2/2 TXT целевой серии зафиксирован один адрес HD_HOTA.dll+0x2051.
    Два события относятся к HD 5.7 R1 и 5.8 R8; четыре физические копии TXT
    во всём корпусе после событийной дедупликации дают те же два события.

Локальный механизм:

    Инструкция cmp [edi+4], esi выполняется при EDI=0 и читает 0x00000004.
    Механизм выведен из точных листингов обеих сборок; для 5.8 R8 его также
    подтверждают 145 совпавших байт DMP и локального бинарника.

Охват семейства:

    Общими являются аварийный приёмник, NULL-контейнер и подсистема таблиц
    текстов. Caller'ы, ключи и непосредственные источники различаются, поэтому
    максимальная подтверждённая связь — общий локальный механизм.

Граница доказанности:

    Происхождение состояния частично установлено, причинная глубина — L1.
    Для 5.8 R8 есть сообщение об отсутствии #en/Files.ini; автор нуля и единая
    глубокая первопричина двух событий не установлены.

2. Проверка листинга и адреса
-----------------------------

Сверка листинга:

- HD_HOTA.dll-5.7 R1.txt: SHA-256 листинга
  de5433bd8378834ac12ab9ea1b19a09b110adfcb529ad01bd7fbb428166040ee,
  imagebase 0x01000000; версия в заголовке соответствует HD 5.7 R1.
- HD_HOTA.dll-5.8-R8.txt: SHA-256 листинга
  88f06be651a395fdc165d78260574dd24d916913f56739d6ff0a415b45d78d25,
  Input SHA-256 EABF3EF1193A6BCD3E5B63EB78D8D13F6160CE5EB85EF2F982CAE33D4A97D715,
  imagebase 0x01000000, метка времени 0x6A8F1466. Input SHA совпадает с
  HD_HOTA.dll; у бинарника SizeOfImage=0x11FA000.

Проверка нормализации:

- 5.7 R1: 0x0B272051 - 0x0B270000 + 0x01000000 = 0x01002051.
- 5.8 R8: 0x04382051 - 0x04380000 + 0x01000000 = 0x01002051.
- В обеих сборках это sub_1002040+0x11, точная граница инструкции.

Точный участок:

    .text:01002049  mov   edi, ecx
    .text:0100204B  test  ebx, ebx
    .text:0100204D  jz    short loc_100207B
    .text:0100204F  xor   esi, esi
    .text:01002051  cmp   [edi+4], esi      ; ВЫЛЕТ
    .text:01002054  jle   short loc_100207B

Функция проверяет строковый аргумент EBX, но не объект ECX/EDI. Затем она
перебирает массив записей, выбирает тип 4, сравнивает строки через stricmp и
возвращает индекс либо -1. В обеих сборках совпадают все 40 инструкций,
включая операнды; функция заканчивается инструкцией retn 4, начинающейся
по 0x0100208B.

Проверка байтов:

- DMP 5.8 R8 содержит 145 байт по VA 0x04382040..0x043820D0. Все они
  совпадают с HD_HOTA.dll, включая окно точки:
  55 8B EC 53 8B 5D 08 56 57 8B F9 85 DB 74 2C 33 F6 39 77 04 7E 25.
- Число 145 относится ко всему проверенному окну. sub_1002040 заканчивается
  инструкцией, начинающейся по 0x0438208B; хвост с 0x0438208E содержит
  выравнивание и начало следующей функции. Это уточнение не меняет
  доказательство байтов вокруг точки сбоя.
- Паспорт модуля DMP (метка времени 0x6A8F1466, SizeOfImage 0x11FA000)
  совпадает с локальным бинарником. Полный SHA загруженного модуля из
  усечённого DMP недоступен и потому не заявляется.

Регистры 5.7 R1:

    ESI=0x00000000  EDI=0x00000000

Регистры 5.8 R8:

Для 5.8 R8 эти регистры относятся к текстовому контексту. Их нельзя

3. Точка сбоя
-------------

Локальный механизм:

- ECX переносится в EDI по 0x01002049.
- В обоих TXT ECX=EDI=0.
- Инструкция cmp [edi+4], esi пытается прочитать счётчик элементов объекта.
- Эффективный адрес: 0x00000000 + 0x4 = 0x00000004, точно совпадает с
  Information: read of address: 0x00000004.

Извлечённые значения:

Параметр                         5.7 R1              5.8 R8
-------------------------------  ------------------  ------------------
Адрес/операция                   0x00000004 / read   0x00000004 / read
ECX -> EDI                       0 -> 0              0 -> 0
Непосредственный caller         +0x925CB            +0x28932
Текстовая таблица               HD.Ini.Txt          HD.Ini.Txt.En
Искомый ключ                     CodePage            SwapMgr.TransferOne

Интерпретация стека и регистров:

- Негодное значение — сам указатель на контейнер, а не индекс цикла и не
  строковый аргумент. ESI=0 здесь штатно создан инструкцией xor esi,esi.
- Оболочки ненулевые: EAX=0x077BCCAC в 5.7 R1 и EAX=0x0353DDFC в
  5.8 R8. Команда mov esi,[eax] загружает ноль именно из поля +0 оболочки.
  Следовательно, запись HD.Ini.Txt* найдена, но указатель на таблицу внутри
  неё равен нулю. В пути 5.7 R1 отсутствие самой записи HD.Ini.Txt после
  поиска и попытки создания привело бы к int 3 по 0x010925B7. Фактический
  вылет ниже по пути подтверждает: запись реестра получена, но её поле +0
  осталось нулевым.
- sub_1002040 сохраняет аргумент String1 в EBX. Нормализация EBX по базе
  модуля даёт 0x011A5B24 в 5.7 R1, где лежит строка "CodePage", и
  0x011FB978 в 5.8 R8, где лежит строка "SwapMgr.TransferOne". Имена
  ключей подтверждены не только листингом, но и регистрами в момент сбоя.
- Значение EDI=0 полностью объясняет аварийный адрес. Для обращения после
  освобождения, выхода за границы кучи, гонки либо случайного битого адреса
  доказательств нет.
- Совпадение EDI=0 в 2/2 уникальных событиях и одинаковая инструкция в двух
  версиях закрепляют локальный механизм, но не автора нулевого состояния.


4. Цепочка вызовов и контекст
-----------------------------

Путь 5.7 R1:

    -> _hd3_.dll+0x10C87
    -> HD_HOTA!Start
    -> получить переменную "HD.Ini.Txt" через реестр
    -> virtual +8 возвращает оболочку; mov esi,[eax] даёт 0
    -> HD_HOTA+0x925CB: sub_1002040("CodePage"), тот же аварийный приёмник

Путь 5.8 R8:

    -> HD_HOTA!sub_10282C0, обработка действия интерфейса
    -> 0x0102889B: проверить клавишу 0x12 (VK_MENU, Alt)
    -> sub_10030B0: GetKeyState и возврат старшего бита состояния
    -> Alt не удерживается: jz по 0x010288B2 ведёт в loc_102891D
    -> получить "HD.Ini.Txt.En" через sub_1002EE0
    -> 0x0102892E: mov esi,[eax] даёт 0
    -> HD_HOTA.dll+0x28932: sub_1002040("SwapMgr.TransferOne"), ВЫЛЕТ

Соседний путь того же обработчика:

    -> Alt удерживается: переход jz не выполняется
    -> 0x010288B4: получить "HD.Ini.Txt.En" через sub_1002EE0
    -> 0x010288C5: mov esi,[eax] без проверки ESI на ноль
    -> HD_HOTA.dll+0x288C9: sub_1002040("SwapMgr.TransferOneAlt")
    -> HD_HOTA.dll+0x288D1: sub_1004180 с тем же ESI

В ветви с Alt затем так же читается HD.Ini.Txt и без проверки выполняются
вызовы по 0x010288F4 и 0x010288FC. В фактической ветви без Alt вторая такая
пара находится по 0x0102895D и 0x01028965. Значит, обе ветви и обе таблицы
имеют одинаковый незащищённый контракт, а вылет зафиксирован на первом
вызове английской таблицы в ветви без Alt.

После успешного поиска каждая пара вызвала бы типизированную функцию доступа
(sub_1004080 в 5.7 или sub_1004180 в 5.8). Эти функции также ожидают
валидный контейнер. Поэтому одна проверка на ноль только внутри sub_1002040
замаскирует первую точку, но не восстановит контракт всей цепочки.


5. Первопричина
---------------

Доказанный локальный дефект:

- Потребитель таблицы текстов получает [value+0]=0 и без проверки передаёт
  это значение в ECX функции sub_1002040. Общий поиск безусловно читает
  [ECX+4].
- Ненулевой EAX в обоих событиях показывает, что оболочка записи существует,
  а отсутствует именно вложенный указатель на таблицу. В 5.8 R8 фактический
  вызов по 0x01028932 не проверяет результат mov esi,[eax].
- Соседняя ветвь SwapMgr.TransferOneAlt по 0x010288C9 имеет тот же изъян;
  последующие обращения к HD.Ini.Txt по 0x010288F4 и 0x0102895D также
  передают EDI без проверки на ноль. Изъян относится к контракту обеих
  ветвей, а не только к одному ключу.
- Перепись 5.8 R8 нашла 729 инструкций вызова sub_1002040 в 114 функциях.
  Это общая функция поиска, а не специальная функция одного действия.

Рабочая гипотеза:

- Для 5.8 R8 наиболее сильный upstream-кандидат — отказ загрузки английской
  таблицы: журнал до вылета сообщает "No Files.ini" для _HD3_Data/Lang/#en,
  а падающий путь сразу запрашивает HD.Ini.Txt.En. Это причинно совместимо с
  нулём, но источник записи поля в DMP не сохранён.
- Для 5.7 R1 ноль возникает во время Start при чтении HD.Ini.Txt/CodePage.
  Старого DMP и сообщения о последнем действии нет. Недостающий файл,
  преждевременная инициализация и другой отказ загрузчика остаются
  различимыми гипотезами.
- Общая глубокая первопричина двух событий не установлена: caller'ы и ключи
  разные. Подтверждён только один аварийный приёмник и механизм.

Исправление:

Исправление на стороне HD-мода:

- Ресурс HD.Ini.Txt* проверять на NULL до первого вызова или обращения.
- Если указатель равен 0, не вызывать поиск и функцию доступа, а вернуть
  безопасное значение по умолчанию.
- Нулевой путь должен восстановить временно изменённое состояние до возврата.
- Перед применением патча выполнить проверку байтовой сигнатуры каждой сборки.
- Сравнить до и после исправления: вызов одного ключа при отсутствующем
  Files.ini должен перейти от вылета к управляемому возврату.

- Проверять контейнер сразу после получения HD.Ini.Txt* и до вызовов
  sub_1002040/sub_1004080/sub_1004180.
- Одну и ту же проверку применять в ветвях с Alt и без Alt, для ключей
  SwapMgr.TransferOneAlt и SwapMgr.TransferOne, а также для последующего
  обращения к основной таблице HD.Ini.Txt.
- При отсутствии таблицы либо сформировать валидный пустой контейнер, либо
  вернуть безопасное значение по умолчанию. Для HD.Ini.Txt.En допустим
  контролируемый fallback к HD.Ini.Txt/литеральному ключу; для CodePage —
  явно выбрать документированное значение по умолчанию.
- Ошибку загрузки Files.ini поднять до уровня владельца ресурса и записывать
  table name, language directory, key и результат загрузчика.
- Не ограничиваться проверкой в sub_1002040: следующий accessor тоже
  разыменовывает тот же this, поэтому такой патч лишь передвинет вылет.

Дифференциальный тест:

- На исправленной сборке отсутствие #en/Files.ini должно приводить к одному
  диагностическому сообщению и безопасному резервному значению без AV.
- Действие SwapMgr проверить дважды: без Alt для SwapMgr.TransferOne и с
  удерживаемой Alt для SwapMgr.TransferOneAlt. Ни одна ветвь не должна
  передавать нулевой контейнер в sub_1002040 или sub_1004180.
- С установленным Files.ini должны сохраниться прежние тексты и поведение
  SwapMgr в обеих ветвях.
- Для пути 5.7 R1 отдельно проверить запуск с отсутствующей или нечитаемой
  основной таблицей: либо управляемый отказ запуска, либо безопасное значение
  по умолчанию, но не обращение к адресу 0x4.

7. Воспроизведение вылета
-------------------------

Тест A — подтверждение ресурса 5.8 R8:

1. На чистой копии HD 5.8 R8/HotA 1.8.1 сохранить рабочий #en/Files.ini.
2. Удалить или переименовать только этот файл и запустить ту же карту.
3. Выполнить действие без Alt, чтобы был выбран SwapMgr.TransferOne.
4. Повторить действие с удерживаемой Alt для SwapMgr.TransferOneAlt.
5. Вернуть Files.ini и повторить обе ветви как положительный контроль.

Тест B — проверка контракта:

1. Поставить breakpoint после sub_1002EE0 и до mov esi,[eax] в падающем пути.
2. Записать имя таблицы, EAX, [EAX], номер потока и стек.
3. При [EAX]=0 проследить последнюю запись этого поля и результат загрузчика.
4. Повторить для Start/HD.Ini.Txt/CodePage в сборке 5.7 R1 либо ближайшей
   воспроизводящей сборке.

Ожидаемый результат исправленной сборки:

- Нет EXCEPTION_ACCESS_VIOLATION на +0x2051; отсутствующая таблица даёт
  контролируемый fallback/default, а полный комплект файлов сохраняет
  прежний результат поиска.

Необходимая телеметрия:

- Полный дамп с кучей и данными, номер потока и полным CONTEXT падающего потока.
- Лог loader'а: requested table, language directory, key, file-open result,
  parser result, returned wrapper и [wrapper+0].
- Точка наблюдения на запись [wrapper+0] и стек последнего источника записи.
- Последний игровой шаг и воспроизводимость после перезапуска.


8. Достоверность и ограничения
------------------------------

Матрица уверенности:

- Точка сбоя: подтверждена
- Локальный механизм: выведен из листинга
- Происхождение состояния: частично установлено
- Охват семейства: подтверждён
- Уровень причинности: L1

Подтверждено:

- Адрес, операция и арифметика NULL+4 подтверждены в 2/2 уникальных событиях.
- Точная функция sub_1002040 содержит 40 инструкций. Между листингами
  5.7 R1 и 5.8 R8 совпадают мнемоники и операнды всех инструкций.
- Для 5.8 R8 Input SHA листинга совпадает с SHA локального бинарника; DMP
  содержит совпадающее 145-байтовое окно и совпадающий паспорт PE. Окно
  включает всю точку сбоя, но его хвост после 0x0438208D относится уже к
  выравниванию и следующей функции.
- В обоих фактических путях оболочка EAX ненулевая, а mov esi,[eax]
  загружает ноль из её поля +0. Ключи CodePage и SwapMgr.TransferOne
  дополнительно подтверждены адресами EBX в момент сбоя.
- Проверка VK_MENU по 0x0102889B выбирает между SwapMgr.TransferOne и
  SwapMgr.TransferOneAlt. В обеих ветвях результаты HD.Ini.Txt.En и
  HD.Ini.Txt передаются в sub_1002040 без проверки на ноль.
- Полная перепись 5.8 R8 нашла 729 инструкций вызова sub_1002040 в
  114 функциях; фактический +0x28932 присутствует как положительный контроль.

Отрицательные результаты:

- Покрытие: просмотрено 5589/5589 TXT; контрольный образец — оба известных
  первичных лога найдены тем же фильтром. Поиск завершён без усечения и
  ошибок чтения. Точный фильтр адреса дал одну distinct-сигнатуру и три
  SHA-дедуплицированные записи; ручная проверка восстановила четвёртый
  физический TXT — точную SHA-копию одного из старых файлов. После событийной
  дедупликации остаются два уникальных вылета.
- Сравнение с оригиналом SoD: N/A — sub_1002040 относится к собственной
  инфраструктуре HD-мода. В её 40/40 инструкциях нет malloc/new, установки
  vtable либо абсолютных вызовов h3hota.exe; фактический caller найден как
  положительный контроль переписи.
- Полный дамп 5.7 R1, пользовательский комментарий и управляемый повтор не
  найдены. Это ограничивает глубокий корень, но не локальную арифметику.

Ограничения:

- DMP 5.8 R8 — усечённый MiniDumpNormal: 35 диапазонов, 50628 байт памяти,
  без Memory64List, полной кучи, глобалов и прав страниц. Автор нулевой записи
  и жизненный цикл таблицы не восстанавливаются.
- ExceptionStream указывает номер потока 12900, тогда как ESP текстового контекста
  принадлежит стеку потока 4128. Наборы регистров и стеков не смешивались.
- Полного SHA загруженного в процессе HD_HOTA.dll из DMP нет. Доказательство
  5.8 опирается на совпадение метки времени и SizeOfImage и байтов функции с локальным
  бинарником, SHA которого совпадает с Input SHA листинга.
- Явное отсутствие #en/Files.ini сильно поддерживает гипотезу 5.8, но без
  трассировки источника записи не доказывает, что это единственное условие. Для события 5.7
  происхождение нуля остаётся открытым.
- UAF, повреждение кучи, гонка и одна общая первопричина для двух caller-путей
  не заявляются без новых данных.


ВЫВОД
-----

Контрольный расчёт:

    EDI = ECX = 0x00000000
    EDI + 4 = 0x00000004
    инструкция = cmp [edi+4], esi
    адрес исключения = 0x00000004, операция = чтение

Происхождение состояния:

    В 5.7 R1 ноль приходит из HD.Ini.Txt перед CodePage; в 5.8 R8 — из
    HD.Ini.Txt.En перед SwapMgr.TransferOne. Сообщение о #en/Files.ini
    поддерживает только второй путь. Последний источник записи не установлен.

Действия:

    Адресат: разработчики HD-мода.

    - Проверять контейнер у поставщика таблицы до поиска и следующей функции
      доступа.
    - Охватить ветви SwapMgr.TransferOne и SwapMgr.TransferOneAlt, а также
      обращения к HD.Ini.Txt.En и HD.Ini.Txt.
    - При нуле применять безопасную резервную таблицу либо значение по
      умолчанию.
    - Журналировать имя ресурса, ключ и путь файла.
    - Не ограничиваться проверкой внутри sub_1002040: следующая функция
      доступа разыменовывает тот же контейнер.

Критерий завершения:

    Исправленная сборка не падает на +0x2051 при отсутствующем Files.ini,
    выдаёт измеримое сообщение о резервном пути, а с полным комплектом файлов
    сохраняет прежний результат. Для L2 нужен полный дамп или точка наблюдения
    за последней записью нулевого поля.
