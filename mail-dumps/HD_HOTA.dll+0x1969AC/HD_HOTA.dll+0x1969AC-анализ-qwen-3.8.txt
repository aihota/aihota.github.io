АНАЛИЗ ВЫЛЕТА HD_HOTA.dll+0x1969AC (карта приключений)
====================================================================

Модель: Qwen 3.8
Дата: 29.07.2026
Заключение: HD-мод (HD_HOTA.dll) не проверяет результат выделения
памяти: функция восстановления кадра карты приключений получает от
operator new нулевой указатель и сразу пишет в него данные клеток.

КРАТКОЕ РЕЗЮМЕ
--------------
Игра строит рабочую копию карты приключений и просит под неё память.
Выделение заканчивается неудачей (operator new возвращает ноль), но
код результат не проверяет и начинает копировать клетки карты в
нулевой буфер. Первая же запись mov [edx],ecx при EDX = 0 роняет
процесс. Упавшая функция исправна во всём, кроме одного: она доверяет
указателю из operator new без проверки на ноль. Почему само выделение
завершилось отказом (исчерпание адресного пространства 32-битного
процесса либо аномальный размер запроса) — по сокращённому минидампу
не установить, это рантайм-вопрос; та же глубокая причина видна в
семействе вылетов отладочного аллокатора HD-мода.

5. Инструкция краша и адресная проверка
---------------------------------------
Точка сбоя — функция sub_11966B0 (восстановление кадра карты
приключений, внутреннее имя конфигурации HD.Af.RepareFunc),
смещение +0x2FC от начала. Падающая инструкция:

    .text:011969AC    mov     [edx], ecx

Это тело цикла, копирующего массив клеток карты. На каждой итерации
код читает одну клетку у движка и переносит 0x26 (38) байт в рабочий
буфер. Адрес приёмника вычисляется так:

    .text:011969A4    imul    edx, ecx, 26h     ; edx = индекс * 38
    .text:011969A7    mov     ecx, [esi]        ; ecx = данные клетки
    .text:011969A9    add     edx, [ebp+var_C]  ; edx += база буфера
    .text:011969AC    mov     [edx], ecx        ; запись в буфер

Приёмник EDX = var_C + индекс * 38. На первой итерации индекс равен
нулю (EBX = 0 — столбец, EDI = 1 — счётчик только что увеличен с
нуля, номер строки var_4 = 0), поэтому EDX = var_C. По контексту
EDX = 0x00000000, значит var_C = 0: база рабочего буфера нулевая.
Адресная проверка: эффективный адрес mov [edx],ecx равен EDX + 0 =
0x00000000, что в точности совпадает с адресом из поля Information
(write of address: 0x00000000). Проверка сошлась.
Записываемое значение ECX = 0xFFFFFFFF — это первые 4 байта клетки
карты, прочитанные из живой клетки (ESI = 0x16610024, исправный
указатель в кучу); источник данных не повреждён, бит именно приёмник.

7. Анализ регистров и группировка
---------------------------------
Инварианты единственного дампа:
    EDX = 0x00000000 — база рабочего буфера (var_C), он же адрес
        сбоя; равен нулю, потому что выделение вернуло ноль.
    ECX = 0xFFFFFFFF — данные первой клетки карты (записываемое
        значение), прочитаны из исправного источника ESI.
    ESI = 0x16610024 — указатель на клетку-источник, живой адрес
        кучи; поставщик данных (A0_GameMap_GetCell) отработал.
    EBX = 0x00000000 — индекс столбца (первая итерация цикла).
    EDI = 0x00000001 — счётчик элементов, увеличен с нуля непосред-
        ственно перед записью; подтверждает, что сбой на первом эле-
        менте буфера.
    EAX = 0x006783C8 — адрес глобала ширины карты A0_Map_X_Size
        (переиспользован в вычислении индекса после того, как
        послужил аргументом operator new).
Группировка не применяется (один дамп). Восстановленный размер
запроса: буфер имеет размер (число_слоёв + 1) * ширина * высота * 38
байт, где ширина и высота — глобалы движка A0_Map_X_Size (0x6783C8)
и A0_Map_Y_Size (0x6783CC), записываются при загрузке карты в
A0_AdvMgr_Init; число слоёв берётся из байта [0x699538 + 0x1FC48].
Для штатных карт это единицы мегабайт; фактические значения глобалов
в момент сбоя по сокращённому минидампу не прочитать (данные кучи
и BSS-состояние не сохранены), поэтому вопрос «разумный размер или
аномальный» остаётся открытым (см. «Достоверность и ограничения»).

8. Первопричина
---------------
Ближайшая причина — пропущенная проверка результата выделения
памяти. Функция выделяет рабочий буфер через operator new и
использует возвращённый указатель без проверки на ноль:

    .text:011968CD    push    eax              ; размер = (слоёв+1)*W*H*38
    .text:011968CE    call    esi              ; esi = 0x617492 = operator new
    .text:011968DB    mov     [ebp+var_C], eax ; var_C = результат (ноль при отказе)
    .text:011968E1    movzx   ecx, byte ptr [esi+1FC48h]
    .text:011968E8    add     ecx, 1
    .text:011968EB    jz      loc_1196A30      ; проверка ТОЛЬКО числа слоёв

Единственное условие после выделения (add ecx,1; jz) проверяет, не
равно ли число слоёв нулю (байт 0xFF), и пропускает цикл в этом
случае. Сам указатель var_C на ноль не проверяется нигде: код
переходит прямо к циклу копирования и пишет в [var_C + индекс*38].
Когда operator new возвращает ноль, первая же запись mov [edx],ecx
при EDX = 0 вызывает нарушение доступа.
operator new здесь — штатный распределитель главного модуля
(h3hota.exe, 0x00617492, ??2@YAPAXI@Z, сводится к _nh_malloc(a1, 1));
при нехватке памяти он возвращает ноль (обработчик нехватки памяти в
игре не установлен на бросок исключения), что и произошло.
Доказательство дефекта — через поставщика и назначение буфера.
Источник клеток исправен: данные даёт A0_GameMap_GetCell_sub_4086D0
(h3hota.exe, _MapCell_ *(this, x, y, z)), возвращающий живую клетку
ESI = 0x16610024; глобалы A0_Map_X_Size (0x6783C8) и A0_Map_Y_Size
(0x6783CC) — штатные размеры карты, записываются при загрузке карты
в A0_AdvMgr_Init и используются в координатной арифметике по всему
модулю. То есть потребитель получает корректные входные данные
и корректный размер, но теряет нулевой указатель на буфер. Родствен-
ный код модуля (штатные обёртки выделения, например строковые
std::_Yarn и __wcsdup) при отказе возвращает ноль без сбоя —
поведение «вернуть ноль и дать вызывающему обработать» для модуля
нормально; здесь же вызывающий (HD.Af.RepareFunc) проверку опустил.
Глубокая причина (почему operator new вернул ноль) неоднородна и по
этому дампу не различима: либо исчерпание адресного пространства
32-битного процесса в долгой сетевой партии, либо аномальный размер
запроса. Та же глубокая картина (отказ выделения в долгих сетевых
партиях, исчерпание либо повреждение размера) задокументирована в
семействе вылетов отладочного аллокатора HD-мода (адреса +0x1A0E,
+0x1A4E, +0x19AE, +0x1ABE; отчёт HD_HOTA.dll-аллокатор-семейство).
Настоящий вылет отличается от того семейства местом сбоя: там падает
сам распределитель (запись mov [esi],esi в ветке отказа), здесь
распределитель честно вернул ноль, а упал потребитель, не проверивший
результат. Корень один — отсутствие корректной обработки отказа
выделения памяти в HD-моде.

11. Воспроизведение вылета
--------------------------
Вылет недетерминирован: он срабатывает не на конкретной карте или
настройке, а в момент, когда выделение памяти под рабочий буфер
карты заканчивается отказом. Гарантированных шагов повтора нет.
Вероятностный путь: длительная сетевая партия (Network Game = 1) под
HD-модом 5.7 R33 с накоплением данных в буферах (в том числе буферах
быстрого боя) до давления на адресное пространство 32-битного
процесса; цель — поймать минидамп с инвариантами EDX = 0 (адрес
сбоя), запись, ESI — живой указатель на клетку, сбой в функции
восстановления кадра карты.
Дифференциальная диагностика (подтверждение причины, не совет):
    - полный дамп кучи (Sys.FullDump = 1) позволяет прочитать глобалы
      размеров карты (A0_Map_X_Size 0x6783C8 / A0_Map_Y_Size
      0x6783CC) и число слоёв в момент сбоя и вычислить фактический
      размер запроса; разумен (единицы МиБ) при нулевом результате —
      исчерпание адресного пространства;
      аномален (сотни МиБ и выше) — повреждение или ошибочное
      вычисление размера выше по стеку;
    - сопоставление с семейством аллокатора: если в той же партии
      ловятся вылеты с EAX = 0 и ESI = адрес сбоя (адрес = начало
      аллокатора + 0x1E), это подтверждает общий корень — отказ
      выделения памяти.

Достоверность и ограничения
---------------------------
Подтверждено:
    - Версия листинга (5.7 R33) сверена по точке входа и имени;
      адрес +0x1969AC разрешается в функцию восстановления кадра
      карты, код которой в точности воспроизводит сбой.
    - Механизм доказан: адресная проверка сошлась (EDX = var_C = 0,
      эффективный адрес mov [edx],ecx равен адресу сбоя 0x00000000);
      var_C получает значение прямо из operator new (call esi,
      esi = 0x00617492) без проверки на ноль; единственный условный
      переход после выделения проверяет число слоёв, а не указатель.
    - Поставщик данных исправен: клетки даёт A0_GameMap_GetCell
      (ESI = 0x16610024 — живой указатель), размеры карты — штатные
      глобалы движка A0_Map_X_Size (0x6783C8) / A0_Map_Y_Size
      (0x6783CC), записываются в A0_AdvMgr_Init при загрузке карты.
    - operator new при отказе возвращает ноль (сводится к
      _nh_malloc(a1, 1)); поведение согласуется с семейством
      вылетов отладочного аллокатора HD-мода.
Ограничения:
    - Единственный дамп; корреляция нескольких вылетов этого адреса
      отсутствует (в наборе из 843 логов HD_HOTA.dll других падений
      в функции восстановления кадра нет).
    - Виновный код в закрытом модуле HD-мода; точка исправления — у
      разработчиков HD-мода.
    - Минидамп сокращённый (без кучи и BSS-состояния): фактический
      размер запроса и причина отказа operator new (исчерпание либо
      аномальный размер) по нему не различимы — нужен полный дамп.
    - Полезность средняя: пропущенная проверка результата выделения
      локализована и доказана, точечное исправление возможно, однако
      глубокая причина отказа памяти — рантайм и общая с семейством
      аллокатора; одна инструкция краха диагноз не исчерпывает.

ВЫВОД
-----
Виновник — HD-мод (закрытый модуль HD_HOTA.dll). Функция
восстановления кадра карты приключений (sub_11966B0) выделяет рабочий
буфер клеток через operator new и использует возвращённый указатель
без проверки на ноль. Когда выделение завершается отказом и operator
new возвращает ноль, первая же запись в буфер (mov [edx],ecx при
EDX = 0) роняет процесс. Дефект — пропущенная проверка результата
выделения памяти; глубокая причина самого отказа (исчерпание
адресного пространства либо аномальный размер запроса в долгой
сетевой партии) по сокращённому минидампу не различима и общая с
семейством вылетов отладочного аллокатора HD-мода.
