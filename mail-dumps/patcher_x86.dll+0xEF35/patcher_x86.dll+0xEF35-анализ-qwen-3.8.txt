КРАТКОЕ РЕЗЮМЕ
--------------
Игра вылетает в движке хуков HD-мода (patcher_x86.dll), когда тот
ведёт учёт вложенных вызовов перехваченных функций. Для каждого
хука патчер хранит в памяти потока отдельное «ведро» со счётчиком
глубины. В момент сбоя счётчик становится отрицательным: выходов
из контекста оказывается больше, чем входов, и счётчик из нуля
уходит в минус один. Отрицательный уровень используется как индекс
массива, который для такого ведра ещё не создавался (указатель на
него нулевой), и чтение по нулевому адресу обрушивает процесс.

Исключение — нарушение доступа (EXCEPTION_ACCESS_VIOLATION), чтение
по адресу 0xFFFFFFD0, что в точности равно 0 + (−6)×8. Корневой
регистр — EAX = 0 (нулевой указатель на буфер ведра). Все пять
дампов падают в одной инструкции; четыре из них — чистый уход
счётчика в минус (индекс −2), один — с повреждёнными регистрами
ведра (мусорный индекс).

3. Сопоставление адресов
------------------------
Формула: IDA_addr = runtime_addr − load_base + imagebase.

Для patcher_x86.dll imagebase = 0x10000000 (из шапки листинга).
Адрес загрузки меняется по дампам (ASLR), смещение точки сбоя
постоянно и равно +0xEF35:

    дамп 5: 0x62B5EF35 − 0x62B50000 + 0x10000000 = 0x1000EF35
    дамп 1: 0x72C1EF35 − 0x72C10000 + 0x10000000 = 0x1000EF35
    дамп 2: 0x6BDBEF35 − 0x6BDB0000 + 0x10000000 = 0x1000EF35

IDA-адрес точки сбоя 0x1000EF35 попадает на границу инструкции
(первая инструкция мнемоникой mov ниже метки loc_1000EF2D), что
подтверждает совпадение сборки.

5. Инструкция краша и адресная проверка
---------------------------------------
Падающая функция sub_1000EE60 (patcher_x86.dll) — функция доступа
к per-thread «ведру» хука. Хвост функции, ведущий к крашу:

    .text:1000EF2D loc_1000EF2D:
    .text:1000EF2D     lea     ecx, [eax+eax*2]      ; ecx = eax×3 (индекс)
    .text:1000EF30     mov     eax, [ebx+1Ch]        ; eax = указатель на буфер ведра
    .text:1000EF33     pop     ebp
    .text:1000EF34     pop     ebx
    .text:1000EF35     mov     eax, [eax+ecx*8]      ; КРАШ: чтение буфер[индекс]
    .text:1000EF38     mov     [esp+arg_24], eax
    .text:1000EF3C     retn

Механика отказа. Регистр EAX несёт указатель на динамический буфер
ведра (поле ведра +0x1C), регистр ECX — индекс элемента, умноженный
на три (шаг элемента 24 байта: ecx×8 = (индекс×3)×8). В момент краша
EAX = 0 — буфер ведра никогда не выделялся. Инструкция читает память
по адресу EAX + ECX×8 = 0 + ECX×8.

Адресная проверка (сошлась для всех пяти дампов):

    дамп 1-4: 0 + 0xFFFFFFFA×8 = 0 + (−6)×8 = −48 = 0xFFFFFFD0  == faulting
    дамп 5:   0 + 0x1C7A0DB9×8 = 0xE3D06DC8 (по модулю 2^32)     == faulting

Для дампов 1-4 индекс элемента = ECX/3 = −6/3 = −2 — отрицательный.
Для дампа 5 ECX = 0x1C7A0DB9 на 3 без остатка не делится, то есть
регистр содержит мусор, а не вычисленный индекс, — это повреждение
состояния ведра, а не арифметический уход индекса.

7. Анализ регистров и группировка
---------------------------------
EAX = 0 во всех пяти дампах — это указатель на буфер ведра (поле
+0x1C), загружаемый инструкцией mov eax, [ebx+1Ch] непосредственно
перед крашем. Нулевое значение означает, что динамический массив
ведра не выделялся.

ECX несёт индекс элемента, умноженный на три:
    дампы 1-4: ECX = 0xFFFFFFFA = −6, индекс = −2. Отрицательный
        индекс — признак ухода счётчика глубины ниже нуля.
    дамп 5: ECX = 0x1C7A0DB9 — мусор (на 3 не делится), регистры
        EDX = 0xFED359E9 тоже мусорные; состояние ведра повреждено.

EBX до краха (в дампах 1-4) указывает на ведро; после pop ebx его
значение в контексте — уже снятое со стека. EDX в дампах 1-4
(0x00855DE8, 0x0073FB28, 0x009E5FE8, 0x008A89B8) — разные рабочие
адреса, не несущие диагностической нагрузки (разные буферы одного
шаблона отказа).

Группировка: ключ — падающая функция sub_1000EE60 + регистровый
инвариант EAX = 0 + общая подсистема (учёт контекста хуков
patcher_x86). Дампы 1-4 — чистый уход счётчика в минус; дамп 5 —
повреждение состояния ведра. Обе подгруппы падают на одной
инструкции при нулевом буфере.

8. Первопричина
---------------
Патчер HD-мода ведёт учёт вложенных вызовов каждого перехваченного
хука через per-thread структуру (TLS). Каждому хуку при установке
выделяется уникальный индекс (глобальный счётчик g_tl_hi_counter,
dword_100B5EC0, растёт атомарно через lock xadd, предел 0x1000 —
при переполнении печатается «g_tl_hi_counter >= TL_ARRAY_SIZE !!!»).
В памяти потока хранится массив «вёдер» (шаг 40 байт = 5×8), по
ведру на хук. Пара функций-перехватчиков, регистрируемых при
установке хука (sub_10009EA0): sub_1000F020 — ВХОД в контекст,
sub_1000EE60 — ВЫХОД.

Функция ВХОДА sub_1000F020 увеличивает счётчик ведра:

    .text:1000F070     mov     eax, [esi]
    .text:1000F072     inc     eax
    .text:1000F073     mov     [esi], eax        ; счётчик++ (норма: 0 -> 1)

Функция ВЫХОДА sub_1000EE60 уменьшает счётчик и по результату
выбирает, что вернуть:

    .text:1000EE84     mov     eax, [ebx]
    .text:1000EE86     dec     eax
    .text:1000EE87     mov     [ebx], eax        ; счётчик--
    .text:1000EE89     mov     ebp, [ebx]
    .text:1000EE8B     test    ebp, ebp
    .text:1000EE8D     jnz     short loc_1000EE99 ; если счётчик != 0 —
                                                 ;   путь вложенности

При сбалансированных вход/выход счётчик идёт 0 -> 1 (вход) и
1 -> 0 (выход); на нуле функция возвращает сохранённое значение
(поле ведра +0x04) и до индексации массива дело не доходит.

Динамический буфер ведра (поле +0x1C) выделяется ЛЕНИВО — только
на пути роста, когда глубина вложенности превышает текущую
ёмкость (malloc в sub_1000EE60 по адресу 0x1000EEE3 и в sub_1000F020
по 0x1000F0C8, с последующим memmove/free/memset). Сам массив вёдер
выделяется функцией входа через LocalAlloc с флагом 0x40 (LPTR =
LMEM_ZEROINIT, .text:1000F03F push 40h), то есть ОБНУЛЯЕТСЯ при
создании: у каждого ведра и счётчик, и поле-указатель +0x1C, и
ёмкость +0x24 изначально равны нулю. Поэтому для ведра, у которого
глубина никогда не превышала порог, поле +0x1C остаётся нулевым —
массив не создавался.

Сбой. В дампах 1-4 функция ВЫХОДА вызывается при счётчике, уже
равном нулю. После dec счётчик становится −1 (ebp = −1, ненулевое).
Проверки знака нет: стоит только test ebp, ebp; jnz loc_1000EE99
(.text:1000EE8B-1000EE8D), а jnz срабатывает на ЛЮБОМ ненулевом
значении — и положительном, и отрицательном, — поэтому уход в минус
обрабатывается как обычная вложенность. Управление идёт на «путь
вложенности» loc_1000EE99, где вычисляется уровень = счётчик − 1 =
−2. Этот уровень попадает в хвост функции (loc_1000EF2D),
превращается в индекс −2 (ECX = −2×3 = −6) и используется для
чтения буфера, указатель на который (поле +0x1C) равен нулю. Между
загрузкой указателя (mov eax, [ebx+1Ch], .text:1000EF30) и
разыменованием (mov eax, [eax+ecx*8], .text:1000EF35) проверки на
NULL нет. Итог — чтение по адресу 0 + (−6)×8 = 0xFFFFFFD0.

Таким образом, первопричина — рассогласование числа входов и
выходов контекста хука, из-за которого счётчик ведра оказывается
равным нулю к моменту выхода и после dec уходит в −1. Статически
это одно из двух, неразличимых без рантайма: либо выходов на один
больше, чем входов (лишний выход), либо вход и выход обращаются к
разным вёдрам (рассогласование индекса хука в поле +0x28 описателя
между парой перехватчиков). В обоих случаях отрицательный уровень
разыменовывает никогда не выделенный буфер ведра. Движок хуков не
проверяет, что счётчик не должен становиться отрицательным, и не
проверяет нулевой указатель буфера перед индексацией.

Сравнение с родственными функциями показывает, что это не единичная
оплошность. У функции выхода sub_1000EE60 есть близнец sub_1000EF40
(также регистрируется при установке хука, sub_10009EA0+188): у неё
та же проверка счётчика (dec; test ebp, ebp; jnz, .text:1000EF5D-
1000EF64) без контроля знака и побайтно идентичный хвост с
индексацией буфера без проверки на NULL (lea ecx, [eax+eax*2];
mov eax, [ebx+1Ch]; mov eax, [eax+ecx*8], .text:1000F004-1000F00C).
Единственное отличие — способ доступа к TLS: sub_1000EF40 зовёт
TlsGetValue, а sub_1000EE60 читает fs:2Ch напрямую. Функций с
индексацией буфера в модуле ровно две (обе — функции выхода), и обе
несут один и тот же дефект: отсутствие проверок — общее свойство
семейства функций учёта контекста патчера, а не случайный пропуск.

Дамп 5 — та же точка сбоя и тот же нулевой буфер (EAX = 0), но
индекс мусорный (ECX = 0x1C7A0DB9, EDX = 0xFED359E9): состояние
ведра или описателя хука повреждено, что даёт чтение по адресу
0xE3D06DC8. Механизм места сбоя идентичен; источник мусора —
повреждение памяти во время работы (см. «Достоверность»).

Виновный код находится целиком в patcher_x86.dll (движок хуков
HD-мода) и вызывается из HD_HOTA.dll. Это инфраструктура HD-мода,
а не HotA и не исходный движок SoD.

9. Условия сбоя
---------------
Вылет наблюдается в разных условиях, единого триггера по логам нет:
    - одиночная игра и сетевая (Network Game 0 и 1);
    - ход активного игрока и чужой ход (Me == Active Player и нет);
    - день первый, недели 11/12/21;
    - разные карты и зёрна генератора (в четырёх дампах Last RMG
      Seed = 0, в одном — 1785389781, карта Jebus Cross);
    - графический режим Graphics.Mode = 5 во всех дампах (внутренняя
      глубина 32 бита, stretchable); режим лишь задаёт путь отрисовки
      и не является виновником — сбой происходит в учёте хуков.
Общее — фаза активного игрового цикла (главный диспетчер игры),
когда HD-мод интенсивно диспетчеризует перехваченные функции.
Версии HD-мода охватывают широкий диапазон (5.6 R24 — 5.7 R33),
HotA во всех дампах 1.8.0.

Модуль: patcher_x86.dll (движок хуков HD-мода)
Функция: sub_1000EE60 (функция доступа к TLS-ведру хука, выход)
Подсистема: инфраструктура хуков HD-мода (учёт контекста хуков)
Класс сбоя: разыменование нулевого указателя
Виновный модуль: HD-мод (patcher_x86.dll; вызов из HD_HOTA.dll)
Были до 1.8.0: нет (не подтверждено; все дампы на HotA 1.8.0,
    дефект в HD-моде, от версии HotA не зависит)
Были в SoD: нет (patcher_x86 — инфраструктура HD-мода, в чистом
    SoD такого движка хуков нет)

Признаки поиска вылета (стабильные сигнатуры, не плавающие с версией):
    - Context-инвариант: EAX = 0x00000000 (нулевой буфер ведра);
      ECX = 0xFFFFFFFA (−6) для подгруппы чистого ухода счётчика,
      адрес сбоя 0xFFFFFFD0 = ECX×8.
    - Паттерн по дизассемблеру patcher_x86.dll (сборка стабильна,
      imagebase 0x10000000):
        lea ecx, [eax+eax*2]
        mov eax, [ebx+1Ch]
        ...
        mov eax, [eax+ecx*8]      ; точка сбоя, +0xEF35
    - Стабильный адрес h3hota.exe в стеке: 0x004F051B (главный
      игровой цикл, A0_MainMenu_sub_4EEA70) — общий кадр V2 во всех
      пяти дампах.
    - Регистрация пары перехватчиков: sub_10009EA0 выставляет
      edx = offset sub_1000EE60 (выход) и ecx = offset sub_1000F020
      (вход); счётчик g_tl_hi_counter (dword_100B5EC0).

11. Воспроизведение вылета
--------------------------
Гарантированных пошаговых сценариев нет: триггер — редкое
рассогласование числа входов/выходов контекста конкретного хука,
которое нельзя вывести из статики (какой именно хук и какая
последовательность вызовов дают рассогласование — определяется во
время работы). Вылет недетерминирован и плавающий: пять дампов
собраны на пяти разных версиях HD-мода за полгода, в одиночной и
сетевой игре, на разных картах.

Вероятностный путь для тестера:
    - массовый прогон партии (одиночной и сетевой) на разных картах
      и зёрнах генератора, в режиме Graphics.Mode = 5; цель — поймать
      момент интенсивной диспетчеризации хуков, на котором счётчик
      контекста одного из хуков уйдёт в минус;
    - ловить минидамп с регистровым инвариантом EAX = 0x00000000 и
      ECX = 0xFFFFFFFA (адрес сбоя 0xFFFFFFD0) — это подтверждает
      чистый уход счётчика; мусорные ECX/EDX при EAX = 0 — вариант
      с повреждением состояния;
    - для установки точного триггера нужен ПОЛНЫЙ минидамп (с кучей):
      сокращённый дамп репортёра (что пришёл в дампе 5, ~105 КБ,
      без кучи) подтверждает точку сбоя и регистры, но не даёт
      содержимое ведра и описателя хука. Полный дамп формируется
      репортёром при включённом <Sys.FullDump> = 1 в hota.ini; по
      нему в отладчике видно, какой хук (его индекс в поле +0x28
      описателя) и в каком состоянии счётчика дал уход в минус.

Дифференциальный тест (диагностика, не совет): поскольку сбой
встроен в движок хуков HD-мода и проявляется на широком диапазоне
версий HD-мода (5.6 R24 — 5.7 R33), сопоставление частоты вылета
между сборками HD-мода локализует регрессию в логике учёта контекста
патчера.

Достоверность и ограничения
---------------------------
Подтверждено:
    - версия листинга patcher_x86.dll сверена по entry point
      (DllEntryPoint @ 0x10012DE6 = imagebase + 0x12DE6, совпадает
      во всех пяти дампах) и по границе инструкции краша;
    - механика сбоя доказана арифметикой: адрес сбоя = EAX + ECX×8,
      сходится для всех пяти дампов (0xFFFFFFD0 = (−6)×8 и
      0xE3D06DC8 = 0x1C7A0DB9×8);
    - инструкция краша mov eax, [eax+ecx*8] и обе функции учёта
      контекста (sub_1000EE60 — выход с dec, sub_1000F020 — вход
      с inc) прочитаны в листинге; уход счётчика 0 -> −1 и индексация
      нулевого буфера показаны по коду;
    - минидамп дампа 5 независимо подтвердил EIP = patcher_x86.dll+
      0xEF35 и регистры (EAX = 0, ECX = 0x1C7A0DB9), ExceptionCode
      0xC0000005;
    - пять дампов сгруппированы по падающей функции, инварианту
      EAX = 0 и общей подсистеме; общий кадр V2 h3hota.exe+0xF051B
      (главный игровой цикл) присутствует во всех дампах;
    - отсутствие проверок — системный паттерн семейства: обе функции
      выхода с индексацией буфера (sub_1000EE60 и её близнец
      sub_1000EF40) прочитаны и несут идентичный дефект (нет контроля
      знака счётчика и нет проверки буфера на NULL).

Ограничения:
    - точный триггер (какой именно хук и какое рассогласование —
      лишний выход либо рассогласование индекса хука между входом и
      выходом) статикой не определяется и не различается
      — это рантайм: нужен полный минидамп с кучей и знание таблицы
      хуков автором патчера;
    - дамп 5 — вариант с повреждением состояния ведра (мусорный
      индекс); источник повреждения памяти по сокращённому дампу
      (без кучи) не установить;
    - листинг HD_HOTA.dll доступен только для версии 5.7 RC11 и не
      совпадает с версиями дампов; имя функции-caller'а в HD_HOTA
      не восстановлено (периферийная обёртка хука, смещается между
      сборками) — на диагноз не влияет, так как падающий модуль
      patcher_x86.dll совпадает;
    - показания игроков отсутствуют (в двух письмах WITH COMMENT —
      только служебный автотекст репортёра).

Обоснование полезности (СРЕДНЯЯ). Лог чётко локализует дефект в
движке хуков patcher_x86.dll и доказывает механику (уход счётчика
контекста в минус и индексация нулевого буфера) — это полноценный
материал для отчёта автору HD-мода. Однако исправление находится в
закрытом модуле HD-мода (не в HotA), а точная последовательность,
приводящая к лишнему выходу контекста, определяется только во время
работы. Поэтому лог полезен и информативен, но точечное исправление
по нему из данного проекта невозможно.

ВЫВОД
-----
Виновник — HD-мод: вылет происходит в его движке хуков
patcher_x86.dll (функция sub_1000EE60), вызываемом из HD_HOTA.dll
при диспетчеризации перехваченных функций во время игрового цикла.
Суть дефекта — рассогласование учёта вложенных вызовов хука:
выходов из контекста оказывается больше, чем входов (лишний выход
либо рассогласование индекса хука между входом и выходом),
per-thread счётчик глубины уходит из нуля в минус, и
отрицательный уровень используется как индекс динамического буфера
ведра, который для такого ведра никогда не выделялся (указатель
нулевой). Чтение по нулевому адресу (0 + (−6)×8 = 0xFFFFFFD0)
вызывает нарушение доступа. Движок хуков не проверяет ни уход
счётчика в минус, ни нулевой указатель буфера перед индексацией.
Дефект воспроизводится на широком диапазоне версий HD-мода
(5.6 R24 — 5.7 R33) при HotA 1.8.0; в SoD такой инфраструктуры
хуков нет. Точный триггер (конкретный хук и вид рассогласования —
лишний выход либо рассогласование индекса хука) определяется только
во время работы и требует полного минидампа с кучей.
