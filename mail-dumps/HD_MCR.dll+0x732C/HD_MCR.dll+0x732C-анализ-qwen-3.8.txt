АНАЛИЗ ВЫЛЕТА HD_MCR.dll+0x732C (отрисовка кадра: эмуляция поверхностей DirectDraw HD-мода)
================================================================================

Модель: Qwen 3.8
Дата: 29.07.2026
Заключение: Виноват HD-мод (HD_MCR.dll). Метод «получить описание
поверхности» читает геометрию из глобальной теневой поверхности,
не проверяя указатель на ноль; поверхность создаётся лениво и к
моменту вызова может быть ещё не создана.

КРАТКОЕ РЕЗЮМЕ
--------------
Игра падает в подмодуле многопоточной отрисовки HD-мода HD_MCR.dll.
Метод объекта-эмулятора DirectDraw-поверхности копирует ширину,
высоту, шаг строки и размер буфера из глобальной теневой поверхности
(GDI DIB-секция, указатель dword_2022244). Перед копированием метод
не проверяет указатель, а глобал создаётся лениво и условно в другом
методе. Когда движок запрашивает описание поверхности раньше, чем
теневая поверхность создана (или когда GDI не смогла её создать),
указатель равен нулю и метод падает, читая поле по смещению +0x14
от нуля. Адрес сбоя 0x00000014 во всех четырёх дампах, регистр-база
EDX = 0 во всех дампах. Вылет воспроизводится до начала партии
(Day 0 0 0; партия стартует с 1 1 1) в одиночной игре, в версиях
HD-мода 5.7 R5, R10 и R33.

    .text:02007329     mov     ecx, [ebp+arg_8]     ; приёмник (аргумент)

Механика: метод копирует четыре поля геометрии из объекта, на который
указывает глобальный указатель dword_2022244, в структуру-приёмник
(аргумент arg_8): шаг строки (+0x14 -> +0x10), размер изображения
(+0x18 -> +0x24), высоту (+0x8 -> +0x0C) и ширину (+0x0C -> +0x8).
Это описание рабочей поверхности отрисовки.

Адресная проверка: база EDX (= dword_2022244 = 0) + смещение поля
0x14 = 0x00000014 == адрес сбоя. Проверка сошлась. Во всех четырёх
дампах EDX = 0, поэтому чтение [edx+14h] каждый раз обращается к
нулевому адресу.

7. АНАЛИЗ РЕГИСТРОВ И ГРУППИРОВКА
---------------------------------
Корневой регистр — EDX. В падающей функции EDX загружается из
глобального указателя dword_2022244:

    .text:02007323     mov     edx, dword_2022244

Во всех четырёх дампах EDX = 0, значит глобальный указатель
dword_2022244 равен нулю. Это не повреждение отдельного объекта
кучи, а нулевое значение самой глобальной переменной.

ECX — указатель на структуру-приёмник (аргумент arg_8); значения
0x0019FD00 / 0x001AFD04 лежат в диапазоне стека (рядом с ESP/EBP
0x0019FCE4 / 0x001AFCE8), то есть приёмник — корректная структура
на стеке вызывающего кода. Приёмник живой, бит именно источник
(глобал dword_2022244).

EAX в дампах разный (0x0548EA60, 0x06B46A80, 0x06FB5AC0, 0x08057B40) —
это меняющиеся между запусками адреса, на механизм не влияют. ESI
(0x90000000 / 0x11CF0000) и EBX (= 0) падающая функция не трогает —
это унаследованные значения регистров вызывающего кода.

Группировка: один адрес сбоя, один регистровый инвариант (EDX = 0,
адрес сбоя 0x14), один вызывающий код. Четыре дампа — один дефект.

8. ПЕРВОПРИЧИНА
---------------
Глобальный указатель dword_2022244 — это теневая рабочая поверхность
(GDI DIB-секция), которую HD_MCR.dll создаёт лениво и условно.
Единственное место записи глобала — метод sub_2007450 (создатель):

    .text:02007507 loc_2007507:
    .text:02007507     mov     ecx, [eax+0Ch]
    .text:0200750A     cmp     ecx, 80h
    .text:02007510     jbe     short loc_2007528   ; размер <= 128 - пропуск
    .text:02007512     cmp     dword_2022244, 0
    .text:02007519     jnz     short loc_2007528   ; уже создана - пропуск
    .text:0200751B     mov     edx, [eax+8]
    .text:0200751E     call    sub_20011A0         ; создать DIB-поверхность
    .text:02007523     mov     dword_2022244, eax  ; сохранить (возможно 0)

Создатель сам проверяет глобал на ноль (cmp dword_2022244, 0) — то
есть модуль знает, что переменная может быть нулевой. Поверхность
создаётся только при размере больше 128 и только пока глобал нулевой.
Функция создания sub_20011A0 возвращает ноль, если GDI не смогла
создать контекст устройства (CreateCompatibleDC) или DIB-секцию
(CreateDIBSection):

    .text:020011DC     mov     [edi], eax          ; hdc
    .text:020011DE     test    eax, eax
    .text:020011E0     jz      short loc_2001237   ; отказ GDI -> ноль
    ...
    .text:02001227     mov     ecx, [edi]
    .text:02001229     mov     [edi+4], eax        ; hbitmap
    .text:0200122C     test    eax, eax
    .text:0200122E     jnz     short loc_2001251
    .text:02001230     push    ecx
    .text:02001231     call    ds:DeleteDC
    .text:02001237 loc_2001237:                    ; путь отказа
    .text:02001237     mov     ecx, edi
    .text:02001239     call    sub_20010A0         ; освободить
    .text:02001240     xor     eax, eax            ; вернуть NULL

Таким образом, ноль в dword_2022244 — штатно достижимое состояние
модуля: поверхность либо ещё не создана (создатель не запускался
до запроса описания), либо её создание завершилось отказом GDI.
Глобальную переменную после создания никто не обнуляет (единственная
запись — в создателе), так что ноль означает именно «поверхность так
и не создана».

Дефект: метод sub_2007320 (получение описания поверхности, слот +0x68
vtable объекта-эмулятора, построенной функцией sub_2002E30) читает
геометрию из dword_2022244 БЕЗ проверки указателя на ноль. Сравнение
с родственным кодом показывает рассинхрон: создатель sub_2007450
проверяет глобал (cmp dword_2022244, 0), а потребитель sub_2007320 —
нет. Когда движок запрашивает описание поверхности раньше, чем теневая
поверхность создана, потребитель разыменовывает ноль.

Это не одна пропущенная проверка, а инвариант всего модуля. Глобальную
переменную dword_2022244 читают около шестнадцати методов (среди них
0x2002C7A, 0x20030B1, 0x2006C7D и другие), и каждый разыменовывает
указатель без проверки на ноль — сразу обращается к полям [ecx+10h],
[eax+18h] и т. п. Модуль повсеместно предполагает, что после
инициализации теневая поверхность существует. Метод sub_2007320
оказался лишь тем потребителем, который движок вызвал первым, пока
глобал ещё оставался нулевым; при том же состоянии любой из остальных
потребителей упал бы так же.

Объект-эмулятор и его vtable — собственная инфраструктура HD-мода
(sub_2002E30 заполняет таблицу методов: +0x58 sub_20072D0 — получение
пиксельного формата 32 бит, +0x64 sub_2007310 — заглушка, возвращающая
S_OK, +0x68 sub_2007320 — получение описания поверхности). Методы
stdcall (sub_2007320 завершается retn 14h) и читают ГЛОБАЛЬНУЮ теневую
поверхность, а не указатель this — это собственный интерфейс HD-мода,
замещающий методы поверхности из ddraw.dll, а не дубль функции движка.

Проверка стороны SoD (h3hota.exe): функция sub_600BB0 из цепочки —
обёртка CreateSurface (вызов lpDD->vtable[0x18]), то есть вызывающий
код, а не заменяемая функция. GDI-функции в движке есть (sub_603DD0:
CreateCompatibleDC + SelectObject + BitBlt), но они работают с
передаваемой структурой и проверяют её поля (test [edi+28h]/[edi+1Ch]
с переходом при нуле); CreateDIBSection, которым HD_MCR создаёт теневую
поверхность, в h3hota.exe отсутствует. Аналога «глобальная теневая
поверхность + метод, читающий её без проверки на ноль» в SoD нет,
поэтому для данного дефекта «Были в SoD» = НЕТ.

11. ВОСПРОИЗВЕДЕНИЕ ВЫЛЕТА
--------------------------
Уровень воспроизводимости: вылет детерминированно наблюдается в
предотыгровом состоянии (Day 0 0 0, до начала партии) в четырёх
независимых дампах трёх версий HD-мода, поэтому базовый сценарий
воспроизводим. Точный момент, когда теневая поверхность оказывается
нулевой (запрос описания раньше создания либо отказ GDI при создании),
уточняется по рантайму.

Условие активации пути: активный подмодуль многопоточной отрисовки
HD-мода HD_MCR.dll (режимы внутренней 32-битной отрисовки HD-мода,
в логах — <Graphics.Mode> = 5) и запрос движком описания рабочей
поверхности (метод vtable +0x68 объекта-эмулятора) до того, как
создатель sub_2007450 наполнил глобал dword_2022244.

Базовый сценарий:
- HotA 1.8.0 + HD-мод 5.7 R33 (или R5/R10);
- <Graphics.Mode> = 5, <Graphics.Threads> >= 1;
- одиночная партия, запуск карты (в логах test.h3m);
- краш наблюдается в предотыгровом состоянии / при инициализации
  отрисовки (Day 0 0 0, до начала партии).

Варьирование:
- перебрать <Graphics.Mode> = 0..7, чтобы определить, в каких режимах
  активируется путь эмуляции поверхностей HD_MCR.dll;
- менять разрешение и размеры рабочей поверхности (создатель наполняет
  глобал только при размере больше 128 — порог cmp ecx, 80h);
- запускать на разных системах/драйверах, чтобы проверить ветвь отказа
  GDI (CreateCompatibleDC / CreateDIBSection возвращают ноль).

Дифференциальный тест (подтверждение причины):
- зафиксировать в рантайме, выполняется ли ветвь создателя
  sub_2007450 (запись в dword_2022244) ДО первого вызова метода
  sub_2007320; если вызов sub_2007320 происходит при dword_2022244 = 0
  — причина (запрос описания до создания) подтверждена;
- проверить возвращаемое значение sub_20011A0: если оно равно нулю,
  глобал обнулён отказом GDI (вторая ветвь того же дефекта — метод
  sub_2007320 не проверяет указатель в обоих случаях).

ДОСТОВЕРНОСТЬ И ОГРАНИЧЕНИЯ
---------------------------
Подтверждено:
- версия листинга HD_MCR.dll.txt сверена по точке входа (RVA 0xAE59
  в логе и в листинге) и по попаданию адреса краша 0x200732C на
  границу инструкции;
- адресная проверка сошлась: EDX (0) + смещение поля 0x14 = адрес
  сбоя 0x00000014, инвариант EDX = 0 во всех четырёх дампах;
- падающая функция sub_2007320 прочитана целиком; доказано, что она
  читает глобал dword_2022244 без проверки на ноль;
- инвариант модуля проверен: другие читатели глобала (0x2002C7A,
  0x20030B1, 0x2006C7D) тоже разыменовывают dword_2022244 без
  проверки на ноль — дефект не единичный, а общий для всех
  потребителей теневой поверхности;
- прочитаны создатель глобала sub_2007450 (с проверкой cmp
  dword_2022244, 0) и функция создания sub_20011A0 (возвращает ноль
  при отказе GDI) — ноль в глобале штатно достижим;
- глобал не обнуляется после создания (единственная запись — в
  создателе), так что ноль означает «поверхность не создана»;
- кадры стека в h3hota HD.exe смаппены на листинг h3hota_HD.exe.txt
  (sub_600BB0, WINGRAPH.CPP); четыре дампа сгруппированы по одному
  адресу сбоя, одному вызывающему коду и одному регистровому
  инварианту;
- проверена сторона SoD: sub_600BB0 — обёртка CreateSurface (вызывающий
  код, не заменяемая функция); GDI-функции h3hota.exe (sub_603DD0)
  работают с передаваемой структурой и проверяют поля, CreateDIBSection
  в h3hota.exe нет — аналога глобальной теневой поверхности и метода её
  описания без проверки в SoD не найдено.

Ограничения:
- точный момент, когда глобал оказывается нулевым (запрос описания
  раньше создания против отказа GDI при создании), по статике
  неразличим — это рантайм-состояние; обе ветви ведут к одному
  дефекту (отсутствие проверки в sub_2007320);
- точный слот vtable, по которому движок вызывает sub_2007320,
  в стеке не разрешён однозначно (кадры 0x00E2xxxx/0x00E5xxxx —
  трамплины patcher_x86 вне модулей, стек частично spliced); на
  механизм и первопричину это не влияет;
- минидампы (.dmp) сокращённые (без кучи), содержимое объектов кучи
  недоступно; для данного дефекта оно и не требуется, так как корень —
  нулевое значение глобальной переменной, а не порча объекта;
- показания игроков отсутствуют (во всех блоках Comment только
  служебный автотекст репортёра).

ВЫВОД
-----
Виновник — HD-мод, подмодуль многопоточной отрисовки HD_MCR.dll.
Метод получения описания поверхности sub_2007320 читает ширину,
высоту, шаг строки и размер буфера из глобальной теневой поверхности
dword_2022244, не проверяя указатель на ноль. Глобальная переменная
создаётся лениво и условно в методе sub_2007450 и к моменту запроса
описания может быть нулевой (поверхность ещё не создана либо GDI не
смогла её создать). Сам создатель проверяет глобал на ноль, а
потребитель — нет; этот рассинхрон и приводит к разыменованию нуля
по смещению +0x14. Дефект находится в закрытом исполняемом файле
HD-мода и воспроизводится в предотыгровом состоянии (Day 0 0 0, до
начала партии) в версиях HD 5.7 R5/R10/R33.
