АНАЛИЗ ВЫЛЕТА HD_TC2.dll+0x5BF5
====================================

Модель: Qwen 3.8
Дата: 31.07.2026
Заключение: HD_TC2.dll — чтение за концом буфера Def-спрайта курсора. Блит True32 читает 4 байта/пиксель (32 бит), но буфер кадра, вероятно, выделен под 16 бит (RGB565) — двукратный перерасход, краш на границе страницы.

КРАТКОЕ РЕЗЮМЕ
--------------
Вылет происходит при смене кадра курсора мыши. Игра рисует Def-спрайт
курсора через конвейер HD-мода: h3hota.exe передаёт кадр в HD_HOTA.dll,
далее hota.dll вызывает блит с цветовым ключом в HD_TC2.dll (True32).
Блит читает пиксели источника по 4 байта (32-битный формат), но буфер
Def-кадра хранит данные в 16-битном формате (RGB565, исходный формат
.def-файлов SoD). Каждая строка читает вдвое больше, чем выделено:
при ширине 44 пикселя блит расходует 176 байт на строку вместо 88.
Перерасход накапливается по строкам, и во второй половине спрайта
чтение выходит за границу выделения — на границу страницы.

Корень — в отсутствии конвертации Def-кадра из 16 бит в 32 бита перед
блитом True32 (или в неверном stride, переданном в объект-поверхность).
Ответственность — HD-мод (конвейер подготовки спрайтов для True32).

    .text:02005BF5  loc_2005BF5:

    .text:02005BF8      cmp     ecx, [ebp+arg_4] ; сравнение с цветовым ключом

    .text:10076B7F      call    eax                  ; вызов блита
    .text:10076B81      pop     esi                  ; возврат сюда

6. Механизм сбоя
----------------
sub_2005B30 — блит с цветовым ключом и отсечением. Принимает 11
аргументов (retn 2Ch): координаты, ширину, высоту, указатели буферов,
шаги строк, границы отсечения, цветовой ключ.

Отсечение ограничивает область:
- ширина: x_смещение + ширина <= arg_1C (ширина источника)
- высота: y_смещение + высота <= arg_20 (высота источника)

Указатель источника: this->field_30 + this->field_2C * строка + столбец * 4,
где this->field_2C — шаг строки, this->field_30 — начало пиксельных данных.

Сбой: отсечение пропустило область, которая выходит за реальный буфер.
Последние пиксели строки (14 в дампе 1, 2 в дампе 2) попадают на
невыделенную страницу. Буфер источника заканчивается ровно на границе
страницы (адреса ...F000 и ...4000).

7. Первопричина
---------------
Ведущая гипотеза: буфер Def-кадра курсора выделен в 16-битном формате
(RGB565, исходный формат .def-файлов SoD), но блит True32 читает его
как 32-битный (4 байта/пиксель). Двукратный перерасход по каждой строке
накапливается, и во второй половине спрайта чтение выходит за выделение.

Подтверждение гипотезы арифметикой:
- Ширина кадра = 44 пикселя, высота = 64 (курсортная поверхность
  создаётся 64x64 в A0_DirectDrawInit_sub_601AB0)
- Буфер 16bpp: 44 * 64 * 2 = 5632 байта
- Блит 32bpp: шаг строки field_2C = 44 * 4 = 176 байт
- Строка Y начинается по base + 176 * Y
- Конец буфера: base + 5632 = base + 176 * 32
- Первое чтение ЗА буфером: строка 32 (Y = 32)
- Дамп 2: EBX = 16 (осталось 16 строк) -> Y = 64 - 16 = 48 >= 32
- Дамп 1: EBX = 2 (осталось 2 строки) -> Y = 64 - 2 = 62 >= 32
- Оба дампа падают ВО ВТОРОЙ половине спрайта, как предсказывает модель

Почему краш не на строке 32, а позже: память за буфером (куча)
картирована — чтение идёт по чужим данным, пока не упрётся в
некартированную страницу. Оба адреса сбоя кратны 0x1000 — граница
страницы, первое немаркированное чтение.

Альтернативная гипотеза (менее вероятна): буфер Def-кадра освобождён
при смене кадра курсора, а объект-поверхность хранит устаревший
указатель (use-after-free). Против: чтение успешно проходит 30-42
пикселя текущей строки (данные читаются, не сразу AV) — память
частично жива, что типичнее для перерасхода, чем для полного
освобождения.

Функция-установщик sub_2005AF0 (HD_TC2, ID 0x44DF20) записывает
field_2C (шаг) и field_30 (указатель) из аргументов вызывающего кода
и ставит field_34 = 1 (внешний владелец, не освобождать). Она лишь
сохраняет переданное — ошибка в том, ЧТО передаётся: шаг 176 (32bpp)
при буфере 5632 байта (16bpp), либо указатель на неконвертированные
данные.

Оригинал SoD (A0_Pcx16_SetBuffer_sub_44DF20) вычисляет field_1C =
field_20 = width * height * 2 (16bpp). Замена HD_TC2 (sub_2005AF0)
эти поля НЕ заполняет — но блит sub_2005B30 их и не использует
(читает только field_2C/field_30).

11. Воспроизведение вылета
--------------------------
Условие активации пути: Graphics.Mode из множества {4, 5, 7}
(внутренние 32 бита) — путь True32 (HD_TC2.dll). В режимах с внутренней
глубиной 16 бит ({0, 1, 2, 3, 6}) используется другой блит-модуль.

Базовый сценарий:
- Запустить партию (одиночную или сетевую) с Graphics.Mode = 7
- Выполнять действия, вызывающие смену кадра курсора (перемещение
  мыши по интерфейсу, смена контекстных курсоров)
- Краш недетерминирован: зависит от состояния буфера поверхности
  курсора в момент блита

Вероятностный характер: сбой привязан к состоянию буфера (освобождение/
пересоздание поверхности курсора при смене кадра). Точный триггер —
момент, когда указатель данных поверхности не соответствует реальной
области выделения. Без полного дампа детерминированный сценарий
не построить.

Дифф-тест: сравнить поведение при Graphics.Mode = 7 (True32) и
Graphics.Mode = 3 (внутренние 16 бит, тот же stretchable-вывод).
Если в режиме 3 краш не воспроизводится — подтверждается привязка
к пути True32.

Достоверность и ограничения
---------------------------
Подтверждено:
- Механизм сбоя доказан арифметикой: EDI+EAX = адрес сбоя в обоих дампах
- Инструкция краша на границе инструкции листинга (отрицательный тест)
- Цепочка вызовов подтверждена V2 (hota.dll+0x76B81, HD_TC2+0x5BF5)
- Полная цепочка: h3hota.exe (A0_MouseMgr_SetMouseCursorFrame ->
  A0_Def_Pointer_Draw -> A0_DefFrame_LargePacks_Draw) -> перехват
  HD-мода -> HD_HOTA -> hota.dll -> HD_TC2
- Ширина блита 44 пикселя в обоих дампах (один спрайт курсора)
- Адреса сбоя на границе страницы — чтение за концом выделения
- sub_2005AF0 (установщик поверхности) прочитан: field_2C/field_30
  из аргументов, field_34=1 (внешний владелец)
- Оригинал SoD (A0_Pcx16_SetBuffer) считает размер 16bpp (width*height*2)
- Курсорная поверхность создаётся 64x64 RGB565 (A0_DirectDrawInit)
- Модель «16bpp буфер, чтение 32bpp» предсказывает краш во второй
  половине спрайта (Y >= 32) — оба дампа (Y=48 и Y=62) попадают

Ограничения:
- Минидампы сокращённые (без кучи): фактическое содержимое field_2C/
  field_30 объекта-поверхности в момент сбоя недоступно
- Гипотеза 16bpp/32bpp подтверждена косвенно (арифметика, формат
  создания поверхности, структура оригинала SoD), но НЕ доказана
  побайтно: полная трассировка конвертации Def-кадра в конвейере
  HD-мода (A0_DefFrame_LargePacks_Draw -> перехват -> HD_HOTA)
  не выполнена
- Timestamp листинга HD_TC2.dll (30.07.2026) новее дампа 2 (05.04.2026);
  тождество подтверждено по RVA/размеру/границе инструкции, побайтно
  не сверялось
- HD_HOTA.dll: для дампа 2 (5.6 R37) листинг отсутствует; кадры
  HD_HOTA периферийны для диагноза

ВЫВОД
-----
Вылет в HD_TC2.dll+0x5BF5 — чтение за концом буфера Def-спрайта
курсора при блите с цветовым ключом в конвейере True32. Блит читает
пиксели по 4 байта (32-битный формат), тогда как буфер кадра, вероятно,
хранит 16-битные данные (RGB565). Двукратный перерасход накапливается
по строкам: при ширине 44 и высоте 64 пикселей буфер исчерпывается
на строке 32, а краш наступает при достижении первой некартированной
страницы (строки 48 и 62 в дампах 1 и 2).

Корень — в конвейере подготовки Def-спрайтов для True32: данные кадра
не конвертируются из 16 бит в 32 бита (или объект-поверхность получает
неверный stride/указатель). Ответственность — HD-мод (HD_HOTA.dll,
перехват A0_DefFrame_LargePacks_Draw). Для окончательного подтверждения
нужен полный дамп (Sys.FullDump = 1): он покажет фактические field_2C/
field_30 и содержимое буфера в момент сбоя.
