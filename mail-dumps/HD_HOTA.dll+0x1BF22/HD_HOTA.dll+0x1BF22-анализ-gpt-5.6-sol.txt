АНАЛИЗ ВЫЛЕТА  HD_HOTA.dll+0x1BF22  (отрисовка миникарты)
================================================================================

    Модель: GPT-5.6 Sol
    Дата:   14.08.2026
    Заключение: HD_HOTA.dll индексирует массив героев по повреждённому
    setup клетки без проверки диапазона 0..155.


КРАТКОЕ РЕЗЮМЕ
--------------

    Вылет происходит при отрисовке миникарты карты приключений. Хук
    HD_HOTA.dll перебирает клетки, распознаёт клетку героя по типу 34 и
    trigger-флагу, затем принимает dword setup клетки за индекс героя.
    По этому индексу он пытается прочитать byte owner_id из встроенного
    массива героев A0_GameMgr.

    В массиве 156 записей размером 0x492, поэтому допустимы только индексы
    0..155. В целевом вылете уже вычисленное смещение ECX равно
    0x25CA0924 вместо допустимых 0x00021620..0x0004DA86. Инструкция
    читает 0x0A810000 + 0x25CA0924 + 0x22 = 0x304B0946 и получает
    EXCEPTION_ACCESS_VIOLATION.

    В корпусе найден ещё один уникальный случай того же механизма:
    HD 5.6 R22, HD_HOTA.dll+0x1AA22. Он повторяет формулу, глобал
    A0_GameMgr, позицию второго прохода миникарты и сетевой контекст.
    Всего семейство представлено 3 логами и 2 уникальными вылетами;
    два старых лога перенесены в подпапку серии.

    Непосредственная причина доказана: setup клетки, которая всё ещё
    помечена как герой, вышел далеко за диапазон массива. Конкретная
    исполнившаяся последовательность порчи по сокращённому дампу не
    восстанавливается. Код миникарты HD-мода и оригинал SoD не проверяют
    верхнюю границу, поэтому повреждённое состояние превращается в вылет.

3. Точка сбоя
-------------

    Инструкция использует dword setup клетки как индекс встроенного
    массива героев. К моменту сбоя ECX уже содержит
    0x21620 + setup * 0x492, а EAX содержит базу A0_GameMgr.
    Поле [+22h] записи героя — byte owner_id; полученное значение затем
    используется как индекс 16-битной палитры миникарты.

    EAX:                              0x0A810000, база A0_GameMgr
    ECX:                              0x25CA0924, вычисленное смещение
    EDX:                              0x00699538, адрес глобала A0_GameMgr
    ESI:                              0x1EC527E4, адрес текущей клетки
    Адрес сбоя:                       0x304B0946

Формула: 0x0A810000 + 0x25CA0924 + 0x22 = 0x304B0946

    Массив начинается по [+21620h], размер записи равен 0x492. Следующий
    объект после 156 записей начинается точно по [+4DF18h]:

Формула: 0x21620 + 156 * 0x492 = 0x4DF18

    Допустимый setup равен 0..155. Тогда ECX до прибавления поля лежит
    в диапазоне 0x00021620..0x0004DA86, а адрес поля owner_id — в
    диапазоне A0_GameMgr+0x21642..A0_GameMgr+0x4DAA8. Наблюдаемое
    ECX = 0x25CA0924 не может получиться из допустимого индекса.

    Решение сравнения по модулю 2^32 даёт setup = 0x309B4D72 по модулю
    2^31. Из-за чётного шага 0x492 два 32-битных значения, различающихся
    старшим битом, дают то же смещение; без памяти клетки точный dword
    не выбирается. Оба варианта заведомо лежат вне 0..155.

    Старый уникальный инцидент повторяет ту же арифметику:

    HD-мод:                           5.6 R22
    Адрес вылета:                     HD_HOTA.dll+0x1AA22
    EAX:                              0x0B2E0000, база A0_GameMgr
    ECX:                              0x278C9FF6, вычисленное смещение
    ESI:                              0x00699538, адрес глобала A0_GameMgr
    Адрес сбоя:                       0x32BAA018
    Setup по модулю 2^31:             0x3A744D93

Формула: 0x0B2E0000 + 0x278C9FF6 + 0x22 = 0x32BAA018

    В двух версиях меняется раскладка временных регистров, но сохраняются
    база GameMgr в EAX, вычисленное смещение в ECX, глобал 0x00699538,
    чтение поля [+22h] и второй проход миникарты. Совпадение выровненных
    баз GameMgr в двух независимых случаях также ослабляет гипотезу о
    повреждении самого глобального указателя: аномален индекс клетки.

    После успешного чтения owner_id код должен обратиться к палитре
    A0_GamePal_16 по 0x006AAD18. До этой операции выполнение не дошло.


4. Цепочка вызовов и контекст
-----------------------------

Карта приключений, обновление изображения
-> один из 13 вызовов A0_AdvMgr_Draw_Minimap_sub_412BA0, h3hota.exe
-> динамический переходник patcher_x86
-> sub_101B170, замена функции миникарты в HD_HOTA.dll
-> A0_GameMap_GetCell_sub_4086D0, поставщик 38-байтовой клетки
-> sub_101B170+0xDB2, HD_HOTA.dll+0x1BF22, ВЫЛЕТ

    Прямых инструкций call sub_101B170 в листинге HD_HOTA.dll нет:
    функция установлена как callback-подмена адреса 0x00412BA0.
    В стеке после двух динамических переходников первый отображаемый
    возврат — sub_102D850+0xB8. Перед ним находится косвенный call eax,
    что соответствует вызову зарегистрированного обработчика.

    Оригинальный A0_AdvMgr_Draw_Minimap имеет все 13 найденных
    call-сайтов. Все они проходят через один заменённый адрес, а setup
    клетки читается уже внутри хука; caller не может проверить его до
    входа в функцию. В целевой сборке hero-ветвь продублирована в двух
    проходах, по RVA 0x1B639 и 0x1BF22, без верхней проверки в обоих.

    сочетание формулы, глобала, положения +0xD82 и minimap-стека
    отделяет его от случайного совпадения адреса.


5. Первопричина
---------------

    HD-мод регистрирует sub_101B170 как замену оригинальной функции
    миникарты A0_AdvMgr_Draw_Minimap_sub_412BA0:

.text:01037F7A  push    sub_101B170        ; адрес функции
.text:01037F87  push    412BA0h
.text:01037F8D  call    dword ptr [ecx+1Ch]

    Внутри хука координаты клетки ограничиваются размерами карты, затем
    поставщик A0_GameMap_GetCell_sub_4086D0 возвращает указатель по
    формуле cells + 38 * linear_index. Поэтому непосредственный указатель
    на клетку и её геометрический индекс получены штатным способом.
    Негодное значение загружается позже из setup_dword0 этой клетки.

    Основные писатели жизненного цикла клетки находятся в движке.
    A0_MoveableObject_PlaceToMap_sub_4D7840 сначала сохраняет прежние
    type, trigger и setup клетки в объект, затем выполняет:

.text:004D78FE  or      byte ptr [eax+0Dh], 10h
.text:004D7902  mov     [eax+1Eh], edx
.text:004D7905  mov     edx, [ebp+ob_setup]
.text:004D7908  mov     [eax], edx

    A0_MoveableObject_RemoveFromMap_sub_4D7950 по сохранённым координатам
    возвращает прежние type, trigger и setup. Эти функции объясняют,
    каким путём hero id попадает в клетку и каким путём может быть
    восстановлено несогласованное содержимое. Сокращённый дамп не хранит
    саму клетку, объект и историю записей, поэтому выбрать конкретный
    вызов PlaceToMap, RemoveFromMap, сетевого обновления либо другой
    источник записи как фактически сработавший путь выбрать нельзя.

    Ветка выбирается только при двух одновременно сохранённых признаках:
    object_type_dword1E = 34 и бит 0x10 в byte [+0Dh]. Это означает, что
    повреждён не весь объект произвольным образом: клетка всё ещё выглядит
    как активный герой, но её setup больше не является hero id 0..155.

    Оригинал SoD по адресу 0x00412F18 имеет ту же развилку и также не
    проверяет верхнюю границу:

.text:00412F05  cmp     dword ptr [ebx+1Eh], 22h
.text:00412F0B  test    byte ptr [ebx+0Dh], 10h
.text:00412F11  mov     edx, [ebx]
.text:00412F13  mov     eax, A0_GameMgr_dword_699538
.text:00412F18  movsx   ecx, byte ptr [eax+edx+4DF18h]

    Старый код индексирует heroes_aval_abyte4DF18[setup], а HD-хук
    индексирует hero_astr21620[setup].owner_id. Представление данных
    изменено, но незащищённый контракт setup унаследован. Следовательно,
    отсутствие проверки не доказывает, что HD-мод создал порчу, однако
    именно HD_HOTA.dll является падающим потребителем и безопасной точкой
    исправления текущего вылета.

    Родственные пути подтверждают слабость контракта. Функция
    A0_GameMgr_GetHero_sub_4317D0 возвращает ноль только для setup = -1,
    а прочие значения без верхней проверки умножает на 0x492. В AI-пути
    A0_AI_Town_Get_BuyHero_Value_sub_431BD0 клетка героя также проверяется
    на -1, но не на setup < 156. В самой sub_101B170 обе копии hero-ветви
    вообще не проверяют даже -1.

    Совет по исправлению автору HD-мода: защитную правку следует внести в обе копии ветви;
    перед умножением выполнять беззнаковую проверку setup < 156. При
    нарушении диапазона клетку следует пропустить либо использовать
    обычный цвет клетки, не читая hero_astr21620. Дополнительная проверка
    owner_id перед индексированием палитры защитит следующий контракт.
    На стороне поставщиков полезно проверять hero id перед PlaceToMap и
    протоколировать координаты при RemoveFromMap, но это уже диагностика
    неустановленного источника состояния.

Связанные, но отдельные семейства:

- HD_HOTA.dll+0x1C053 относится к той же sub_101B170 и тому же классу
  несогласованной _MapCell_, но падает в ветви type 98 при обращении к
  towns_list через miu_setup. Это близкий кандидат общего класса источников записи,
  а не та же падающая инструкция.
- HD_HOTA.dll+0xA91F использует тот же hero_astr21620 и шаг 0x492, но
  индекс приходит из списка героев игрока при обновлении портретов.
  Поставщик и механизм отличаются, поэтому семья не объединяется.

    Строгий корпусный отпечаток текущей семьи включал одновременно
    модуль HD_HOTA.dll, чтение EAX + ECX + 0x22, наличие глобала
    0x00699538 в EDX или ESI и minimap-стек. После переноса старых логов
    в mail-dumps/HD_HOTA.dll не осталось ни одного кандидата. Во всём
    mail-dumps все кандидаты находятся в текущей папке: 3 файла и
    2 уникальных инцидента.


6. Условия сбоя
---------------

    Для достижения падающей инструкции одновременно необходимы:

- выполняется отрисовка миникарты карты приключений;
- текущая 38-байтовая клетка имеет object_type_dword1E = 34;
- в byte [+0Dh] клетки установлен trigger-бит 0x10;
- setup_dword0 клетки не входит в диапазон hero id 0..155;
- код доходит до одной из двух hero-ветвей, не выбрав цвет специальной
  выделенной клетки раньше.

    В обоих уникальных инцидентах активен UI.HiRezCore = 1 и игра
    сетевая, Network Game = 1. Это полезная корреляция для поиска
    источника записи, но двух случаев недостаточно, чтобы объявить сеть причиной.
    Me и Active Player различаются: в R40 Me = 1 при Active Player = 0,
    а в R22 Me = 0 при Active Player = 0.

    Графические параметры не образуют инвариант. У R40 Graphics.Mode = 7,
    Graphics.Threads = 12 и Quick Combat = 0; у R22 соответственно 5,
    3 и 1. В обоих случаях Graphics.AdvMap.Threads = -1 и Memory.Mod = 0.
    Эти значения описывают окружение, но не входят в адресную формулу.

    Карты и игровые даты также различаются. Целевой случай произошёл на
    карте pipetko,atata 2026.08.13 20;03 {Default}.h3m в месяце 2,
    неделе 1, день 1. Старый — на карте gomel555,IgorIS7,wwwVitekwww
    2026.02.06 17;24 {Default}.h3m в месяце 3, неделе 1, день 7.

    Приложенный AUTOSAVE является производным файлом аварийного комплекта,
    а не доказанным исходным вводом. Повторный разбор распаковал 473 923 байта:
    сигнатура H3SVG найдена после внутренней обёртки по смещению 0x49,
    определена версия формата 10, а имя карты совпало с именем из лога.
    Два возможных 32-битных представителя setup, 0x309B4D72 и 0xB09B4D72,
    в распакованном потоке не найдены. Этот ноль не устанавливает
    происхождение состояния: AUTOSAVE является производным файлом, а
    авторитетное представление поля клетки в формате сейва не разобрано.


7. Воспроизведение вылета
-------------------------

    Механизм потребителя воспроизводим управляемо, но естественный источник
    повреждённого setup пока не установлен.

    Роль 1 — подтверждение точки с отладчиком на HD 5.7 R40:

1. Запустить HotA 1.8.0 с HD 5.7 R40 и открыть карту приключений, на
   которой виден хотя бы один герой и обновляется миникарта.
2. Поставить breakpoint перед 0x0101BF0F с поправкой на фактическую базу
   HD_HOTA.dll либо журналировать обе hero-ветви по RVA 0x1B639 и 0x1BF22.
3. На входе проверить type = 34, trigger-бит 0x10 и сохранить координаты
   клетки, ESI, setup и базу A0_GameMgr.
4. В контролируемом прогоне заменить setup этой клетки большим значением
   вне 0..155. Для повторения целевого ECX под той же базой подходит один
   из 32-битных представителей класса 0x309B4D72 modulo 2^31.
5. Продолжить выполнение. Ожидаемый адрес остановки или исключения —
   HD_HOTA.dll+0x1BF22, а эффективный адрес равен
   A0_GameMgr + 0x21620 + setup * 0x492 + 0x22 по модулю 2^32.

    Роль 2 — поиск естественного источника состояния:

1. Добавить проверку 0 <= setup < 156 после A0_GameMap_GetCell и сохранять
   координаты первой клетки type 34, нарушившей инвариант.
2. Поставить аппаратную точку наблюдения на setup этой клетки либо
   инструментировать A0_MoveableObject_PlaceToMap_sub_4D7840,
   A0_MoveableObject_RemoveFromMap_sub_4D7950 и сетевые обновления героев.
3. Повторять сетевые игры с перерисовкой миникарты до первой неправильной
   записи, сохраняя полный дамп памяти и стек источника записи до следующего кадра.
4. Сопоставить момент записи с перемещением, удалением, телепортацией,
   сменой владельца и восстановлением клетки под героем.

    Дифференциальная проверка исправления:

- без патча искусственные setup = -1, 156 и большие dword доходят до
  вычисляемого обращения в одной из hero-ветвей;
- с проверкой unsigned setup < 156 все невалидные значения пропускаются,
  а индексы 0 и 155 продолжают давать штатный цвет;
- тест повторяется для обоих сайтов 0x1B639 и 0x1BF22;
- дополнительная проверка owner_id не допускает индекс палитры вне
  принятого диапазона цветов игроков;
- полный сетевой прогон после патча не должен скрывать первый источник записи:
  диагностический счётчик нарушений сохраняется отдельно от пропуска.

    Без отладчика доступен только вероятностный прогон сетевых карт с
    полными дампами. Совпадение одного адреса без регистровой формулы
    недостаточно: признаком успешного повтора служат тип 34, trigger-бит,
    глобал 0x00699538 и выход setup за диапазон 0..155.


8. Достоверность и ограничения
------------------------------

Подтверждено:

- текстовый лог и сохранённый CONTEXT минидампа совпадают: EIP
  0x0418BF22, регистры EAX/ECX/EDX/ESI и чтение 0x304B0946;
- перевод EIP во время выполнения при базе 0x04170000 дал RVA 0x1BF22 и точную
  инструкцию sub_101B170+0xDB2 в листинге HD 5.7 R40;
- адресная формула целевого и старого инцидентов полностью сходится;
- геометрия массива доказана смещениями: начало 0x21620, шаг 0x492,
  156 записей и следующая область 0x4DF18;

- поле [+22h] идентифицировано как owner_id независимым AI-потребителем;
- поставщик клетки A0_GameMap_GetCell_sub_4086D0 и источники записи PlaceToMap и
  RemoveFromMap прочитаны в оригинальном листинге;
- регистрация sub_101B170 как подмены 0x00412BA0 подтверждена кодом;
- оригинал SoD прочитан и повторяет тот же незащищённый setup-контракт;

- во всех 30 доступных листингах HD_HOTA.dll 5.7 найдено 60 точных
  сайтов, ровно по 2 на листинг;
- разбор 3 логов целевой папки дал 2 уникальных вылета: R40 +0x1BF22
  и R22 +0x1AA22;
- строгий поиск просмотрел 3554 txt-файла, из которых 3501 распознан
  как логи вылетов с Exception и Context; контрольный образец R40 найден,
  а вне текущей папки кандидатов не осталось;
- в плоской папке mail-dumps/HD_HOTA.dll проверены 1383 распознанных
  лога вылета, строгих кандидатов после переноса — 0;

- два старых txt перенесены по relocation-manifest.json, назначения
  проверены, источники отсутствуют; парных dmp в корпусе нет;
- SHA-256 двух старых файлов одинаков:
  0c458b3d71019140e734528f8cff60de2f4081ad85cc3deab96aea373cb7ac4c;
- SHA-256 целевого dmp:
  a93b3303844bf74dc4bf6d79b211a538c9e6cc957d10106ae67decdf65091465;
- SHA-256 AUTOSAVE:
  3c382c7d749bb94752dbf5f6b5cdf90d074f95a11ed2748add6acc296f8daaf0.

Статический чек-лист:

- 1. Падающая инструкция и арифметика: прочитано; обе формулы равны
  адресам чтения из логов.
- 2. Фактический caller: прочитано; callback проходит через динамические
  переходники, первый отображаемый возврат — sub_102D850+0xB8.
- 3. Поставщик данных: прочитано; клетку возвращает 0x004086D0, setup
  записывают и восстанавливают PlaceToMap и RemoveFromMap.
- 4. Все потребители функции: прочитаны все 13 call-сайтов оригинала;
  хук заменяет общий адрес, прямых call sub_101B170 нет.

- 5. Родственные функции: прочитаны обе копии hero-ветви, GetHero и
  AI-путь; верхней проверки setup < 156 в них нет.
- 6. Vtable и тип: N/A; _MapCell_ — плоская запись 38 байт, а массив
  героев встроен в A0_GameMgr.
- 7. Оригинал SoD: прочитан A0_AdvMgr_Draw_Minimap_sub_412BA0 и его
  обращение heroes_aval_abyte4DF18[setup].
- 8. Источники записи и жизненный цикл: прочитаны PlaceToMap и RemoveFromMap;
  конкретный исполнившийся источник записи по статике не установлен.

- 9. Кросс-версия: прочитаны 30 доступных листингов и 2 уникальных
  корпусных инцидента; листинга 5.6 R22 нет.
- 10. Триггер: доказаны type 34, trigger-бит и отрисовка миникарты;
  событие первой порчи по статике не установлено.
- 11. Арифметика выделения: отрицательный результат; в 1780 строках
  HD-функции и 817 строках оригинала найдено 0 выделений и 0 пар
  «выделение + копирование».
- Осталось установить при выполнении: точный dword setup, координаты клетки,
  первый источник записи и состояние полной памяти в момент порчи.

Обоснование трёх осей:

    Доказанность механизма указана как «выведено из листинга», потому что
    точная инструкция, версия, адрес, регистры, арифметика и структура
    массива совпадают, но управляемый повтор после патча ещё не выполнен.

    Происхождение состояния указано как «частично установлено»: известно,
    что нарушен setup клетки героя и прочитаны основные источники записи его
    жизненного цикла, но не установлен вызов, впервые записавший негодный
    dword в конкретной игре.

    Связь дополнительного R22-инцидента подтверждена смешанным способом:
    R40 имеет листинг и DMP, а R22 — два одинаковых txt без DMP и без
    листинга версии; связь держится на регистровой формуле, глобале,
    minimap-стеке и относительной позиции функции.

Ограничения:

- MiniDumpNormal содержит 44 небольших диапазона и 50 816 байт памяти;
  страницы A0_GameMgr по 0x0A810000 и клетки по 0x1EC527E4 в него не
  попали, поэтому setup нельзя прочитать непосредственно;
- из-за 32-битного переполнения и чётного шага 0x492 адресная формула
  задаёт setup только по модулю 2^31;
- полного образа HD_HOTA.dll нет; 64 сохранённых байта вокруг точки сбоя
  совпадают с листингом R40, но SHA-256 всего загруженного модуля недоступен;
- листинга HD_HOTA.dll 5.6 R22 нет, поэтому старый RVA нельзя подтвердить
  побайтно и нельзя назвать точное имя функции той сборки;

- для двух старых txt нет dmp; их содержимое даёт контекст и стек, но не
  память процесса;
- AUTOSAVE распакован, H3SVG и совпадающее имя карты найдены, но точное
  представление поля клетки в формате сейва не установлено; ноль по двум
  представителям setup не используется как вывод о происхождении состояния;
- два уникальных вылета не доказывают, что Network Game = 1 является
  источником порчи, несмотря на совпадение этого признака;
- конкретные координаты клетки, игровой жест и первый источник записи не сохранены;

- общая первопричина с отдельной семьёй +0x1C053 остаётся вероятной, но
  не доказанной одной исполнившейся записью.

Отрицательные результаты:

- среди 1383 распознанных логов вылетов в mail-dumps/HD_HOTA.dll после
  переноса найдено 0 строгих кандидатов; контрольный целевой лог найден
  тем же детектором в общей выборке;
- среди 3501 распознанного лога вылета из 3554 просмотренных txt во всём
  mail-dumps нет кандидатов вне текущей папки; внутри неё найдено
  3 файла и 2 уникальных SHA-инцидента;
- в 30 доступных листингах 5.7 не найдено сборок с нулём либо более чем
  двумя точными hero-сайтами: найдены все 60 ожидаемых сайтов;
- для двух старых txt найдено 0 парных dmp; контрольный dmp целевого R40
  находится рядом и корректно распознаётся;

- в 1780 строках sub_101B170 и 817 строках оригинальной функции найдено
  0 выделений и 0 пар «выделение + копирование»; это не allocator-баг;
- в падающей функции нет установок vtable; полиморфный объект на пути не
  создаётся;
- проверка координат перед A0_GameMap_GetCell ограничивает их размерами
  карты, поэтому статических признаков выхода самого linear_index клетки
  за буфер не найдено;
- в 473 923 распакованных байтах AUTOSAVE найдено 0 вхождений каждого из
  двух представителей setup, 0x309B4D72 и 0xB09B4D72; H3SVG и имя карты
  служат контролем распаковки, но производная роль файла и отсутствие
  разбора поля клетки не позволяют считать этот ноль доказательством.


ВЫВОД
-----

    Непосредственно виновен HD_HOTA.dll: по адресу
    HD_HOTA.dll+0x1BF22 функция sub_101B170 принимает повреждённый
    setup_dword0 клетки героя за индекс массива из 156 записей и без
    проверки читает hero_astr21620[setup].owner_id. В целевом случае
    допустимое смещение 0x00021620..0x0004DA86 заменено значением
    0x25CA0924, а формула точно даёт адрес чтения 0x304B0946.

    Автору HD-мода следует перед обоими сайтами RVA 0x1B639 и 0x1BF22
    проверять unsigned setup < 156 и при нарушении пропускать hero-ветвь.
    Следом следует ограничить owner_id перед индексированием палитры.
    Для локализации источника порчи нужен отдельный полный прогон с
    наблюдением за PlaceToMap, RemoveFromMap и сетевыми источниками записи клетки;
    отсутствие этого наблюдения не мешает безопасно закрыть падающий
    потребитель, но не позволяет приписать первую ошибочную запись одной функции.

    HD_HOTA.dll+0x1AA22 в HD 5.6 R22 относится к той же семье: формула,
    глобал и позиция второго minimap-прохода совпадают. Два старых txt
    представляют один дополнительный уникальный инцидент и уже перенесены
    в папку серии. Вылеты +0x1C053 и +0xA91F связаны подсистемой или
    массивом, но имеют другие ветви и поставщиков, поэтому не объединены.
