Модель: Qwen 3.8

Заключение: Виновник — HD-мод (HD_TC2.dll, подсистема True32). Порт

КРАТКОЕ РЕЗЮМЕ
--------------
Игра упала при копировании изображения в режиме True32: функция
HD_TC2.dll, которая должна рисовать 16-битную поверхность, читала
данные как 32-битные и ушла за конец буфера-источника.

Исключение — EXCEPTION_ACCESS_VIOLATION (чтение) по адресу
0x1648E000. Сбой произошёл внутри SSE-копирования _memmove_0
(модуль HD_TC2.dll), которое построчно переносит пиксели. Корневой
регистр — ESI (указатель на источник): ESI = 0x1648DFB0, чтение
[ESI+50h] = 0x1648E000 попадает на границу страницы, за которой
память уже не отображена. Непосредственный вызывающий код —
True32-блиттер sub_2005B30, порт функции SoD A0_Pcx16_Draw: оригинал
копирует по 2 байта на пиксел (16 бит), а порт — по 4 байта (32 бита).

3. Точка сбоя
-------------
Инструкция краха (HD_TC2.dll, функция _memmove_0, цикл прямого
SSE-копирования блоками по 128 байт):

    .text:02011A96  movdqa xmm4, xmmword ptr [esi+40h]
    .text:02011A9B  movdqa xmm5, xmmword ptr [esi+50h]   ; ВЫЛЕТ
    .text:02011AA0  movdqa xmm6, xmmword ptr [esi+60h]

_memmove_0 — собственная SSE-реализация memmove внутри HD_TC2.dll
(копия CRT-помощника с метками XmmCopyAligned_0, XmmCopyLargeLoop_0).
Она честно копирует заданное число байт; причина не в ней, а в том,
кто передал ей размер и указатели.

Адресная проверка (для копирования: регистр-источник == адрес сбоя):
    ESI = 0x1648DFB0  (источник)
    [ESI+50h] = 0x1648DFB0 + 0x50 = 0x1648E000 = адрес сбоя
Чтение совпадает с адресом исключения 0x1648E000.

Механика отказа. movdqa читает 16 байт. Предыдущее чтение
[ESI+40h] = 0x1648DFF0..0x1648DFFF прошло успешно (страница
0x1648D000..0x1648DFFF отображена), а следующее [ESI+50h] =
0x1648E000 упирается в первую неотображённую страницу 0x1648E000.
Адрес сбоя выровнен ровно по границе страницы — это признак чтения
за самым концом выделения: буфер-источник отображён по 0x1648DFFF,
а сразу за ним памяти нет. По стеку минидампа источник и приёмник
различаются явно: memmove вызван как memmove(dest=[esp]=0x0E323648,
src=[esp+4]=0x1648DF28, size=[esp+8]); источник (ESI, к моменту сбоя
0x1648DFB0) — буфер спрайта this, приёмник (EDI = 0x0E3236D0) — целевая
поверхность экрана. Запись в приёмник шла без сбоя; битая сторона —
источник (буфер спрайта).

4. Цепочка вызовов и контекст
-----------------------------
Сырой обход стека V2 в логе пропустил кадр блиттера и показал
сразу hota.dll; настоящую цепочку восстановили по стеку из
минидампа (адрес возврата _memmove_0 лежит на стеке явно):

-> h3hota HD.exe — игровой код отрисовки (интерфейс/диалоги, карта приключений, эффекты боя)
-> HD_HOTA.dll — слой перехватов HD-мода
-> hota.dll sub_10076B00 — диспетчер формата поверхности
-> HD_TC2.dll sub_2005B30 — True32-порт функции SoD A0_Pcx16_Draw
-> HD_TC2.dll _memmove_0 — ВЫЛЕТ: чтение [ESI+50h] = 0x1648E000

Обоснование кадров по стеку минидампа:
    [ESP+8] = 0x03B45C3C = HD_TC2.dll+0x5C3C  (возврат из
              _memmove_0 в sub_2005B30, точка вызова 0x2005C37)
    [EBP+4] = 0x6D626B81 = hota.dll+0x76B81  (возврат из
              sub_2005B30 в sub_10076B00, после call eax)

Диспетчер hota.dll sub_10076B00 проверяет FourCC формата поверхности
в поле [+14h]. Для формата 'P32F' (0x46323350) он вызывает собственный
обработчик hota.dll; для любого другого формата передаёт работу
HD-моду через глобальный менеджер dword_106349DC (виртуальный вызов
[edx+2Ch] возвращает указатель на блиттер, затем call eax с this =
поверхность). В данном вылете пройдена вторая ветвь — формат
источника НЕ 'P32F'.

Подсистема. sub_2005B30 зарегистрирована как перехват функции SoD
A0_Pcx16_Draw_sub_44DF80 (паттерн регистрации push offset sub_2005B30
/ push 44DF80h / call [ecx+3Ch]). Оригинальная функция — универсальный
блиттер 16-битных поверхностей Pcx16: в движке её вызывают около 30
функций (эффекты боя A0_Battle_Stack_DrawShot_Bullet, статические
изображения диалогов A0_DlgStaticPcx16_Draw и A0_DlgStaticPcx8_Draw_
ToScreen, полное обновление карты приключений A0_AdvMgr_FullUpdate
и другие). Источник (спрайт this) — объект _Pcx16_, то есть 16-битная
поверхность по самому контракту функции (оригинал копирует WORD по
2 байта на пиксел). Кадры стека ниже диспетчера hota.dll (окрестности
A0_DlgStaticPcx16_Draw, A0_Pcx8_Draw_To_Pcx16, A0_AdvMgr_FullUpdate)
указывают скорее на отрисовку интерфейса/диалога или карты приключений,
чем боя; впрочем, точный вызывающий код определяется только в рантайме
(нижние кадры могут быть остатками предыдущих вызовов).

5. Первопричина
---------------
Дефект — рассинхрон формата между данными и блиттером в конвейере
True32 HD-мода.

Оригинал SoD A0_Pcx16_Draw_sub_44DF80 — строго 16-битная функция
(имя Pcx16 отражает формат). Она копирует по 2 байта на пиксел:

    .text:0044E002  lea  eax, [eax+ebx*2]   ; 2 * src_x (16 бит)
    .text:0044E00F  lea  ebx, [ecx+edx*2]   ; 2 * dst_x (16 бит)
    .text:0044E038  *(_WORD *)dst = *(_WORD *)src  ; копия WORD
    .text:0044E04A  v19 = v19 + 2           ; +2 байта на пиксел

Порт HD_TC2 sub_2005B30 использует те же самые смещения полей
объекта (шаг строки в [+2Ch], буфер в [+30h]), но копирует уже
по 4 байта на пиксел (32 бита), построчно через memmove:

    .text:02005C2A  lea  eax, ds:0[edx*4]   ; размер строки = ширина*4
    .text:02005C34  push eax                ; Size = ширина*4 (32 бита)
    .text:02005C35  push edi                ; Src = this->buffer (источник)
    .text:02005C36  push esi                ; dest = surface_buffer (приёмник)
    .text:02005C37  call _memmove_0
    .text:02005C42  add  esi, [ebp+arg_24]  ; приёмник += surface_scaneline
    .text:02005C45  add  edi, [eax+2Ch]     ; источник += [this+2Ch]
    .text:02005C4B  sub  ebx, 1             ; счётчик строк (высота)

То есть размер копирования на строку всегда ширина*4 (в расчёте на
32-битные данные). Источник — буфер самого спрайта this ([this+30h],
шаг [this+2Ch]); приёмник — целевая поверхность surface_buffer, её шаг
surface_scaneline передаётся в arg_24. Аргументы конкретного вызова,
извлечённые из стека минидампа (EBP = 0x001A9D70): область рисования
291x284, размер строки arg_28 = 1164 = 291*4 (32 бита), назначение
1180x664 с шагом surface_scaneline = 4732 (примерно 1180*4 — приёмник
действительно 32-битный). Источник же (спрайт this = 0x11BCBC40)
стартует с 0x1648DF28 и исчерпывает своё выделение на границе страницы
0x1648E000: из нужных на строку 1164 байт отображено лишь 216.

В режиме True32 (Graphics.Mode = 5) HD-мод должен заранее преобразовать
16-битные спрайты Pcx16 в 32-битные, чтобы такое копирование было
корректным. Если спрайт this остался 16-битным (его буфер и/или шаг
[+2Ch] соответствуют 2 байтам на пиксел), чтение ширина*4 заходит за
конец его выделения — наблюдаемый сбой на границе страницы 0x1648E000.

Поставщик битых аргументов — sub_2005B30 (размер ширина*4 при 16-битном
спрайте); более глубокий поставщик — конвейер True32-преобразования
HD-мода, который не привёл этот спрайт к 32 битам. Хук sub_2005AF0
(замена A0_Pcx16_SetBuffer) лишь пассивно сохраняет переданные ему
буфер ([+30h]) и шаг ([+2Ch]) спрайта и сам ничего не преобразует —
формат спрайта определяется выше по потоку. Падающая вспомогательная
функция _memmove_0 и сам блиттер sub_2005B30 для 32-битных данных
корректны.

Виновный модуль — HD-мод (HD_TC2.dll, подсистема True32). Оригинальная
функция SoD корректна: она читает 16-битные данные как 16-битные и за
границы буфера не выходит. Дефект внесён портом HD-мода, который
применяет 32-битный размер копирования к данным, не всегда
преобразованным в 32 бита; это не наследуется от SoD. Поле формата
[+14h] поверхности, которую диспетчеризует hota.dll, в данном вылете
не равно 'P32F' (пройдена вторая ветвь) — согласуется с не-32-битной
природой данных.

7. Воспроизведение вылета
-------------------------
Гарантированной пошаговой последовательности нет: сбой зависит от
того, какая именно поверхность Pcx16 окажется не преобразована в
32 бита, а это статикой не определяется (объект-источник в минидампе
отсутствует). Ниже — вероятностный путь и дифференциальный тест.

Условие активации пути: режим True32 (Graphics.Mode из набора
4/5/7 — внутренняя глубина 32 бита) и операция отрисовки, которая
копирует 16-битную поверхность Pcx16 (статические изображения
диалогов и интерфейса, элементы карты приключений, эффекты боя).

Вероятностный путь: запустить игру в режиме Graphics.Mode = 5 и
прогонять сценарии с активной отрисовкой поверхностей Pcx16
(открытие диалогов с изображениями, перемещение по карте приключений,
бои) на разных разрешениях и
картах, чтобы поймать момент, когда конкретная поверхность отдастся
блиттеру в 16 битах. Цель — снять полный минидамп.

Дифференциальный тест (подтверждение причины): повторить тот же
сценарий, переключив Graphics.Mode на режим с внутренней глубиной
16 бит (например 0/1/2/3/6). Если в 16-битном режиме вылет
исчезает, а в True32 возвращается — механизм «32-битное чтение
16-битного источника» подтверждён.

Что ловить в полном дампе (для локализации конкретной поверхности):
включить <Sys.FullDump> = 1 в _HD3_Data/Settings/hota.ini, затем в
полученном полном дампе прочитать объект-источник — его шаг строки
[+2Ch], указатель буфера [+30h] и FourCC формата [+14h]; сравнить
шаг с ожидаемым для 32 бит (ширина*4) и для 16 бит (ширина*2).

8. Достоверность и ограничения
------------------------------
Подтверждено:
- Версия листинга HD_TC2.dll: imagebase 0x2000000, точка входа
  DllEntryPoint (0x200E8A7) совпадает с логом; инструкция краха
  сверена побайтно с кодом из минидампа (66 0F 6F 6E 50).
- Точка сбоя и адресная арифметика: ESI + [+50h] = 0x1648E000
  в точности равно адресу исключения; битая сторона — источник.
- Непосредственный вызывающий код — sub_2005B30: адрес возврата
  0x03B45C3C извлечён из стека минидампа (сырой обход V2 в логе
  этот кадр пропустил и показал сразу hota.dll).
- Контракт прочитан побайтно: оригинал SoD A0_Pcx16_Draw — 16 бит
  (2 байта/пиксел, копия WORD), порт HD_TC2 sub_2005B30 — 32 бита
  (4 байта/пиксел, memmove с размером ширина*4); смещения полей
  объекта ([+2Ch], [+30h]) идентичны.
- Регистрация перехвата: sub_2005B30 замещает функцию SoD по
  адресу 0x44DF80 (A0_Pcx16_Draw).
- Аргументы вызова из стека минидампа: размер строки arg_28 = 1164
  = 291*4 (копирование 32-битное), приёмник 1180x664 с шагом 4732
  (примерно 1180*4 — 32-битный экран); источник и приёмник различены
  по стеку (memmove dest=[esp], src=[esp+4]) — перерасход идёт по
  буферу спрайта this, а не по внешней поверхности.

Ограничения:
- Единственный дамп: уверенность в механизме высокая (подтверждён
  арифметикой, аргументами из стека и чтением поставщика), но
  обобщение о частоте и распространённости ограничено одним
  наблюдением.
- Минидамп сокращённый (только код и стек): куча и объект спрайта
  this (0x11BCBC40) отсутствуют, поэтому его точный шаг [+2Ch] и
  формат не прочитать. Факт 16-битного размера выделения спрайта
  доказан геометрией (из нужных на строку 1164 байт отображено лишь
  216, сбой на границе страницы): будет ли шаг [+2Ch] равен 582
  (16 бит) или 1164 (32 бита при укороченном буфере), буфер спрайта
  рассчитан на 16 бит. Для прямого чтения шага и формата нужен
  полный дамп.
- Конкретный спрайт/эффект, оказавшийся 16-битным, статикой не
  определяется — нужна воспроизводимость.
- Часть нижних кадров стека (ntdll RtlAllocateHeap, отдельные кадры
  HD_HOTA/h3hota) — вероятные остатки предыдущих вызовов, а не
  реальная цепочка этого вылета.

Полезность лога — СРЕДНЯЯ. Механизм и виновник локализованы точно
(32-битное чтение 16-битного источника в True32-блиттере HD_TC2),
но падающая вспомогательная функция и сам блиттер корректны для
32-битных данных: дефект находится у поставщика — в конвейере
True32-преобразования поверхностей HD-мода. Точечная правка возможна
не в точке сбоя, а конкретная не преобразованная поверхность
определяется только в рантайме (полный дамп / воспроизведение).

ВЫВОД
-----
Виновник — HD-мод (модуль HD_TC2.dll, подсистема True32). Суть
дефекта: True32-порт sub_2005B30 замещает 16-битную функцию SoD
A0_Pcx16_Draw и копирует пиксели как 32-битные (ширина*4 байта на
строку через memmove). Когда поверхность-источник остаётся 16-битной,
суммарное чтение примерно вдвое превышает её выделение и завершается
