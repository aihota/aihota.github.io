====================================================

Модель: Qwen 3.8
Дата: 28.07.2026
Заключение: Виновник — HD-мод (HD_HOTA.dll). Перехватчик обновления
сетевого лобби передаёт оконной процедуре нулевой указатель на диалог,
а та обращается к нему по смещению 0x48.

КРАТКОЕ РЕЗЮМЕ
--------------
Когда HD-мод обновляет интерфейс сетевого лобби, он отправляет оконной
процедуре лобби отложенное уведомление и намеренно подставляет ей
нулевой указатель на диалог — инструкцией «xor ecx, ecx» перед самым
вызовом. Живой объект диалога у перехватчика при этом есть, и выше по
коду он им пользуется. Оконная процедура указатель не проверяет
и уходит в цепочку обработки, которая в конце читает поле объекта по
смещению 0x48 от нуля. Итог — обращение по адресу 0x00000048 и вылет.
Корневой регистр — EBX: он равен нулю и служит базой для чтения. Путь
детерминирован, но срабатывает только на одном редком событии в сетевом
лобби — потому репорт и единичный. Дефект находится в закрытом модуле
HD-мода, так что это материал для репорта разработчикам HD-мода, а не
правка кода HotA.

5. Инструкция краша и адресная проверка
---------------------------------------
Точка сбоя (функция sub_1060430, метка loc_1060462):

    .text:01060462  loc_1060462:                  ; CODE XREF: sub_1060430+2E
    .text:01060462                  mov     eax, [ebx+48h]

Адресная проверка: база (EBX = 0x00000000) плюс смещение поля 0x48
даёт 0x00000048 — ровно адрес сбоя из Exception. Проверка сошлась.

Как устроен отказ. Функция sub_1060430 — thiscall: объект диалога
приходит в ECX и оседает в EDI. В начале функции есть ветка, которая
выбирает объект-элемент управления:

    .text:01060444                  mov     edi, ecx        ; edi = this
    .text:0106044C                  mov     eax, 5FF5B0h    ; eax = константа
    .text:01060451                  test    edi, edi        ; this == NULL?
    .text:01060453                  jz      short loc_1060460
    .text:01060455                  push    1068h
    .text:0106045A                  call    eax             ; ebx = GetControl(0x1068)
    .text:0106045C                  mov     ebx, eax
    .text:0106045E                  jmp     short loc_1060462
    .text:01060460  loc_1060460:
    .text:01060460                  xor     ebx, ebx        ; ebx = 0
    .text:01060462  loc_1060462:
    .text:01060462                  mov     eax, [ebx+48h]  ; КРАШ

Если this равен NULL, код обнуляет EBX (ветка loc_1060460) и тут же,
без всякой проверки, читает [ebx+48h]. Проверка «test edi,edi»
получается половинчатой: базу обнулить обнулили, а вот чтение поля
дальше не прикрыли. Ниже по функции объект диалога (EDI) читают
напрямую и тоже не проверяя:

    .text:01060582  loc_1060582:
    .text:01060582                  mov     eax, [edi]      ; также this без проверки

Выходит, у sub_1060430 вообще нет рабочего пути при this == NULL:
она падает либо на [ebx+48h], либо чуть позже на [edi].

проверили дизассемблированием реально загруженного модуля под Wine

7. Анализ регистров и группировка
---------------------------------
Регистровая картина (единственный дамп):
    EDI = 0x00000000  — объект диалога (this), равен NULL;
    EBX = 0x00000000  — база для чтения, обнулена веткой loc_1060460;
    ECX = 0x00000000  — равен this (на входе sub_1060430; по дороге к
                        точке сбоя не менялся);
    EAX = 0x005FF5B0  — константа-указатель на вспомогательную функцию:
                        её загружает «mov eax, 5FF5B0h», и она так и
                        остаётся в EAX, потому что при this == NULL
                        вызов пропускается переходом jz. Сама эта
                        константа в EAX прямо говорит, что пройден путь
                        this == NULL через ветку loc_1060460;
    ESI = 0x22B93EE8  — указатель на элемент массива лобби
                        (esi = [массив + индекс*4], корректный).

Все четыре «нулевых» регистра (ECX, EDX, EBX, EDI) вместе с константой
в EAX складываются в один и тот же путь: this равен NULL от самого
входа и до точки сбоя.


8. Первопричина
---------------
Нулевой указатель диалога — не следствие порчи памяти. Код HD-мода сам
его создаёт и сам проносит по всей цепочке вызовов.

Источник нуля — перехватчик sub_1077070. В конце функции, обновив
элементы интерфейса лобби, код передаёт отложенное уведомление оконной
процедуре:

    .text:01077532                  mov     edx, dword_120F378  ; уведомление
    .text:01077538                  test    edx, edx
    .text:0107753A                  jz      short loc_1077543   ; если нет — пропуск
    .text:0107753C                  xor     ecx, ecx            ; this = NULL
    .text:0107753E                  call    sub_106FDD0         ; вызов с this=NULL

Инструкция «xor ecx, ecx» намеренно кладёт в ECX (то есть в this) ноль.
При этом исправный объект диалога у функции есть: он приходит в arg_4,
ложится в EDI и активно используется выше по коду (чтение полей
[edi+65h], [edi+388h], вызовы методов объекта). Иначе говоря,
перехватчик мог передать настоящий объект, а передаёт ноль.

У оконной процедуры sub_106FDD0 (191 case сообщений лобби) проверки
this == NULL нет ни на входе, ни в теле: на входе сразу «mov edi, ecx»
и прыжок в таблицу сообщений, а многие case'ы читают EDI напрямую.
Договор у процедуры простой — this всегда живой (штатный диспетчер
движка передаёт настоящий объект). Передача нуля этот договор ломает.

Дальше ноль едет транзитом по всей цепочке:
  - sub_106FDD0 case 23 передаёт управление sub_106A570, ECX не трогая
    (исходный this так и остаётся нулевым);
  - sub_106A570 прячет this в локальную переменную и позже передаёт его
    обратно в оконную процедуру:

    .text:0106A5A6                  mov     [ebp-44h], ecx      ; сохранить this
    .text:0106B83C                  mov     ecx, [ebp-44h]      ; this (= NULL)
    .text:0106B83F                  mov     edx, edi
    .text:0106B841                  call    sub_106FDD0         ; case 11

  - sub_106FDD0 case 11 передаёт this дальше, в sub_1060640:

    .text:0106FE6B                  mov     edx, dword_120F25C
    .text:0106FE71                  mov     ecx, edi            ; this (= NULL)
    .text:0106FE73                  push    1
    .text:0106FE75                  call    sub_1060640

  - sub_1060640 перед вызовом sub_1060430 ECX не меняет, поэтому нулевой
    this доезжает до падающей функции, где обнуляет EBX и приводит к
    чтению [0+48h].

Что штатный путь передаёт исправный объект, видно по соседнему коду:
та же функция sub_1070310 (sub_1077070 зовёт её прямо перед проблемной
передачей) отправляет ТО ЖЕ уведомление с живым объектом и с
проверкой:

    .text:01071B73                  mov     edx, dword_120F378
    .text:01071B79                  mov     ecx, eax            ; this = var_7C (валидный)
    .text:01071B7B                  call    sub_106FDD0

Глобальная переменная dword_120F378 (отложенное уведомление)
выставляется в sub_1070310 и после передачи НЕ обнуляется (единственная
запись — .text:01071B51). Поэтому sub_1077070, вызвав sub_1070310,
видит её ненулевой и передаёт то же уведомление ещё раз — уже с нулевым
this.

Если сравнить два пути, всё видно: штатный диспетчер (sub_1070310)
передаёт живой объект под проверкой «test eax,eax; jz», а проблемный
перехватчик (sub_1077070) — ноль без проверки. Дефект и есть это
расхождение между двумя путями передачи одного и того же уведомления.

Кроме того, сама падающая функция sub_1060430 защищена неполно: при
this == NULL она обнуляет EBX, но чтение [ebx+48h] дальше не прикрывает.
Это вторичная грань того же дефекта в HD-моде.

Детерминированность и частота. Путь детерминирован: каждый раз, когда
перехватчик sub_1077070 срабатывает и отложенное уведомление
dword_120F378 попадает в case, который читает this (здесь case 23,
затем case 11 при dword_120F37C != 3), случается обращение по нулевому
указателю. Редкость вылета объясняется тем, что sub_1077070 — узкий
перехватчик одного конкретного события сетевого лобби (зарегистрирован
через виртуальный метод [ecx+1Ch] объекта dword_120F564), а не общий
насос сообщений. Детерминированный сбой на редком пути и даёт
единичные репорты — это вяжется с одним имеющимся дампом.

11. Воспроизведение вылета
--------------------------
По воспроизводимости: сбой детерминирован, но живёт на редком пути.
Гарантированного рецепта «нажми сюда — получи вылет» статика не даёт:
точное событие сетевого лобби, которое запускает перехватчик sub_1077070
с нужным отложенным уведомлением, видно только в рантайме.

Вероятностный путь для тестера:
  1) Среда: HD-мод 5.7 R33, HotA 1.8.0, сетевая партия (Network Game = 1).
  2) Действия в сетевом лобби / окне настройки мультиплеера: менять
     состояние слотов игроков (вход/выход игрока, смена готовности,
     переназначение, старт партии) — это как раз те события, которые
     обновляют иконки игроков (person / playing / global / lock) и
     могут выставить отложенное уведомление.
  3) Массовый прогон: многократно гонять сценарии настройки сетевой
     партии на разных раскладах слотов, пока не совпадёт «перехватчик
     сработал + отложенное уведомление попало в case, читающий this».
  4) Что ловить в минидампе: EBX = 0, EDI = 0, ECX = 0, EAX = 0x005FF5B0,
     адрес сбоя читает [ebx+48h]; в стеке — цепочка sub_1077070, затем
     оконная процедура лобби (case 23), диспетчер, оконная процедура
     (case 11), sub_1060640, sub_1060430.

Дифференциальная проверка (подтверждает причину): если в рантайме
перехватить перехватчик sub_1077070 и подать на вход оконной процедуры
живой объект диалога вместо нуля — либо обнулить отложенное уведомление
dword_120F378 до проблемной передачи, — вылет на этом пути пропадает.
Значит, причина именно в передаче нулевого указателя.


Достоверность и ограничения
---------------------------
Подтверждено:
- версия листинга HD_HOTA.dll-5.7 R33 сходится с логом по точке входа
  (entry point 0x09084547 ложится на DllEntryPoint @ 0x011C4547) и по
  тому, что адрес сбоя попадает в осмысленный код иконок лобби;
- падающий путь и точка вызова проверены дизассемблированием
  загруженного модуля под Wine (HD_HOTA.dll по базе 0x023D0000):
  «xor ecx, ecx» стоит прямо перед «call sub_106FDD0» (ECX уходит
  нулевым), падающая инструкция «mov eax, [ebx+48h]» и весь путь
  совпадают с листингом побайтно;
- адресная проверка сошлась: EBX (0) + 0x48 == 0x00000048;
- механизм (где и как падает) доказан чтением падающей функции и всей
  цепочки, по которой проходит нулевой указатель, — уверенность
  высокая;
- место дефекта (перехватчик sub_1077070 передаёт this = NULL
  инструкцией «xor ecx, ecx», хотя живой объект есть) доказан чтением
  кода — уверенность высокая;
- штатный путь (sub_1070310) передаёт живой объект с проверкой, что
  подтверждает договор «this всегда живой» и ненормальность нулевого
  пути.

Ограничения:
- дамп единственный, поэтому корреляция по серии недоступна;
- точное событие сетевого лобби, запускающее перехватчик sub_1077070
  с нужным уведомлением, статикой не установить (перехватчик
  зарегистрирован через виртуальный метод, а идентификатор события
  0x587FD0 его смысла не раскрывает) — это точка проверки в рантайме;
- кадры 02D0D409 / 02D11D91 — трамплины patcher_x86, листинга для них
  не существует по определению; кадры h3hota_HD.exe (0x1FFACB,
  0x184F0C) — периферийный вызывающий мост, для диагноза не нужны;
- вердикт полезности ВЫСОКАЯ: код сам создаёт неверное значение
  (нулевой указатель диалога) и сам передаёт его в функцию, которая его
  читает, при том что живой объект есть. Это локализованный конкретный
  дефект. Отсутствие проверок памяти здесь вторично и само по себе
  полезность не обосновывает — обосновывает именно созданный неверный
  вход.


ВЫВОД
-----
Виновник — HD-мод (модуль HD_HOTA.dll, версия 5.7 R33). Перехватчик
обновления сетевого лобби sub_1077070 передаёт отложенное уведомление
оконной процедуре лобби sub_106FDD0 и намеренно подставляет нулевой
указатель диалога (инструкция «xor ecx, ecx»), хотя живой объект
диалога у него есть и выше по коду он им пользуется. Оконная процедура
указатель не проверяет и через цепочку case 23, диспетчер sub_106A570,
case 11, sub_1060640 доходит до sub_1060430, которая читает нулевую базу
по смещению 0x48 (адрес сбоя 0x00000048). Штатный диспетчер того же
уведомления передаёт живой объект с проверкой — это и показывает, что
нулевой путь ненормален. Дефект в логике HD-мода; материал предназначен
для репорта разработчикам HD-мода, а не для правки кода HotA.
