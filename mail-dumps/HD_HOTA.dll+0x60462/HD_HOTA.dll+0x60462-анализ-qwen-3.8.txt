КРАТКОЕ РЕЗЮМЕ
--------------
При обновлении интерфейса сетевого лобби HD-мод диспетчит отложенное
уведомление оконной процедуре лобби, намеренно передавая ей нулевой
указатель на объект диалога (инструкция «xor ecx, ecx» перед вызовом),
хотя валидный объект диалога у callback'а есть и используется им выше.
Оконная процедура не проверяет указатель и уходит в цепочку обработки,
которая заканчивается чтением поля объекта по смещению 0x48 от нуля.
Итог — обращение по адресу 0x00000048 и аварийное завершение. Корневой
регистр — EBX (равен 0), база разыменования. Вылет детерминирован для
конкретного редкого события в сетевом лобби, чем объясняется единичный
репорт. Дефект находится в закрытом модуле HD-мода — это репорт
разработчикам HD-мода, а не правка кода HotA.

5. Инструкция краша и адресная проверка
---------------------------------------
Точка сбоя (функция sub_1060430, метка loc_1060462):

    .text:01060462  loc_1060462:                  ; CODE XREF: sub_1060430+2E
    .text:01060462                  mov     eax, [ebx+48h]

Адресная проверка: база(EBX = 0x00000000) + смещение поля 0x48 ==

Механика отказа. Функция sub_1060430 — thiscall, объект диалога
приходит в ECX и сохраняется в EDI. В голове функции есть ветка выбора
объекта-элемента управления:

    .text:01060444                  mov     edi, ecx        ; edi = this
    .text:0106044C                  mov     eax, 5FF5B0h    ; eax = константа
    .text:01060451                  test    edi, edi        ; this == NULL?
    .text:01060453                  jz      short loc_1060460
    .text:01060455                  push    1068h
    .text:0106045A                  call    eax             ; ebx = GetControl(0x1068)
    .text:0106045C                  mov     ebx, eax
    .text:0106045E                  jmp     short loc_1060462
    .text:01060460  loc_1060460:
    .text:01060460                  xor     ebx, ebx        ; ebx = 0
    .text:01060462  loc_1060462:
    .text:01060462                  mov     eax, [ebx+48h]  ; КРАШ

Когда this равен NULL, код обнуляет EBX (ветка loc_1060460) и тут же
БЕЗ проверки разыменовывает [ebx+48h]. То есть проверка «test edi,edi»
реализована лишь наполовину: обнулить базу обнулили, а последующее
чтение поля не защитили. Ниже по функции объект диалога (EDI)
разыменовывается напрямую и тоже без проверки:

    .text:01060582  loc_1060582:
    .text:01060582                  mov     eax, [edi]      ; также this без проверки

Значит функция sub_1060430 в принципе не имеет рабочего пути при
this == NULL: она падает либо на [ebx+48h], либо позже на [edi].

7. Анализ регистров и группировка
---------------------------------
Регистровый инвариант (единственный дамп):
    EDI = 0x00000000  — объект диалога (this), равен NULL;
    EBX = 0x00000000  — база разыменования, обнулена веткой loc_1060460;
    ECX = 0x00000000  — равен this (на входе sub_1060430; на пути к
                        точке сбоя не переопределялся);
    EAX = 0x005FF5B0  — константа-указатель на вспомогательную функцию,
                        загружена инструкцией «mov eax, 5FF5B0h» и НЕ
                        перезаписана, так как при this == NULL вызов
                        пропущен переходом jz. Наличие этой константы
                        в EAX прямо подтверждает пройденный путь
                        (this == NULL, ветка loc_1060460);
    ESI = 0x22B93EE8  — указатель на элемент массива лобби
                        (esi = [массив + индекс*4], корректный).

Все четыре «нулевых» регистра (ECX, EDX, EBX, EDI) и константа в EAX
согласованно описывают один и тот же путь: this равен NULL от самого
входа до точки сбоя.


8. Первопричина
---------------
Нулевой указатель диалога не является следствием порчи памяти — он
явно производится самим кодом HD-мода и передаётся по цепочке вызовов.

Поставщик нулевого указателя — callback sub_1077070. В конце функции,
после обновления элементов интерфейса лобби, код диспетчит отложенное
уведомление оконной процедуре:

    .text:01077532                  mov     edx, dword_120F378  ; уведомление
    .text:01077538                  test    edx, edx
    .text:0107753A                  jz      short loc_1077543   ; если нет — пропуск
    .text:0107753C                  xor     ecx, ecx            ; this = NULL
    .text:0107753E                  call    sub_106FDD0         ; вызов с this=NULL

Инструкция «xor ecx, ecx» намеренно кладёт в ECX (this) ноль. При этом
валидный объект диалога у функции ЕСТЬ — он приходит в arg_4,
сохраняется в EDI и активно используется выше по функции (чтение полей
[edi+65h], [edi+388h], вызовы методов объекта). То есть callback мог
передать реальный объект, но передаёт ноль.

Оконная процедура sub_106FDD0 (191 case сообщений лобби) не имеет
проверки this == NULL ни на входе, ни в теле: на входе сразу
«mov edi, ecx» и переход в таблицу сообщений, а многие case'ы
разыменовывают EDI напрямую. Контракт процедуры — this всегда валиден
(штатный диспетчер движка передаёт реальный объект). Передача нуля
нарушает этот контракт.

Дальше ноль транзитом проходит по цепочке:
  - sub_106FDD0 case 23 передаёт управление sub_106A570, не меняя ECX
    (исходный this остаётся нулевым);
  - sub_106A570 сохраняет this в локальную переменную и позже передаёт
    его обратно в оконную процедуру:

    .text:0106A5A6                  mov     [ebp-44h], ecx      ; сохранить this
    .text:0106B83C                  mov     ecx, [ebp-44h]      ; this (= NULL)
    .text:0106B83F                  mov     edx, edi
    .text:0106B841                  call    sub_106FDD0         ; case 11

  - sub_106FDD0 case 11 передаёт this дальше в sub_1060640:

    .text:0106FE6B                  mov     edx, dword_120F25C
    .text:0106FE71                  mov     ecx, edi            ; this (= NULL)
    .text:0106FE73                  push    1
    .text:0106FE75                  call    sub_1060640

  - sub_1060640 не переопределяет ECX перед вызовом sub_1060430,
    поэтому нулевой this попадает в падающую функцию, где обнуляет EBX
    и приводит к чтению [0+48h].

Подтверждение того, что штатный путь передаёт валидный объект: та же
самая функция sub_1070310 (которую sub_1077070 вызывает непосредственно
перед проблемным диспетчем) диспетчит ТО ЖЕ уведомление с валидным
объектом и под проверкой:

    .text:01071B73                  mov     edx, dword_120F378
    .text:01071B79                  mov     ecx, eax            ; this = var_7C (валидный)
    .text:01071B7B                  call    sub_106FDD0

Глобальная переменная dword_120F378 (отложенное уведомление)
устанавливается в sub_1070310 и НЕ обнуляется после диспетча
(единственная запись — .text:01071B51). Поэтому sub_1077070 после
вызова sub_1070310 видит её ненулевой и повторно диспетчит то же
уведомление — уже с нулевым this.

Сравнение с родственными путями: штатный диспетчер (sub_1070310)
передаёт валидный объект под проверкой «test eax,eax; jz», а проблемный
callback (sub_1077070) — ноль без проверки. Расхождение между двумя
путями диспетча одного и того же уведомления и есть дефект.

Дополнительно: падающая функция sub_1060430 содержит неполную защиту
(обнуляет EBX при this == NULL, но не защищает последующее чтение
[ebx+48h]). Это вторичный фактор того же дефекта в HD-моде.

Детерминированность и частота. Путь детерминирован: всякий раз, когда
callback sub_1077070 срабатывает и отложенное уведомление dword_120F378
маршрутизируется в case, разыменовывающий this (здесь case 23, далее
case 11 при dword_120F37C != 3), происходит обращение по нулевому
указателю. Редкость вылета объясняется тем, что sub_1077070 — узкий
callback конкретного события сетевого лобби (зарегистрирован через
виртуальный метод [ecx+1Ch] объекта dword_120F564), а не общий насос
сообщений: детерминированный сбой в редком пути даёт единичные репорты,
что согласуется с одним имеющимся дампом.

11. Воспроизведение вылета
--------------------------
Уровень воспроизводимости: детерминированный сбой в редком пути.
Гарантированной пошаговой последовательности «нажать сюда — получить
вылет» статика не даёт, потому что точное событие сетевого лобби,
запускающее callback sub_1077070 с нужным отложенным уведомлением,
устанавливается только наблюдением в рантайме.

Вероятностный путь для тестера:
  1) Среда: HD-мод 5.7 R33, HotA 1.8.0, сетевая партия (Network Game = 1).
  2) Действия в сетевом лобби / окне настройки мультиплеера: смена
     состояния слотов игроков (вход/выход игрока, смена готовности,
     переназначение, старт партии) — это события, обновляющие иконки
     игроков (person / playing / global / lock) и способные выставить
     отложенное уведомление.
  3) Массовый прогон: многократно повторять сценарии настройки сетевой
     партии на разных конфигурациях слотов, добиваясь совпадения
     «callback сработал + отложенное уведомление маршрутизировалось
     в разыменовывающий this case».
  4) Что ловить в минидампе: EBX = 0, EDI = 0, ECX = 0, EAX = 0x005FF5B0,
     адрес сбоя читает [ebx+48h]; в стеке — цепочка sub_1077070, затем
     оконная процедура лобби (case 23), диспетчер, оконная процедура
     (case 11), sub_1060640, sub_1060430.

Дифференциальная диагностика (подтверждение причины): если в рантайме
перехватить callback sub_1077070 и подать на вход оконной процедуры
валидный объект диалога (вместо нуля) либо обнулить отложенное
уведомление dword_120F378 до проблемного диспетча, вылет в этом пути
исчезает — это подтверждает, что причина именно в передаче нулевого
указателя.


Достоверность и ограничения
---------------------------
Подтверждено:
- версия листинга HD_HOTA.dll-5.7 R33 совпадает с логом по точке входа
  (entry point 0x09084547 маппится в DllEntryPoint @ 0x011C4547) и по
  разрешению адреса сбоя в осмысленный код иконок лобби;
- адресная проверка сошлась: EBX (0) + 0x48 == 0x00000048;
- механизм (где и как падает) доказан чтением падающей функции и
  всей цепочки передачи нулевого указателя — высокая уверенность;
- место дефекта (callback sub_1077070 передаёт this = NULL инструкцией
  «xor ecx, ecx» при наличии валидного объекта) доказан чтением кода —
  высокая уверенность;
- штатный путь (sub_1070310) передаёт валидный объект под проверкой,
  что подтверждает контракт «this всегда валиден» и аномальность
  нулевого пути.

Ограничения:
- единственный дамп — корреляция по серии недоступна;
- точное событие сетевого лобби, запускающее callback sub_1077070
  с нужным уведомлением, статикой не устанавливается (callback
  зарегистрирован через виртуальный метод, идентификатор события
  0x587FD0 не раскрывает его смысл) — это точка проверки в рантайме;
- кадры 02D0D409 / 02D11D91 — трамплины patcher_x86, листинга для них
  не существует по определению; кадры h3hota_HD.exe (0x1FFACB,
  0x184F0C) — периферийный вызывающий мост, для диагноза не требуются;
- вердикт полезности ВЫСОКАЯ: код сам производит неверное значение
  (нулевой указатель диалога) и передаёт его в функцию, которая его
  разыменовывает, при наличии валидного объекта — это локализованный
  конкретный дефект. Отсутствие проверок памяти здесь вторично и само
  по себе полезность не обосновывает; обоснование — именно
  сгенерированный неверный вход.


ВЫВОД
-----
Виновник — HD-мод (модуль HD_HOTA.dll, версия 5.7 R33). Callback
обновления сетевого лобби sub_1077070 диспетчит отложенное уведомление
оконной процедуре лобби sub_106FDD0, намеренно передавая нулевой
указатель диалога (инструкция «xor ecx, ecx»), тогда как валидный
объект диалога у callback'а есть и используется им выше. Оконная
процедура не проверяет указатель и через цепочку case 23, диспетчер
sub_106A570, case 11, sub_1060640 доходит до sub_1060430, которая
разыменовывает нулевую базу по смещению 0x48 (адрес сбоя 0x00000048).
Штатный диспетчер того же уведомления передаёт валидный объект под
проверкой, что подтверждает аномальность нулевого пути. Это дефект
логики HD-мода; материал предназначен для репорта разработчикам
HD-мода, а не для правки кода HotA.
