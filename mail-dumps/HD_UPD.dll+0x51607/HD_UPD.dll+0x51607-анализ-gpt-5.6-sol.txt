КРАТКОЕ РЕЗЮМЕ
---------------

Процесс начал исполнять не код, а пиксельные данные встроенного значка
128x128 из секции .rsrc HD_UPD.dll. Аварийный EIP 0x70561607, окно памяти
минидампа и точная локальная DLL совпадают. По этому адресу лежат байты
FF 1A. Если механически трактовать их как x86, получается дальний
косвенный вызов через [EDX], после которого зарегистрировано чтение
0xFFFFFFFF.

Имя TryUpdate в автоматическом стеке ошибочно. Настоящая функция
TryUpdate заканчивается на 0x1000550C, тогда как пересчитанный адрес
аварии равен 0x10051607 и находится в .rsrc. Это подтверждает класс
сбоя, но не показывает, какой callback, return address или иной указатель
передал управление в данные.

Источник перехода восстановить нельзя: ExceptionStream называет поток
15456, а ESP аварийного CONTEXT попадает в стек потока 16724. Эти источники
нельзя объединять в доказанную цепочку. Дополнительный полный проход
корпуса нашёл только этот один уникальный случай.

2. Проверка листинга и адреса
-----------------------------

Runtime-база HD_UPD.dll равна 0x70510000. Адрес пересчитан без
неопределённой дельты:

    0x70561607 - 0x70510000 = RVA 0x51607
    0x10000000 + 0x51607 = IDA VA 0x10051607
    RVA 0x51607 - 0x15C00 = файловое смещение 0x3BA07

RVA попадает в .rsrc: начало 0x3B000, VirtualSize 0x38DA8.
Характеристики секции 0x40000040 означают читаемые данные без флага
исполнения. Фактические права страницы во время сбоя неизвестны, потому
что в DMP нет MemoryInfoList.

Точная DLL имеет TimeDateStamp 0x6A7C2A5A, SizeOfImage 0x76000,
entry RVA 0x7F82 и SHA-256
c04f80ffd94f6c8244d2fd95fad4cf23d7910199b1fe2b5e804be7967d53b9fa.
Поле Input SHA256 листинга R40 содержит тот же хэш. Сам файл листинга
имеет SHA-256
10c6c8bdb1aa5f795efe09a674a7faf072400b0ceed7e861b6a5e929f9bed202.

В 160220 строках точного листинга нет инструкции с адресом 0x10051607.
Экспорт TryUpdate начинается на 0x100047E0, последний retn 10h находится
на 0x10005509, а endp - на 0x1000550C. Следовательно, автоматическое имя
TryUpdate возле EIP является протеканием диапазона через нелистингованные
данные, а не настоящей функцией аварии.

3. Точка сбоя
-------------

DMP сохранил страницу EIP. Окно в DMP и локальной DLL совпадает:

    0x70561600: 00 16 4D FF 01 3E 92 FF 1A AE F1 FF 34 D0 F4 FF
                                      ^ EIP = 0x70561607

Байты с EIP равны FF 1A. Их механическая x86-декодировка:

    FF 1A    call far ptr [edx]

Это не штатная инструкция HD_UPD.dll, а два байта BGRA-пикселей,
случайно интерпретированные процессором как команда. EDX равен
0x08831984, а не 0xFFFFFFFF. Память по EDX в MiniDumpNormal отсутствует,
поэтому точная микроарифметика чтения 0xFFFFFFFF не восстанавливается.
Это чтение является вторичным эффектом уже произошедшего перехода в данные.

Ресурсный путь: RT_ICON, type 3, id 2, language 1049. Данные начинаются
на RVA 0x4E958, имеют размер 0x10828 и заканчиваются на RVA 0x5F180.
Аварийная точка лежит на смещении 0x2CAF внутри ресурса. DIB описывает
32-битный значок 128x128; поле высоты 256 включает XOR- и AND-маски.

    HD_UPD base + 0x4E958 = начало RT_ICON 2
    начало RT_ICON 2 + 0x2CAF = 0x70561607
    [заголовок DIB][пиксели ... FF 1A ...][маска]

4. Цепочка вызовов и контекст
-----------------------------

Доказанная цепочка начинается только с уже ошибочной цели перехода:

-> неизвестный источник косвенной передачи управления - не захвачен
-> HD_UPD.dll .rsrc, RT_ICON 2, пиксельные данные
-> 0x70561607, байты FF 1A - ВЫЛЕТ при исполнении данных

Exception CONTEXT содержит EIP 0x70561607 и ESP 0x00199F48, но
ExceptionStream указывает номер потока 15456. Этот ESP принадлежит диапазону стека
номер потока 16724: 0x001997F0..0x001A0000. ThreadList-контекст номер потока 15456 имеет
EIP 0x777F411C и ESP 0x02CDEE50; контекст номер потока 16724 имеет EIP 0x75EB101C
и ESP 0x001997F4. Ни один из них не совпадает с аварийным CONTEXT ни по
одному из девяти основных регистров.

Содержимое памяти возле 0x00199F48 образует отдельный кандидат контекста.
На вершине находится 0x02CE01B9 вне всех модулей; страница этого адреса
в дампе отсутствует. Ниже встречаются адреса подготовки предглавного меню
в h3hota HD.exe и UI/DEF-обработчиков HD_HOTA.dll. Из-за расхождения
потоков этот набор нельзя использовать как фактического caller аварии.
Стек номер потока 15456 относится к ntdll/dbgcore и записи минидампа, а не даёт
цепочку до 0x70561607.

5. Первопричина
---------------

Подтверждённая непосредственная причина - ошибочная передача управления
на 0x70561607, то есть внутрь пиксельных данных ресурса. Процессор затем
исполнял произвольные байты изображения. Это полностью объясняет
недостоверную инструкцию FF 1A и вторичный нарушение доступа.

Не установлен источник управляющего адреса. Дамп не содержит страницу
предполагаемого runtime-трамплина 0x02CE01B9, память по регистрам EAX,
ECX и EDX, а также полную кучу и глобальное состояние. Поэтому нельзя
различить повреждённый return address, неверно зарегистрированный callback,
битый function pointer и иной косвенный переход.

TryUpdate проверен отдельно, чтобы исключить ложную символизацию. Полное
тело 0x100047E0..0x1000550C содержит 1085 строк, 131 call, 14 косвенных
вызовов разрешённых API-указателей и три пути возврата. Статического
перехода в .rsrc не найдено. Поиск сайта 0x004FBC52 во всех доступных
R40-листингах нашёл только саму инструкцию h3hota, но не регистрацию
перехвата. Эти отрицательные результаты не закрывают неизвестный
виртуальный dispatch или runtime-запись указателя.

Таким образом, HD_UPD.dll однозначно владеет ошибочной целью в своём
ресурсе, но модуль и инструкция, сформировавшие эту цель, не атрибутированы.
Нельзя называть причиной загрузку значка, TryUpdate или конкретный UI-путь:
для такой связи нет доказанной цепочки.

6. Условия сбоя
---------------

Наблюдаемая среда: HotA 1.8.0, HD-мод 5.7 R40, Windows 10 build 19045,
одиночная игра, test.h3m, день 0 00, игрок 0. Разрешение 1024x768,
Graphics.Mode=2, четыре графических потока, OpenGL.Upscaling=2.
Update.CheckAtStart=0. Отчёт сформирован автоматически из побочного потока.

Отдельный стек-кандидат согласуется с подготовкой предглавного меню и
UI/DEF-обёртками, но это лишь ориентир для трассировки. Ни карта, ни число
потоков, ни режим обновления не доказаны как причина. Достаточное условие
известно только на низком уровне: косвенный target должен стать равным
0x70561607 либо другому адресу неисполняемых данных.

7. Воспроизведение вылета
-------------------------

Детерминированный пользовательский сценарий по одному событию не
восстанавливается. Для диагностического повтора нужен вероятностный прогон:

1) Использовать HotA 1.8.0 и HD-мод 5.7 R40 с тем же набором модулей.
2) Повторять запуск игры и переходы через главное/предглавное меню к
   сценарию test.h3m, не объявляя этот путь причиной заранее.
3) Включить <Sys.FullDump> = 1 и сохранять свежий patcher_x86 dump.txt.
4) При событии фиксировать EIP источника косвенного перехода, адрес ячейки
   с target, прежнее и новое значение, номер потока и полный стек одного потока.
5) Отдельно журналировать регистрацию и вызов callback/hook: источник записи,
   owner, target и PE-секцию target.

Признак успешного захвата - трасса, в которой последняя штатная инструкция
перед 0x70561607 видна вместе с адресом хранилища указателя и его источник записи.
Совпадение только конечного EIP повторит локальный диагноз, но не установит
первый источник порчи.

Дифференциальная проверка для HD-мода: перед регистрацией и перед косвенным
вызовом принимать target только внутри исполняемой секции загруженного PE.
Target из .rsrc должен быть отклонён и записан в журнал, а штатные callback
из .text - пройти без изменения поведения. Исчезновение вылета подтвердит
защиту потребителя; происхождение ошибочного target всё равно проверяется
отдельной трассировкой источника записи.

8. Достоверность и ограничения
------------------------------

Независимые оценки:

Точка сбоя: подтверждена DMP-окном и точным бинарником.
Локальный механизм: подтверждён как исполнение данных после плохого EIP.
Первый источник состояния: не установлен.
Полнота семьи: подтверждена в границах 5496 из 5496 TXT и окна +/-0x100.

Подтверждено:

- Точка сбоя подтверждена: EIP, модуль и RVA одинаковы в TXT и DMP.
- DMP-окно и локальная DLL совпадают; по EIP лежат FF 1A.
- RVA 0x51607 входит в пиксели RT_ICON 2/1049 внутри .rsrc.
- Точный R40-листинг связан с DLL одинаковым Input SHA-256.
- TryUpdate заканчивается на 0x1000550C и не содержит аварийный адрес.
- Полный корпусный проход прочитал 5496 из 5496 TXT; точный и ближний
  диапазон содержат только текущий уникальный случай.

Ограничения:

- ExceptionStream называет поток 15456, а диапазоном ESP владеет поток
  16724. Регистры и независимый стек не объединялись в единую цепочку.
- MiniDumpNormal не содержит полную кучу, глобалы, MemoryInfoList и
  страницы по EAX, ECX, EDX и 0x02CE01B9.
- Не приложен patcher_x86 dump.txt; регистрация hook/callback не видна.
- Единственный инцидент не даёт сравнить значения target между повторами.
- Фактические runtime-права страницы .rsrc неизвестны. PE-флаг секции
  запрещает исполнение, но состояние DEP по этому событию не доказано.

Отрицательные результаты:

- 0 строк с собственным адресом 0x10051607; измеренное покрытие равно
  160220 строкам R40-листинга. Контроль - TryUpdate и его границы найдены
  тем же индексом и полным проходом.
- 0 статических переходов в .rsrc в 1085 строках TryUpdate; просмотрены
  131 call, включая 14 косвенных, и три возврата.
- 0 найденных регистраций для h3hota-сайта 0x004FBC52 во всех доступных
  R40-листингах; найдено только собственное место инструкции.
- 0 сохранённых байт по 0x08831984, 0x08A66620, 0x08A66B47 и странице
  0x02CE01B9; отсутствие относится только к MemoryList этого DMP.
- 0 из 25 ThreadList-контекстов совпадают с Exception CONTEXT; у потоков
  15456 и 16724 совпало 0 из 9 основных регистров.
- 0 дополнительных точных или близких уникальных случаев после полного
  прохода 5496 из 5496 TXT.

ВЫВОД
-----

HD_UPD.dll+0x51607 - подтверждённый переход управления в пиксельные данные
встроенного RT_ICON, а не сбой функции TryUpdate. Байты FF 1A в DMP и
точной DLL совпадают; зарегистрированное чтение 0xFFFFFFFF возникло уже
после начала исполнения данных.

Рекомендуемое исправление:

HD-моду следует отклонять косвенные адреса вне исполняемых PE-секций.
Проверку надо выполнять при регистрации и перед каждым косвенным вызовом.
Адреса .rsrc надо отклонять, а источник записи и владельца указателя -
журналировать. Такая защита закрывает локальный потребитель, но не заменяет
поиск источника ошибочного указателя. Для его атрибуции нужен полный DMP
или трасса последнего штатного перехода с адресом ячейки назначения и
свежим patcher_x86 dump.txt.
