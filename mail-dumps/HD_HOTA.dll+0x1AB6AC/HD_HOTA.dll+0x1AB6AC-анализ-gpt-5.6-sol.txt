    Заключение: HD_HOTA.dll принимает пустой слот армии с типом -1 за выбранный и читает элемент [-1] таблицы существ.


КРАТКОЕ РЕЗЮМЕ
--------------

    Вылет происходит в обработчике просмотра героя из диалога таверны. Перед открытием окна героя HD-мод сохраняет семь типов и семь количеств армейских стеков, выбирает стек существа минимального уровня, временно оставляет от него одну единицу, показывает окно героя и затем восстанавливает армию.

    Алгоритм безусловно начинает поиск с индекса слота 0. Кандидатов со значением -1 он пропускает, но текущий выбранный слот перед обращением к таблице существ не проверяет. В целевом случае слоты 0 и 1 пусты, а слот 2 заполнен: тип -1 из слота 0 умножается на размер записи 0x74, поэтому сравнение читает запись перед началом таблицы.

    Диагноз арифметически подтверждён регистрами и инструкцией, статически подтверждён листингами R39 и R30, а корпусный поиск нашёл ту же сигнатуру ещё в четырёх уникальных инцидентах.

    Подтверждённые материалы перемещены в подпапку Краш-логи и дампы старых версий HD-мода: 7 логов, представляющих 4 связанных уникальных вылета, и 1 минидамп R30. Во всём mail-dumps вместе с целевым случаем остаются 8 логов и 5 уникальных инцидентов.

3. Точка сбоя
-------------

    Инструкция сравнивает нулевой индекс уровня кандидата в EAX с полем +4 текущей выбранной записи существа. Левый операнд уже прочитан успешно, а правый операнд обращается по адресу EDX + ECX + 4.

    EAX:                              0x00000006
    ECX:                              0xFFFFFF8C, то есть -0x74
    EDX:                              0x0C620000, база таблицы существ
    ESI:                              0x00000000, выбран слот 0
    EDI:                              0x006747B0, адрес глобального указателя таблицы
    Faulting address:                 0x0C61FF90

Формула: 0x0C620000 - 0x74 + 4 = 0x0C61FF90

    ECX получается инструкцией imul из типа существа в выбранном слоте. Значение -0x74 однозначно означает тип -1. Это штатный сентинел пустого армейского слота, а не произвольный повреждённый указатель.

    Текущий ESI остался равен 0. Первый кандидат, слот 1, был пропущен проверкой на -1; затем слот 2 прошёл эту проверку, его поле уровня было прочитано как 6, и код попытался сравнить его с уровнем несуществующего существа из слота 0. Поэтому для целевого вылета доказана конфигурация: слот 0 пуст, слот 1 пуст, слот 2 заполнен.

5. Первопричина
---------------

    Поставщик данных вычисляется как запись героя в A0_GameMgr: идентификатор берётся из dword_12175A8 по текущему индексу dword_120DCD8, размер записи героя равен 0x492, а армия начинается по смещению +0x91. Листинг h3hota.exe прямо обозначает lea [hero+91h] как &hero->army и копирует 14 dword: семь типов по +0x91..+0xA9 и семь количеств по +0xAD..+0xC5.

    Глобал 0x006747B0 обозначен в оригинальном листинге как Main_MonsersTable_off_6747B0. Он указывает на массив struct_Creature с размером записи 0x74. Второе dword записи, поле +4, последовательно равно 0 для копейщика, 1 для стрелка и 2 для грифона, то есть это нулевой индекс уровня существа.

    Дефект находится в локальной логике HD_HOTA.dll. Поиск начинается с ESI = 0, хотя type[0] может быть равен -1. Для слотов 1..6 проверяется только type[candidate] != -1, после чего без проверки выполняется чтение Creature[type[ESI]].level. Если первый слот пуст, а более поздний заполнен, обращение к Creature[-1] неизбежно.

    Сентинел -1 является допустимой частью контракта _Army_. Оригинальные функции A0_Army_Get_AI_Value_sub_44A950, A0_Army_Get_Stack_Count_sub_44A990 и A0_Army_GetSummCreatureCount_sub_44AA70 обходят все семь слотов и перед использованием каждого типа явно сравнивают его с -1. HD-обработчик нарушает этот образец.

    Совет по исправлению автору HD-мода: инициализировать выбранный индекс значением -1, принимать первый непустой слот без сравнения и сравнивать уровни только после выбора допустимого слота. Для полностью пустой армии нужен отдельный выход. Дополнительно следует проверять диапазон типа существа перед умножением на 0x74; перестановка армии или принудительное заполнение слота 0 маскирует дефект, но не исправляет контракт.

6. Условия сбоя
---------------

    Обязательные условия целевого пути:

- открыт диалог выбора или просмотра героя из таверны;
- обработчик получает сообщение 0x200, подтип 0x0E, item id 0x190;
- dword_120DCD8 не равен -1, то есть герой выбран;
- выбранная запись героя имеет type[0] = -1;
- хотя бы один более поздний армейский слот имеет допустимый тип существа.

    Для адреса R39 +0x1AB6AC дополнительно type[1] = -1 и type[2] != -1. Если первым заполненным окажется слот 1, 3, 4, 5 или 6, тот же дефект может проявиться на R39 по адресам +0x1AB685, +0x1AB6D3, +0x1AB6FA, +0x1AB721 или +0x1AB748. Инцидент R30 +0x160D2A подтверждает вариант, где первым заполненным является слот 4.

    Network Game = 0, Graphics.Mode = 7, Graphics.Threads = 4, Graphics.AdvMap.Threads = -1, Memory.Mod = 0 и Quick Combat = 0 описывают окружение, но не участвуют в достигнутой ветви и не являются причиной. Дефект детерминирован содержимым семи слотов армии.


7. Воспроизведение вылета
-------------------------

    Роль 1 — тестер без отладчика:

1. Запустить HotA 1.8.0 с HD-модом R39 и подготовить героя, доступного из диалога таверны.
2. Оставить слоты армии 0 и 1 пустыми, а в слот 2 поместить один допустимый стек. Для точного повтора целевого регистра выбрать существо уровня 7, у которого поле уровня равно 6.
3. Открыть таверну, перейти к выбору этого героя и вызвать просмотр окна героя для элемента 0x190.
4. Зафиксировать новый лог вылета. Ожидаемый адрес для R39 — HD_HOTA.dll+0x1AB6AC.

    Дифференциальная проверка:

- тот же стек в слоте 0 должен устранить вылет;
- тот же стек в слоте 1 при пустом слоте 0 должен перенести вылет на R39 +0x1AB685;
- стек в слоте 2 при пустых слотах 0 и 1 должен вернуть целевой +0x1AB6AC;
- стек в слоте 4 при пустых слотах 0..3 должен дать аналог четвёртого сравнения, как в R30.

    Роль 2 — подтверждение причины с отладчиком или новым минидампом:

- остановиться перед R39 0x03ABB6AC с учётом фактической базы модуля;
- проверить ESI = 0, ECX = 0xFFFFFF8C и EDI = 0x006747B0;
- подтвердить faulting = EDX - 0x70;
- после патча проверить все семь одиночных размещений стека и полностью пустую армию: обращений к индексу -1 быть не должно.

- в 30 из 30 доступных листингов HD_HOTA.dll найдена та же последовательность выбора; дефект присутствует от доступных RC9 и RC11, R1 и далее до R40;

ВЫВОД
-----

    Виновен HD_HOTA.dll: в sub_11AB4A0 по адресу HD_HOTA.dll+0x1AB6AC обработчик просмотра героя в таверне разыменовывает штатный сентинел пустого армейского слота как индекс существа. Инициализация ESI нулём нарушает контракт разреженной _Army_: кандидат проверяется на -1, а текущий выбранный тип — нет. Формула EDX - 0x74 + 4 точно даёт faulting-адрес, оригинальные функции демонстрируют обязательную проверку сентинела, а четыре независимых связанных инцидента повторяют тот же отпечаток в RC7, RC10, RC12 и R30.

    Автору HD-мода следует заменить безусловный best = 0 на поиск первого непустого слота, обрабатывать полностью пустую армию и проверять диапазон типа перед индексированием Creature[]. Это локальный детерминированный дефект логики, а не сбой драйвера, графического режима или случайная порча памяти. Неполный дамп не позволяет назвать точный id существа и writer конфигурации слотов, но эти ограничения не меняют доказанную первопричину.
