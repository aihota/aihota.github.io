АНАЛИЗ ВЫЛЕТА HD_SCX2.dll+0x221F
====================================

Модель: Qwen 3.8
Дата: 02.08.2026
Заключение: 6-байтовый хук hota.dll на 50D090h затирает байт 50D095h
NOP-заполнением (0x04 -> 0x90); HD_SCX2.dll читает этот байт как сдвиг
шага курсорной таблицы и получает 0x90 (сдвиг 16) вместо 4 -- шаг
раздувается до 0x90000, таблица выделена под меньший размер, выход за
границы при любом типе курсора >= 1 в 32-битных режимах.

Визуализация вылета
-------------------

См. врезку (extra.html).

КРАТКОЕ РЕЗЮМЕ
--------------

Модуль системных курсоров HD-мода (HD_SCX2.dll, «HD_SysCurX2») при
установке курсора обращается к таблице по индексу «тип * шаг + кадр».
Шаг таблицы код читает из байта 50D095h -- это непосредственный операнд
инструкции SoD `shl eax, 4` (оригинальное значение 0x04, шаг 9*16=144).
Но hota.dll ставит на начало функции (50D090h) 6-байтовый хук
(E9 <адрес> 90 = JMP + NOP), и NOP-заполнение ложится ровно на байт
50D095h, меняя его с 0x04 на 0x90. HD_SCX2.dll читает 0x90 как сдвиг:
по модулю 32 это 16, шаг = 9 << 16 = 0x90000 (589824 записи на тип).
Курсорная таблица, на которую указывает 50D09Dh, выделена под гораздо
меньший размер, поэтому любое обращение к типу >= 1 читает память
далеко за пределами буфера.

Предусмотренная кодом перезапись шага настройкой HotA.ArtifactsCount
(~146, реальное число кадров артефактов) НЕ срабатывает: к моменту
чтения настройка равна 0 (HD_SCX2.dll авторегистрирует её с нулём
раньше, чем hota.dll записывает корректное значение), и шаг остаётся
0x90000.

Вылет воспроизводится в 32-битных графических режимах (4, 5, 7) на любой
карте, в любом состоянии игры (включая предыгровое меню). Наблюдается
на 12 версиях HD-мода (5.6 R37 -- 5.7 R35), 34 уникальных вылета.

Модуль:  HD_SCX2.dll (HD_SysCurX2.pdb, подмодуль HD-мода)
Версия HotA:  1.8.0
Версии HD-мода:  5.6 R37, 5.7 RC2, RC6, RC7, RC9, RC11, R6, R10, R19, R21, R22, R24, R35
Класс сбоя:  выход за границы массива
Подсистема:  системные курсоры (отрисовка)
Полезность лога для исправления:  ВЫСОКАЯ
Уникальных вылетов:  34
Исключение:  EXCEPTION_ACCESS_VIOLATION, чтение
Инструкция:  .text:0200221F  mov edx, [ecx+eax*8+4]
Формула адреса:  faulting = ECX + EAX * 8 + 4
Графические режимы:  4 x2, 5 x19, 7 x13 (все -- 32 бит внутренние)

2. Проверка листинга и адреса
------------------------------

Листинг: modules/HD_SCX2.dll.txt
Imagebase:  0x2000000
Timestamp:  6A6D5823 (01.08.2026)
PDB:  HD_SysCurX2.pdb

Entry point лога (R35): 0x03F9623D, load_base 0x03F90000.
IDA-адрес: 0x03F9623D - 0x03F90000 + 0x2000000 = 0x200623D.
В листинге по 0x200623D -- процедура (библиотечная функция CRT).

Адрес сбоя: 0x03F9221F - 0x03F90000 + 0x2000000 = 0x200221F.
По этому адресу: `mov edx, [ecx+eax*8+4]` -- граница инструкции.

Пример контекста (дамп 10, R35):

    Exception { Module: HD_SCX2.dll, Address: HD_SCX2.dll+0x221F }
    Information: read of address: 0x05C84AF4
    Context { EAX: 0x00090001, ECX: 0x05804AE8, EBX: 0x00000001 }

Проверка: ECX + EAX * 8 + 4 = 0x05804AE8 + 0x480008 + 4
= 0x05C84AF4 -- совпадает с адресом сбоя.

3. Точка сбоя
--------------

    .text:0200220F  mov eax, [ebp+arg_4]      ; тип курсора (0-4)
    .text:02002212  imul eax, [ebp+var_4]     ; * шаг таблицы
    .text:02002216  add eax, [ebp+arg_0]      ; + индекс кадра
    .text:02002219  mov ecx, ds:50D09Dh       ; указатель на таблицу
    .text:0200221F  mov edx, [ecx+eax*8+4]    ; СБОЙ: чтение записи

ECX -- указатель на динамически выделенную курсорную таблицу
(записан HD-модом в байты инструкции h3hota.exe по адресу 0x50D09D).
EAX -- вычисленный индекс записи (тип * шаг + кадр).
Каждая запись таблицы -- 8 байт; читается второе поле (смещение +4).

4. Цепочка вызовов и контекст
------------------------------

    hota.dll MainProc (игровой цикл)
    -> HD_HOTA.dll+0x1A7950 (диспетчер событий)
    -> [трамплин patcher_x86]
    -> HD_HOTA.dll+0x174E0 (вызов плагина)
    -> HD_SCX2.dll+0x2030 sub_2002030 (установка курсора)
    -> HD_SCX2.dll+0x221F mov edx,[ecx+eax*8+4] <-- ВЫЛЕТ

Вызывающий код в HD_HOTA.dll (R35, 0x1761C):

    .text:01017617  call dword ptr [eax+2Ch]  ; виртуальный вызов
    .text:0101761A  mov ecx, esi
    .text:0101761C  call eax                  ; вызов sub_2002030
    .text:0101761E  pop edi                   ; адрес возврата

Регистровые инварианты (34 дампа):
- EBX (тип курсора): 1 x25, 2 x8, 4 x1
- EAX: всегда = EBX * 0x90000 + малое число (0-0x75)
- EDX = ESI + 0x54 (указатель MouseMgr + поле 54h)
- Адрес сбоя: всегда в куче, разбросан (зависит от базы таблицы)

5. Первопричина
----------------

Функция sub_2002030 устанавливает системный курсор по типу (arg_4,
0-4) и индексу кадра (arg_0). Шаг таблицы (var_4) определяется так:

    .text:0200214B  movzx ecx, byte ptr ds:50D095h  ; байт из кода h3hota.exe
    .text:02002152  mov eax, 9
    .text:02002157  shl eax, cl                     ; 9 << байт
    .text:02002159  mov [ebp+var_4], eax

Адрес 50D095h -- непосредственный операнд инструкции SoD
`shl eax, 4` (байты C1 E0 **04**) в функции
A0_MouseMgr_DrawCursor_sub_50CF90; оригинальный байт = 4,
шаг = 9 << 4 = 144 (совпадает с таблицей SoD). Однако hota.dll
ставит на начало этой функции (50D090h) 6-байтовый LoHook
(запись патчера: `0050D090 06 LoHook 0000001909 - HotA`), который
заменяет первые 6 байт (50D090-50D095 = `lea eax,[eax+eax*8]` +
`shl eax,4`) на JMP + NOP. Реальные байты в дампе:
`E9 F7 77 B4 00 90` -- NOP-заполнение (0x90) ложится ровно на
байт 50D095h, затирая оригинальный операнд 0x04. HD_SCX2.dll
читает 0x90 как сдвиг; x86 маскирует сдвиг по модулю 32:
0x90 mod 32 = 16, поэтому `shl eax, 0x90` = `shl eax, 16`.
Шаг раздувается до 9 << 16 = 0x90000 (589824 записи на тип).
Указатель таблицы по 50D09Dh тоже пишется hota.dll
(`0050D09D 04 Patch 0000000438 - HotA`): таблица выделена под
реальный (малый) шаг hota.dll, а не под 0x90000, который получает
HD_SCX2.dll из затёртого байта.

Предусмотренная защита -- перезапись шага настройкой HotA:

    .text:0200216E  and ecx, 8                 ; бит 3 HD.ExeVersion
    .text:02002171  jz short loc_200219D       ; если 0 -- НЕ перезаписывать
    .text:02002173  push offset "HotA.ArtifactsCount"
    .text:02002198  mov edx, [eax]
    .text:0200219A  mov [ebp+var_4], edx       ; var_4 = ArtifactsCount

HotA.ArtifactsCount -- реальное число кадров артефактов: hota.dll
(sub_100F2410) вычисляет его как max([артефакт+41h]+1), начальное
значение 146 (0x92). Рантайм (winedbg): к моменту первого вызова
курсора dword_10634DF4 = 0xA6 (166) -- значение ВЫЧИСЛЕНО, но
настройка патчера ещё НЕ зарегистрирована hota.dll. sub_2002940
в HD_SCX2.dll авторегистрирует отсутствующую настройку с начальным
значением 0 (код 0x200295A: push 0; call [vtable+30h]). Проверка
`cmp [eax], 0; jz` пропускает перезапись, и var_4 остаётся 0x90000.
Регистрация hota.dll (vtable+30h) ОБНОВЛЯЕТ существующую настройку
(подтверждено дизассемблером patcher_x86+0xE3D0), но происходит
ПОСЛЕ первого вызова курсора -- гонка инициализации.

Проверка границ:

    .text:020021FB  imul ecx, [ebp+var_4], 5  ; var_4 * 5
    .text:020021FF  cmp eax, ecx              ; индекс < var_4 * 5?
    .text:02002201  jge short loc_2002275     ; если >= -- другой путь

При var_4 = 0x90000 предел = 0x2D0000. Любой индекс с типом <= 4
проходит проверку (максимум: 4 * 0x90000 + 0x8FFFF = 0x2CFFFF <
0x2D0000). Но реальная таблица выделена с меньшим шагом -- обращение
по индексу ~0x90000 (тип 1) читает далеко за её пределами.

Дефект НЕ унаследован от SoD: в чистом SoD байт 50D095h = 4 (шаг 144),
таблица (dword_67FFA0) согласована с этим шагом, хука hota.dll нет.
Рассинхрон возникает только в связке HotA + HD-мод: хук hota.dll на
50D090h затирает байт, который HD_SCX2.dll использует как источник
шага. Это конфликт двух модификаций: hota.dll перехватывает функцию
расчёта шага, а HD_SCX2.dll полагается на байт, который этот перехват
затирает; указатель таблицы (50D09Dh) при этом пишется hota.dll под
её собственный (малый) шаг.

6. Условия сбоя
----------------

- Графический режим: ТОЛЬКО 32-битные внутренние режимы (4, 5, 7).
  В 16-битных режимах (0-3, 6) модуль HD_SCX2.dll не активен.
- Состояние игры: любое -- от предыгрового меню (Day 0 0 0) до
  середины партии (Day 4 4 2).
- Карта: любая (test.h3m, Salvation.h3m, Reclamation.h3m, прочие).
- Сеть: преимущественно одиночная (32 из 34), 2 сетевых.
- Разрешение: любое (от 1062x664 до 2560x1440).
- Триггер: смена типа курсора на значение >= 1 (например, при
  наведении на объект карты, выборе артефакта, входе в бой).

7. Воспроизведение вылета
--------------------------

Условие активации пути: 32-битный графический режим (4, 5 или 7)
в сочетании с HotA (хук hota.dll на 50D090h установлен, байт 50D095h
затёрт в 0x90).

Базовый сценарий:
- Запустить игру с Graphics.Mode = 5 (или 4, 7).
- В главном меню или в партии выполнить действие, меняющее тип
  курсора на >= 1 (наведение на объект карты, открытие окна,
  выбор артефакта).
- Вылет происходит в потоке отрисовки (SIDE THREAD).

Варьирование:
- Режимы 0-3, 6: вылет НЕ воспроизводится (модуль не активен).
- Без HotA (чистый SoD под HD-модом): бит 3 не установлен,
  var_4 остаётся 144 -- вылет НЕ воспроизводится.

8. Достоверность и ограничения
-------------------------------

Подтверждено:
- Формула адреса сбоя (ECX + EAX*8 + 4) сходится для всех 33 дампов
  с известным адресом (1 дамп без адреса сбоя в поле Information).
- Инструкция сбоя попадает на границу инструкции в листинге.
- Entry point листинга совпадает с логом R35.
- var_4 = 0x90000 = 9 << 16 выведено из EAX всех 34 дампов
  (согласуется с EBX и arg_0; доказывает байт 50D095h = 0x90).
- РАНТАЙМ (winedbg, 180_rus, Mode=7): байт 50D095h = 0x90
  (патчен с 04), указатель таблицы 50D09Dh = 0x1C25888 (куча).
- Код sub_2002030 прочитан: источник var_4, проверка границ,
  доступ к таблице -- цитированы.
- HotA.ArtifactsCount прочитан в hota.dll (sub_100F2410):
  max([артефакт+41h]+1), начальное 146; поле +41h -- WORD
  (макс 0xFFFF) -- ArtifactsCount НЕ может быть 0x90000.
- Бит 3 HD.ExeVersion = 1: подтверждено логами
  («EXE_VERSION & HOTA» в секции Log всех дампов).
  Код _HD3_.dll (0x1000C918): бит 3 = флаг HOTA.
- ArtifactsCount = 0 к моменту чтения: sub_2002940 (HD_SCX2.dll)
  авторегистрирует отсутствующую настройку с начальным значением 0
  (код 0x200295A-0x2002961: push 0; call [vtable+30h]).
- Оригинальный код SoD (50D090-50D09B): шаг 144, байт = 4.

Ограничения:
- Точный размер выделения курсорной таблицы известен по границе
  сегмента дампа (~1.23 МБ), но не из заголовка heap-блока; код,
  выделяющий таблицу (в hota.dll), статически не читался.
- Листинг HD_SCX2.dll один (без версионных суффиксов); для версий
  5.6 R37 -- 5.7 R35 адрес +0x221F стабилен (все 34 дампа падают
  на нём), что подтверждает неизменность функции.
- Точный момент регистрации ArtifactsCount относительно первого
  вызова курсорной функции ПОДТВЕРЖДЁН рантаймом (winedbg,
  180_rus): в момент первого вызова sub_2002030 внутренняя
  переменная hota.dll dword_10634DF4 = 0xA6 (166, вычислена),
  но настройка патчера «HotA.ArtifactsCount» ещё НЕ
  зарегистрирована hota.dll -- sub_2002940 авторегистрирует
  её с 0. Регистрация hota.dll (vtable+30h, обновляет
  существующую) происходит ПОСЛЕ первого вызова курсора.

Рантайм-подтверждение (winedbg + полный дамп, 180_rus, Mode=7):
- Байты 50D090-50D095 = E9 F7 77 B4 00 90: 6-байтовый LoHook hota.dll
  (JMP + NOP), NOP-заполнение 0x90 на месте байта 50D095h.
  Запись патчера: `0050D090 06 LoHook 0000001909 - HotA`.
- Указатель таблицы 50D09Dh пишет hota.dll (`0050D09D 04 Patch
  0000000438 - HotA`); в дампе [50D09D] = указатель на кучу.
- Размер таблицы (полный дамп, граница сегмента): ~1.23 МБ
  (161518 записей по 8 байт). Для шага 0x90000 нужно
  0x90000 * 5 * 8 = 23.6 МБ -- в ~18 раз больше.
- Запись [4] таблицы = {0x0A, 0x0C} (единственная ненулевая
  в первых 128 байтах); остальные -- нули.

ВЫВОД
-----

Виновник: HD-мод (модуль HD_SCX2.dll, подсистема системных курсоров)
в связке с hota.dll.

Дефект: HD_SCX2.dll вычисляет шаг курсорной таблицы как 9 << [50D095h],
читая байт 50D095h как непосредственный операнд инструкции SoD
`shl eax, 4` (оригинал 0x04, шаг 144). Но hota.dll ставит 6-байтовый
LoHook на начало функции (50D090h), и NOP-заполнение хука затирает
байт 50D095h значением 0x90. HD_SCX2.dll читает 0x90 как сдвиг
(по модулю 32 = 16) и получает шаг 9 << 16 = 0x90000 (589824 записи
на тип). Указатель таблицы (50D09Dh) пишет hota.dll под её собственный
малый шаг (~1.23 МБ всего). Проверка границ формально проходит
(индекс < 0x90000 * 5), но не защищает от выхода за реальный буфер.
Любой тип курсора >= 1 вызывает чтение за границами в 32-битных
графических режимах.

Предусмотренная кодом коррекция шага через HotA.ArtifactsCount
(~146) не срабатывает: настройка равна 0 (авторегистрация HD_SCX2.dll
опережает hota.dll).

Совет по исправлению (HD-мод): источник шага в HD_SCX2.dll
(sub_2002030/sub_2001D80, код `9 << [50D095h]`) ненадёжен -- байт
50D095h затирается хуком hota.dll на 50D090h. Не брать шаг из этого
байта при работе с HotA; использовать согласованный с hota.dll
источник -- настройку HotA.ArtifactsCount (~146, совпадает с реальным
размером таблицы), устранив гонку инициализации (читать её после
регистрации hota.dll, а не авторегистрировать с 0), либо подставлять
корректный шаг по умолчанию (144) вместо 9 << [затёртый байт].

Вылет стабильно воспроизводится на 12 версиях HD-мода (5.6 R37 --
5.7 R35), 34 уникальных лога. В чистом SoD дефект отсутствует
(оригинальный байт = 4, шаг 144 согласован с таблицей, хука нет).
