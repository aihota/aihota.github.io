АНАЛИЗ ВЫЛЕТА HD_SCX2.dll+0x221F
====================================

Модель: Qwen 3.8
Дата: 02.08.2026
Заключение: HD_SCX2.dll берёт шаг курсорной таблицы как 9 << [байт
50D095h]; 6-байтовый хук hota.dll на 50D090h затирает этот байт
NOP-заполнением (0x04 -> 0x90), поэтому шаг ПО УМОЛЧАНИЮ становится
0x90000 (вместо 144). В норме HD-мод перезаписывает шаг значением
HotA.ArtifactsCount (= 166, его же выставляет hota.dll), и обращения
к таблице безопасны. Вылет -- РЕДКИЙ сбой этой перезаписи (гонка
инициализации: к моменту вызова курсора флаг HOTA уже выставлен, ветка
перезаписи входит, но HotA.ArtifactsCount ещё 0) -> шаг остаётся
0x90000 -> чтение за границей таблицы в 32-битных режимах.

Визуализация вылета
-------------------

См. врезку (extra.html).

КРАТКОЕ РЕЗЮМЕ
--------------

Модуль системных курсоров HD-мода (HD_SCX2.dll, «HD_SysCurX2») при
установке курсора обращается к таблице по индексу «тип * шаг + кадр».
Шаг (cur_hotspots_count) код вычисляет так: шаг по умолчанию = 9 << [байт 50D095h]
(непосредственный операнд инструкции SoD `shl eax, 4`, оригинал 0x04,
шаг 9*16=144); затем, если EXE_VERSION & HOTA и HotA.ArtifactsCount != 0,
шаг ПЕРЕЗАПИСЫВАЕТСЯ на HotA.ArtifactsCount.

hota.dll ставит на начало функции (50D090h) 6-байтовый хук
(E9 <адрес> 90 = JMP + NOP), и NOP-заполнение ложится ровно на байт
50D095h, меняя его с 0x04 на 0x90. Поэтому шаг ПО УМОЛЧАНИЮ становится
9 << 16 = 0x90000 (589824 записи на тип) -- неверное значение. Однако
hota.dll выставляет HotA.ArtifactsCount = 166 (реальное число кадров
артефактов), и в норме перезапись срабатывает: шаг = 166, обращения
к таблице безопасны (подтверждено автором HD-мода на Windows 11:
cur_hotspots_count = 166).

Вылет происходит, когда перезапись НЕ срабатывает и шаг остаётся
0x90000 по умолчанию: к моменту вызова курсора флаг HOTA уже выставлен
(ветка перезаписи входит), но HotA.ArtifactsCount ещё равен 0
(HD_SCX2.dll авторегистрирует настройку с нулём раньше, чем hota.dll
записывает 166). Тогда обращение к типу >= 1 читает память далеко
за пределами таблицы (выделена под гораздо меньший размер). Это гонка
инициализации, поэтому вылет РЕДОК.

Вылет случается в 32-битных графических режимах (4, 5, 7). Наблюдается
на 12 версиях HD-мода (5.6 R37 -- 5.7 R35), 35 уникальных вылетов --
единицы, а не тысячи, что и доказывает редкость сбоя перезаписи
(детерминированный баг дал бы массовые вылеты).

------------------------------

IDA-адрес: 0x03F9623D - 0x03F90000 + 0x2000000 = 0x200623D.

По этому адресу: `mov edx, [ecx+eax*8+4]` -- граница инструкции.

Пример контекста (дамп 10, R35):

    Exception { Module: HD_SCX2.dll, Address: HD_SCX2.dll+0x221F }
    Information: read of address: 0x05C84AF4
    Context { EAX: 0x00090001, ECX: 0x05804AE8, EBX: 0x00000001 }

Проверка: ECX + EAX * 8 + 4 = 0x05804AE8 + 0x480008 + 4
= 0x05C84AF4 -- совпадает с адресом сбоя.

3. Точка сбоя
--------------

    .text:0200220F  mov eax, [ebp+arg_4]      ; тип курсора (0-4)
    .text:02002212  imul eax, [ebp+var_4]     ; * шаг таблицы
    .text:02002216  add eax, [ebp+arg_0]      ; + индекс кадра
    .text:02002219  mov ecx, ds:50D09Dh       ; указатель на таблицу
    .text:0200221F  mov edx, [ecx+eax*8+4]    ; СБОЙ: чтение записи

ECX -- указатель на динамически выделенную курсорную таблицу;
хранится по адресу 0x50D09D (4-байтовый патч hota.dll
`0050D09D 04 Patch 0000000438 - HotA`, перекрывает поле смещения
инструкции h3hota.exe).
EAX -- вычисленный индекс записи (тип * шаг + кадр).
Каждая запись таблицы -- 8 байт; читается второе поле (смещение +4).

5. Первопричина
----------------

Функция sub_2002030 устанавливает системный курсор по типу (arg_4,
0-4) и индексу кадра (arg_0). Шаг таблицы (var_4) определяется так:

    .text:0200214B  movzx ecx, byte ptr ds:50D095h  ; байт из кода h3hota.exe
    .text:02002152  mov eax, 9
    .text:02002157  shl eax, cl                     ; 9 << байт
    .text:02002159  mov [ebp+var_4], eax

Адрес 50D095h -- непосредственный операнд инструкции SoD
`shl eax, 4` (байты C1 E0 **04**) в функции
A0_MouseMgr_DrawCursor_sub_50CF90; оригинальный байт = 4,
шаг = 9 << 4 = 144 (совпадает с таблицей SoD). Однако hota.dll
ставит на начало этой функции (50D090h) 6-байтовый LoHook
(запись патчера: `0050D090 06 LoHook 0000001909 - HotA`), который
заменяет первые 6 байт (50D090-50D095 = `lea eax,[eax+eax*8]` +
`shl eax,4`) на JMP + NOP. Реальные байты в дампе:
`E9 F7 77 B4 00 90` -- NOP-заполнение (0x90) ложится ровно на
байт 50D095h, затирая оригинальный операнд 0x04. HD_SCX2.dll
читает 0x90 как сдвиг; x86 маскирует сдвиг по модулю 32:
0x90 mod 32 = 16, поэтому `shl eax, 0x90` = `shl eax, 16`.
Шаг по умолчанию раздувается до 9 << 16 = 0x90000 (589824 записи
на тип). Само по себе это ещё не вылет: код перезаписывает var_4
настройкой HotA.ArtifactsCount (см. ниже), и в норме шаг становится
166. Указатель таблицы по 50D09Dh пишет hota.dll
(`0050D09D 04 Patch 0000000438 - HotA`): таблица выделена под
реальный шаг hota.dll -- 166 записей/тип x 5 типов x 8 байт =
6648 байт (подтверждено заголовком блока кучи под Wine), а не под
0x90000 по умолчанию.

Предусмотренная защита -- перезапись шага настройкой HotA:

    .text:0200216E  and ecx, 8                 ; бит 3 HD.ExeVersion
    .text:02002171  jz short loc_200219D       ; если 0 -- НЕ перезаписывать
    .text:02002173  push offset "HotA.ArtifactsCount"
    .text:02002198  mov edx, [eax]
    .text:0200219A  mov [ebp+var_4], edx       ; var_4 = ArtifactsCount

Проверка `and ecx, 8` читает бит 3 (HOTA) настройки HD.ExeVersion.
Семантика флагов (статика, _HD3_.dll sub_1000C6B0): глобал
dword_1004C8CC хранит флаги EXE_VERSION в младшем байте: бит 0 (1) =
SOD, бит 1 (2) = WOG, бит 2 (4) = TE, бит 3 (8) = HOTA, бит 4 (0x10) =
WT, бит 5 (0x20) = ERA, бит 7 (0x80) = SW; настройка HD.ExeVersion =
dword_1004C8CC (пишется в 0x1000C8CE). Флаги вычисляет sub_1000C6B0
(sub_10008440 из ini «ExeVersionFlags» или автодетект sub_10008840),
она же логирует «EXE_VERSION & HOTA» (проверка `test cl, 8` в
0x1000C918).

Точный триггер (согласуется со всеми дампами): к моменту вылета
sub_1000C6B0 УЖЕ отработала -- бит HOTA выставлен (поэтому во всех
логах есть «EXE_VERSION & HOTA»), ветка перезаписи ВХОДИТ. Но
hdv("HotA.ArtifactsCount") возвращает 0 (настройка ещё не
зарегистрирована hota.dll) -> перезапись пропускается -> var_4
остаётся 0x90000. Порядок под Wine (рантайм, winedbg): регистрация
ArtifactsCount (hota.dll, hota+0xF610D) происходит РАНЬШЕ
sub_1000C6B0 -- в момент регистрации ArtifactsCount глобал
dword_1004C8CC = 0x1000AA90 (младший байт 0x90 = WT+SW, бит HOTA ещё
НЕ выставлен), т.е. sub_1000C6B0 ещё не выполнялась. Под Wine порядок
«ArtifactsCount -> sub_1000C6B0 -> курсор» даёт var_4 = 166 (вылета
нет); на машинах с вылетом вызов курсора типа >= 1 попадает в окно
ПОСЛЕ sub_1000C6B0 (HOTA-бит уже выставлен), но ДО регистрации
ArtifactsCount hota.dll.

HotA.ArtifactsCount -- реальное число кадров артефактов: hota.dll
(sub_100F2410) вычисляет его как max([артефакт+41h]+1), начальное
значение 146 (0x92); фактически hota.dll выставляет 166 (0xA6).
В НОРМЕ перезапись срабатывает: подтверждено автором HD-мода на
Windows 11 -- cur_hotspots_count = 166 (не 0x90000 по умолчанию),
обращения к таблице безопасны. Поэтому вылет РЕДОК (35 логов, а не
тысячи): он происходит, только когда перезапись НЕ успела сработать
к моменту вызова курсора. sub_2002940 в HD_SCX2.dll авторегистрирует
отсутствующую настройку с начальным значением 0 (код 0x200295A:
push 0; call [vtable+30h]); если к этому моменту hota.dll ещё не
записала 166, проверка `cmp [eax], 0; jz` пропускает перезапись
и var_4 остаётся 0x90000. Регистрация hota.dll (vtable+30h)
ОБНОВЛЯЕТ существующую настройку (подтверждено дизассемблером
patcher_x86+0xE3D0), но может произойти ПОСЛЕ первого вызова
курсора -- гонка инициализации. Рантайм (winedbg, Wine): внутренняя
переменная hota.dll dword_10634DF4 = 0xA6 (166) уже вычислена
к моменту вызова курсора -- значение готово, но момент его записи
в настройку патчера относительно вызова курсора плавает (гонка).

Проверка границ:

    .text:020021FB  imul ecx, [ebp+var_4], 5  ; var_4 * 5
    .text:020021FF  cmp eax, ecx              ; индекс < var_4 * 5?
    .text:02002201  jge short loc_2002275     ; если >= -- другой путь

При var_4 = 0x90000 (когда перезапись НЕ сработала) предел =
0x2D0000. Любой индекс с типом <= 4 проходит проверку (максимум:
4 * 0x90000 + 0x8FFFF = 0x2CFFFF < 0x2D0000). Но реальная таблица
выделена с меньшим шагом (~166) -- обращение по индексу ~0x90000
(тип 1) читает далеко за её пределами. В норме (var_4 = 166) индекс
типа 1 = 166 + кадр, что укладывается в таблицу, и вылета нет.

Дефект НЕ унаследован от SoD: в чистом SoD байт 50D095h = 4 (шаг 144),
таблица (dword_67FFA0) согласована с этим шагом, хука hota.dll нет.
Рассинхрон возникает только в связке HotA + HD-мод: хук hota.dll на
50D090h затирает байт, который HD_SCX2.dll использует как источник
шага по умолчанию. hota.dll маскирует это неверное значение по умолчанию, выставляя
HotA.ArtifactsCount = 166 (перезапись шага); вылет -- редкое проявление
конфликта, когда маскировка не успевает (гонка инициализации) и в силу
вступает шаг по умолчанию 0x90000 из затёртого байта.

6. Условия сбоя
----------------

- Графический режим: ТОЛЬКО 32-битные внутренние режимы (4, 5, 7).
  В 16-битных режимах (0-3, 6) модуль HD_SCX2.dll не активен.
- Состояние игры: любое -- от предыгрового меню (Day 0 0 0) до
  середины партии (Day 4 4 2).
- Карта: любая (test.h3m, Salvation.h3m, Reclamation.h3m, прочие).
- Сеть: преимущественно одиночная (33 из 35), 2 сетевых.
- Разрешение: любое (от 1062x664 до 2560x1440).
- ОС: вылет НЕ привязан к версии Windows. Поле GetVersionEx в логах
  врёт (отдаёт Windows 8/7/XP), но точное RtlGetVersion (появилось
  с 5.7 R11) показывает реальную ОС -- Windows 11 (напр. лог R35-2:
  RtlGetVersion = "Windows 11" 10.0.26200, GetVersionEx = "Windows 8"
  6.2.9200). То есть вылет случается и на Windows 11 (как у автора
  HD-мода, где перезапись работает) -- это гонка, а не ОС-специфика.
- Триггер: смена типа курсора на значение >= 1 (например, при
  наведении на объект карты, выборе артефакта, входе в бой) В МОМЕНТ,
  когда перезапись шага ещё не сработала: флаг HOTA уже выставлен,
  но HotA.ArtifactsCount ещё 0 -- гонка инициализации. Поэтому вылет
  плавающий: на одной машине/запуске перезапись успевает (шаг 166,
  вылета нет), на другой -- нет (шаг 0x90000, вылет).

7. Воспроизведение вылета
--------------------------

Условие активации пути: 32-битный графический режим (4, 5 или 7)
в сочетании с HotA (хук hota.dll на 50D090h установлен, байт 50D095h
затёрт в 0x90) И несработавшая к моменту вызова курсора перезапись
шага: флаг HOTA уже выставлен, но HotA.ArtifactsCount ещё 0 -- гонка
инициализации.

Базовый сценарий (плавающий, не детерминированный):
- Запустить игру с Graphics.Mode = 5 (или 4, 7).
- В главном меню или в партии выполнить действие, меняющее тип
  курсора на >= 1 (наведение на объект карты, открытие окна,
  выбор артефакта).
- Вылет случается, только если смена курсора произошла ДО того,
  как hota.dll записала HotA.ArtifactsCount = 166 (перезапись
  шага не успела). На большинстве запусков перезапись успевает
  и вылета нет -- поэтому вылет редкий и плавающий, не
  воспроизводится гарантированно.
- Вылет происходит в потоке, который меняет курсор: как в главном
  (17 дампов, AUTOMATIC CRASH REPORT FROM THE MAIN THREAD), так
  и в побочном потоке отрисовки (8 дампов, FROM A SIDE THREAD;
  остальные 10 логов -- NO COMMENT, без маркера потока).

Варьирование:
- Режимы 0-3, 6: вылет не случается (модуль HD_SCX2.dll не активен).
- Без HotA (чистый SoD под HD-модом): байт 50D095h не затёрт
  (остаётся 0x04), var_4 по умолчанию = 144 -- вылет не случается.

8. Достоверность и ограничения
-------------------------------

Подтверждено:
- Формула адреса сбоя (ECX + EAX*8 + 4) сходится для всех 34 дампов
  с известным адресом (1 дамп без адреса сбоя в поле Information).
- Инструкция сбоя попадает на границу инструкции в листинге.
- Entry point листинга совпадает с логом R35.
- var_4 = 0x90000 = 9 << 16 выведено из EAX всех 35 дампов
  (согласуется с EBX и arg_0).
- Байт 50D095h = 0x90 -- NOP-заполнение 6-байтового хука hota.dll
  на 50D090h: реальные байты E9 F7 77 B4 00 90 (JMP + NOP), запись
  патчера `0050D090 06 LoHook 0000001909 - HotA` -- рантайм
  (winedbg + полный дамп, 180_rus, Mode=7).
- JMP хука ведёт на трамплин патчера (0x0105488C), который возвращает
  управление на 50D096h (сразу после затёртых 6 байт): hota.dll
  полностью заменяет расчёт шага своей логикой -- рантайм (дамп).
- Указатель таблицы 50D09Dh пишет hota.dll -- запись патчера
  `0050D09D 04 Patch 0000000438 - HotA`; в дампе [50D09D] = указатель
  на кучу.
- Код sub_2002030 прочитан: источник var_4, проверка границ,
  доступ к таблице -- цитированы.
- HotA.ArtifactsCount прочитан в hota.dll (sub_100F2410):
  max([артефакт+41h]+1), начальное 146; поле +41h -- WORD
  (макс 0xFFFF) -- ArtifactsCount НЕ может быть 0x90000.
- Бит 3 HD.ExeVersion = 1 (флаг HOTA): подтверждено логами
  («EXE_VERSION & HOTA» в секции Log всех дампов) и кодом
  _HD3_.dll (0x1000C918).
- byte_2017258 = 1 (путь ArtifactsCount в курсорной функции
  активен) -- рантайм (winedbg).
- В НОРМЕ перезапись шага срабатывает: подтверждено автором HD-мода
  на Windows 11 -- cur_hotspots_count = 166 (HotA.ArtifactsCount),
  не 0x90000 по умолчанию; обращения к таблице безопасны.
- Гонка инициализации как триггер вылета ПОДТВЕРЖДЕНА контрастом:
  все 35 дампов дают var_4 = 0x90000 (перезапись НЕ сработала), тогда
  как в норме var_4 = 166 (перезапись сработала). Механизм сбоя
  перезаписи: sub_2002940 (HD_SCX2.dll) авторегистрирует настройку
  «HotA.ArtifactsCount» с 0 (код 0x200295A: push 0; call [vtable+30h]);
  если к моменту вызова курсора hota.dll ещё не записала 166, проверка
  `cmp [eax], 0; jz` пропускает перезапись и var_4 остаётся 0x90000.
  Рантайм (winedbg, Wine): внутренняя переменная hota.dll
  dword_10634DF4 = 0xA6 (166) уже вычислена к моменту вызова курсора
  (значение готово, но момент записи в настройку плавает -- гонка).
- vtable+30h патчера ОБНОВЛЯЕТ существующую настройку (дизассемблер
  patcher_x86+0xE3D0) -- рантайм (winedbg): после регистрации hota.dll
  значение становится 166, но запоздавший относительно вызова курсора
  апдейт уже не предотвращает вылет в неудачном запуске.
- Оригинальный код SoD (50D090-50D09B): шаг 144, байт = 4, хука нет.
- Семантика флагов EXE_VERSION (статика, _HD3_.dll sub_1000C6B0):
  глобал dword_1004C8CC, младший байт: SOD=бит0, WOG=бит1, TE=бит2,
  HOTA=бит3 (8), WT=бит4, ERA=бит5, SW=бит7; HD.ExeVersion =
  dword_1004C8CC; проверка HOTA -- `test cl, 8` (0x1000C918).
- Вылет НЕ привязан к ОС: лог R35-2 даёт RtlGetVersion = "Windows 11"
  10.0.26200 (точное) при GetVersionEx = "Windows 8" 6.2.9200 (ложное);
  прежняя корреляция «старые Windows по GetVersionEx» -- артефакт лжи
  GetVersionEx, реальная ОС машин с вылетом -- Windows 11.
- Размер курсорной таблицы (рантайм, Wine, полный дамп): указатель
  [50D09D] = 0x01B88D40; заголовок блока кучи даёт Size = 831
  (x8 = 6648 байт) = 166 записей/тип x 5 типов x 8 байт + 8 байт
  заголовок -- таблица выделена ровно под ArtifactsCount = 166.
  Содержимое почти нулевое (единственная ненулевая запись [2] =
  {0x0A, 0x0C} в первых 8 записях). Шаг по умолчанию 0x90000 даёт индекс
  типа 1 на смещении 0x480000 (4.7 МБ) -- в ~700 раз за пределами

Ограничения:
- Размер таблицы снят под Wine (заголовок блока кучи Wine совместим с NT,
  интерпретация Size=831 даёт в точности 166x5x8); на Windows размер
  ожидается тем же (таблица выделяется hota.dll под ArtifactsCount),
  но напрямую не измерялся.
- Листинг HD_SCX2.dll один (без версионных суффиксов); для версий
  5.6 R37 -- 5.7 R35 адрес +0x221F стабилен (все 35 дампов падают
  на нём), что подтверждает неизменность функции.

ВЫВОД
-----

Виновник: HD-мод (модуль HD_SCX2.dll, подсистема системных курсоров)
в связке с hota.dll.

Дефект: HD_SCX2.dll вычисляет шаг курсорной таблицы ПО УМОЛЧАНИЮ как
9 << [50D095h], читая байт 50D095h как непосредственный операнд
инструкции SoD `shl eax, 4` (оригинал 0x04, шаг 144). Но hota.dll
ставит 6-байтовый LoHook на начало функции (50D090h), и NOP-заполнение
хука затирает байт 50D095h значением 0x90. HD_SCX2.dll читает 0x90
как сдвиг (по модулю 32 = 16) и получает шаг по умолчанию 9 << 16 =
0x90000 (589824 записи на тип) -- неверное значение. В норме HD-мод
перезаписывает шаг настройкой HotA.ArtifactsCount = 166 (её же
выставляет hota.dll), и обращения к таблице безопасны (подтверждено
автором HD-мода на Windows 11: cur_hotspots_count = 166). Указатель
таблицы (50D09Dh) пишет hota.dll под её малый шаг -- 166 записей/тип
x 5 типов x 8 байт = 6648 байт (подтверждено заголовком блока кучи).

Вылет -- РЕДКИЙ сбой перезаписи (гонка инициализации): к моменту
вызова курсора флаг HOTA уже выставлен (ветка перезаписи входит),
но HotA.ArtifactsCount ещё 0 (авторегистрация HD_SCX2.dll опережает
запись hota.dll), поэтому шаг остаётся 0x90000 по умолчанию. Тогда
проверка границ формально проходит
(индекс < 0x90000 * 5), но не защищает от выхода за реальный буфер,
и тип курсора >= 1 читает за границами таблицы в 32-битных режимах.
Редкость (35 логов, а не тысячи) доказывает, что в норме перезапись
успевает и вылета нет.

Совет по исправлению (HD-мод): источник шага по умолчанию `9 << [50D095h]`
(sub_2002030/sub_2001D80) небезопасен -- байт 50D095h затирается хуком
hota.dll на 50D090h, поэтому значение по умолчанию даёт 0x90000 вместо 144. Безопасная
перезапись через HotA.ArtifactsCount это маскирует, но зависит от гонки
инициализации. Направление правки: не полагаться на затёртый байт как
источник значения по умолчанию (подставлять корректное значение по умолчанию, напр. 144, либо
гарантированно дожидаться HotA.ArtifactsCount до первого использования
шага -- не авторегистрировать настройку с 0 в HD_SCX2.dll, чтобы
перезапись не могла «не успеть»).

Вылет случается на 12 версиях HD-мода (5.6 R37 -- 5.7 R35),
35 уникальных логов. В чистом SoD дефект отсутствует (оригинальный
байт = 4, шаг 144 согласован с таблицей, хука нет).
