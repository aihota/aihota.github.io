====================================================================
АНАЛИЗ ВЫЛЕТА HD_HOTA.dll+0x1B921D (диалог найма HD-мода:
конструктор не проверил отказ создания объекта)
====================================================================

Модель: Qwen 3.8
Дата: 30.07.2026
Заключение: HD-мод (HD_HOTA.dll). Конструктор объекта сетки найма
sub_11B9210 не проверяет возврат функции создания: получив NULL
(отказ operator new), он пишет таблицу виртуальных методов по
нулевому указателю. Один дефект в сборках 5.7 RC4 / RC10 / R33,
адрес сбоя плавает по образу.

КРАТКОЕ РЕЗЮМЕ
--------------
Игрок в городе нажал Ctrl-клик по существам (Stormbirds), чтобы
нанять всех, и получил вылет. Непосредственная причина: функция
создания объекта-сетки sub_11B6EC0 вернула NULL (не смогла выделить
память), а конструктор sub_11B9210 возврат не проверил и сразу
выполнил запись таблицы виртуальных методов по адресу в EAX. Поскольку
EAX = 0, запись mov [eax], off_120BD7C прошла по нулевому адресу.
Функция создания sub_11B6EC0 отрабатывает правильно: при отказе
выделения она корректно возвращает NULL (и даже освобождает уже
созданный заголовок). Ошибка именно в потребителе — конструктор
доверяет возврату без проверки. Объект создаётся лениво, при первом
открытии диалога найма (глобальный экземпляр dword_12154B0 ещё равен
нулю). Тот же дефект виден ещё в двух логах других сборок — 0x168EAD
(5.7 RC4) и 0x1697FD (5.7 RC10): та же сигнатура (запись по нулю,
EAX = 0, малый индекс в EBX, одинаковый размер кадра), тот же
относительный разнос вызывающей и падающей функций. Между сборками
функция смещается по образу, поэтому адрес плавает: 0x168EAD (RC4),
0x1697FD (RC10), 0x1B921D (R33). В коде есть парный конструктор
sub_11B9230 (запись off_120BD6C, адрес 0x1B923D в R33) с той же
непроверенной записью — логов по нему пока нет.
Почему именно operator new вернул NULL — по сокращённому минидампу
не видно: это либо исчерпание адресного пространства 32-битного
процесса, либо повреждённые размеры сетки (нужен полный дамп кучи).

3. Сопоставление адресов
------------------------
Все три адреса — одна и та же инструкция записи таблицы виртуальных
методов в крошечном конструкторе, лежащая на смещении +0xD от начала
функции. В листинге R33 конструктор sub_11B9210 начинается с
0x011B9210; инструкция краха mov [eax], off_120BD7C — по 0x011B921D,
то есть +0xD от начала (push edx = 1 байт, mov edx,ecx = 2,
mov ecx,offset = 5, call = 5; итого 13 = 0xD). Между сборками функция
смещается по образу, поэтому адрес краха = (начало конструктора в
данной сборке) + 0xD:
    0x1B921D = начало 0x1B9210 + 0xD  (5.7 R33)
    0x168EAD = начало 0x168EA0 + 0xD  (5.7 RC4)
    0x1697FD = начало 0x1697F0 + 0xD  (5.7 RC10)
Косвенное подтверждение тождества функций: относительный разнос
между вызывающей функцией (sub_11B30D0) и падающим конструктором
стабилен по сборкам — в R33 это 0x1B9210 − 0x1B30D0 = 0x6140, в RC4
0x168EA0 − 0x162D80 = 0x6120, в RC10 0x1697F0 − 0x1636D0 = 0x6120.
Формула сопоставления стандартная: IDA_addr = runtime_addr −
load_base + imagebase (imagebase HD_HOTA.dll = 0x01000000).

4. Верификация версии листинга

Разбор выполнен по листингу R33 (HD_HOTA.dll-5.7 R33.txt, imagebase
0x01000000, timestamp 6A6186F1). Сверка по точке входа: поле
«entry point: 0x08354547» секции Modules лога соответствует процедуре
start листинга по адресу 0x011C4547 (0x08354547 − 0x08190000 +
0x01000000). Отрицательный тест версии пройден: адрес сбоя 0x011B921D
попадает точно на границу инструкции (mov [eax], off_120BD7C), а не
в середину. Для адресов 0x168EAD (RC4) и 0x1697FD (RC10) точных
листингов нет; их принадлежность к тому же конструктору подтверждена
идентичной сигнатурой (запись по нулю, EAX = 0, EBX = малый индекс,
размер кадра 0x18) и стабильным относительным разносом вызывающей и
падающей функций (0x6120 против 0x6140 у R33), но не побайтным
чтением инструкции в этих сборках.

5. Инструкция краша и адресная проверка
---------------------------------------
Падающая функция sub_11B9210 (R33) целиком:

    .text:011B9210  push    edx
    .text:011B9211  mov     edx, ecx
    .text:011B9213  mov     ecx, offset asc_11FBD50 ; "*"
    .text:011B9218  call    sub_11B6EC0
    .text:011B921D  mov     dword ptr [eax], offset off_120BD7C  ; КРАШ
    .text:011B9223  retn

Это конструктор производного класса: он зовёт функцию создания
sub_11B6EC0 (та возвращает указатель на объект в EAX и ставит базовую
таблицу виртуальных методов 63B9C8h), затем перезаписывает [eax]
таблицей производного класса off_120BD7C. Между call и mov нет
проверки test eax,eax / jz — возврат не проверяется.

Адресная проверка: эффективный адрес записи mov [eax],... равен
EAX + 0 = 0x00000000 + 0 = 0x00000000, что в точности совпадает с
полем Information «write of address: 0x00000000». Проверка сошлась.

Таблица off_120BD7C (R33):

    .data:0120BD7C  off_120BD7C  dd offset sub_11B91D0  ; деструктор
    .data:0120BD80               dd offset sub_11B33E0  ; виртуальный метод

Идентификация объекта: производная таблица off_120BD7C накладывает
поверх базового класса игры. Базовая таблица off_63B9C8 лежит в
h3hota.exe (imagebase 0x400000, три метода: sub_44DCF0, sub_55D300,
sub_44DF10; конструктор базы sub_44DC40 ставит mov [esi], off_63B9C8).
Функция создания sub_11B6EC0 ставит базовую таблицу (mov [edi],
63B9C8h), а конструктор sub_11B9210 перезаписывает её производной.
Производный метод sub_11B33E0 — саморазрушение объекта: mov eax,[ecx];
mov eax,[eax]; call eax (зовёт собственный деструктор vtable+0 с
аргументом 1). Дефект находится в производном конструкторе HD-мода,
базовый код игры на пути сбоя не участвует.

------------------
sub_1015780 (обработчик расширенного менеджера города HD-мода;

    -> sub_11B9210 (конструктор объекта-сетки, КРАШ)

Подтверждение цепи:
    - Статически sub_11B9210 вызывается ТОЛЬКО из sub_11B30D0
      (CODE XREF: sub_11B30D0+71, sub_11B30D0+89).
    - V1-стек: верхний кадр [ HD_HOTA.dll+0x1B30D0 ] (= sub_11B30D0);
      сам конструктор sub_11B9210 без стекового кадра (не bp-based),
      поэтому обходчик относит сбой к ближайшей кадровой функции
      sub_11B30D0.
    - V2-стек содержит адрес возврата sub_11B30D0 (0x081A5FC3 =
      IDA 0x01015FC3 ≈ место вызова 0x15FBE+5), подтверждая присутствие
      sub_11B30D0 в стеке.
    - Решающая сверка: EDI в момент сбоя = 0x0839BD9C. Это рантайм-
      адрес глобального экземпляра dword_120BD9C (IDA 0x0120BD9C;
      0x0120BD9C − 0x01000000 + 0x08190000 = 0x0839BD9C). Именно этот
      указатель sub_1008360/sub_1015780 передаёт как this в sub_11B30D0
      (mov ecx, offset dword_120BD9C ... call sub_11B30D0). Совпадение
      точное.
Стек зашумлён трамплинами patcher_x86 (адреса 0x02A8xxxx без модуля),
но несущие кадры (sub_11B30D0, возврат к sub_1015780) восстановимы.

7. Анализ регистров и группировка
---------------------------------
Инварианты по всем 3 логам:
    EAX = 0 — функция создания вернула NULL (главный инвариант).
    EBX = малый индекс (3 / 2 / 8) — номер жилищного слота существа
        под курсором: sub_11B3060 делает хит-тест прямоугольников
        слотов (x, y, ширина, высота) и возвращает индекс
        прямоугольника, содержащего точку (arg_0, arg_4). Малые
        значения — штатный индекс слота, а не повреждённый.
    EBP − ESP = 0x18 — одинаковый размер стекового кадра вызывающей
        функции во всех логах (одна и та же функция).
    EDI = адрес глобального экземпляра менеджера (this); в R33 это
        0x0839BD9C = dword_120BD9C, в RC4/RC10 — те же логические
        данные, но по другим адресам сборки (0x03B76D98 / 0x04537D98).
    Нарушение доступа — всегда ЗАПИСЬ по адресу 0x00000000.
Группировка: все 3 лога — один механизм (конструктор не проверил
возврат функции создания). Различия (версия, карта, одиночная/сетевая
партия, индекс слота) на механизм не влияют.

8. Первопричина
---------------
Ближайшая причина: дефектная ветка конструктора sub_11B9210 (и парного
sub_11B9230). Функция создания sub_11B6EC0 спроектирована корректно:
она проверяет оба выделения (заголовок 56 байт и буфер данных
stride × count) и при отказе operator new освобождает уже созданный
заголовок и возвращает NULL:
    .text:011B6F58  mov  [edi+30h], eax     ; указатель на буфер данных
    .text:011B6F5B  test eax, eax
    .text:011B6F5D  jnz  short loc_11B6F75  ; успех -> вернуть edi
    .text:011B6F5F  push edi
    .text:011B6F60  mov  eax, 60B0F0h       ; operator delete
    .text:011B6F65  call eax                ; освободить заголовок
    .text:011B6F6A  ...  xor eax, eax       ; вернуть NULL
То есть поставщик данных (sub_11B6EC0) свой контракт соблюдает — NULL
при отказе. Потребитель (sub_11B9210) контракт нарушает: пишет таблицу
виртуальных методов по возврату без проверки. Это и есть дефект.
Дефект — непоследовательность, а не отсутствие идиомы в модуле. Нулевой
возврат фабрики — штатный случай: ряд потребителей корректно обрабатывает
его проверкой test reg,reg / jz (0x10091A6: mov ecx,eax; test ecx,ecx;
jz; 0x11B20F0: test eax,eax; jz; 0x11B2295 и 0x11B704A: mov edi,eax;
test edi,edi; jz). Корректный образец защиты от NULL в модуле есть.
Однако конструкторы сеток диалога найма проверку пропускают: sub_11B9210
(off_120BD7C), sub_11B9230 и sub_11B9250 (оба off_120BD6C: mov esi,eax;
mov [esi], off_120BD6C) пишут таблицу виртуальных методов по возврату без
test. Тем же путём идёт sub_1005540 (разыменовывает [ebx+24h]/[ebx+28h]/
[ebx+2Ch]/[ebx+30h] без проверки), 0x103485D (читает [eax+4]/[eax+8]),
0x11B76D9 (push [eax+30h]) и 0x11B0FF0 (кладёт результат в глобал как
есть). Соседний конструктор sub_11B33F0 не проверяет уже сам operator new
(617492h), сразу пиша поля объекта ([edi+4]=0 ...). Всего у фабрики
sub_11B6EC0 19 точек вызова: часть защищена проверкой, часть (включая
путь найма) — нет. Фабрика-сестра sub_11B8A90 (объект крупнее, 56Ch;
базовая таблица 63BA14h) устроена так же: корректно возвращает NULL при
отказе (проверены оба operator new и освобождение заголовка), а её
потребители sub_11B9230/sub_11B9250 возврат не проверяют.
Структурный корень дефекта виден по оригиналу игры. Функция создания
sub_11B6EC0 — прямой порт конструктора базового класса из h3hota.exe
(sub_44DC40): раскладка объекта совпадает по полям (+1Ch/+20h размер,
+24h количество, +28h второй размер, +2Ch шаг, +30h буфер данных,
+34h флаг). Но модель владения объектом изменена. В игре sub_44DC40
получает this (esi = ecx) уже выделенным вызывающим кодом (объект-член,
не возвращаемый указатель) и пишет таблицу виртуальных методов в
гарантированно живой объект; путь «вернуть NULL-объект» там отсутствует
в принципе, поэтому vtable-запись игры не падает даже без проверки
выделения буфера. HD-мод переделал конструктор члена в фабрику, которая
сама выделяет объект (operator new, 38h) и возвращает указатель,
способный оказаться NULL, однако потребители сохранили рассчитанную на
объект-член идиому безусловного разыменования возврата. Смена модели
владения (член -> возвращаемый кучный указатель) при сохранении старой
идиомы и есть причина, почему отсутствующая проверка приводит к сбою.
Это подтверждается потребителем самой игры. При кучном создании объекта
игровой код sub_462600 выделяет его тем же operator new (38h) и
ПРОПУСКАЕТ конструирование при NULL (cmp eax, edi; jz, где edi = 0),
а в sub_43EFE0 сетка создаётся как локальный стековый объект
(lea ecx, [ebp+var_90]) вообще без выделения. Игра всегда передаёт
конструктору sub_44DC40 гарантированно валидный объект; HD-мод проверку
при переносе потерял. Отсутствие проверки — доказанное отклонение от
корректного образца, а не принятая в коде идиома.
Глубинная причина (почему operator new вернул NULL) по сокращённому
минидампу не установима. Функция создания возвращает NULL в одном из
четырёх случаев: (а) count ≤ 0; (б) arg_0 ≤ 0; (в) отказ operator new
для заголовка 56 байт; (г) отказ operator new для буфера данных. Первые
два — повреждённые либо ошибочные размеры сетки, последние два —
исчерпание адресного пространства 32-битного процесса. Значения count
и arg_0 читаются из глобальной структуры (ds:6992D0h -> [+40h] ->
[+24h]/[+28h]) и в дампе не видны. Косвенные данные: HD-мод имеет
задокументированную проблему исчерпания 32-битной кучи (семейство
отладочного аллокатора HD_HOTA.dll+0x1A4E/0x1A0E — отказы выделений
вплоть до 1 МиБ в сетевых партиях), поэтому исчерпание вероятно; но
повреждённые размеры не исключены. Различение — только по полному
дампу кучи.

9. Условия сбоя
---------------
    Версии HD-мода: 5.7 RC4, RC10, R33; HotA 1.8.0 (все 3 лога).
    Игра: и одиночная (RC4, RC10), и сетевая (R33) — сбой не привязан
        к сетевому режиму.
    День партии: 1 32 (R33), 1 35 (RC4), 2 31 (RC10) — первая половина
        партии.
    Graphics.Mode = 5 во всех логах; не является условием (в падающей
        функции нет ветвления по режиму).
    Триггер (по показанию игрока R33): открытие диалога найма и
        Ctrl-клик «нанять всех». Объект-сетка создаётся лениво при
        первом использовании менеджера найма (глобальный экземпляр
        dword_12154B0 ещё равен нулю), поэтому сбой происходит в момент
        первого создания объекта, когда выделение памяти не удалось.

Модуль: HD_HOTA.dll (HD-мод)
Функция: конструктор объекта-сетки диалога найма sub_11B9210 (R33);
    инструкция mov [eax], off_120BD7C на смещении +0xD от начала
    функции. Функция создания sub_11B6EC0 (2D-буфер) возвращает NULL
    корректно; потребитель возврат не проверяет.
Подсистема: диалог найма существ в городе (HD-мод)
Класс сбоя: отказ кучи
Виновный модуль: HD-мод (HD_HOTA.dll)
Были до 1.8.0: не подтверждено — все 3 лога на HotA 1.8.0; дампов
    HotA до 1.8.0 нет.
Были в SoD: нет — менеджер диалога найма (dword_120BD9C) и его
    объекты-сетки это код HD-мода (обработчик sub_1015780
    зарегистрирован инициализатором HD-мода sub_1034EC0); в чистом
    SoD этот расширенный диалог найма отсутствует. Подтверждено
    чтением оригинала: базовый конструктор игры sub_44DC40 работает
    с объектом-членом (this передаётся выделенным), путь «фабрика
    вернула NULL -> разыменование» в игре отсутствует, поэтому
    оригинал так не падает.

Признаки поиска в других версиях:
    Context-инварианты: EAX = 0, запись по адресу 0x00000000,
        EBX = малый индекс, размер кадра EBP − ESP = 0x18.
    Текстовая сигнатура: крошечный конструктор (push edx; mov edx,ecx;
        mov ecx,offset <имя>; call <функция создания>; mov [eax],
        offset <таблица>; retn) БЕЗ проверки test eax,eax перед mov
        [eax],....
    Адрес краха = (начало конструктора в данной сборке) + 0xD;
        относительный разнос вызывающей (sub_11B30D0-эквивалент) и
        падающей функций ≈ 0x6120–0x6140.
    Парный конструктор sub_11B9230 (R33: 0x1B923D, mov [eax],
        off_120BD6C) и sub_11B9250 (mov [esi], off_120BD6C) — тот же
        дефект, логов пока нет. Проверку возврата фабрики пропускают
        также sub_1005540, 0x103485D, 0x11B76D9, 0x11B0FF0 и
        конструктор sub_11B33F0; при этом ряд потребителей проверку
        ставит (0x10091A6, 0x11B20F0, 0x11B2295, 0x11B704A).

11. Воспроизведение вылета
--------------------------
Вылет недетерминирован (зависит от состояния адресного пространства
в момент первого создания объекта-сетки). Вероятностный путь: под
HD-модом 5.7 RC4+ открыть город и впервые вызвать диалог найма
существ (по показанию — Ctrl-клик «нанять всех») в условиях, когда
выделение памяти под сетку завершается отказом; целевые инварианты
ловимого дампа — EAX = 0, запись по адресу 0x00000000, EBX = малый
индекс, адрес краха = начало конструктора + 0xD для данной сборки.
Для различения исчерпания кучи и повреждённых размеров сетки — полный
дамп кучи (Sys.FullDump = 1 в _HD3_Data/Settings/hota.ini): разумен
запрос (малый буфер сетки) при NULL — исчерпание; аномален (сотни
МиБ / ГБ) либо count/arg_0 ≤ 0 — повреждение размеров выше по стеку.

Достоверность и ограничения
---------------------------
Подтверждено:
    - Механизм доказан побайтно (R33): конструктор sub_11B9210 пишет
      таблицу виртуальных методов по возврату функции создания без
      проверки; EAX = 0 -> запись по нулю. Адресная проверка сошлась
      (EAX + 0 = 0x00000000 = адрес сбоя).
    - Функция создания sub_11B6EC0 корректно возвращает NULL при отказе
      (прочитаны обе проверки operator new и освобождение заголовка).
    - Подсистема установлена: this = dword_120BD9C (точное совпадение
      EDI = 0x0839BD9C с рантайм-адресом глобального менеджера найма),
      вызывающий код — обработчик городского экрана HD-мода sub_1015780.
    - Семья из 3 адресов (RC4/RC10/R33): один дефект, адрес плавает
      (начало конструктора + 0xD), стабилен относительный разнос
      функций 0x6120–0x6140.
    - Дефект — непоследовательность: из 19 точек вызова фабрики
      sub_11B6EC0 часть корректно проверяет возврат (test reg,reg; jz:
      0x10091A6, 0x11B20F0, 0x11B2295, 0x11B704A), а путь найма
      (sub_11B9210/9230/9250) и ряд других (sub_1005540, 0x103485D,
      0x11B76D9, 0x11B0FF0) проверку пропускают; корректный образец в
      модуле существует. Фабрика-сестра sub_11B8A90 тоже возвращает
      NULL корректно.
    - Объект идентифицирован: базовый класс в h3hota.exe (off_63B9C8,
      конструктор sub_44DC40), производная таблица off_120BD7C; дефект
      в производном конструкторе HD-мода, базовый код игры не на пути
      сбоя.
    - Структурный корень доказан сравнением с оригиналом: sub_11B6EC0
      — порт игрового sub_44DC40 (раскладка полей совпадает), но HD-мод
      сменил модель владения (объект-член -> возвращаемый кучный
      указатель), сохранив идиому безусловного разыменования; оригинал
      игры (this передаётся выделенным) так не падает.
    - Корректный образец в игре прочитан: sub_462600 проверяет
      operator new перед конструированием (cmp eax, edi; jz), sub_43EFE0
      создаёт сетку стековым объектом — игра всегда передаёт валидный
      объект; отсутствие проверки в HD-моде — доказанное отклонение.
    - Фабрика побайтно стабильна: sub_11B6EC0 идентична в R31 и R33,
      присутствует в R20/R29/RC9/RC11 (по одной точке записи базовой
      таблицы 63B9C8h).
    - Подсистема подтверждена тремя независимыми фактами: this =
      dword_120BD9C, хит-тест жилищных слотов sub_11B3060, регистрация
      sub_1015780 по настройке HD.UI.Ext.TownMgr.
Ограничения:
    - Виновный код в закрытом модуле HD-мода; точка исправления — у
      разработчиков HD-мода.
    - Для адресов 0x168EAD (RC4) и 0x1697FD (RC10) точных листингов
      нет; принадлежность к тому же конструктору подтверждена
      сигнатурой и относительным разносом функций, но не побайтным
      чтением (уровень проверки: R33 — побайтно; RC4/RC10 — по
      регистрам и стеку).
    - Минидамп сокращённый (без кучи): причина отказа operator new
      (исчерпание адресного пространства либо повреждённые размеры
      сетки count/arg_0) по нему не различима — нужен полный дамп.
    - Полезность средняя: дефект потребителя (отсутствие проверки
      возврата) локализован и доказан, но глубинный триггер отказа
      выделения — рантайм; одна инструкция краха диагноз не исчерпывает.

ВЫВОД
-----
Вылет HD_HOTA.dll+0x1B921D (и родственные 0x168EAD / 0x1697FD) —
дефект HD-мода: конструктор объекта-сетки диалога найма sub_11B9210
не проверяет возврат функции создания sub_11B6EC0. Функция создания
отрабатывает правильно и при отказе operator new возвращает NULL, но
конструктор сразу пишет таблицу виртуальных методов по EAX, и при
EAX = 0 происходит запись по нулевому адресу. Объект создаётся лениво
при первом открытии диалога найма (показание игрока: Ctrl-клик «нанять
всех» в городе). Один дефект в сборках 5.7 RC4 / RC10 / R33, адрес
сбоя плавает по образу (начало конструктора + 0xD). В коде есть парный
конструктор sub_11B9230 (0x1B923D) с той же непроверенной записью.
Почему operator new вернул NULL (исчерпание 32-битной кучи либо
повреждённые размеры сетки) — по сокращённому минидампу не различимо,
нужен полный дамп кучи. Виновник — HD-мод (закрытый модуль
HD_HOTA.dll).
