АНАЛИЗ ВЫЛЕТА HD_TC2.dll+0x67B0 (отрисовка интерфейса (True Color))
==============================================================================

Модель: Qwen 3.8
Дата: 30.07.2026
Заключение: Блиттер True Color HD_TC2.dll исправен (точный порт рисовалки
SoD); вылет — следствие: на входе спрайт Pcx8 с невалидным буфером
пикселей (нуль, висячий указатель или короче объявленной ширины),
который движок SoD подаёт при отрисовке экрана города.


КРАТКОЕ РЕЗЮМЕ
--------------
Игра падает при отрисовке экрана города (вход в город, открытие постройки
замка — магазина). EXCEPTION_ACCESS_VIOLATION (чтение) в модуле HD_TC2.dll
по адресу HD_TC2.dll+0x67B0, инструкция "mov cl, [edx]" во внутреннем цикле
блиттера 8-битного палитрового спрайта в 32-битный буфер (sub_20066E0).
EDX — указатель на текущий байт-пиксель ИСТОЧНИКА; во всех 114 дампах этого
адреса EDX совпадает с адресом сбоя.

Сам блиттер дефекта НЕ содержит: это побайтно точный 32-битный порт штатной
рисовалки SoD A0_Pcx8_Draw_sub_44F940 (h3hota.exe, 0x44F940), которую HD-мод
подменяет в режиме True Color. Ни оригинал SoD, ни порт не проверяют буфер
данных источника (Pcx8+0x30) — по контракту вызывающий обязан передать
годный спрайт. Объект спрайта при этом ЖИВ: блиттер успешно читает его шаг
строки (Pcx8+0x2C) и палитру (Pcx8+0x24C), а проверка указателя спрайта на
нуль в A0_DlgStaticPcx8_Draw_ToScreen проходит. Бит именно буфер пикселей.

Первопричина — дефект жизненного цикла спрайта Pcx8 (движок SoD, h3hota.exe,
унаследован HD-модом), и проявляется он ДВУМЯ путями. Первый (56 дампов):
функция чтения файла A0_Pcx8_ReadFromFile (и её порт HD_TC2!sub_2008A30)
выделяет пиксельный буфер через operator new и при отказе выделения оставляет
this+0x30 = NULL, возвращая код ошибки; создатель A0_Pcx8_CreateFromFile этот
код НЕ проверяет и возвращает полусозданный спрайт. Второй (58 дампов):
спрайт корректно освобождается, но рисуется по старой ссылке (гонка времени
жизни) — память уже переиспользована (в дампах видно чужое содержимое, имя
ресурса "CmNumWHD.pcx"), указатель буфера читается как нуль или висячий
адрес. В обоих случаях проверка указателя спрайта на нуль при отрисовке
объект пропускает, и блиттер падает на чтении буфера. В обычном 16-битном
режиме то же самое роняет оригинал SoD на эквивалентной инструкции
"mov dl,[ecx]" внутри h3hota.exe (~0x44F9EF): точка отказа сместилась бы в
h3hota.exe, причина осталась бы той же.

«невалидный буфер пикселей спрайта». Постоянство падающего модуля (size
0x3CF000, один и тот же код по offset 0x67B0) при 23 версиях HD-мода
усиливает вывод об одном пути.

5. ИНСТРУКЦИЯ КРАША И АДРЕСНАЯ ПРОВЕРКА
---------------------------------------
Функция HD_TC2.dll!sub_20066E0 — блит 8-битного палитрового спрайта в
32-битный (True Color) буфер. Объект-спрайт "this" (ECX, сохранён в var_4):
    this+0x2C  = шаг строки источника (scanline_size)
    this+0x30  = буфер пиксельных данных источника (8 бит/пиксель)
    this+0x24C = таблица палитры (256 элементов по 4 байта = 32bpp)

Подготовка адреса строки источника (перед циклом):
    .text:02006770  mov  eax, [ebp+var_4]      ; this
    .text:02006777  mov  edi, [eax+2Ch]        ; шаг строки
    .text:0200677A  imul edi, [ebp+arg_0]      ; шаг * y
    .text:02006781  add  edi, [eax+30h]        ; + буфер пикселей источника
    .text:02006787  add  edi, [ebp+var_8]      ; + смещение строки
    .text:02006794  mov  [ebp+arg_C], edi      ; arg_C = указатель источника
    .text:0200678E  mov  eax, [eax+24Ch]       ; таблица палитры
    .text:0200679A  mov  [ebp+arg_4], eax

Внутренний цикл (точка сбоя):
    .text:020067A2  mov  edx, edi              ; edx = текущий байт источника
    .text:020067A8  mov  ebx, [ebp+arg_4]      ; ebx = таблица палитры
    .text:020067AB  mov  esi, ecx              ; esi = ширина (счётчик)
    .text:020067B0  mov  cl, [edx]             ; СБОЙ: читаем байт-индекс
    .text:020067B2  lea  edx, [edx+1]          ; ++источник
    .text:020067B5  test cl, cl
    .text:020067B7  jz   short loc_20067C1     ; 0 = прозрачный пиксель
    .text:020067B9  movzx ecx, cl
    .text:020067BC  mov  ecx, [ebx+ecx*4]      ; палитра[index] -> 32bpp цвет
    .text:020067BF  mov  [eax], ecx            ; запись в приёмник
    .text:020067C1  add  eax, 4
    .text:020067C4  sub  esi, 1                ; --ширина
    .text:020067C7  jnz  short loc_20067B0

Механика отказа. EDX берётся напрямую из EDI = this+0x30 (+ шаг*y +
смещение), то есть из буфера данных источника. На "mov cl,[edx]"
происходит чтение источника. Адресная проверка: адрес сбоя == EDX во всех
114 дампах (смещение поля = 0, прямое разыменование). [OK]
    - Источник = нуль: this+0x30 == 0, первый пиксель первой строки ->
      EDI = EDX = 0 -> чтение 0x00000000.
    - Висячий указатель: this+0x30 = крупный невалидный адрес -> EDI = EDX
      указывает в незамапленную память уже на первом пикселе.
    - Выход за буфер: строка началась годно (EDI), но объявленная ширина
      (ESI + пройдено) увела EDX за границу страницы. Пример (дамп -180):
      EDI = 0x20A8AFDE, EDX = 0x20A8B000 (= EDI + 0x22), полная ширина
      0x22 + ESI(0x18) = 0x3A.

Важное уточнение механизма. ДО сбоя блиттер читает this+0x2C (шаг строки)
и this+0x24C (таблица палитры) — эти чтения проходят во всех дампах (сбой
именно на данных, не на них). Значит, сам объект-спрайт размещён и жив,
таблица палитры у него есть; бит ТОЛЬКО буфер пикселей this+0x30. Это
сужает причину: не «битый указатель на спрайт», а «спрайт жив, но его
пиксельный буфер невалиден» (не загружен, освобождён или короче ширины).

В функции есть клипирование по ПРИЁМНИКУ (ширина к холсту по arg_1C, высота
к холсту по arg_20), но НЕТ ни одной проверки указателя или протяжённости
ИСТОЧНИКА (this+0x30) перед разыменованием.

Верхние кадры (надёжные, по дампам одинаковы; пример — дамп -7, стек V2):

      вызывающий код: hota.dll+0x76EE1      (адрес возврата диспетчера)
      далее HD_HOTA.dll+0x513E
      далее трамплины patcher_x86 (0x02A8xxxx) -- в листингах отсутствуют
      далее h3hota.exe 0x44FDA7 / 0x45032C  (движок SoD, отрисовка диалога)

Диспетчер в hota.dll (loc_10076E60), откуда приходит вызов:
    .text:10076E60  push esi
    .text:10076E61  mov  esi, [esp+0Ch]          ; esi = спрайт-источник
    .text:10076E65  cmp  dword ptr [esi+14h], 46323350h  ; тег формата "P32F"
    .text:10076E6C  jnz  short loc_10076EA6
    ... (ветка "P32F": источник уже 32bpp, call sub_10079630) ...
    .text:10076EAA  mov  eax, dword_106349D4     ; vtable драйвера рендера HD
    .text:10076EB7  mov  edx, [eax]
    .text:10076EDA  call dword ptr [edx+2Ch]     ; выбрать блиттер по режиму
    .text:10076EDD  mov  ecx, esi                ; ecx = this = спрайт-источник
    .text:10076EDF  call eax                     ; -> HD_TC2!sub_20066E0
    .text:10076EE1  pop  esi                     ; <- адрес возврата в стеке

Диспетчер получает объект-спрайт (esi = [esp+0Ch]) и через vtable драйвера
рендера HD (dword_106349D4) выбирает блиттер под активный графический режим;
в режиме True Color это HD_TC2!sub_20066E0, вызываемый с этим объектом как
this. Поле this+0x14 (тег формата "P32F") и this+0x24C (таблица палитры 32bpp)
заполняются HD-модом; буфер пикселей this+0x30 и шаг строки this+0x2C — поля
исходного спрайта SoD.

Путь отрисовки в движке SoD (h3hota.exe), приводящий к диспетчеру:
    A0_DlgStaticPcx8_ProcMsg_sub_450200 (0x450200)   ; обработчик сообщения
      вызывает A0_DlgStaticPcx8_Draw_ToScreen_sub_450120 (0x450120)
        вызывает A0_Pcx8_Draw_To_Pcx16_sub_44FA80 (0x44FA80)
          вызывает A0_Pcx8_Draw_sub_44F940 (0x44F940)  ; перехвачена HD-модом
            через диспетчер hota.dll -> HD_TC2!sub_20066E0

Рисуется экранный элемент «статический Pcx8» (_DlgStaticPcx8_) — фоновая
картинка или графика постройки в диалоге/на экране города. Подсистема —
отрисовка интерфейса в режиме True Color.

Регистрация блиттеров HD_TC2 как замен функций SoD (sub_2008CA0):
    .text:02009C2E  push offset sub_20066E0      ; блиттер HD_TC2
    .text:02009C3B  push 44F940h                 ; адрес оригинала SoD
    .text:02009C41  call dword ptr [ecx+3Ch]     ; patcher: хук 0x44F940
То есть HD_TC2 в режиме True Color подменяет штатную 8bpp-рисовалку SoD
своей 32bpp-версией.


7. АНАЛИЗ РЕГИСТРОВ И ГРУППИРОВКА
---------------------------------
EDX — единственный регистр-носитель причины: EDX == адрес сбоя во всех 114
дампах (адресная проверка прямая, смещение поля = 0). ESI == ECX — счётчик
ширины строки источника (значения 0x18, 0x3A, 0x320, 0x627 и др.) — это
размеры спрайтов, не размеры выделений и не контрольные значения. EDI == EDX
в подгруппах «нуль» и «висячий» (начало строки), EDI = EDX - N в подгруппе
«выход за буфер». EAX — указатель приёмника (32bpp), EBX — таблица палитры;
оба годны (приёмник клипится), что исключает версию «битый буфер приёмника».

Группировка по состоянию указателя источника (а не по одному адресу сбоя):

  Подгруппа            Дампов  EDX/EDI            Признак
  -------------------- ------  ------------------ --------------------------
  Источник = нуль      77      EDX=EDI=0          this+0x30 == 0
  Висячий указатель    24      EDX=EDI, крупный   this+0x30 = невалидный адрес
  Выход за буфер       13      EDX больше EDI     ширина увела за границу страницы

Три подгруппы — три проявления ОДНОГО шаблона «буфер пикселей спрайта
невалиден», а не три разных бага. Механизм один (разыменование источника
без проверки), различается лишь то, КАК именно буфер невалиден.

«Мусорная ширина» оказалась ключом к подгруппе. В 20 дампах подгруппы «нуль»
ESI=ECX=0x4448576D, и это НЕ случайный мусор, а константа HD_HOTA.dll
(dword в .rdata, присутствует во всех версиях HD_HOTA; её читает обёртка
блита sub_10051xx). Вместе с двумя соседними dword она складывается в
12-байтовое имя ресурса:
    0x754E6D43 0x4448576D 0x7863702E  ->  "CmNu"+"mWHD"+".pcx" = "CmNumWHD.pcx"
(обёртка блита HD_HOTA сверяет это имя у поверхности по this+0/+4/+8).
Ещё в 1 дампе ширина ESI=0x706D622E = ASCII ".bmp" (фрагмент имени файла).
И то и другое — содержимое ПЕРЕИСПОЛЬЗОВАННОЙ памяти: спрайт освобождён, а
его память занята другим ресурсом ("CmNumWHD.pcx" / именем ".bmp"), и
отрисовка по старой ссылке читает чужое содержимое как «ширину» (и нуль как
указатель буфера). Это прямое доказательство обращения к освобождённой памяти
(use-after-free) в ~21 дампе подгруппы «нуль».

Уточнённое разбиение подгруппы «нуль» (77 дампов) по значению ширины:
    реальные ширины (0x30 x35, 0x3A x14, 0x66 x2, 0x320 x2,
      0xFC x2, 0x39C x1) .................... 56  -> отказ operator new
      (буфер не выделен, ширина осталась от заголовка файла)
    переиспользованная память ("CmNumWHD.pcx" x20,
      ".bmp" x1) ............................ 21  -> обращение к
      освобождённой памяти (use-after-free)

Разные значения EDX/ESI/карт/дней в разных дампах = разные спрайты и
аргументы одного шаблона отказа.


8. ПЕРВОПРИЧИНА
---------------
Функция HD_TC2!sub_20066E0 НЕ является носителем дефекта. Это побайтно
точный 32-битный порт штатной рисовалки SoD A0_Pcx8_Draw_sub_44F940
(h3hota.exe, 0x44F940), активируемый хуком в режиме True Color.

Сравнение с оригиналом SoD (8bpp -> 16bpp):
    .text:0044F9EF  mov  dl, [ecx]             ; читает байт источника, БЕЗ
                                               ; проверки (эквивалент mov cl,[edx])
    .text:0044F9F2  test dl, dl
    .text:0044F9F7  jz   short loc_44FA0A      ; 0 = прозрачный
    .text:0044FA02  mov  dx, [edi+edx*2+50h]   ; таблица палитры 16bpp (off +0x50)
    .text:0044FA07  mov  [eax], dx             ; запись 16bpp
    .text:0044FA19  mov  ecx, [edi+2Ch]        ; шаг строки (this+0x2C)
Логика идентична порту: те же поля this+0x2C (шаг) и this+0x30 (буфер), то же
чтение источника без проверки, тот же признак прозрачного пикселя (нулевой
индекс). Отличие только в формате приёмника: оригинал пишет 16bpp (таблица
по 2 байта, off +0x50), порт — 32bpp (таблица по 4 байта, base this+0x24C).
Сигнатуры функций одинаковы (thiscall, 12 аргументов, retn 2Ch). В обеих
функциях клипится только приёмник, проверка источника отсутствует.

Контракт «блиттер доверяет источнику» унаследован от SoD, а не привнесён
HD-модом. Проверка по стабильному адресу оригинала (0x44F940) подтверждает:
оригинал SoD содержит тот же паттерн без проверки.

Что именно невалидно. Блиттер успешно читает this+0x2C (шаг) и this+0x24C
(таблица палитры) ДО сбоя; проверка указателя спрайта на нуль в
A0_DlgStaticPcx8_Draw_ToScreen_sub_450120 тоже проходит:
    .text:00450122  mov  ecx, [eax+30h]        ; ecx = указатель спрайта Pcx8
    .text:00450125  test ecx, ecx
    .text:00450127  jz   short locret_450163   ; нулевой спрайт -> выход, НЕ падает
Значит, объект-спрайт размещён и жив; бит только его буфер пикселей
(Pcx8+0x30). Это сужает причину до жизненного цикла пиксельного буфера.

Жизненный цикл спрайта Pcx8 (прочитан в h3hota.exe и HD_TC2.dll). Спрайт —
кэшированный ресурс с подсчётом ссылок:
    A0_Load_Pcx8_sub_55AA10 (0x55AA10, перехвачена HD_HOTA.dll):
      - поиск имени в дереве ресурсов A0_GameResourceTree_dword_69E560;
        при находке — инкремент счётчика ссылок (inc [eax+18h]) и возврат
        кэшированного спрайта;
      - при отсутствии — fopen("rb") файла на диске, при неудаче —
        резервный путь в LOD-архивы (A0_LodTbls_stru_69E570);
      - при успехе — operator new(0x56C) и A0_Pcx8_CreateFromFile_sub_44F5A0.
    A0_Pcx8_CreateFromFile_sub_44F5A0 (0x44F5A0) создаёт объект и вызывает
    A0_Pcx8_ReadFromFile_sub_44F710 для заполнения буфера пикселей.
    A0_Pcx8_ReadFromFile (0x44F710, перехвачена HD_TC2.dll, замена —
    sub_2008A30) выделяет пиксельный буфер и заполняет его; она же (в порте
    HD_TC2) строит 32-битную таблицу палитры по this+0x24C.

Конкретный дефектный путь (доказан статически, для подгруппы «нуль»).
Функция чтения файла — и оригинал SoD A0_Pcx8_ReadFromFile_sub_44F710, и её
замена HD_TC2!sub_2008A30 (логика идентична: порт воспроизводит движок) —
выделяет пиксельный буфер через operator new и при отказе выделения оставляет
его нулевым, возвращая код ошибки:
    .text:0044F751  call ??2@YAPAXI@Z      ; operator new(ширина*высота)
    .text:0044F759  mov  [ebx+30h], eax    ; this+0x30 = буфер
    .text:0044F761  mov  eax, 2            ; при отказе: код ошибки 2,
    .text:0044F76A  retn 1Ch               ; this+0x30 остаётся NULL
    (в HD_TC2!sub_2008A30 то же: call 617492h = operator new; mov [ebx+30h],
     eax; при NULL — возврат 2, буфер не заполняется)
Создатель спрайта код возврата чтения НЕ проверяет:
    .text:0044F67E  call A0_Pcx8_ReadFromFile_sub_44F710
    .text:0044F684  mov  eax, ebx          ; возврат объекта БЕЗ проверки
    .text:0044F695  retn 20h               ; кода ошибки чтения
Поэтому при отказе выделения буфера объект Pcx8 возвращается полусозданным:
указатель спрайта не нулевой, таблица палитры this+0x24C размещена, а буфер
пикселей this+0x30 = NULL. Проверка указателя спрайта на нуль в
A0_DlgStaticPcx8_Draw_ToScreen такой объект пропускает, и блиттер падает на
чтении нулевого буфера.

Цепочка полностью унаследована от SoD: функция чтения с отказом выделения и
создатель, не проверяющий возврат, — код h3hota.exe; HD-мод лишь воспроизводит
функцию чтения (sub_2008A30) и переносит точку краша в HD_TC2.dll в режиме
True Color. В 16-битном режиме та же цепочка роняет оригинал SoD в h3hota.exe.

Подгруппы и два корневых механизма. Материал 114 дампов распадается на ДВА
механизма жизненного цикла буфера (оба в коде Pcx8, оба унаследованы от SoD):

  Механизм                         Дампов  Признак
  -------------------------------  ------  -------------------------------
  Отказ operator new (буфер не     56      ширина реальная (от заголовка
  выделен, this+0x30 = 0)                  файла), буфер нулевой
  Обращение к освобождённой        58      ширина = чужое содержимое
  памяти (use-after-free: буфер            ("CmNumWHD.pcx"/".bmp"), либо
  освобождён, память переиспользо-         висячий адрес, либо выход за
  вана или страница возвращена             границу освобождённого буфера
  системе)

Первый механизм доказан статически (цепочка ReadFromFile/CreateFromFile
выше). Второй (58 дампов = 21 в подгруппе «нуль» с переиспользованной
памятью + 24 «висячий» + 13 «выход за буфер») подтверждён содержимым
переиспользованной памяти (имя "CmNumWHD.pcx", фрагмент ".bmp").

Проверка счётчика ссылок (negative result): функция освобождения ресурса
A0_GameResource_DerefOrDestruct_sub_55D300 (vtable+4 спрайта Pcx8, её
вызывает A0_DlgStaticPcx8_SetPcx при смене картинки) работает корректно —
декремент счётчика (this+0x18) с защитой от ухода в минус, возврат при
ненулевом счётчике, удаление из дерева и деструкция только при счётчике,
равном нулю; деструктор A0_Pcx8_Destruct_sub_44F6A0 освобождает буфер
this+0x30 через operator delete. Статического бага счётчика ссылок нет.
Поэтому обращение к освобождённой памяти — не ошибка подсчёта ссылок, а
проблема времени жизни: отрисовка спрайта выполняется ПОСЛЕ его корректного
освобождения (гонка при разборке диалога/экрана города), что подтверждается
и содержимом переиспользованной памяти. Это рантайм-зависимое состояние.

Контрольная проверка «детерминированность против частоты»: и отказ operator
new в 32-битном процессе при крупных буферах True Color, и гонка времени
жизни при разборке экрана — события недетерминированные, что согласуется с
единичными вылетами у конкретных пользователей при обычном входе в город, а
не с падением у всех подряд.

Виновник — код жизненного цикла спрайта Pcx8: функция чтения файла
(A0_Pcx8_ReadFromFile_sub_44F710 и её порт HD_TC2!sub_2008A30), оставляющая
нулевой буфер при отказе выделения, и создатель
A0_Pcx8_CreateFromFile_sub_44F5A0, не проверяющий код возврата чтения. Оба —
код движка SoD (h3hota.exe), унаследованный HD-модом; HD_TC2.dll — исправный
порт рисовалки, место проявления, не причина. Подтвердить, что в конкретных
дампах сработал именно отказ operator new (а не иной путь обнуления или
освобождения буфера), по сокращённым минидампам нельзя — нужно состояние
кучи (полный дамп); см. «Достоверность и ограничения».


9. УСЛОВИЯ СБОЯ
---------------
Из логов (фактическое состояние, не шаги повтора):
    - HotA 1.8.0 во всех дампах; HD-мод от 5.6 R15 до 5.7 R34 (23 сборки).
    - Активен путь отрисовки True Color: Graphics.Mode = 5 (77 дампов),
      7 (31), 4 (4) — все три режима внутренней 32-битной отрисовки;
      используется рендер HD_TC2 (True32), штатная рисовалка SoD подменена.
      Во внутренних 16-битных режимах (0/1/2/3/6) этот адрес НЕ возникает —
      там работает оригинал SoD в h3hota.exe.
    - Memory.Mod = 0 во всех дампах: не давление кучи (и инструкция не
      строковая, а одиночное чтение).
    - Network Game = 0 у 105 дампов, 1 у 9: преимущественно одиночная игра.
    - Краш не привязан к карте/дню/игроку: разные карты, разные дни
      (преимущественно игровое состояние, не предыгровое), Active Player
      и 0, и 3. Quick Combat и 0, и 1 — не связан с режимом боя.
    - Триггер (по комментариям игроков, 4 дампа): вход в город / открытие
      постройки замка — «open shop in castle», «When entering the town!
      First appearance», «Entering the town, repeatable», «пробую зайти в
      город, сразу выдает ошибку». Момент отрисовки спрайта, чей буфер
      пикселей невалиден.


10. СВОДНЫЕ ДАННЫЕ
------------------
Адрес сбоя:        HD_TC2.dll+0x67B0
Модуль:            HD_TC2.dll (True Color рендер HD-мода, HD_True32.pdb)
Функция:           sub_20066E0 (блит 8bpp-спрайта в 32bpp-буфер)
Подсистема:        отрисовка интерфейса (True Color)
Класс сбоя:        разыменование нулевого указателя
Виновный модуль:   h3hota.exe (движок SoD) — функция чтения Pcx8
                   A0_Pcx8_ReadFromFile_sub_44F710 (оставляет нулевой буфер
                   при отказе operator new) и создатель
                   A0_Pcx8_CreateFromFile_sub_44F5A0 (не проверяет код
                   возврата чтения); унаследовано HD-модом (порт функции
                   чтения HD_TC2!sub_2008A30 воспроизводит тот же дефект).
                   HD_TC2.dll — исправный порт рисовалки, место проявления.
Были до 1.8.0:     нет (не подтверждено: все дампы — HotA 1.8.0)
Были в SoD:        да (дефект унаследован: и рисовалка A0_Pcx8_Draw_sub_44F940
                   не проверяет буфер источника, и функция чтения
                   A0_Pcx8_ReadFromFile_sub_44F710 оставляет нулевой буфер при
                   отказе operator new, и создатель
                   A0_Pcx8_CreateFromFile_sub_44F5A0 не проверяет код возврата —
                   всё это код h3hota.exe; в 16-битном режиме та же цепочка
                   падает в h3hota.exe на эквивалентной инструкции)

Признаки поиска вылета в старых версиях HotA / в SoD. Адрес
HD_TC2.dll+0x67B0 НЕ стабилен между версиями HD-мода (код смещается по
образу). Стабильные сигнатуры для опознания пути независимо от версии:

Контекст-инварианты (в логе):
    - адрес сбоя == EDX == EDI (для подгрупп «нуль» и «висячий»);
    - ESI == ECX (счётчик ширины строки спрайта);
    - модуль исключения = HD_TC2.dll, операция = read;
    - частый частный случай: read of address 0x00000000;
    - Graphics.Mode из {4, 5, 7} (внутренняя 32-битная отрисовка).

Текстовые сигнатуры по дизассемблеру HD_TC2 (любой версии):
    - цикл "mov cl,[edx] / lea edx,[edx+1] / test cl,cl / movzx ecx,cl /
      mov ecx,[ebx+ecx*4] / mov [eax],ecx" (палитра -> 32bpp);
    - подготовка источника "mov edi,[eax+2Ch] / imul edi,... /
      add edi,[eax+30h]" (шаг и буфер источника из this+0x2C/+0x30);
    - таблица палитры из "mov eax,[eax+24Ch]".

Стабильные адреса h3hota.exe (общие для всех версий HotA, EXE неизменен):
    - 0x44F940  A0_Pcx8_Draw_sub_44F940 — ОРИГИНАЛ SoD этого блиттера;
      точка эквивалентного отказа "mov dl,[ecx]" (~0x44F9EF);
    - 0x44FA80  A0_Pcx8_Draw_To_Pcx16_sub_44FA80 — 16bpp-обёртка;
    - 0x450120  A0_DlgStaticPcx8_Draw_ToScreen_sub_450120 — рисование
      экранного элемента (проверка указателя спрайта на нуль, 0x450125);
    - 0x55AA10  A0_Load_Pcx8_sub_55AA10 — загрузчик/кэш спрайта Pcx8;
    - диспетчер hota.dll с тегом "P32F": "cmp dword ptr [esi+14h], 46323350h"
      далее "mov eax, <глобал драйвера> / call [edx+2Ch] / mov ecx,esi /
      call eax".


11. ВОСПРОИЗВЕДЕНИЕ ВЫЛЕТА
--------------------------
Условие активации пути: режим True Color (Graphics.Mode = 4, 5 или 7 —
внутренняя 32-битная отрисовка), чтобы штатная рисовалка SoD была подменена
блиттером HD_TC2. Во внутренних 16-битных режимах тот же дефект проявляется
вылетом в h3hota.exe (другой адрес), а не в HD_TC2.dll.

Базовый сценарий (по показаниям игроков):
    - запустить партию (одиночную или сетевую — не принципиально);
    - войти в город / открыть экран замка или постройку (магазин);
    - вылет происходит в момент отрисовки графики города/постройки.
  Один игрок отмечает «Entering the town, repeatable» (повторяется при
  входе в тот же город), другой — «First appearance» (при первом входе).

Честная оговорка: точный ресурс, чей буфер пикселей невалиден, по имеющимся
данным не установлен, поэтому гарантированно детерминированного плана
повтора нет. Путь вероятностный: зависит от состояния кэша ресурсов
(какой спрайт не догружен или освобождён к моменту отрисовки). Варьирование:
разные города/постройки, повторные входы-выходы из города (смена состояния
кэша), разные сборки HD-мода. Полезный дифф-тест: тот же сценарий во
внутреннем 16-битном режиме (Graphics.Mode 0/1/2/3) — если дефект тот же,
вылет сместится в h3hota.exe (адрес ~0x44F9EF), подтвердив общее происхождение.

Для подтверждения корня в рантайме нужен ПОЛНЫЙ минидамп (с кучей): штатно
репортёр HD-мода прикладывает сокращённый дамп (без кучи), который подтверждает
точку сбоя, но не даёт содержимое объекта Pcx8 (счётчик ссылок, состояние
буфера). Полный дамп формируется при включённом твике <Sys.FullDump> = 1 в
hota.ini; он позволит в отладчике осмотреть объект спрайта в момент сбоя и
различить «буфер не загружен» и «буфер освобождён».


ДОСТОВЕРНОСТЬ И ОГРАНИЧЕНИЯ
---------------------------
Подтверждено:
    - 115 дампов (114 по адресу 0x67B0), один непосредственный вызывающий
      код, одна инструкция; адресная проверка (адрес сбоя == EDX) сходится
      во всех 114 дампах;
    - устойчивые инварианты (EDI==EDX, ESI==ECX) и три согласованные
      подгруппы одного шаблона (нуль 77 / висячий 24 / выход за буфер 13);
    - эквивалентность падающей функции и оригинала SoD доказана инструкция
      в инструкцию (раздел 8); путь отрисовки прослежен от экранного
      элемента Pcx8 через движок SoD до диспетчера hota.dll;
    - объект-спрайт жив (чтения this+0x2C/+0x24C проходят, проверка указателя
      в Draw_ToScreen проходит) — бит только буфер пикселей this+0x30;
    - статически доказан дефектный путь для подгруппы «нуль»: функция чтения
      A0_Pcx8_ReadFromFile_sub_44F710 (и её порт HD_TC2!sub_2008A30) при отказе
      operator new оставляет this+0x30 = NULL и возвращает код ошибки, а
      создатель A0_Pcx8_CreateFromFile_sub_44F5A0 код возврата не проверяет и
      возвращает полусозданный спрайт; HD-мод перехватывает функции жизненного
      цикла Pcx8 (чтение, загрузчик) и воспроизводит дефект;
    - второй механизм (обращение к освобождённой памяти, 58 дампов) подтверждён
      содержимым переиспользованной памяти: «мусорная ширина» 0x4448576D —
      константа HD_HOTA.dll, часть 12-байтового имени ресурса "CmNumWHD.pcx"
      (0x754E6D43 0x4448576D 0x7863702E), а 0x706D622E = ".bmp"; память
      освобождённого спрайта занята другим ресурсом, отрисовка по старой
      ссылке читает чужое содержимое;
    - счётчик ссылок ресурса проверен (negative result): функция освобождения
      A0_GameResource_DerefOrDestruct_sub_55D300 корректна (декремент с
      защитой, удаление только при нулевом счётчике), статического бага
      подсчёта ссылок нет — обращение к освобождённой памяти вызвано гонкой
      времени жизни (отрисовка после корректного освобождения);
    - шаблон воспроизводится на 23 сборках HD-мода (5.6 R15 — 5.7 R34);
    - триггер «вход в город / постройка замка» подтверждён четырьмя
      независимыми комментариями игроков.

Ограничения:
    - По механизму «отказ operator new» (56 дампов) доказан дефектный ПУТЬ,
      но не его АКТИВАЦИЯ в каждом конкретном дампе: что выделение буфера
      отказало именно в этих вылетах, по сокращённым минидампам (без кучи) не
      установить — нужен полный дамп (с кучей) или знание автора кода.
    - По механизму «обращение к освобождённой памяти» (58 дампов) доказан факт
      переиспользования памяти (содержимое "CmNumWHD.pcx"/".bmp") и корректность
      счётчика ссылок, но конкретная точка, где отрисовка расходится с
      освобождением (какой экран/диалог и в какой момент разборки рисует уже
      освобождённый спрайт), по статике не локализована — это гонка времени
      жизни, рантайм-зацепка.
    - В наборе один листинг HD_TC2.dll (свежая сборка HotA/181), тогда как
      дампы относятся к 23 сборкам HD-мода. Соответствие установлено по
      совпадению кода в точке сбоя (offset 0x67B0 на границе инструкции,
      virtual size 0x18B54 неизменен) и регистровым инвариантам; побайтная
      сверка каждой из 23 сборок не выполнялась.
    - Одиночный дамп HD_TC2.dll+0x6CD0 (запись, HD 5.6 R15, состояние
      Day = 0 00 — до партии, вызывающий код внутри HD_TC2+0x6E2A) — НЕ
      часть этого механизма: в текущем листинге offset 0x6CD0 попадает в
      другую функцию (код сместился между сборками 5.6 и 5.7), операция и
      состояние отличаются. Учтён как отдельный вылет; в анализ 0x67B0 не
      включался.
    - Ретро-флаг «Были до 1.8.0» не подтверждён (все дампы — HotA 1.8.0);
      наличие в более ранних версиях HotA отдельной проверкой не изучалось.


ВЫВОД
-----
Краш в HD_TC2.dll — следствие, а не первопричина. Блиттер sub_20066E0
исправен: это побайточно точный 32-битный порт штатной рисовалки SoD
A0_Pcx8_Draw_sub_44F940, и он, как и оригинал, по контракту не проверяет
буфер данных источника (this+0x30) — клипится только приёмник. Падение
происходит потому, что при отрисовке экрана города (вход в город, открытие
постройки замка) движок SoD подаёт блиттеру спрайт Pcx8 с невалидным
буфером пикселей: нулевым (77 дампов), висячим (24) или короче объявленной
ширины (13). Сам объект-спрайт при этом жив — бит только его пиксельный
буфер. Дефект жизненного цикла спрайта Pcx8 проявляется двумя путями
(оба унаследованы от SoD). Первый (56 дампов, доказан статически): функция
чтения Pcx8 (A0_Pcx8_ReadFromFile_sub_44F710 и её порт HD_TC2!sub_2008A30)
при отказе operator new оставляет буфер пикселей this+0x30 = NULL и возвращает
код ошибки, а создатель A0_Pcx8_CreateFromFile_sub_44F5A0 код возврата не
проверяет и возвращает полусозданный спрайт, который затем рисуется. Второй
(58 дампов): спрайт корректно освобождается (счётчик ссылок отрабатывает
штатно — проверено, бага подсчёта нет), но рисуется по старой ссылке — гонка
времени жизни; память переиспользована, что прямо видно по содержимому
("CmNumWHD.pcx", ".bmp") в поле ширины и по висячим адресам/выходу за границу
освобождённого буфера. Весь дефектный код — в движке SoD (h3hota.exe), HD-мод
его воспроизводит и переносит точку краша в HD_TC2.dll; в 16-битном режиме то
же самое падает в h3hota.exe на эквивалентной инструкции. Статически доказаны
ОБА пути и факт переиспользования памяти; что НЕ доказано и чтением не
закрыть — активация каждого механизма в конкретном дампе (состояние кучи для
отказа operator new; точный момент «освобождение vs отрисовка» для гонки) —
это рантайм-зацепки, нужен полный дамп с кучей либо знание автора кода.
Полезность лога СРЕДНЯЯ: точка сбоя, объект и оба дефектных пути
локализованы, триггер установлен, но окончательное подтверждение активации —
рантайм; правка блиттера (закрытого модуля HD-мода) причину не устраняет.
